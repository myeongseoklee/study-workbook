# 학습 진도 기록

`~/Desktop/private/study`의 학습 진도와 풀이 환경을 다룬다. 기록은 **`study-log` 브랜치**(`.study-log/` worktree), 풀이는 **`sol/{패키지}/{번호}` 브랜치**(`.sol/{패키지}/{번호}/` worktree)에 있다.

**어떤 명령도 브랜치를 전환하지 않는다.** 레포 루트는 항상 main이고, 기록과 풀이는 각자의 worktree에서 산다. 사용자가 무엇을 하고 있든 안전하다는 뜻이고, 동시에 **에이전트가 `git switch`를 쓰면 안 된다는 뜻**이기도 하다.

```bash
S=~/Desktop/private/study/.claude/skills/study-progress/scripts/progress.js
```

이하 `node $S ...`로 표기한다. 모든 명령은 레포 루트 어디서 실행해도 된다(스크립트가 경로를 스스로 찾는다).

## ⚠️ 두 가지 원칙

### 원칙 1 — "통과했다"는 자기 보고를 기록하지 않는다

사용자가 "03-01 됐어"라고 해도 **`check`로 실제 테스트를 돌려 확인한 뒤에만** 통과로 기록한다. `sol/` 브랜치가 있고 TODO가 사라졌다는 것은 통과의 증거가 아니다 — TODO만 지우고 아무 값이나 반환해도 그렇게 보인다. 진도가 거짓이면 복습 판단이 전부 어긋난다.

그래서 과제 상태에 `미확인`이 있다. "풀은 것 같은데 검증 안 됨"이라는 뜻이고, `check`가 이것을 `통과` 또는 `막힘`으로 확정한다.

### 원칙 2 — 기록은 근거가 살아 있을 때만 유효하다

`[x] 통과`는 **어떤 명세와 어떤 풀이로** 통과했는지까지 말해야 뜻이 있다. main의 과제가 개정되면 그 체크는 과거의 사실일 뿐인데 화면에서는 현재의 사실처럼 보인다. 그래서 판정에 들어간 두 입력의 지문이 기록에 함께 남는다.

```
- [x] 02-01  통과 (4/4) · 2026-08-07  · spec:ec1c3f8 sol:28d8187
                                          └ 명세 파일  └ 풀이 브랜치
```

`status`가 매번 대조해 어긋난 것을 `⚠`로 세운다.

| 신호 | 뜻 | 처방 |
|---|---|---|
| `명세가 바뀌었다` | main의 테스트가 개정됐다 | `check --stale` — 새 명세로 다시 돌린다. 실패하면 문서를 다시 봐야 한다 |
| `풀이가 바뀌었다` | `sol/` 브랜치에 새 커밋이 있다 | `check --stale` — 그냥 다시 돌리면 된다 |
| `본문이 개정됐다` | 읽은 문서·워크북이 바뀌었다 | 사용자에게 알리고 다시 볼지 묻는다. 자동으로 읽음을 해제하지 않는다 |
| `지문 없음` | 무엇으로 통과했는지 모른다 | `check` 재실행 |

**⚠가 떠도 체크는 지우지 않는다.** 판정 없이 통과를 취소하는 것도 똑같이 근거 없는 기록이다. 지우는 것은 `check`(과제)와 사람(문서)의 몫이고, 스크립트는 표시만 한다.

지문은 커밋 SHA가 아니라 **내용**의 해시다 — rebase·amend로 이력이 바뀌어도 내용이 같으면 유효하고, 커밋하지 않은 수정도 잡힌다.

### 원칙 3 — 결정적인 것은 스크립트, 서술형은 직접 편집

| 대상 | 방법 |
|---|---|
| 문서 읽음, 워크북 파트 | `node $S mark …` — 체크박스 토글은 결정적이다. 직접 파일을 고치면 서식이 흔들려 집계가 깨진다 |
| 코딩 과제 상태 | `node $S check …` — 실제 테스트 판정만이 근거다 |
| **오답 노트, 메모, 회고** | **Read/Edit로 기록 파일을 직접 편집** — 자연어를 표로 옮기는 것은 판단이 필요해서 인자로 넘길 수 없다 |

### 과제 번호는 문서 번호다

`03-01`은 "`docs/03-*`에서 나온 첫 과제"다(회차 시리즈는 `e01-02-01`). 사용자가 `3-1`처럼 옛 번호나 워크북 문항 번호로 부르면 **워크북 파트 3의 문항 번호일 수 있으니** `status`로 실제 과제 목록을 확인한 뒤 대응시킨다. 규칙은 레포 `README.md` § 규약 2가 원천이다.

**풀이 브랜치가 옛 배치를 담고 있으면** `check`가 그렇다고 알린다(크래시하지 않는다). 과제 배치가 개정된 뒤 만든 브랜치가 아니라면 풀이를 새 구조(`src/{과제}/index.ts`)로 옮겨야 판정할 수 있다.

## Phase 0: 요청 분류

| 사용자 발화 | 동작 |
|---|---|
| "어디까지 했지", "진도", "뭐 남았어" | `status` |
| "3장까지 읽었어", "이거 읽음" | `mark <패키지> docs <범위>` |
| "워크북 파트1 풀었어" | `mark <패키지> workbook 1` |
| "03-01 풀래", "이 과제 시작할래" | `start <패키지> 03-01` → 명세를 읽어주고 무엇을 만들지 안내 |
| "03-01 통과했어", "이 과제 됐어" | `check <패키지> 03-01` (**검증 후** 기록) |
| "선택 문제도 풀었어" | `check <패키지> 03-01/extra-1-graph-router` |
| "다 풀었어", "정리해줘" | `check` → 통과 확인 후 `done <패키지> 03-01` |
| "기록이 최신인가", "과제 바뀐 거 반영해줘" | `check --stale` |
| "1-4랑 1-11 틀렸어" | 기록 파일의 **오답 노트 표를 직접 편집** |
| "저장해", "커밋해" | `save` |
| "다음에 뭐 할까", "복습할 거 골라줘" | `status`로 먼저 확인 → 추천 |

**과제를 저작·개정한 직후에는 `check --stale`을 돌린다.** 명세를 고치면 그 과제의 통과 기록은 근거를 잃는다. `study-repo`로 과제를 손본 세션이라면 마무리에 이것을 함께 제안한다.

**기록 브랜치가 없으면** `status`가 그렇다고 알려준다. 그때는 `node $S init`을 먼저 돌린다 — 멱등이라 이미 있어도 안전하고, 패키지·문서·과제가 새로 생겼을 때 항목을 동기화하는 용도로도 쓴다(자료를 새로 만든 직후에 한 번 돌리면 좋다).

과제·문서가 **이름을 바꾸거나 사라지면** `init`이 옛 항목을 알린다. 통과 기록이 붙어 있던 항목이면 새 항목으로 옮긴 뒤 `init --prune`으로 지운다 — 조용히 지우면 기록이 함께 날아간다.

**패키지를 특정할 수 없으면** `status`를 먼저 보여주고 어느 것인지 확인한다. 이름은 부분 일치로 받는다(`mcp` → `mcp-protocol`).

## 문서 읽음 기록

```bash
node $S mark mcp-protocol docs 00-03      # 범위 — 00,01,02,03
node $S mark mcp-protocol docs mrtr       # 부분 일치 — 08-mrtr-client-features.md
node $S mark mcp-protocol docs 90 91      # 목록
node $S mark mcp-protocol docs 05 --undo  # 해제
```

**자연어 해석 지침**

- "N장까지 읽었어" → `00-0N` (개요부터 그 장까지). "N장 읽었어"(하나만) → `0N`
- 문서 번호는 `00`~`12`가 본문, `90`(암기)·`91`(용어)·`99`(참고)는 별도다. "다 읽었어"는 `00-99`로 한 번에 처리된다
- 회차 폴더가 있는 패키지(`coding-agent-architecture`의 `ep01-`·`ep02-`)는 키가 `ep01-…/03-foo.md` 형태다. 이때는 `ep02`처럼 회차로, 또는 파일명 조각으로 지정한다
- **애매하면 되묻지 말고 처리한 뒤 무엇을 표시했는지 보고한다.** 스크립트가 표시한 항목을 전부 출력하므로 틀렸으면 `--undo`로 즉시 되돌릴 수 있다. 확인 질문을 매번 하면 기록이 귀찮은 일이 된다

## 풀이 환경 열고 닫기

```bash
node $S start multi-agent-systems 04-01     # main에서 분기 + worktree + 의존성
node $S start multi-agent-systems 04-01 --no-install   # 의존성은 나중에 (빠른 확인용)
node $S done  multi-agent-systems 04-01     # worktree만 정리 (브랜치·커밋은 남는다)
```

`start`는 `.sol/{패키지}/{번호}/`에 worktree를 열고, 새 worktree에 빠져 있는 두 가지를 메운다 — `pnpm install` + testkit 빌드, 그리고 gitignore된 `.env`를 원본으로 심볼릭 링크. **브랜치가 이미 있으면 그것을 재개한다** — 재도전이든 이어풀기든 같은 명령이다. 멱등이라 이미 열려 있으면 경로만 알려주되, 의존성이 없으면 설치를 다시 시도한다.

`.env`를 잇지 않으면 API 키를 쓰는 과제가 **테스트 수집 단계에서** `process.exit(1)`로 죽는다. 화면에는 스위트 실패로 보여서 원인이 풀이인 줄 알게 되므로, `pnpm`이 PATH에 없을 때 `corepack pnpm`으로 넘어가는 것과 함께 자동으로 처리한다.

`done`은 worktree만 걷어낸다. **커밋하지 않은 변경이 있으면 거부하고** 무엇이 남았는지 보여준다 — 버리려면 `--force`.

### 에이전트의 역할은 환경을 열어주는 것까지다

**과제를 대신 풀지 않는다.** 사용자가 학습하려고 만든 문제이고, 답을 받으면 그 목적이 사라진다. `start` 후에는 이렇게 돕는다:

1. `tests/{과제}/index.test.ts`를 **읽고 무엇을 만들어야 하는지 설명한다** — 명세는 문제와 함께 주어지는 것이라 보여줘도 된다(레포 `README.md` § 규약 2)
2. 함정으로 보이는 경계 조건을 짚어준다 (빈 배열, off-by-one, 부등호 방향)
3. 막혔다고 하면 **어느 문서로 돌아갈지** 안내한다. 코드를 주지 않는다
4. `solutions/`는 통과한 뒤에 연다 — 먼저 열면 과제가 독해로 바뀐다

사용자가 명시적으로 "답 알려줘", "네가 풀어줘"라고 하면 그때는 응한다. 다만 통과 기록에 남는 것은 그 풀이가 아니라 **`check`가 실제로 돌린 결과**라는 점은 그대로다.

## 코딩 과제 확정

```bash
node $S check mcp-protocol 03-01                        # 필수 문제 하나
node $S check mcp-protocol 03-01/extra-1-graph-router    # 선택 문제 하나
node $S check mcp-protocol                              # 그 패키지의 필수 전체
node $S check mcp-protocol --extras                     # 선택까지 전체
node $S check --stale                                   # 지문이 어긋난 것만 (전 패키지)
```

`sol/{패키지}/{번호}` 브랜치의 풀이를 체크아웃 없이 꺼내 실제 테스트를 돌린다. 선택 문제도 **같은 브랜치**에 있다 — 브랜치는 과제 번호 단위다. 결과에 따라 기록에 `통과 (16/16)` 또는 `막힘 (3/16 실패)`가 날짜·지문과 함께 남는다.

**완료 집계는 필수 문제(`index`)만 센다** (레포 `README.md` § 규약 2). 선택은 `(+선택 2/5)`로 따로 표시된다 — 안 해도 그 과제는 완료다.

- **브랜치가 없으면** `미시작`으로 보고된다 — 실패가 아니다. 아직 시작 안 한 것이면 `start`를 안내한다(레포 `README.md` § 규약 4)
- **`△ 커밋하지 않은 변경이 있다`가 뜨면** 판정은 **커밋된 풀이**로 한 것이다. 화면의 코드와 판정 대상이 다르므로, 커밋한 뒤 다시 `check`하라고 안내한다 — 이걸 놓치면 "고쳤는데 왜 그대로 막힘이지"에서 시간을 버린다
- **`△ 브랜치의 명세가 main과 다르다`가 뜨면** `sync-sol`을 제안한다. 판정 자체는 main 기준이라 정확하지만, 사용자가 그 브랜치에서 직접 `pnpm test`를 돌리면 옛 명세를 봐서 결과가 어긋난다
- **선택 문제의 풀이 파일이 없어도** `미시작`이다. 안 해도 되는 것을 실패로 세면 "선택"이 아니게 된다
- **막힘이면** 실패한 항목을 사용자에게 보여주고 어느 문서로 돌아갈지 안내한다. 실패 상세가 필요하면 그 브랜치에서 `pnpm test {번호}`를 직접 돌린다
- 종료 코드는 "판정을 할 수 있었는가"다. `막힘`도 0으로 끝난다 — 못 푼 것은 정상적인 학습 상태다

## 풀이 브랜치를 main에 맞추기

```bash
node $S sync-sol                        # 전부
node $S sync-sol multi-agent-systems    # 한 패키지
```

main의 최신 내용을 `sol/` 브랜치에 반영한다. **체크아웃하지 않고**, rebase가 아니라 머지라서 이미 push된 브랜치도 force 없이 올라간다. 트리는 main을 바닥에 깔고 풀이 폴더만 브랜치 것으로 덮으므로 충돌이 없다.

- 이미 main을 품은 브랜치는 건너뛴다 (멱등)
- **worktree가 열려 있으면** 깨끗할 때만 반영하고 worktree까지 맞춘다. 작업 중이면 건너뛴다 — 커밋하거나 `done` 후 다시 돌리라고 안내한다
- **풀이 폴더 밖을 건드린 브랜치는 건너뛴다** — 규약 위반이지만, 그 변경을 조용히 버리는 것은 이 명령이 할 일이 아니다. 사용자에게 알리고 판단을 맡긴다
- 반영 후 `sol:` 지문이 바뀌므로 `check --stale`이 재판정을 요구한다. 둘을 이어서 돌리면 된다

```markdown
| 문항 | 내가 쓴 답 | 정답 | 왜 틀렸나 (지식 부족 / 오해 / 부주의) | 재확인 |
|---|---|---|---|---|
| 1-4 | -32022라고 답 | -32602 (필수 _meta 누락은 malformed) | 오해 | 2026-08-12 |
```

**"왜 틀렸나"를 세 범주 중 하나로 반드시 분류한다.** 원인이 다르면 처방이 다르다 — 지식 부족은 다시 읽기, 오해는 개념 교정, 부주의는 반복 훈련이다. 사용자가 이유를 말하지 않았으면 대화에서 추론해 적고, 근거가 없으면 사용자에게 한 번 묻는다.

정답 칸은 `93-solutions.md`에서 확인해 적는다. 추측으로 채우면 오답 노트가 오답을 가르친다.

빈 템플릿 행(`|  |  |  |  |  |`)이 남아 있으면 첫 항목을 쓸 때 치운다.

## 세션 마무리

```bash
node $S save "MCP 03장까지 · 워크북 파트1"
```

**push가 기본이다** (`--no-push`로 생략). 기록이 `origin/study-log`에 올라가 다른 기기에서도 보인다.

> **레포가 public이다.** 진도·막힌 과제·오답 노트가 공개된다. 사용자가 이 기본값을 선택했으므로 매번 확인하지 않되, **오답 노트에 사적인 내용(사내 정보, 개인 신상)을 적지 않는다.** 학습 내용에 관한 것만 쓴다.

기록만 하고 저장하지 않으면 worktree에만 남는다. `status`가 마지막에 `△ 저장하지 않은 기록이 있다`로 알려주므로, 대화가 끝날 때 그 신호가 있으면 `save`를 제안한다.

## 진도로 판단할 때

"다음에 뭐 할까" 같은 요청에는 `status`를 근거로 답한다.

- **⚠(지문 어긋남)**이 있으면 그것이 먼저다. 근거가 낡은 기록 위에서 다음을 추천하면 추천도 낡는다. `check --stale`로 정리한 뒤 판단한다
- **막힘**이 있으면 그것이 최우선이다 — 막힌 채로 다음 과제로 가면 같은 개념에서 또 막힌다
- **미확인**이 있으면 `check`를 먼저 돌린다. 통과했는지 모르는 상태가 쌓이면 진도가 의미를 잃는다
- 문서를 다 읽었는데 워크북이 0이면 워크북을 권한다 — 읽은 것과 꺼내 쓰는 것은 다른 활동이고, 그 간극을 드러내는 것이 워크북의 목적이다
- 오답 노트의 `재확인` 날짜가 지났으면 그 문항을 다시 물어본다

## 흔한 실수

| 실수 | 결과 |
|---|---|
| 사용자 말만 듣고 `통과`로 기록 | 진도가 거짓이 되고 복습 판단이 전부 어긋난다. **반드시 `check`** |
| 과제를 개정하고 `check --stale`을 안 돌림 | 옛 명세로 받은 통과가 현재의 사실인 척 남는다 |
| ⚠가 떴는데 체크를 손으로 지움 | 판정 없이 취소하는 것도 근거 없는 기록이다. `check`가 결정한다 |
| 기록 파일의 앞 세 섹션을 Edit로 직접 수정 | 서식이 흔들려 집계가 깨진다. 그 셋은 `mark`·`check`만 |
| `git switch`로 브랜치를 옮김 | 사용자의 작업을 밀어낸다. 풀이는 `start`가 여는 worktree에서 하고, 판정은 `check`가 체크아웃 없이 한다 |
| 과제를 대신 풀어 줌 | 학습이 목적인 문제다. 명세를 읽어주고 막힌 지점을 짚되, 코드는 사용자가 쓴다 |
| 커밋 전에 `check` | 판정은 커밋된 풀이로 한다 — 방금 고친 것이 반영되지 않는다 |
| worktree를 손으로 `rm -rf` | git이 등록을 붙들고 있어 다음 `start`가 막힌다. `done`을 쓴다 (막혔으면 `git worktree prune`) |
| `init`을 두려워함 | 멱등이다. 새 패키지·문서·과제 동기화가 필요하면 그냥 돌린다 |
| `save`를 잊음 | worktree에만 남아 다른 기기에서 안 보인다 |

## 관련

- **`study-repo`** — 패키지·과제 저작, 규약 감사. 진도와 책임이 다르다
- **cc-system의 `study-material-generator`** — 학습 자료 생성. 자료를 새로 만든 뒤에는 `init`으로 항목을 동기화한다
- 레포 규약의 단일 진실 원천은 `README.md`다 (§ 규약 7 「학습 기록」)
