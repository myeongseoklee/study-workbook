# study 레포 운영

학습 워크북 모노레포(`~/Desktop/private/study`)를 운영한다. 이 스킬은 **레포를 관리**하고, 학습 자료 생성은 `cc-system`의 `study-material-generator`가 한다.

## ⚠️ 규약의 단일 진실 원천은 README.md다

**작업을 시작하기 전에 레포 루트 `README.md`를 읽는다.** 규약 5개(문서화 / 문제·정답 분리 / 기술 스택 / 풀이 브랜치 / 패키지 추가)가 거기 있다.

이 스킬은 그 규약을 **집행**하고, 규약 내용을 다시 적지 않는다. 두 곳에 적으면 어긋나고, 어긋나면 어느 쪽이 맞는지 알 수 없어진다. **README와 이 문서가 다르면 README가 맞다.**

## Phase 0: 요청 분류와 컨텍스트 확인

먼저 무엇을 요청받았는지 가른다. 갈래마다 실행 모드가 다르다.

| 요청 | 갈래 | 실행 모드 |
|---|---|---|
| "패키지 추가", "새 주제" | **A. 패키지 추가** | 스크립트 (에이전트 불필요) |
| "과제 추가", "문제 만들어" | **B. 과제 추가** | 에이전트 팀 (생성-검증) |
| "이 과제 풀래", "풀이 시작", "테스트 돌려" | **C. 풀이 지원** | 스크립트 + 직접 처리 |
| "규약 점검", "감사", "레포 상태" | **D. 감사** | 서브 에이전트 1명 |
| "규약 수정", "브랜치 정리", "설정 고쳐" | **E. 유지보수** | 직접 처리 |

**컨텍스트 확인** — 갈래를 정한 뒤 현재 상태를 본다.

```bash
cd ~/Desktop/private/study
git branch --show-current                  # 지금 어느 브랜치인가
ls packages/                               # 어떤 패키지가 있나
node .claude/skills/study-repo/scripts/audit-conventions.js   # 규약 상태
```

**브랜치 확인이 특히 중요하다.** 지금 `sol/` 브랜치에 있다면 사용자가 풀이 중이므로, 문제 파일을 고치는 작업(B·E)은 그 풀이를 오염시킨다. 이 경우 먼저 알린다.

## 갈래 A: 패키지 추가

`scaffold.sh`가 규약이 요구하는 파일과 설정을 한 번에 만든다. 손으로 만들면 `package.json` 스크립트나 `tsconfig` 상속을 빠뜨리기 쉽고, 그 누락은 감사에서 잡히기 전까지 조용히 남는다.

```bash
.claude/skills/study-repo/scripts/scaffold.sh package <주제-slug> "<한 줄 설명>"
```

그다음 세 가지를 처리한다.

1. **README "현재 패키지" 표에 한 줄 추가** — 스크립트가 하지 않는다. 설명은 사용자에게 확인받은 문구를 쓴다
2. **지식 문서는 이 스킬이 쓰지 않는다** — `study-material-generator`로 넘긴다. 그 스킬이 산출물 위치를 물을 때 이 패키지를 지정하라고 안내한다
3. **감사 실행** — 스캐폴딩 직후 감사를 돌려 설정 누락을 확인한다

## 갈래 B: 과제 추가 (에이전트 팀)

**실행 모드: 에이전트 팀 (생성-검증 패턴)**

과제는 만드는 것과 그것이 실제로 판정 기능을 하는지 확인하는 것이 별개 작업이다. 통과하는 테스트를 보고 "됐다"고 하면 **아무것도 검사하지 않는 테스트**가 그대로 남는다. 그래서 저작과 검증을 분리한다.

```
TeamCreate(members: [assignment-author, assignment-verifier])
    ↓
author:   scaffold → 성공 기준·인터페이스 작성 → check() 작성 → 검증용 정답 구현
    ↓ SendMessage(과제번호, 검증용 구현 경로)
verifier: ① 스켈레톤 실패  ② 정답 통과  ③ 흔한 오답 검출  ④ 실패 메시지 품질
    ↓ 재작업 필요하면 author에게 되돌림
오케스트레이터: 판정 수집 → 사용자 보고
```

두 에이전트 모두 `model: "opus"`로 호출한다.

**verifier의 ③이 이 팀의 핵심 가치다.** ①②는 스크립트가 자동으로 하지만, "흔한 오답을 겨냥하는가"는 주제 이해가 필요하다. 이 검증이 없으면 정답만 통과시키는 관문형 테스트가 통과한다.

**차단 규칙**: ①이 실패(스켈레톤인데 통과)하면 ②③을 진행하지 않고 즉시 author에게 되돌린다. 그 상태에서 나머지 검증은 의미가 없다.

## 갈래 C: 풀이 지원

풀이 절차는 README § 규약 4가 정한다. 이 스킬은 그 절차를 **실행하고 규약 위반을 막는다**.

**풀이 시작 요청 시:**

```bash
git switch -c sol/<패키지>/<과제번호>
```

브랜치명이 규약 형식(`sol/{패키지}/{과제}`)인지 확인한다. 사용자가 다른 이름을 원하면 규약을 알리고, 그래도 원하면 따른다 — 사용자의 레포다.

**테스트 실행 요청 시:**

```bash
npm run test:<과제번호> --workspace <패키지>
```

실패하면 **답을 알려주지 않는다.** 실패 항목의 메시지를 읽어주고, 그 항목이 어느 원리에 해당하는지 문서 위치(`📍 되짚기`)를 가리킨다. `solutions/`를 열어 답을 찾는 것은 규약이 막는 행위다 — 거기엔 테스트가 있을 뿐이지만, 테스트를 읽고 기대값을 역산하는 것도 학습을 건너뛰는 것이다.

**커밋 요청 시:**

현재 브랜치가 `main`이면 **거부하고 알린다.** main은 문제 상태를 유지해야 한다. `sol/` 브랜치로 옮기고 커밋한다.

```bash
git add -A && git commit -m "sol(<패키지>): <과제번호> <한 줄 설명>"
```

**머지 요청 시**: main으로 머지하지 않는다는 규약을 알린다. 풀이 브랜치는 남겨 두는 것이 규약의 의도다.

## 갈래 D: 감사 (서브 에이전트)

**실행 모드: 서브 에이전트 1명** — 감사는 독립 작업이고 팀 통신이 필요 없다.

`convention-auditor`를 `model: "opus"`로 호출한다. 그 에이전트가 스크립트를 먼저 돌리고, 스크립트가 셀 수 없는 것(자기완결성, 문항 품질, 암기 선별)을 직접 검토한다.

감사 결과를 받으면 **위반과 제안을 구분해** 사용자에게 보고한다. 위반은 규약을 어긴 것이고 제안은 규약에 없는 개선이다. 섞으면 사용자가 무엇을 반드시 고쳐야 하는지 모른다.

수정은 사용자 확인 후 진행한다. 감사가 곧 수정 승인은 아니다.

## 갈래 E: 유지보수

**규약 자체를 바꾸는 요청**이면 `README.md`를 고치고, 그 변경이 스크립트 검사와 어긋나지 않는지 확인한다. 규약을 바꿨는데 `audit-conventions.js`가 옛 규약을 검사하면 감사가 거짓 위반을 낸다 — 둘을 함께 고친다.

**브랜치 정리 요청**이면 규약 형식에 안 맞는 브랜치를 나열하고, 각각이 규약 제정 전 잔재인지 실수인지 판단해 보고한다. 삭제는 사용자 확인 후에만 한다 — 풀이가 담긴 브랜치를 지우면 되돌릴 수 없다.

**cc-system 하네스와의 경계**: 자료 생성 규격(문항 작성법, 분량, 암기 선별 기준)은 `cc-system`의 `study-material-generator`가 정한다. 이 레포의 규약은 **배치·명명·스택·브랜치**를 정한다. 경계가 모호한 요청이면 어느 쪽 책임인지 먼저 가른다.

## 데이터 전달

| 무엇 | 어디로 |
|---|---|
| 과제 파일 (문제·테스트) | `packages/{패키지}/src/`, `solutions/` — 레포에 커밋 |
| 검증용 정답 구현 | 임시 경로 (`/tmp` 등) — **커밋하지 않는다** |
| 감사 보고 | 대화로 반환. 파일로 남기지 않는다 (레포를 오염시키지 않기 위해) |
| 팀 내부 조율 | `SendMessage` |

**검증용 정답 구현을 레포에 남기지 않는 것이 중요하다.** 남으면 학습자가 그것을 보고 베낀다.

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 스크립트가 "패키지가 없다" | 레포 루트에서 실행했는지, 패키지명 오타인지 확인 |
| `verify-assignment.sh` ①에서 통과 | 테스트가 비어 있다 — author에게 즉시 되돌림, ②③ 진행 안 함 |
| `verify-assignment.sh` ②에서 실패 | 테스트가 틀렸는지 검증용 구현이 틀렸는지 먼저 가른다 |
| 검증 중 중단 | **원상 복구 확인 필수** — `src/`에 `🎯 TODO`가 돌아왔는지. 안 돌아왔으면 `git checkout -- src/` |
| 감사 스크립트 크래시 | 사실을 보고하고 수동 감사로 폴백. 스크립트 고장을 이유로 감사를 건너뛰지 않는다 |
| main에서 커밋 요청 | 거부하고 `sol/` 브랜치로 안내 |
| 규약과 스크립트가 어긋남 | README를 진실로 보고 스크립트를 고친다 |

재시도는 1회. 재실패하면 그 부분 없이 진행하고 **무엇이 빠졌는지 보고에 명시**한다.

## 테스트 시나리오

**정상 흐름 (과제 추가)**
```
입력: "stateful-context-design에 4-1 과제 추가해줘 — 컨텍스트 축출 정책 구현"
→ Phase 0: 갈래 B 판별, 브랜치 확인(main), 감사로 현재 상태 파악
→ TeamCreate(author, verifier)
→ author: scaffold.sh assignment → 기준 5개 + 인터페이스 작성 → check 5개 → 검증용 구현
→ verifier: ① 실패 ✓  ② 5/5 ✓  ③ 오답 2종 각각 정확히 겨냥 ✓  ④ 메시지 진단 가능 ✓
→ 팀 정리 → 사용자 보고 (과제 경로, 기준·check 개수, 검증 결과)
```

**에러 흐름 (빈 테스트)**
```
입력: 위와 동일
→ verifier ①: 스켈레톤인데 통과 → 즉시 차단, author에게 되돌림
→ author: check가 src를 호출하지 않았음을 확인, 수정
→ verifier 재검증 → 통과
→ 보고에 "1회 재작업 발생 (빈 테스트)" 명시
```

**에러 흐름 (풀이 중 문제 수정 요청)**
```
입력: "3-1 문제 설명을 고쳐줘"  (현재 브랜치: sol/stateful-context-design/3-1)
→ Phase 0: 브랜치가 sol/*임을 감지
→ 사용자에게 알림: 지금 풀이 중이므로 문제 파일 수정이 풀이와 섞인다.
   main으로 옮겨 고치고 브랜치를 rebase할지, 지금 브랜치에서 진행할지 확인
→ 사용자 선택에 따라 진행
```

## 번들 스크립트

| 스크립트 | 용도 |
|---|---|
| `scripts/audit-conventions.js` | 규약 중 기계가 셀 수 있는 항목 검사. 종료 코드 0=통과, 1=위반 |
| `scripts/scaffold.sh` | 패키지·과제 스캐폴딩. `package` / `assignment` 모드 |
| `scripts/verify-assignment.sh` | 과제 양방향 검증(①스켈레톤 실패 ②정답 통과). 원본 자동 복구 |

스크립트를 고칠 때는 **규약(README)이 먼저**다. 규약을 바꾸지 않고 스크립트만 느슨하게 만들면 감사가 무력화된다.
