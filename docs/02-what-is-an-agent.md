# 02. 에이전트란 무엇인가 — 프레임워크 없이 손으로 만들기 (0주차)

## 학습 목표

이 챕터를 다 읽고 실습하면, 에이전트가 결국 **하나의 `while` 루프**임을 코드로 이해하고, "워크플로"와 "에이전트"를 구분할 수 있으며, 프레임워크가 나중에 무엇을 대신 해주는지 판단할 수 있다.

## 선수 지식

[01. 선수 지식](01-prerequisites.md)의 tool_use(함수 호출) 개념. 이게 이 챕터의 전부다.

## 핵심 원리 (WHY) — 에이전트는 루프다

프레임워크(LangGraph 등)부터 배우면, 추상화 뒤에서 무엇이 도는지 영영 모른다. "무지의 무지"를 가장 빠르게 깨는 방법은 **프레임워크 없이 순수 파이썬 + LLM SDK로 루프 하나를 짜보는 것**이다. 100줄이 안 넘고, 이게 에이전트의 전부다.

에이전트의 본질:

```
목표를 준다
반복:
    LLM에게 현재 상황(대화 히스토리)을 보내고 다음 행동을 묻는다
    LLM이 "이 툴을 호출해줘"라고 하면 → 내 코드가 실제로 실행 → 결과를 히스토리에 추가
    LLM이 "다 끝났어, 최종 답은 이거야"라고 하면 → 루프 종료
```

즉 에이전트 = **LLM 호출 → tool_use 파싱 → 함수 실행 → 결과 주입 → 반복**. LLM은 "다음에 뭘 할지" 판단만 하고, 실제 행동(툴 실행)과 루프 제어는 당신 코드가 한다.

## 필수 지식 (HOW) — 워크플로 vs 에이전트

Anthropic이 *Building Effective Agents*에서 정립한 구분이 실무의 기준이 되었다. 둘 다 "에이전틱 시스템"이지만 통제권의 위치가 다르다:

- **워크플로(Workflow)**: LLM과 툴이 **미리 정해진 코드 경로**로 오케스트레이션된다. 흐름을 개발자가 코드로 고정한다. 예측 가능하고 디버깅이 쉽다.
- **에이전트(Agent)**: LLM이 **스스로 자기 프로세스와 툴 사용을 동적으로 결정**한다. 어떤 순서로 무엇을 할지 LLM이 정한다. 유연하지만 통제가 어렵고 비싸다.

> **실무 판단:** 흐름이 뻔하면 워크플로로 고정하라. 흐름을 미리 알 수 없을 때만 에이전트에게 통제권을 넘겨라. "에이전트가 멋있어서" 통제권을 넘기면 디버깅 지옥이 온다.

### 5가지 워크플로 설계 패턴

Anthropic이 정리한, 완전한 에이전트로 가기 전에 알아야 할 워크플로 패턴들. 대부분의 실무 문제는 이 조합으로 풀린다:

| 패턴 | 구조 | 언제 쓰나 |
|------|------|----------|
| **프롬프트 체이닝(Prompt Chaining)** | LLM 호출을 순서대로 연결, 각 단계가 앞 단계 출력을 입력으로 | 작업을 고정된 하위 단계로 쪼갤 수 있을 때 |
| **라우팅(Routing)** | 입력을 분류해서 알맞은 경로로 보냄 | 입력 종류마다 다른 처리가 필요할 때 |
| **병렬화(Parallelization)** | 여러 LLM 호출을 동시에 돌리고 결과를 합침 | 독립적 하위 작업이 동시에 가능할 때 |
| **오케스트레이터-워커(Orchestrator–Worker)** | 리드 LLM이 작업을 쪼개 워커들에게 위임하고 종합 | 하위 작업 개수를 미리 알 수 없을 때 (→ [04장 멀티 에이전트](04-multi-agent-patterns.md)의 기반) |
| **평가자-최적화(Evaluator–Optimizer)** | 한 LLM이 생성하고 다른 LLM이 평가·피드백, 반복 개선 | 명확한 평가 기준이 있고 반복으로 품질이 오를 때 |

이 패턴들의 공통점: **흐름을 개발자가 통제한다.** 완전한 에이전트는 이 통제권을 LLM에게 넘긴 것이다.

## 🛠 직접 해볼 것 — 100줄짜리 에이전트

이번 주 실습의 전부는 **프레임워크 없이 계산기 에이전트 하나 짜기**다.

- [ ] LLM SDK(`openai`, 기본 provider는 Gemini OpenAI 호환)로 단순 호출 하나 성공시키기
- [ ] 툴 2개 정의: `add(a, b)`, `multiply(a, b)` — LLM에게 이름·설명·인자 스키마(JSON Schema)를 알려준다
- [ ] **핵심 루프 구현**:
  - [ ] 대화 히스토리(배열)를 만든다
  - [ ] `while (true) { ... }` 안에서 LLM을 `await`로 호출한다
  - [ ] 응답이 tool_use면 → 해당 JS 함수를 실제로 실행 → 결과를 히스토리에 `push` → 계속
  - [ ] 응답이 최종 텍스트면 → 출력하고 `break`
- [ ] "(3 + 5) × 2는?" 을 물어보고, LLM이 add를 부르고 그 결과로 multiply를 부르는 **여러 스텝**을 눈으로 확인
- [ ] **안전장치 추가**: 최대 반복 횟수(예: 10회) 초과 시 강제 종료 — 무한 루프 방지 (이게 왜 필요한지 체감하는 게 실습의 목적)

**의도적으로 관찰할 것:**
- [ ] 툴 결과를 히스토리에 안 넣으면 어떻게 되나? (LLM이 자기가 뭘 했는지 잊는다 → 상태 관리의 필요성)
- [ ] 툴 실행이 예외를 던지면? (재시도/에러 핸들링을 당신이 직접 짜야 한다 → 프레임워크가 대신 해줄 부분)
- [ ] max_iterations를 안 걸면? (무한 루프 가능 → 타임아웃의 필요성)

이 세 가지 "불편함"이 바로 [03장 LangGraph](03-langgraph-basics.md)가 해결해주는 것들이다. 불편함을 먼저 겪어야 프레임워크의 가치를 안다.

## ⚠️ 암기 필수

- [ ] **에이전트 = LLM 호출 → tool_use 파싱 → 함수 실행 → 결과 주입 → 반복.** (이 루프가 에이전트의 정의)
- [ ] **워크플로(개발자가 흐름 통제) vs 에이전트(LLM이 흐름 통제)** — 통제권의 위치가 둘을 가른다. 흐름이 뻔하면 워크플로.
- [ ] **툴 실행 주체는 LLM이 아니라 당신 코드.** LLM은 요청(JSON)만 반환한다.
