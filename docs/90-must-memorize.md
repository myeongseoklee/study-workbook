# 90. 암기 필수 카드 — 검색 없이 즉답할 것

이 카드는 **각 챕터의 암기 항목만 모은 것**이다. 처음부터 외우려 하지 마라 — 챕터를 소화하면 대부분 유도된다. 설계·디버깅 현장에서 검색할 여유가 없을 때 즉답해야 하는 것만 담았다.

## 판단 경계 (설계 시점에 즉시 필요)

- [ ] **멀티 에이전트는 두 종류: 축 A(오케스트레이터-워커, 일회성 워커) vs 축 B(전문가 협업, 1급 시민 동료).** 설계 전에 어느 쪽인지 정하라. → [04장](04-multi-agent-patterns.md)
- [ ] **"나누기"와 "플랫폼으로 짓기"는 별개 결정.** 승격 게이트: ① 다팀 독립개발 ② 독립 배포/스케일 ③ 외부 연동 ④ 런타임 개방. 아무것도 안 걸리면 앱 레이어(함수+중앙 오케스트레이터)가 정답. → [08장](08-agent-platform-infra.md)
- [ ] **멀티 에이전트 정당화 3조건: ① 병렬화 가능 ② 독립 컨텍스트 필요 ③ 명확한 병합 규칙.** 하나라도 빠지면 단일 에이전트가 낫다. → [07장](07-should-you-build-multi-agent.md)
- [ ] **기본값은 "나누지 않는다".** 나누면 비용·지연·실패 지점이 곱셈으로 는다. 먼저 단일 에이전트 + 툴 여러 개를 시도. → [07장](07-should-you-build-multi-agent.md)
- [ ] **워크플로(개발자가 흐름 통제) vs 에이전트(LLM이 흐름 통제).** 흐름이 뻔하면 워크플로로 고정하라. → [02장](02-what-is-an-agent.md)
- [ ] **RAG 필요 조건: 지식이 (a) 모델에 없고 (b) 프롬프트에 다 넣기엔 크고 (c) 자주 바뀜.** 아니면 과잉. → [06장](06-rag-when-needed.md)

## 불변 트레이드오프 (모르면 잘못된 선택을 반복)

- [ ] **단일 작성자 원칙: 읽기·판단은 여러 에이전트로 병렬, 쓰기(최종 상태 확정)는 단일 스레드.** 어기면 컨텍스트 파편화·모순 결정으로 깨진다. → [04장](04-multi-agent-patterns.md)
- [ ] **멀티 에이전트의 이득은 병렬화 가능한 작업에서만 나온다.** 순차 의존 작업은 나눠도 이득 없음. → [04장](04-multi-agent-patterns.md)
- [ ] **핸드오프의 품질 = 넘기는 컨텍스트의 품질.** 컨텍스트 없이 넘기면 받는 쪽이 맥락 없이 재시작. → [04장](04-multi-agent-patterns.md)
- [ ] **RAG 품질은 검색 품질이 좌우한다.** 생성 모델 바꾸기 전에 검색부터 의심. → [06장](06-rag-when-needed.md)
- [ ] **벡터 검색은 의미에 강하고 정확한 코드/ID에 약하다 → 하이브리드(벡터+키워드)로 보완.** → [06장](06-rag-when-needed.md)
- [ ] **`interruptBefore`(액션 전 승인) vs `interruptAfter`(실행 후 검토, 액션 이미 실행됨).** 되돌릴 수 없는 액션은 반드시 before. 프리빌트 `createAgent` 에는 이 옵션이 없고 `humanInTheLoopMiddleware` 로 툴 단위로 건다. → [03장](03-langgraph-basics.md)
- [ ] **조정(오케스트레이션)은 없앨 수 없다 — 위치(중앙집중 vs 분산)만 바뀐다.** 인프라로 가도 오케스트레이터는 서비스가 될 뿐 사라지지 않는다. 실무 기본값은 중앙집중. → [04장](04-multi-agent-patterns.md), [08장](08-agent-platform-infra.md)
- [ ] **MCP는 에이전트↔도구, A2A는 에이전트↔에이전트.** 방향이 다르다. 경쟁 아님, 층이 다름. → [08장](08-agent-platform-infra.md)

## 진단 신호 (장애 중 검색할 여유 없음)

- [ ] **에이전트는 비결정적 → "한 번 돌려보니 됨"은 증명이 아니다.** 분포를 평가셋으로 봐야 한다. → [05장](05-eval-and-observability.md)
- [ ] **실패는 유형(툴 호출 / 라우팅 / 무한 루프 / 컨텍스트 오염)을 먼저 분류하고 유형별로 고친다.** 뭉뚱그리면 못 고친다. → [05장](05-eval-and-observability.md)
- [ ] **병렬 결과가 사라지면 리듀서(덮어쓰기 vs append)를 의심하라.** → [03장](03-langgraph-basics.md)
- [ ] **인터럽트가 안 되면 체크포인터가 있는지 확인하라** — 인터럽트는 체크포인터를 전제로 한다. → [03장](03-langgraph-basics.md)

## 핵심 제약 (아키텍처를 좌우)

- [ ] **에이전트 = LLM 호출 → tool_use 파싱 → 함수 실행 → 결과 주입 → 반복.** 툴 실행 주체는 LLM이 아니라 당신 코드. → [02장](02-what-is-an-agent.md)
- [ ] **에이전트 = 프롬프트(역할) + 도구. 협업 = 그걸 순서대로 부르고 결과를 넘기는 코드.** 마법이 아니다. → [04장](04-multi-agent-patterns.md)
- [ ] **에이전트를 인프라로 짓기 = 마이크로서비스로 짓기.** 함수→서비스, 서비스디스커버리→레지스트리, OpenAPI→Agent Card. 새것은 Agent Card와 A2A/MCP 둘뿐. → [08장](08-agent-platform-infra.md)
- [ ] **StateGraph는 `.compile()` 해야 실행 가능.** 빌더는 설계도, 컴파일된 것이 실행체. → [03장](03-langgraph-basics.md)
- [ ] **체크포인터 선택: MemorySaver(개발) / SqliteSaver(단일 서버) / PostgresSaver(멀티 인스턴스).** → [03장](03-langgraph-basics.md)
- [ ] **패키지 경계: 그래프 원시요소는 `@langchain/langgraph`, 프리빌트 `createAgent`·미들웨어는 `langchain`.** `langchain` 은 상위 레이어지 스코프 패키지의 대체재가 아니다. → [03장](03-langgraph-basics.md)

## 학습 순서 제약

- [ ] **오케스트레이션 먼저, RAG 나중.** RAG는 부분집합이지 핵심이 아니다 — RAG부터 배우면 검색만 익히고 에이전트를 못 만든다. → [00장](00-overview.md)
