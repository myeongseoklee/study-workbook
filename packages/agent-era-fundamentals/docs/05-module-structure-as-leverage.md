# 05. 구조가 레버리지다 — 규칙을 문서가 아니라 명세 파일에 둔다

## 학습 목표

깊은 모듈이 에이전트 환경에서 특히 유효한 이유와 **그것이 동시에 위험한 이유**를 함께 이해한다. 그리고 아키텍처 규칙을 산문이 아니라 **기계가 판정하는 명세**로 옮기는 방법을 익힌다.

## 선수 지식

- 04장의 궤적. 모듈에도 궤적이 있다는 확장까지
- 모듈 사이의 의존 방향이라는 개념. 의존 역전이라는 말을 들어 봤으면 충분하다

## 핵심 원리 (WHY) — 좋은 구조가 주는 것은 사람에게 주던 것과 같다

진행자가 "잘 설계된 모듈에서 얻는 레버리지가 무엇이냐"고 묻자 밥은 새로운 논거를 꺼내지 않는다 `[28:11~28:40]`.

> **지저분한 코드 대 깨끗한 코드에서 했던 것과 똑같은 논증이다.** 잘 나뉘어 있고 그 사이의 인터페이스가 잘 규율된 것은 **사람이 붙잡을 수 있다.** 우리가 머릿속에서 구획을 나누기 때문이다. 그런데 **모델도 그렇게 한다.** 아마 임계점은 조금 다르겠지만.

01장의 명제가 구조 층위에서 반복된다. 같은 이유, 다른 임계점이다.

## 필수 지식 (HOW) — 깊은 모듈이 특히 잘 맞는다

진행자가 John Ousterhout의 **깊은 모듈(deep module)** 개념을 꺼낸다 `[30:09~30:37]`.

| | 인터페이스 | 감춰진 구현 |
|---|---|---|
| **얕은 모듈** | 넓다 | 적다 |
| **깊은 모듈** | **좁다** | **많다** |

진행자의 관찰은 이렇다. 깊은 모듈은 모델에게 특히 좋은데, **구현을 이해하지 않고 인터페이스만 읽어도 되기 때문**이다. 밥은 전적으로 동의하면서 관찰을 덧붙인다 `[30:37]`.

> 모델은 **인터페이스 이름에 주의를 기울인다.** 구조에 주의를 기울인다. 그 덕분에 **그 아래의 코드를 읽지 않아도 되게 해 준다.** 이것은 **위험이면서 동시에 이점이다.**

### "위험이면서 이점"을 그냥 넘기지 않는다

이 한마디에 실무 판단이 걸려 있다. 모델이 인터페이스만 읽고 구현을 건너뛴다는 것은, **인터페이스가 약속한 것과 구현이 하는 일이 어긋나 있으면 모델이 그것을 알아채지 못한다**는 뜻이다. 밥이 바로 이어 조건을 단다.

> **코드가 일관된 한** 괜찮다.

| | 인터페이스와 구현이 일치할 때 | 어긋날 때 |
|---|---|---|
| 사람 | 구현을 읽다 발견할 수 있다 | 발견할 수 있다 (느리지만) |
| **모델** | **빠르고 정확하다** | **읽지 않으므로 발견하지 못한다** |

그래서 이름을 잘못 지은 함수, 실제로는 부수 효과가 있는 조회 함수, 문서와 다르게 동작하는 인터페이스는 **에이전트 환경에서 사람이 있을 때보다 더 비싼 결함**이 된다.

밥은 모델이 참고하는 것을 하나 더 언급한다 `[30:37]`.

> 모델은 **테스트에도 주의를 기울인다.** 시스템이 무엇을 하는지 이해하려고 테스트를 읽는다.

테스트가 명세 역할을 한다는 오래된 주장에 근거가 하나 더 붙은 셈이다. 다만 같은 위험이 따라온다. 테스트가 실제 요구와 다르면 모델은 **테스트 쪽을 믿는다.**

## 필수 지식 (HOW) — 밥이 구조를 다뤄 온 방식

밥은 최근까지 이 영역을 수동으로 다뤘다 `[26:20~26:47]`. 에이전트에게 시스템을 만들게 한 뒤 **에이전트를 심문했다.**

> 여기 구조가 어떻게 되어 있나. 이 모듈은 저 모듈과 어떻게 관계되나. 애초에 모듈이 뭐가 있나. 이것들이 서로 어떻게 이야기하나.

그리고 그가 밝히는 결과가 솔직하다.

> **그러고 나서 대답이 끔찍하게 무서워서 겁에 질리곤 했다.**

그러면 직접 모듈 구획을 설계하고, 어떻게 나뉘어야 하는지와 어떻게 통신해야 하는지를 정해 구현 계획을 내려보냈다. 이 방식의 한계는 분명하다. **사람이 매번 개입해야 한다.**

### 도구 1: 아키텍처 뷰어

밥은 에이전트에게 아키텍처 뷰어를 만들게 했다 `[26:47~27:14]`. 화면에 UML 다이어그램을 띄워 **모듈 구조와 의존이 흐르는 방향**을 보여 주고, 모듈을 클릭하면 하위 모듈이 보이고, 다시 클릭하면 코드가 뜬다. 원하는 만큼 파고들며 어느 층위에서든 구조를 볼 수 있다.

이것이 하는 일은 **구조를 읽는 비용을 낮추는 것**이다. 사람이 개입해야 한다면 개입 비용이라도 낮춰야 한다.

### 도구 2: 의존 규칙 명세와 체커

더 중요한 것은 이쪽이다 `[27:14~28:11]`.

> 어느 모듈이 어느 모듈에 의존해야 하는지, 어느 것이 어느 것에 의존하면 안 되는지, 의존이 어떻게 흘러야 하는지를 정의할 수 있는 **또 다른 결정론적 도구**를 만들었다. 그것이 **에이전트가 위반할 수 없는 단정한 명세 파일**로 들어간다. 마지막에 도는 체커가 있어서, 위반하면 **어떻게든 고쳐야 한다.**

에이전트가 위반을 고치는 방법도 밥이 열거한다. **의존을 역전시키거나, 인터페이스를 끼워 넣거나, 모듈을 반으로 쪼개거나** 하는 식이다.

02장의 원리가 아키텍처 층위에서 실현된 형태다. "레이어를 지켜라"라고 문서에 적는 대신, **지켜졌는지를 기계가 판정한다.**

| | 문서에 적힌 아키텍처 규칙 | 명세 파일 + 체커 |
|---|---|---|
| 언제 확인되나 | 사람이 리뷰할 때 (놓치면 끝) | **매번** |
| 위반의 결과 | 지적받거나 안 받거나 | **통과 못 한다** |
| 컨텍스트 소비 | 프롬프트에 넣으면 소비한다 | **없다** |
| 표현 범위 | 뉘앙스까지 | **판정 가능한 관계만** |

### 밥이 아직 못 한 것

밥은 이 부분을 자동화하려 시도하고 있으며 **성과가 신통치 않다**고 밝힌다 `[28:11]`. 진행자도 자기가 정확히 같은 처지라고 답한다. 즉 **구조를 정하는 일 자체는 아직 사람의 몫으로 남아 있다.** 07장에서 밥이 애자일 방식으로 돌아가며 "마지막의 수동 정리 단계에서 영영 벗어나지 못할지도 모른다"고 말하는 것과 이어진다.

## 이 장에서 이어지는 과제

**`05-01-dependency-checker`** — 밥이 만든 것과 같은 종류의 체커를 만든다. 허용된 의존 관계를 담은 명세와 실제 의존 그래프를 받아 위반과 순환을 찾아낸다.

소스 코드를 파싱하지 않는다. 입력은 **이미 추출된 의존 그래프**이고, 과제가 묻는 것은 **규칙을 어떻게 표현하고 위반을 어떻게 판정하는가**다.

## 자가 진단

- 지금 코드베이스에서 인터페이스가 약속한 것과 구현이 하는 일이 어긋난 자리를 아는가. 사람만 다룰 때보다 그 결함이 왜 더 비싸졌는가
- 우리 프로젝트의 아키텍처 규칙은 어디에 적혀 있는가. 그것을 **판정하는 것**은 무엇인가. 사람뿐인가
- 그 규칙 중 기계가 판정할 수 있는 것과 없는 것을 갈라 보라. 판정 가능한 쪽은 지금 무엇으로 지켜지고 있는가
