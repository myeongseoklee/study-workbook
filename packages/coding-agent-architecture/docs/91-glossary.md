# 91. 용어 해설집

단순 사전이 아니라 **레이어별로 묶고, 개념 간 인과 관계**와 함께 정리한다. 각 용어는 [정의 / 왜 존재하나 / 인접 개념과의 차이] 순으로 본다.

---

## 레이어 1 — 왜 에이전트인가 (한계와 구분)

**단일 모델 호출 (Single Call)**
프롬프트를 한 번 넣고 응답을 한 번 받는 방식. 사전학습 지식에 갇히고, 사람이 긴 프롬프트를 못 쓰며, 텍스트 밖 행동을 사람이 대행해야 한다는 한계 때문에 에이전트가 등장했다. → 에이전트 루프의 반대말.

**워크플로우 (Workflow)**
**코드가** 흐름을 제어하는 방식(고정 그래프). LangChain·LangGraph·n8n. 결정적이지만 유연성이 없다. ↔ 에이전트.

**에이전트 (Agent) / 에이전틱 AI**
**모델이** 흐름을 제어하는 방식. 반복 횟수·방법을 모델이 자율 결정. 유연하지만 결정성이 낮다(뽑기). "제어 흐름의 위치"가 워크플로우와의 유일한 구분선.

**SDD (Spec-Driven Development, 스펙 주도 개발)**
만들기 전에 모든 스펙을 정의하고 그대로 개발시킨다는 방법론. 강의는 "사람은 원하는 걸 글로 못 쓴다"며 비판하고, 대신 **모델과 함께 프롬프트를 써 내려가는 세션**을 대안으로 제시한다.

**RLVR (검증 가능한 보상 기반 강화학습)**
정답이 있는 문제(코딩 등)를 모델이 다양하게 푼 뒤 정답 맞은 궤적을 학습 데이터로 되먹이는 학습법. 결과로 **알파고식** 비인간적·창의적 해법이 나오며, 코드가 점점 리뷰하기 어려워지는 배경. → 비결정성을 증폭시키는 원인.

## 레이어 2 — 에이전트 루프의 뼈대

**요청 (Request)**
턴을 시작시키는 트리거. 사람뿐 아니라 **모델도** 발생시킨다(서브에이전트의 입력). → 턴의 시작점.

**턴 (Turn)**
요청부터 최종 응답까지. 오픈AI는 "쓰레드(thread)"라고도 부른다. 스케줄러(코덱스)로 경계가 애매해지는 중. → 세션이 담는 단위.

**이터레이션 (Iteration)**
한 턴 안의 연속적 모델 호출([도구 호출 → 결과 → 또 도구 호출]). 한 번의 응답에 리즈닝·어시스턴트 메시지·다중 도구 호출이 **병렬·스트림**으로 쏟아진다. → 턴 안쪽 반복.

**세션 (Session)**
턴을 담는 그릇. 컨텍스트를 **단조 증가**(늘어나기만)시키며 문제를 해결. "모델과 함께 거대한 프롬프트를 써 내려가는 과정". → 서브에이전트도 실체는 세션.

**컨텍스트 (Context)**
모델에 전송되는 히스토리 전체(시스템 프롬프트 + 대화 + 도구 결과 + …). 세션 안에서 단조 증가한다. → 희석·비용·KV 캐시의 근원.

---

## 레이어 3 — 확장된 제어권 (모델에게 넘기는 것)

**서브에이전트 (Sub-agent)**
모델이 **도구를 통해 생성한 세션**. 여는 진짜 이유는 **컨텍스트 분리** — 같은 모델도 컨텍스트를 비우면 다른 시각으로 같은 문제를 본다(예: 객관적 리뷰어). "에이전트"라는 이름은 마케팅 용어, 실체는 세션. ↔ 세션(사람이 연 것).

**골 (Goal)**
턴이 끝나는 시점에 모델이 "목표 달성했나?"를 재검토해 새 턴을 스스로 일으키는 것. 구현상 **"요청 큐에 넣는 도구"**가 있다는 뜻. → 이터레이션 제어를 넘어 턴 제어까지 모델에게 넘긴 것.

**에이전트 메시징 / 스티어링 (Steering)**
세션 간 요청·응답을 주고받는 것. 실체는 **메시지 큐에 넣고 세션이 가져가는 것**, 또는 진행 중 세션에 중간 메시지를 삽입하는 것. 하네스 책의 "에이전트 통신도"는 이걸 은유로 포장한 것. → 골·서브에이전트와 함께 "제어권 확장" 삼형제.

---

## 레이어 4 — 도구와 훅 (제어권을 넘기는 통로)

**도구 (Tool)**
모델이 제어권을 행사하는 통로. **어디까지 도구로 주는가 = 모델에게 어디까지 제어권을 넘기는가.** 기능을 코드에 가두면 워크플로우, 도구로 주면 에이전트.

**전용 도구 vs 범용 도구 (Dedicated vs Generic)**
전용=용도별 다양한 도구(Claude Code), 범용=쉘 하나로 통침(Codex). 전용은 약한 모델 실수를 줄이고, 범용은 강한 모델을 요구. → 도구 설계의 첫 번째 축.

**스킬 (Skill)**
도구보다 풍부한 설명(예제·퓨샷·참조 스크립트)을 담는 단위. 최근 추세는 **"도구는 터미널 하나 + 나머지는 스킬로 기술"** 통합. → 도구 설명의 빈약함을 보완.

**부수 효과 (Side Effect)**
도구가 결과값 외에 일으키는 것 — 스트리밍, 큐 삽입, **컨텍스트에 프롬프트 삽입**, 서브에이전트 열기. → 리마인더가 대표 사례.

**리마인더 (Reminder)**
로그가 길어져 단계를 까먹는 모델에게, 도구가 현재 위치 근처에 단계 정보를 재삽입하는 부수 효과. **약한 모델일수록 필요.** → 훅으로 구현.

**훅 (Hook)**
턴 루프의 단계 사이 이벤트에 걸어 기능을 붙였다 뗐다 하는 장치. 턴 루프를 중지시키거나 메시지를 추가. 사용자 훅 + 에이전트 기본 기능 다수가 훅. 강한 모델일수록 훅을 뺀다. → 리마인더·가드레일·스트림 가드·반복 감지의 구현 틀.

**가드레일 (Guardrail)**
민감 정보 유출·부적절 요청을 막는 장치. **휴먼 체크는 횟수가 많으면 100% 무력화**되므로, 정규식 기반 자동 검사·프롬프트 리라이팅·출력 필터로 만들어야 한다.

**요청 큐 / 대기열 (Request Queue)**
응답 중 들어온 요청을 쌓아두는 곳. 코드가 처리하면 워크플로우, **도구로 큐 삽입을 제공하면 골**이 성립. 최근엔 여러 큐를 **하나로 통합**해 감시.

## 레이어 5 — 컨텍스트 경제와 하드웨어

**컨텍스트 희석 (Context Dilution)**
세션이 길어져 성능이 떨어지는 현상. 원인은 어텐션이 아니라 **모순·중복 토큰의 누적**(사람이 말을 바꾸기 때문). → 4시-7시 규칙의 근거.

**4시-7시 규칙**
컨텍스트 도넛을 시계로 볼 때 **4시**에 마지막 요청(성능 최고점), 7시 마지노선, 9시·컴팩션 후는 쓰레기. 강사의 경험칙(민감/어려운 작업). → 폴더 격리 아키텍처 요구로 이어짐.

**컴팩션 (Compaction)**
컨텍스트가 한계에 다다르면 이전 히스토리를 요약해 압축하는 것. 4시-7시 관점에선 "9시 이후 + 컴팩션 = 쓰레기". → 장시간 자율 작업의 비용 원천.

**폴더 격리 (Folder Isolation)**
파일 하나여도 폴더로 나눠, 바이브 코딩의 **뽑기가 그 폴더 안에서만** 일어나게 하는 것. 바이브 코딩의 최강 가드레일. 하루 수십 번 수정되는 현실 제품을 안 깨고 유지하는 유일한 길. → 변화율 기반 아키텍처.

**뽑기 (비결정성, Non-determinism)**
샘플링·디코딩의 무작위성 + 자율성에서 오는 예측 불가능성. 격리 없이는 수정 하나가 전역 파일을 바꾼다. → 폴더 격리로 국소화.

**KV 캐시 (KV Cache)**
어텐션 계산의 Key·Value를 세션별로 캐싱한 것. 컨텍스트가 클수록 VRAM을 많이 잡아먹어 **컨텍스트 크기 = 비용**. 온프레미스에선 동시 세션 수를 직접 제한. → 컨텍스트 크기 정책·H200 세션 산수의 핵심.

**양자화 (Quantization) / Q4·Q5**
모델 가중치를 낮은 비트로 압축. **Q4는 원본 분포에서 벗어나 사실상 다른 모델**, Q5부터 원본 성향 유지(KL 발산 ~0.03 이내). → 로컬 LLM의 두 번째 하한.

**KL 발산 (KL Divergence)**
양자화 모델의 출력 분포가 원본에서 얼마나 벗어났는지의 척도. ~0.03 이내여야 원본 성향 유지 → Q5 하한의 근거.

**H200**
NVIDIA 데이터센터 GPU, 카드당 141GB VRAM(HBM3e). 온프레미스 로컬 LLM의 기본 단위. → KV 세션 산수의 출발점.

## 레이어 6 — 세션과 컨텍스트의 구현 (#2)

**KV 캐시 식별 ID (KV Cache ID)**
모델이 들고 있는 KV 캐시를 가리키는 키. **세션의 실체가 바로 이것**이다 — 캐시 ID가 다르면 다른 세션이다. 화면의 대화창은 이 실체의 껍데기. → 세션 수 = 캐시 세트 수 = 메모리 비용.

**프리픽스 캐시 (Prefix Cache)**
컨텍스트 앞부분이 변하지 않는다는 전제로 그 부분의 KV 캐시를 재사용하는 것. 앞을 한 글자만 고쳐도 뒤 캐시가 전부 무효가 된다. **에이전트 컨텍스트가 append-only 불변 리스트인 이유가 이것** — 취향이 아니라 캐시를 살리기 위한 구조적 요구. ↔ 컴팩션과 충돌한다.

**캐시 영속화 / 복원 (Cache Persistence / Restore)**
유휴 세션의 KV 캐시를 약 20분 뒤 내릴 때 **디스크에 직렬화해 저장**하고, 재입장 시 다시 올려주는 기능. 없으면 재입장마다 거대한 앞부분을 재처리해 프롬프트 프로세싱이 오래 걸린다. → 클로드 코드의 기능.

**포크 (Fork)**
이전 컨텍스트를 이어받은 새 세션을 만드는 것. 실체는 **KV 캐시 복사**여서 재계산 없이 즉시 시작된다.

**세션별 인스턴스 (Session-per-Instance)**
개별 세션마다 채널을 개설해 운영하는 방식(클로드 코드). 채팅 서버가 방을 소켓으로 격리하는 구조와 같다. **클라이언트가 세션을 점유**한다. ↔ 스트림 서버.

**스트림 서버 (Stream Server)**
서버 입장에서 세션을 "식별 ID만 다른 동일한 메시지"로 보는 방식(코덱스). 거대한 이벤트 흐름 하나가 있을 뿐이다. **클라이언트가 세션을 점유하지 않아** 모바일·브라우저·CLI가 같은 세션을 동시에 볼 수 있다. → 원격 지원의 근거.

**콜드 스트림 / 핫 스트림 (Cold / Hot Stream)**
스트림 구독의 두 단계. 세션 서버를 처음 열 때 과거 이벤트를 한 번에 받아오는 것이 콜드, 이후 실시간 수신이 핫.

**기반 컨텍스트 (Base Context)**
시스템 프롬프트·툴 정의·인스트럭션·퍼미션·에이전트별 프롬프트·AGENTS.md 체인·실행 환경·README 등으로 구성되며 **세션 시작 시 계산 후 고정**되는 부분. 예산 목표는 모델 컨텍스트의 **5% 이내**(코덱스 실측 약 4%). ↔ 턴 로그.

**턴 로그 (Turn Log)**
요청·응답·도구 호출이 쌓이는 히스토리. 뒤로만 자라는 **단조 증가 불변 리스트**이며 컴팩션의 대상이다.

**이름 해소 규칙 (Name Resolution Priority)**
같은 이름의 자원이 전역·프로젝트·시스템 여러 곳에 있을 때 누가 이기는지의 규칙. 스킬만이 아니라 **MCP·툴·프롬프트·커맨드·플러그인·룰스** 전부에서 필요하다. → 부가 기능이 아니라 아키텍처 필수 요소.

**스캐폴딩 스킬 + 2단계 로딩 (Scaffolding Skill)**
전역에는 스캐폴딩 스킬만 두고, 실행 시 `assets`의 기본 세트를 프로젝트로 복사해 **그 프로젝트 유형 전용 스킬셋**을 심는 방식. 로딩이 전역→프로젝트 2단계로 일어나는 성질을 이용해 기반 컨텍스트를 작게 유지한다.

**잘림 정책 (Truncation Policy)**
컨텍스트 오버플로 시 추론 서버가 적용하는 정책. **롤링 윈도우**(앞을 계속 뭉갬) / **중간 절단**(중간에서 끊음) / **정지**(리미트에서 끊어버림). 셋 다 코딩에 치명적이라 **그 전에 컴팩트해야 한다**. → 컴팩션 트리거의 존재 이유.

**컴팩트 레코드 (Compact Record)**
컴팩션 결과를 로그에 append하는 항목. **스냅샷 구분점** 역할을 해서, 모델 입력은 **마지막 컴팩트 레코드 아래로만** 구성된다. 전체 로그에는 여러 개가 존재하며 로그 자체는 지우지 않는다 → 저장 구조(불변)와 재생 범위(가변)의 분리.

**컴팩트 레코드 병합 (Compact Merge)**
연속된 컴팩트 레코드를 모아 다시 요약해 세대별 열화를 완화하는 기법. **원래 RAG의 청크 병합**에서 왔다.

**검색형 요약 (Retrieval-style Summary)**
각 턴을 한 줄로 요약하고 참조 ID를 붙여, 상세가 필요하면 **모델이 도구를 호출해 조회**하게 하는 컴팩션 방식. 모델 요약보다 정보 분실이 적다. 단 턴이 쌓이면 여기에도 슬라이딩 윈도우가 붙는다.

## 레이어 7 — 비즈니스 제품 요구 (#2)

**온프레미스 (On-premise)**
고객사 내부 인프라에서만 구동되는 납품 형태. **웹 검색 / 외부 모델 / 보안 프로그램과의 공존**을 전부 깨뜨리며, 그 때문에 상용 에이전트가 통하지 않아 **직접 만든 제품의 시장이 생긴다.** → 이 회차 전체의 사업적 전제.

**모델 라우터 (Model Router)**
어떤 요청을 어느 모델로 보낼지 정하는 계층. 기업의 핵심 요구는 **엔터프라이즈 할당 토큰 소진 시 사내 LLM으로 무중단 전환**. 최소 구현은 "개인이 쓸 모델을 서버가 내려주기"(산업용은 회사가 모델을 지정한다).

**거버넌스 → 가드레일 (Governance → Guardrail)**
거버넌스는 사내 규정·정책("이 절차로 한다", "USB로 데이터를 못 갖고 나간다"). 에이전트도 이를 지켜야 하므로 **정책을 가드레일로 변환해 연동**하는 기능이 필요하다.

**풋프린트 (Footprint)**
로그인 시 수집하는 흔적(사내 IP, 부서, 지급 노트북의 보안 코드 등). 보안 정책 때문에 회사마다 요구가 크게 달라 **커스터마이즈가 필수**다.

**중간관리자 위임 (Delegated Administration)**
AX팀이 전부 관리하지 않고 팀장에게 팀원 관리를 넘기는 기능. 이것이 있으면 **관리자 페이지가 로그인 주체에 따라 달라진다.** 없으면 산업용이 성립하지 않는다.

**공유드라이브 강제 (Shared-drive-only Project Creation)**
프로젝트 생성 자체를 공유드라이브에서만 허용해 **소스 코드 노출을 막는** 기능. 팀·개인 공간 설정이 S3 버킷 설정과 같은 일이 되고, 사내 GitLab·GitHub Enterprise 연동까지 확장된다.

**정보검색센터 (Information Retrieval Center)**
온프레미스 웹검색 대체 + 사내 라이브러리·문서·코드 검색 + 사용 로그 수집을 통한 자기성찰·학습 데이터셋 확보를 묶은 구성요소.

**궤적 학습 / 자기 성찰 (Trajectory Learning / Self-reflection)**
에이전트 이용 로그를 수집해 학습에 되먹이는 것. 정기적 파인튜닝의 입력이 된다. → RLVR 선호 정렬과 연결.

**터보 모노레포 (Turborepo Monorepo)**
`turbo.json`으로 여러 모듈을 구성하는 아키텍처. **하부가 JS 프로젝트가 아니어도 된다**(C++·파이썬 통합 빌드). `apps` = 오케스트레이션(빌드 단위 서비스), `packages` = 핵심 도메인(라이브러리)이며 참조는 **`apps` → `packages` 단방향**, `packages`에는 프레임워크 지식이 들어가지 않는다.

**PGVector**
PostgreSQL에 벡터 확장을 꽂은 것. 이 강의에서는 여기에 **카프카를 대신할 이벤트 스트림 플러그인까지 얹어** 벡터 검색과 이벤트 스트림을 한 인프라로 처리한다 → 온프레미스에서 미들웨어 수를 줄이는 선택.

**RHEL 컨테이너 차단**
레드햇 엔터프라이즈 + 사내 보안 환경에서 **도커 컨테이너를 막아놓는** 정책. "도커가 보안상 유리하다"는 일반론이 현장에서 뒤집히는 지점이며, 네이티브 설치형이 필요해지는 이유.

**오퍼레이터 (Operator)**
새 팀 운영 모델에서 원탁의 컴퓨터 한 대를 조작하는 사람. 팀은 모여 계획 문서를 확정하고 던진 뒤 퇴근하며, 오전에 모여 리뷰한다. → 개인 생산력이 아니라 팀 생산력을 만드는 배치.

## 레이어 8 — 이벤트 기반 에이전트 서버 (#4)

4강의 어휘다. 앞 레이어와 달리 **한 결정에서 파생된 용어 집합**이라, 순서대로 읽는 편이 낫다.

**CPS (Continuation-Passing Style)**
요청과 함께 "응답을 나중에 받을 곳(continuation)"만 던져두고 바로 다음 일로 넘어가는 호출 방식. 응답을 기다리지 않으므로 **리턴이 없고**, 결과는 훗날 그 목적지로 별도 배달된다. 그래서 남는 것은 함수가 아니라 부수효과 프로시저뿐이다. → 컨티뉴에이션의 정체는 **콜백**이고, 차이는 "모든 진행이 콜백 연쇄로만 이뤄진다"는 전면성이다.

**컨티뉴에이션 (Continuation)**
"이 요청의 결과를 나중에 어디로 보낼지"를 가리키는 위치. 봉투에서는 `replyChannel` 필드가 이 자리다.

**역전된 클라이언트-서버 (Inverted Client-Server)**
CPS를 택하면 서버가 클라이언트를 호출해야 하므로 **클라이언트도 서버가 되는** 상태. 이걸 피하려고 클라이언트가 엔드포인트를 열지 않으면 남는 형태가 발행-구독이다. → `event-sourcing-msa`의 「채널이 계약이다」와 같은 지점.

**엔벨로프 / 봉투 (Envelope)**
모든 이벤트를 감싸는 래퍼. 진짜 내용(페이로드)은 그 안에 들어간다. 페이로드는 기능마다 다르고 계속 늘어나지만 봉투는 거의 안 바뀌므로, **봉투가 서버·워커·클라이언트의 불변 계약**이 된다. 라우팅·재시도·추적을 전부 봉투만 보고 처리한다.

**`eventKey` / `transactionKey` / 인과 키**
`eventKey`는 이벤트 1건의 고유 ID로 **재시도하면 바뀐다**. `transactionKey`는 멱등 경계로 **재시도해도 안 바뀐다** — 그래서 검문소가 알아본다. `parentEventKey`·`causationEventKey`·`correlationKey`는 인과 그래프의 간선이다. 이 셋을 섞으면 멱등이 작동하지 않는다(`eventKey`로 판정하면 모든 재시도가 새 요청으로 통과).

**계층 컨텍스트 (Hierarchical Context)**
`sessionKey → runKey → turnKey → iterationKey → stepKey → toolCallKey`. 1강의 3계층(세션·턴·이터레이션)이 그대로 필드로 승격되고 아래로 셋이 더 붙는다.

**자기 서술성 (Self-description)**
이벤트가 자기 위치를 스스로 설명하므로 **서버가 상태를 몰라도 라우팅**되는 성질. *"이벤트는 이벤트 자체 메시지만으로 완전해야 돼."* 이것이 워커의 무상태(교체 가능)와 샤드의 무상태(증식 가능)를 동시에 가능하게 한다.

**`sequence`**
스트림 조각의 단조 증가 순번. 같은 `transactionKey`를 공유하는 조각들(모델 토큰, 도구 출력)을 구분한다. **재정렬과 누락 감지** 두 가지 용도 — 3 다음에 5가 오면 4가 빠졌음을 안다.

**멱등성 (Idempotency)**
같은 요청이 두 번 도착해도 실제 처리는 한 번만 일어나게 만드는 것. **트랜잭션이 아니다** — 원자성·격리를 주지 않고, "재시도가 안전하다"는 성질일 뿐이다.

**at-least-once / exactly-once**
큐가 실제로 보장하는 것은 최소 한 번 전달(at-least-once)뿐이다. exactly-once는 *"설계를 잘해서 얻는 게 아니라 애초에 존재하지 않는 목표"* — 응답을 못 받은 쪽은 "실행됐는데 응답만 유실"과 "실행 자체가 안 됨"을 구분할 방법이 없기 때문이다.

**키 기반 멱등 / 검문소 (Key-based Idempotency / Gate)**
모든 동작 앞에 "이 키를 이미 처리했는가"만 확인하는 게이트 하나를 세우는 방식. 🔴 **엄밀히 말하면 멱등이 아니다** — 동작이 멱등해진 게 아니라 실행 여부가 키라는 인자로 결정되는 **인자 기반 분기**다. 다만 이 게이트 하나가 모든 동작의 개별 멱등 구현을 대체한다.

**세 갈래 판정 (`claimed` / `running` / `duplicate` / `conflict`)**
검문소의 결과. 표에 끼워넣기 성공이면 `claimed`(내가 담당), 같은 키·같은 페이로드인데 처리 중이면 `running`(대기), 끝났으면 `duplicate`(저장된 결과 반환), **키가 같은데 페이로드가 다르면 `conflict`(오류)**. 마지막 칸을 조용히 삼키면 클라이언트가 잘못된 성공을 믿는다.

**페이로드 해시 (Payload Hash)**
검문소가 요청 내용의 동일성을 상수 시간에 비교하기 위해 저장하는 값. 객체 키 순서는 무시해야 하고(재시도 시 직렬화 순서가 바뀔 수 있다) 배열 순서는 유지해야 한다(순서가 의미다).

**아웃박스 (Outbox)**
검문소 기록과 큐 발행이 서로 다른 시스템일 때 생기는 어긋남("DB에는 썼는데 발행은 실패")을 막는 패턴. 발행할 메시지를 같은 트랜잭션 안에서 테이블에 쓰고, 별도 프로세스가 그것을 보고 실제 발행한다. → 큐도 같은 DB 안에 있으면(PGMQ) 이 어긋남이 애초에 작다.

**PGMQ**
PostgreSQL에 "줄 서기 기능"만 추가하는 확장. 하는 일은 세 가지 — **꺼내기 / 지우기 / 점유 중이라고 마킹하기**. 보장하는 것은 선입선출과 큐 접근자 사이의 **가벼운 동기화** 둘뿐이다. 선택 근거는 성능이 아니라 **운영 대상 수와 정합성**이다(*"실제로 느려지는 구간은 큐가 아니라 AI 모델이 답변을 생각하는 시간"*).

**가시성 타임아웃 (Visibility Timeout, `vt`)**
메시지를 읽으면 그 시간 동안 다른 워커에게 보이지 않게 하는 값. 만료되면 다시 보이므로 **워커 사망 시 자동 복구의 유일한 메커니즘**이다. 짧으면 중복 배정, 길면 그만큼 멈춰 있다.

**하트비트 / `set_vt`**
처리가 길어지는 작업이 점유를 연장하는 것. *"화장실 칸의 사용 중 표시를 계속 갱신하지 않으면 남이 문을 열고 들어옴."* 연장할 틈은 작업이 쪼개져 있어야 생긴다 — 취소 가능성과 같은 요구다.

**삭제 시점 (Deletion Timing)**
🔴 4강 설계의 핵심 손잡이. 가져갈 때 지우면 **유실**, 완료·저장 후 지우면 **중복**이 남는다. 이 설계는 **못 고치는 문제(유실)를 고칠 수 있는 문제(중복)로 치환한 뒤 멱등 키로 흡수**한다.

**이벤트 리플레이 (Event Replay)**
오간 이벤트를 전부 시간순으로 남겨 두어, 문제가 생겼을 때 "이 요청이 정확히 어떤 경로로 처리됐는지"를 재구성하는 것. 판정 표(`agent_execution`, 트랜잭션당 1행·갱신)와 이벤트 로그(`agent_events`, 트랜잭션당 N행·추가만)가 별개인 이유다.

**이벤트가 곧 API (Event-as-API)**
요청–응답 짝으로 정의하던 프로토콜이 사라지고 **이벤트 타입 정의가 유일한 계약**이 되는 상태. 정의하기는 쉬워지는 대신, 요청과 응답의 짝이 코드 어디에도 안 적힌다 — 그 짝을 런타임에서는 인과 키가, 문서에서는 패밀리 표가 담당한다.

**이벤트 패밀리 (Event Family)**
`session.*` `turn.*` `iteration.*` `tool.*` `process.*` `hook.*` `model.*` `state.*` `approval.*` `artifact.*` — 열 종류. **도구는 논리적 호출, 프로세스는 물리적 실행**으로 분리해 어떤 언어의 프로그램도 붙일 수 있게 한 것이 설계 결정이다.

**합타입 / 유니온 (Sum Type / Union — `VibeEvent`)**
패밀리 열 개를 "A 또는 B 또는 C…"로 묶은 타입. 통로(큐 전송·이벤트 로그·웹소켓 허브)는 이것 하나만 받는 함수 한 벌로 끝나면서 안에 어떤 패밀리가 들어 있는지는 정보로 남는다. **새 기능은 파일 하나 + 유니온에 한 줄 → 확장 비용이 상수.** 단 판별 태그가 없으면 `any`와 안전성이 같다.

**워커 스레드 풀 (Worker Thread Pool)**
접수(요청 받기)와 처리(실제 일)를 다른 주체에게 맡기는 배치. 파라미터 셋 — `min`(채용 지연 방지), `max`(무한 고용 방지), `maxQueue`(역압). *"워커를 만드는 거 채용 절차라고 생각하면 채용은 오래 걸리잖아요."*

**슬롯 은퇴·교체 (Slot Retire / Replace)**
워커가 오류로 죽으면 슬롯을 은퇴시키고 새 워커로 자리를 메우는 것. `error`와 `exit`이 연달아 오는 것이 정상이라 **이미 은퇴했으면 아무 일도 하지 않아야** 한다(그렇지 않으면 워커가 두 배로 뜬다).

**취소 가능성의 전제 (Abortability)**
🔴 `AbortSignal`을 받는 것은 인터페이스일 뿐이다. 실제로 취소되려면 **작업이 잘게 쪼개져 중간에 멈출 지점이 있어야** 한다. 즉 취소 가능성은 런타임 기능이 아니라 **코드 구조의 성질**이다. 쪼갤 수 없으면 외부 프로세스로 분리해 죽일 수 있게 만든다.

**허용 목록 (Action Whitelist)**
워커가 미리 허락된 작업만 하게 하는 것. **"목록에 없는 낯선 작업이 오면 시도조차 하지 않고 바로 실패로 처리"** — 워커는 임의 코드 실행 지점이므로 여기가 열려 있으면 이벤트를 주입할 수 있는 누구든 서버에서 임의 작업을 돌린다.

**세션 = 채널 (Session-as-Channel)**
세션 하나를 개별 채널로 취급하는 것. 이 도메인은 흔한 pub/sub과 형태가 반대다 — **채널은 매우 많고(세션 수만큼) 구독자는 1~3명.** 그래서 팬아웃 최적화의 장점이 거의 안 나타나고 채널당 고정 비용이 중요해진다.

**샤드 분리 (Shard Separation)**
진실의 원본은 중앙 저장소에 두고 **채널 구독·발행 책임만** 무상태 서버 여러 개로 나누는 확장 방식. 병목이 서버→클라이언트 송신이기 때문이다(수신은 싸다). 4강 시점에는 **계획으로만 남았다** — *"이것까지 우리가 구현할지는 잘 모르겠어요."*

## 레이어 9 — 브로커 인프라와 로컬 모델 해부학 (#5)

5강의 어휘다. 앞의 레이어 8이 "무엇을 잃고 무엇으로 갚는가"였다면 이쪽은 **"그렇게 만든 물건을 몇 번 쓸 수 있는가"**의 어휘다. 뒤쪽 절반(모델 해부학)은 성격이 달라 따로 묶었다.

### 9-1. 병목과 참가자

**접수 대기 / 요청 처리 / 응답 대기 (세 병목)**
트래픽이 막히는 세 자리. 각각 **입구 · 처리기 · 연결 슬롯**을 고갈시킨다. 앞의 둘은 하드웨어로 완화되지만 **응답 대기는 구조를 바꿔야 사라진다** — 슬롯을 붙잡는 시간이 그대로면 서버를 늘려도 사용자 증가율에 먹혀 같은 자리로 돌아온다. → 4강 CPS의 **두 번째 독립 근거**가 이것이다.

**채널 기반 송수신 (Channel-based Messaging)**
서버가 상대를 1대1로 알지 않고 "이 채널을 구독한 소켓 목록"만 들고 있는 방식. 목적은 라우팅 효율이 아니라 **식별성을 없애는 것**이다 — 상태가 있으면 그 서버는 대체 불가능해지고 대수를 늘릴 때 상태 분할이 새 문제로 올라온다. → 레이어 8의 「채널이 계약이다」가 인프라 층에서 다시 나타난 것.

**PGMQ**
PostgreSQL의 메시지큐 확장. `write` · `read` · `delete` · `set_vt` · `archive` 다섯 연산만 지원한다. 🔴 고르는 결정적 이유는 성능이 아니라 **MQ와 영속화 테이블을 한 트랜잭션으로 묶을 수 있다**는 것 — 전용 브로커에서는 그 트랜잭션이 원리적으로 불가능해 "메시지는 보냈는데 저장은 실패"의 보정 코드가 상시 필요하다.

**가시성 타임아웃 (`set_vt` / Visibility Timeout)**
워커가 메시지를 꺼낸 뒤 일정 시간 다른 워커에게 그 메시지를 숨기는 원자적 연산. 그동안 워커가 죽으면 `delete`가 호출되지 않아 타임아웃 후 메시지가 다시 보인다. → 4강 6장의 "삭제 시점"이 PGMQ 연산으로 구현된 자리.

**이벤트 브로커 (Event Broker)**
🔴 **"전달하는 서버"가 아니라 "처리하지 않는 서버"**다. 클라이언트에게는 소켓 서버로 보이고, MQ에게는 클라이언트 하나로 보인다. 처리 로직이 없어 공유할 상태가 없고, 그래서 대수를 늘려도 정합성 문제가 안 생긴다 — **무능이 곧 확장성이다.** → 반대로 어떤 중간 계층을 무한 증설하고 싶다면 그 계층에서 로직을 걷어내야 한다.

**프록시 효과 (Broker as DB Proxy)**
브로커가 끼면 DB가 상대하는 것이 클라이언트 수가 아니라 **브로커 수**가 되는 현상. `클라이언트 수만 → 브로커 수십~수백 → MQ 1대`로 접속 수가 접힌다. MySQL 프록시가 하는 일과 같은 성질.

**경쟁 소비 (Competing Consumers)**
하나의 큐를 여러 소비자가 나눠 갖는 방식. **한 메시지는 한 소비자에게만** 간다. 작업 배분에는 맞지만 결과 전달에는 맞지 않는다 — 브로커 셋이 같은 큐를 읽으면 내 채널 이벤트를 남이 집어가 버린다.

**팬아웃 tail (Fan-out Tail)**
같은 로그를 여러 소비자가 **각자 커서를 들고 따라 읽는** 방식. `SELECT … WHERE position > $cursor ORDER BY position LIMIT n`. 🔴 큐와 결정적으로 다른 점은 **"읽기가 읽기"**라는 것 — 큐의 `read`는 가시성 타임아웃을 거는 `UPDATE`라 읽는 쪽을 N배 늘리면 쓰기도 N배가 되지만, 로그는 모두 같은 꼬리를 읽으므로 그 페이지가 이미 공유 버퍼에 있다.

**커서 (Cursor)**
브로커가 "내가 어디까지 읽었는가"를 기록한 위치 하나. 이벤트가 불변이므로 커서만 있으면 락도 동기화도 필요 없다. → **브로커의 상태가 커서 하나와 소켓 맵뿐**이 되고, 그래서 브로커는 언제든 버려도 되는 프로세스가 된다.

**봉합 비용 (Cost of Patching)**
어떤 선택을 유지하기 위해 덧붙여야 하는 장치들의 총합. 결과 경로를 큐로 밀어붙이면 라우터 프로세스 · 브로커별 전용 큐 · 두 번째 아웃박스 · identity lease · 전용 테이블 셋이 필요해진다. **개별 장치는 각각 합리적으로 보이므로, 목록으로 모아 놓기 전에는 잘 드러나지 않는다** — 목록이 원래 문제보다 길면 선택 자체를 다시 본다.

**팻 클라이언트 / 신 클라이언트 (Fat / Thin Client)**
해석·상태 조립·렌더링을 클라이언트가 다 하는가, 서버가 만들어 준 것을 표시만 하는가. 🔴 **서버의 무지와 클라이언트의 두께는 같은 결정의 양면이다** — 서버가 상대를 모르기로 하면 상대에 맞춘 화면을 만들 수 없다. 가장 아픈 비용은 번들 크기가 아니라 **버전 분기**(계약의 한쪽이 사용자 기기에 있다).

**이벤트 타입 협약 (Event-Type Contract)**
🔴 이 구조에서 **"애플리케이션"의 정의** — 클라이언트와 워커 사이에 맺어진, 어떤 이벤트 타입을 주고받을지의 합의. 브로커와 MQ는 이 협약을 모르므로 애플리케이션이 늘어도 **코드도 인스턴스도 그대로 재사용된다.** 단 논리적 격리는 완전해도 **물리적 격리는 없다**(용량·커넥션·DB 장애는 공유).

**순수 라이브러리 (Pure Library)**
다른 제품으로 떼어 갈 수 있는 패키지. 🔴 판별식은 의견이 아니라 **"의존성이 전부 외부인가"**다 — 사내 패키지를 하나라도 import하면 이미 그 제품에 묶여 있다. "인프라는 영원히 재사용"이라는 주장이 코드 수준에서 지켜지는 자리.

### 9-2. 로컬 모델 해부학

**추측 디코딩 (Speculative Decoding)**
작고 빠른 제안자가 다음 토큰 여러 개를 미리 내놓고 본체 모델이 **한 번에 검증**하는 가속 기법. 검증이 생성보다 싸므로 제안이 맞을수록 빨라진다. 현실적 기대치는 **10~20%이고 두 배는 없다.**

**MTP (Multi-Token Prediction)**
본체 모델에 딸린 **추측 디코딩 전용 별도 웨이트**. 별도의 초안 모델을 쓰는 대신 이것을 쓴다. 동봉되면 같은 양자화라도 파일이 0.2~1GB 커진다 → **같은 이름·같은 비트인데 크기가 다른 이유** 중 하나.

**초안 길이 (Draft Length)**
한 번에 제안할 토큰 수. 🔴 **앞에서부터 채택**되므로 첫 토큰이 거부되면 뒤가 전부 무효가 된다 — 비용은 길이 k에 비례하고 이득은 채택률 p의 k제곱으로 줄어든다. 그래서 최적값이 작다(권장 최대 2 / 최소 0).

**채택 임계 (Acceptance Threshold)**
제안 토큰을 받아들일 유사도 기준. 낮추면 속도는 오르고 품질이 그만큼 내려간다 — 0.75로 두면 최악의 경우 원 모델 대비 그 수준까지 떨어질 수 있다. **품질을 파는 다이얼**이다.

**PTQ (Post-Training Quantization)**
학습이 끝난 모델을 나중에 낮은 정밀도로 변환하는 것. 모델이 반올림 오차를 겪어 본 적이 없어 저비트로 갈수록 품질이 뚜렷하게 떨어진다. 비트 선택은 자유롭다(2·3·4·5·6·8…).

**QAT (Quantization-Aware Training)**
🔴 **학습 중에 양자화 오차를 흉내 내며** 가중치를 잡는 방식. 오차에 견디도록 학습됐으므로 같은 비트의 PTQ보다 낫다. 대신 학습 시점에 목표 비트를 정하므로 **선택지가 좁다(보통 4·8비트).** 다만 "한 단계 위 비트와 같다"고 가정하면 안 된다 — 모델마다 다르고 자랑만큼은 아니다.

**이미지 타워 / 오디오 타워 (Vision / Audio Encoder)**
멀티모달 입력을 처리하는 **별도 모듈**. 모델 카드에 본체와 분리해 파라미터 수가 표기되고, 🔴 **튜닝하면서 통째로 뺄 수 있다** — 원본이 멀티모달이어도 그 튜닝본은 아닐 수 있다. 코딩 에이전트에서는 이것이 곧 **"스크린샷을 던질 수 있는가"**이고, 모델 선택의 1차 필터다.

**용량 공백 (Capacity Gap)**
모델 크기가 연속 분포가 아니라서 생기는 빈 구간. 카탈로그에서 37GB 다음이 82GB로 뛰는 식이다(2026-08 관측). 그래서 **메모리를 더 사도 올릴 수 있는 모델이 안 느는 구간**이 존재하고, 128GB가 64GB 대비 실익이 작다는 판단이 여기서 나온다. → 판단 순서를 "메모리를 얼마 살까"가 아니라 **"어떤 모델을 올릴 건데 그게 몇 GB인가"**로 뒤집어야 하는 이유.

**KV 캐시 양자화 (KV Cache Quantization)**
KV 캐시를 낮은 정밀도로 저장해 VRAM을 아끼는 것. 🔴 **짧은 세션에서는 멀쩡하고 100턴 넘는 긴 세션에서 무너진다** — 오차가 턴을 거치며 누적되기 때문이다. 짧은 테스트를 통과하므로 QA에서도 안 잡히고, 코딩 워크로드에서는 결국 풀어야 해서 **절약을 전제로 짠 용량 계획이 무너진다.** → 2강 1장의 "세션 = KV 캐시"가 운영 비용으로 돌아오는 자리.

**통합 메모리 (Unified Memory)**
CPU와 GPU가 같은 메모리를 공유하는 구성. 큰 모델이 올라가는 대신 **대역폭이 전용 VRAM보다 낮다.** 같은 GB 수라도 개인 실험용과 납품 장비의 값이 다르다 — "돌기만 하면 되는가"가 갈림길이다.
