# 91. 용어 해설집

단순 사전이 아니라 **레이어별로 묶고, 개념 간 인과 관계**와 함께 정리한다. 각 용어는 [정의 / 왜 존재하나 / 인접 개념과의 차이] 순으로 본다.

---

## 레이어 1 — 왜 에이전트인가 (한계와 구분)

**단일 모델 호출 (Single Call)**
프롬프트를 한 번 넣고 응답을 한 번 받는 방식. 사전학습 지식에 갇히고, 사람이 긴 프롬프트를 못 쓰며, 텍스트 밖 행동을 사람이 대행해야 한다는 한계 때문에 에이전트가 등장했다. → 에이전트 루프의 반대말.

**워크플로우 (Workflow)**
**코드가** 흐름을 제어하는 방식(고정 그래프). LangChain·LangGraph·n8n. 결정적이지만 유연성이 없다. ↔ 에이전트.

**에이전트 (Agent) / 에이전틱 AI**
**모델이** 흐름을 제어하는 방식. 반복 횟수·방법을 모델이 자율 결정. 유연하지만 결정성이 낮다(뽑기). "제어 흐름의 위치"가 워크플로우와의 유일한 구분선.

**SDD (Spec-Driven Development, 스펙 주도 개발)**
만들기 전에 모든 스펙을 정의하고 그대로 개발시킨다는 방법론. 강의는 "사람은 원하는 걸 글로 못 쓴다"며 비판하고, 대신 **모델과 함께 프롬프트를 써 내려가는 세션**을 대안으로 제시한다.

**RLVR (검증 가능한 보상 기반 강화학습)**
정답이 있는 문제(코딩 등)를 모델이 다양하게 푼 뒤 정답 맞은 궤적을 학습 데이터로 되먹이는 학습법. 결과로 **알파고식** 비인간적·창의적 해법이 나오며, 코드가 점점 리뷰하기 어려워지는 배경. → 비결정성을 증폭시키는 원인.

## 레이어 2 — 에이전트 루프의 뼈대

**요청 (Request)**
턴을 시작시키는 트리거. 사람뿐 아니라 **모델도** 발생시킨다(서브에이전트의 입력). → 턴의 시작점.

**턴 (Turn)**
요청부터 최종 응답까지. 오픈AI는 "쓰레드(thread)"라고도 부른다. 스케줄러(코덱스)로 경계가 애매해지는 중. → 세션이 담는 단위.

**이터레이션 (Iteration)**
한 턴 안의 연속적 모델 호출([도구 호출 → 결과 → 또 도구 호출]). 한 번의 응답에 리즈닝·어시스턴트 메시지·다중 도구 호출이 **병렬·스트림**으로 쏟아진다. → 턴 안쪽 반복.

**세션 (Session)**
턴을 담는 그릇. 컨텍스트를 **단조 증가**(늘어나기만)시키며 문제를 해결. "모델과 함께 거대한 프롬프트를 써 내려가는 과정". → 서브에이전트도 실체는 세션.

**컨텍스트 (Context)**
모델에 전송되는 히스토리 전체(시스템 프롬프트 + 대화 + 도구 결과 + …). 세션 안에서 단조 증가한다. → 희석·비용·KV 캐시의 근원.

---

## 레이어 3 — 확장된 제어권 (모델에게 넘기는 것)

**서브에이전트 (Sub-agent)**
모델이 **도구를 통해 생성한 세션**. 여는 진짜 이유는 **컨텍스트 분리** — 같은 모델도 컨텍스트를 비우면 다른 시각으로 같은 문제를 본다(예: 객관적 리뷰어). "에이전트"라는 이름은 마케팅 용어, 실체는 세션. ↔ 세션(사람이 연 것).

**골 (Goal)**
턴이 끝나는 시점에 모델이 "목표 달성했나?"를 재검토해 새 턴을 스스로 일으키는 것. 구현상 **"요청 큐에 넣는 도구"**가 있다는 뜻. → 이터레이션 제어를 넘어 턴 제어까지 모델에게 넘긴 것.

**에이전트 메시징 / 스티어링 (Steering)**
세션 간 요청·응답을 주고받는 것. 실체는 **메시지 큐에 넣고 세션이 가져가는 것**, 또는 진행 중 세션에 중간 메시지를 삽입하는 것. 하네스 책의 "에이전트 통신도"는 이걸 은유로 포장한 것. → 골·서브에이전트와 함께 "제어권 확장" 삼형제.

---

## 레이어 4 — 도구와 훅 (제어권을 넘기는 통로)

**도구 (Tool)**
모델이 제어권을 행사하는 통로. **어디까지 도구로 주는가 = 모델에게 어디까지 제어권을 넘기는가.** 기능을 코드에 가두면 워크플로우, 도구로 주면 에이전트.

**전용 도구 vs 범용 도구 (Dedicated vs Generic)**
전용=용도별 다양한 도구(Claude Code), 범용=쉘 하나로 통침(Codex). 전용은 약한 모델 실수를 줄이고, 범용은 강한 모델을 요구. → 도구 설계의 첫 번째 축.

**스킬 (Skill)**
도구보다 풍부한 설명(예제·퓨샷·참조 스크립트)을 담는 단위. 최근 추세는 **"도구는 터미널 하나 + 나머지는 스킬로 기술"** 통합. → 도구 설명의 빈약함을 보완.

**부수 효과 (Side Effect)**
도구가 결과값 외에 일으키는 것 — 스트리밍, 큐 삽입, **컨텍스트에 프롬프트 삽입**, 서브에이전트 열기. → 리마인더가 대표 사례.

**리마인더 (Reminder)**
로그가 길어져 단계를 까먹는 모델에게, 도구가 현재 위치 근처에 단계 정보를 재삽입하는 부수 효과. **약한 모델일수록 필요.** → 훅으로 구현.

**훅 (Hook)**
턴 루프의 단계 사이 이벤트에 걸어 기능을 붙였다 뗐다 하는 장치. 턴 루프를 중지시키거나 메시지를 추가. 사용자 훅 + 에이전트 기본 기능 다수가 훅. 강한 모델일수록 훅을 뺀다. → 리마인더·가드레일·스트림 가드·반복 감지의 구현 틀.

**가드레일 (Guardrail)**
민감 정보 유출·부적절 요청을 막는 장치. **휴먼 체크는 횟수가 많으면 100% 무력화**되므로, 정규식 기반 자동 검사·프롬프트 리라이팅·출력 필터로 만들어야 한다.

**요청 큐 / 대기열 (Request Queue)**
응답 중 들어온 요청을 쌓아두는 곳. 코드가 처리하면 워크플로우, **도구로 큐 삽입을 제공하면 골**이 성립. 최근엔 여러 큐를 **하나로 통합**해 감시.

## 레이어 5 — 컨텍스트 경제와 하드웨어

**컨텍스트 희석 (Context Dilution)**
세션이 길어져 성능이 떨어지는 현상. 원인은 어텐션이 아니라 **모순·중복 토큰의 누적**(사람이 말을 바꾸기 때문). → 4시-7시 규칙의 근거.

**4시-7시 규칙**
컨텍스트 도넛을 시계로 볼 때 **4시**에 마지막 요청(성능 최고점), 7시 마지노선, 9시·컴팩션 후는 쓰레기. 강사의 경험칙(민감/어려운 작업). → 폴더 격리 아키텍처 요구로 이어짐.

**컴팩션 (Compaction)**
컨텍스트가 한계에 다다르면 이전 히스토리를 요약해 압축하는 것. 4시-7시 관점에선 "9시 이후 + 컴팩션 = 쓰레기". → 장시간 자율 작업의 비용 원천.

**폴더 격리 (Folder Isolation)**
파일 하나여도 폴더로 나눠, 바이브 코딩의 **뽑기가 그 폴더 안에서만** 일어나게 하는 것. 바이브 코딩의 최강 가드레일. 하루 수십 번 수정되는 현실 제품을 안 깨고 유지하는 유일한 길. → 변화율 기반 아키텍처.

**뽑기 (비결정성, Non-determinism)**
샘플링·디코딩의 무작위성 + 자율성에서 오는 예측 불가능성. 격리 없이는 수정 하나가 전역 파일을 바꾼다. → 폴더 격리로 국소화.

**KV 캐시 (KV Cache)**
어텐션 계산의 Key·Value를 세션별로 캐싱한 것. 컨텍스트가 클수록 VRAM을 많이 잡아먹어 **컨텍스트 크기 = 비용**. 온프레미스에선 동시 세션 수를 직접 제한. → 컨텍스트 크기 정책·H200 세션 산수의 핵심.

**양자화 (Quantization) / Q4·Q5**
모델 가중치를 낮은 비트로 압축. **Q4는 원본 분포에서 벗어나 사실상 다른 모델**, Q5부터 원본 성향 유지(KL 발산 ~0.03 이내). → 로컬 LLM의 두 번째 하한.

**KL 발산 (KL Divergence)**
양자화 모델의 출력 분포가 원본에서 얼마나 벗어났는지의 척도. ~0.03 이내여야 원본 성향 유지 → Q5 하한의 근거.

**H200**
NVIDIA 데이터센터 GPU, 카드당 141GB VRAM(HBM3e). 온프레미스 로컬 LLM의 기본 단위. → KV 세션 산수의 출발점.

## 레이어 6 — 세션과 컨텍스트의 구현 (#2)

**KV 캐시 식별 ID (KV Cache ID)**
모델이 들고 있는 KV 캐시를 가리키는 키. **세션의 실체가 바로 이것**이다 — 캐시 ID가 다르면 다른 세션이다. 화면의 대화창은 이 실체의 껍데기. → 세션 수 = 캐시 세트 수 = 메모리 비용.

**프리픽스 캐시 (Prefix Cache)**
컨텍스트 앞부분이 변하지 않는다는 전제로 그 부분의 KV 캐시를 재사용하는 것. 앞을 한 글자만 고쳐도 뒤 캐시가 전부 무효가 된다. **에이전트 컨텍스트가 append-only 불변 리스트인 이유가 이것** — 취향이 아니라 캐시를 살리기 위한 구조적 요구. ↔ 컴팩션과 충돌한다.

**캐시 영속화 / 복원 (Cache Persistence / Restore)**
유휴 세션의 KV 캐시를 약 20분 뒤 내릴 때 **디스크에 직렬화해 저장**하고, 재입장 시 다시 올려주는 기능. 없으면 재입장마다 거대한 앞부분을 재처리해 프롬프트 프로세싱이 오래 걸린다. → 클로드 코드의 기능.

**포크 (Fork)**
이전 컨텍스트를 이어받은 새 세션을 만드는 것. 실체는 **KV 캐시 복사**여서 재계산 없이 즉시 시작된다.

**세션별 인스턴스 (Session-per-Instance)**
개별 세션마다 채널을 개설해 운영하는 방식(클로드 코드). 채팅 서버가 방을 소켓으로 격리하는 구조와 같다. **클라이언트가 세션을 점유**한다. ↔ 스트림 서버.

**스트림 서버 (Stream Server)**
서버 입장에서 세션을 "식별 ID만 다른 동일한 메시지"로 보는 방식(코덱스). 거대한 이벤트 흐름 하나가 있을 뿐이다. **클라이언트가 세션을 점유하지 않아** 모바일·브라우저·CLI가 같은 세션을 동시에 볼 수 있다. → 원격 지원의 근거.

**콜드 스트림 / 핫 스트림 (Cold / Hot Stream)**
스트림 구독의 두 단계. 세션 서버를 처음 열 때 과거 이벤트를 한 번에 받아오는 것이 콜드, 이후 실시간 수신이 핫.

**기반 컨텍스트 (Base Context)**
시스템 프롬프트·툴 정의·인스트럭션·퍼미션·에이전트별 프롬프트·AGENTS.md 체인·실행 환경·README 등으로 구성되며 **세션 시작 시 계산 후 고정**되는 부분. 예산 목표는 모델 컨텍스트의 **5% 이내**(코덱스 실측 약 4%). ↔ 턴 로그.

**턴 로그 (Turn Log)**
요청·응답·도구 호출이 쌓이는 히스토리. 뒤로만 자라는 **단조 증가 불변 리스트**이며 컴팩션의 대상이다.

**이름 해소 규칙 (Name Resolution Priority)**
같은 이름의 자원이 전역·프로젝트·시스템 여러 곳에 있을 때 누가 이기는지의 규칙. 스킬만이 아니라 **MCP·툴·프롬프트·커맨드·플러그인·룰스** 전부에서 필요하다. → 부가 기능이 아니라 아키텍처 필수 요소.

**스캐폴딩 스킬 + 2단계 로딩 (Scaffolding Skill)**
전역에는 스캐폴딩 스킬만 두고, 실행 시 `assets`의 기본 세트를 프로젝트로 복사해 **그 프로젝트 유형 전용 스킬셋**을 심는 방식. 로딩이 전역→프로젝트 2단계로 일어나는 성질을 이용해 기반 컨텍스트를 작게 유지한다.

**잘림 정책 (Truncation Policy)**
컨텍스트 오버플로 시 추론 서버가 적용하는 정책. **롤링 윈도우**(앞을 계속 뭉갬) / **중간 절단**(중간에서 끊음) / **정지**(리미트에서 끊어버림). 셋 다 코딩에 치명적이라 **그 전에 컴팩트해야 한다**. → 컴팩션 트리거의 존재 이유.

**컴팩트 레코드 (Compact Record)**
컴팩션 결과를 로그에 append하는 항목. **스냅샷 구분점** 역할을 해서, 모델 입력은 **마지막 컴팩트 레코드 아래로만** 구성된다. 전체 로그에는 여러 개가 존재하며 로그 자체는 지우지 않는다 → 저장 구조(불변)와 재생 범위(가변)의 분리.

**컴팩트 레코드 병합 (Compact Merge)**
연속된 컴팩트 레코드를 모아 다시 요약해 세대별 열화를 완화하는 기법. **원래 RAG의 청크 병합**에서 왔다.

**검색형 요약 (Retrieval-style Summary)**
각 턴을 한 줄로 요약하고 참조 ID를 붙여, 상세가 필요하면 **모델이 도구를 호출해 조회**하게 하는 컴팩션 방식. 모델 요약보다 정보 분실이 적다. 단 턴이 쌓이면 여기에도 슬라이딩 윈도우가 붙는다.

## 레이어 7 — 비즈니스 제품 요구 (#2)

**온프레미스 (On-premise)**
고객사 내부 인프라에서만 구동되는 납품 형태. **웹 검색 / 외부 모델 / 보안 프로그램과의 공존**을 전부 깨뜨리며, 그 때문에 상용 에이전트가 통하지 않아 **직접 만든 제품의 시장이 생긴다.** → 이 회차 전체의 사업적 전제.

**모델 라우터 (Model Router)**
어떤 요청을 어느 모델로 보낼지 정하는 계층. 기업의 핵심 요구는 **엔터프라이즈 할당 토큰 소진 시 사내 LLM으로 무중단 전환**. 최소 구현은 "개인이 쓸 모델을 서버가 내려주기"(산업용은 회사가 모델을 지정한다).

**거버넌스 → 가드레일 (Governance → Guardrail)**
거버넌스는 사내 규정·정책("이 절차로 한다", "USB로 데이터를 못 갖고 나간다"). 에이전트도 이를 지켜야 하므로 **정책을 가드레일로 변환해 연동**하는 기능이 필요하다.

**풋프린트 (Footprint)**
로그인 시 수집하는 흔적(사내 IP, 부서, 지급 노트북의 보안 코드 등). 보안 정책 때문에 회사마다 요구가 크게 달라 **커스터마이즈가 필수**다.

**중간관리자 위임 (Delegated Administration)**
AX팀이 전부 관리하지 않고 팀장에게 팀원 관리를 넘기는 기능. 이것이 있으면 **관리자 페이지가 로그인 주체에 따라 달라진다.** 없으면 산업용이 성립하지 않는다.

**공유드라이브 강제 (Shared-drive-only Project Creation)**
프로젝트 생성 자체를 공유드라이브에서만 허용해 **소스 코드 노출을 막는** 기능. 팀·개인 공간 설정이 S3 버킷 설정과 같은 일이 되고, 사내 GitLab·GitHub Enterprise 연동까지 확장된다.

**정보검색센터 (Information Retrieval Center)**
온프레미스 웹검색 대체 + 사내 라이브러리·문서·코드 검색 + 사용 로그 수집을 통한 자기성찰·학습 데이터셋 확보를 묶은 구성요소.

**궤적 학습 / 자기 성찰 (Trajectory Learning / Self-reflection)**
에이전트 이용 로그를 수집해 학습에 되먹이는 것. 정기적 파인튜닝의 입력이 된다. → RLVR 선호 정렬과 연결.

**터보 모노레포 (Turborepo Monorepo)**
`turbo.json`으로 여러 모듈을 구성하는 아키텍처. **하부가 JS 프로젝트가 아니어도 된다**(C++·파이썬 통합 빌드). `apps` = 오케스트레이션(빌드 단위 서비스), `packages` = 핵심 도메인(라이브러리)이며 참조는 **`apps` → `packages` 단방향**, `packages`에는 프레임워크 지식이 들어가지 않는다.

**PGVector**
PostgreSQL에 벡터 확장을 꽂은 것. 이 강의에서는 여기에 **카프카를 대신할 이벤트 스트림 플러그인까지 얹어** 벡터 검색과 이벤트 스트림을 한 인프라로 처리한다 → 온프레미스에서 미들웨어 수를 줄이는 선택.

**RHEL 컨테이너 차단**
레드햇 엔터프라이즈 + 사내 보안 환경에서 **도커 컨테이너를 막아놓는** 정책. "도커가 보안상 유리하다"는 일반론이 현장에서 뒤집히는 지점이며, 네이티브 설치형이 필요해지는 이유.

**오퍼레이터 (Operator)**
새 팀 운영 모델에서 원탁의 컴퓨터 한 대를 조작하는 사람. 팀은 모여 계획 문서를 확정하고 던진 뒤 퇴근하며, 오전에 모여 리뷰한다. → 개인 생산력이 아니라 팀 생산력을 만드는 배치.

## 레이어 8 — 관리 서버의 구현 어휘 (#3)

**세션 키 / 세션 토큰 (Session Key)**
로그인 성공 시 발급되는 인증 토큰. 이 회차의 핵심은 발급이 아니라 **회수**다 — 관리자가 세션 키를 제거하면 그 사람의 로그인이 취소된다. 무상태 검증형(JWT만)으로 만들면 이 기능이 성립하지 않는다. ↔ 2강의 세션(모델 KV 캐시 식별자)과 이름만 같고 층이 다르다.

**유휴 만료 (Idle Timeout)**
일정 시간 요청이 없으면 세션 키를 만료시키는 정책(시연값 7200초). **기록 보관 기간**(86400초)과 별개 설정이며, 전자는 보안 목적, 후자는 감사·디스크 목적이다.

**필터 승인 (Filter-based Approval)**
가입 신청 정보가 조건에 맞으면 자동 승인하는 정책. 조건은 **IP 대역**(확인이 싸지만 위치는 신원이 아니다)과 **사번 인사DB 조회**(신원에 가깝지만 연동이 필요)로 나뉘고, 보통 겹쳐 쓴다. ↔ 수동 승인 / 자동 승인.

**필수 가입 JSON (Required Signup Metadata)**
가입 시 반드시 받아야 하는 추가 필드 정의(예: `{"department":"operations"}`). 필터가 판단할 값을 만들어 주므로 **받을 필드를 정하는 것이 필터 조건을 정하는 것보다 먼저**다.

**마스터 계정 (Master Account)**
최상위 관리자. **DB가 아니라 환경변수(`.env`)로 지정**되어 DB 쓰기 권한만으로는 승격할 수 없고, 변경에 서버 재기동이 필요하다. 콤마로 여러 명을 지정해 승인자 단일 실패점을 막는다.

**퍼미션 레이어 (Permission Middleware Layer)**
모든 요청을 한 층에서 걸러 권한을 판정하는 미들웨어. **기본값이 거부**이고 로그인·가입만 예외로 명시한다. 엔드포인트마다 검사를 붙이면 빠뜨린 곳이 조용히 열린다. → 2강 9장의 인가 대상(도구·저장소·스킬·RAG)이 이 층의 정책 항목이 된다.

**프로토콜 패키지 (`common/protocol`)**
프론트와 서버가 **둘 다 봐야 하는 통신 규격**을 두는 자리. 양쪽에 따로 선언하면 어긋남을 컴파일러가 잡지 못한다. 도메인 패키지는 `common`·`server`·`front`로 갈리고 이 규격이 `common`에 들어간다.

**엔드포인트 / 모델 / 프리셋 (Endpoint / Model / Preset)**
모델 등록의 3계층. 엔드포인트는 추론 서버(API 형식·인증 헤더), 그 아래 모델, 그 아래 **프리셋 = 모델 식별자 + 샘플링 파라미터 조합**이다. 같은 모델을 온도만 달리해 여러 개 등록하며 **이름이 실질적 키**가 된다. 파라미터를 클라이언트가 보내게 하면 조직별 모델 통제가 무너진다.

**모델스 프로토콜 (`/v1/models`)**
OpenAI 호환 서버의 모델 목록 조회 규격. 이것이 표준이라 엔드포인트 종류를 몰라도 목록을 받을 수 있고, 실패 시 수동 등록으로 떨어진다.

**모달리티 지정 (Modality Declaration)**
그 프리셋이 텍스트·이미지·사운드·비디오 중 무엇을 받는지 사람이 등록하는 것. 같은 이름의 모델이라도 **적재된 배포본에서 비전이 제거됐을 수 있어** 이름으로 추론할 수 없다.

**다중 루트 조직 트리 (Multi-root Organization Tree)**
최상위 조직이 여러 개 존재할 수 있는 구조(지사 A·지사 B). `parentId: string | null`로 표현되며 **루트를 하나로 제한하는 것이 조직도 설계의 가장 흔한 실수**다. 제한은 스키마·쿼리·권한 판정에 퍼져 되돌리기가 비싸다.

**조직 책임자 (Organization Responsibility)**
조직 노드의 관리자. 권한 범위가 **노드 단독**이거나 **하위 계층 전체**이며, 후자는 나중에 생기는 노드까지 포함한다. 마스터가 임명하고 책임자가 다시 임명하는 **재귀적 위임**이되 자기 권한을 넘지 못한다.

**인수 테스트 우선 (Acceptance-first Testing)**
에이전트가 코드를 쓸 때 단위 테스트보다 사용자 경로 검증을 앞세우는 방침. 근거는 단위 테스트 실패가 **재생성(뽑기)으로 이어질 뿐**이라는 것. 단 전제는 순수 로직이 얇은 CRUD·화면 영역이며, 판정 기준이 명확한 로직에는 단위 테스트가 **명세**로 남는다.

**내장 브라우저 (Built-in Browser)**
에이전트 클라이언트가 자체적으로 갖는 브라우저. 스크린샷·조작·테스트를 자연어 지시로 수행해 Playwright·헤드리스 구성을 대체하고, 사용자의 포커스·마우스를 빼앗지 않는다.

**테스트 리포트 적재 (Dated Test Reports)**
테스트 결과를 날짜별 산출물로 남기는 규정. 세션 로그는 시도·실패가 뒤섞여 길지만 리포트는 결과만 정렬돼 있어 되짚기가 빠르고 **세션이 사라져도 남는다.**
