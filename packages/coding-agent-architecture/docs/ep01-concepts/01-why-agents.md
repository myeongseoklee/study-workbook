# 01. 왜 에이전트인가 — 단일 모델 호출의 한계와 "제어 흐름"의 이동

## 학습 목표

단일 모델 호출(single call)이 왜 실무 문제를 못 푸는지 네 가지 한계로 설명하고, "워크플로우"와 "에이전트"를 가르는 **유일한 구분선**을 말할 수 있다.

## 핵심 원리 (WHY) — 단일 모델 호출은 왜 부족한가

모델을 한 번만 호출해서(프롬프트 넣고 응답 받고 끝) 문제를 풀려고 하면 네 가지 벽에 부딪힌다. 에이전트는 이 네 벽을 각각 무너뜨리기 위해 존재한다.

### 한계 1 — 지식이 사전학습에 갇힌다

도구가 없는 모델은 프리트레이닝(사전학습) 시점의 지식으로만 답한다. 실시간 정보(오늘 날씨, 현재 코드베이스 상태)는 접근할 수 없다. → **도구**가 이 벽을 넘는다.

### 한계 2 — 샘플링/디코딩은 매번 "랜덤 뽑기"다

모델이 마지막에 토큰을 만들어내는 과정(샘플링·디코딩)에는 확률적 무작위성이 있다. 같은 프롬프트라도 매번 조금씩 다른 답이 나온다. 이 **비결정성**은 없앨 수 없는 성질이며, 뒤에서 볼 RLVR 학습과 결합하면 "예측 불가능하지만 창의적인 해법"으로 증폭된다(아래 참고).

### 한계 3 — 사람은 프롬프트를 충분히 길게 쓸 수 없다 (가장 중요)

이것이 에이전트가 등장한 진짜 이유다. 우리가 풀고 싶은 문제는 미묘한 코딩·설계 문제인데, 그걸 한두 마디로 설명할 수 없다. 그렇다고 사람이 수백 줄짜리 프롬프트를 앉아서 쓰지도 않는다.

그래서 강의는 **스펙 주도 개발(SDD, Spec-Driven Development)을 정면으로 비판한다**: "만들기 전에 모든 스펙을 글로 정의하고 그대로 개발시킨다"는 발상은 비현실적이다. 사람은 무언가를 *원하기만* 하지, 원하는 것이 무엇인지 정교하게 글로 쓰는 데는 서툴다. 스펙을 제대로 쓰려면 팀 단위 인력을 투입해야 한다.

**해법: 프롬프트를 모델과 함께 작성한다.** 하나의 세션에서 여러 턴에 걸쳐 모델과 대화하는 행위의 본질은 이것이다 —

> 세션이 끝날 때 우리가 원하는 결과를 얻는다는 건, 그 세션에서 주고받은 **모든 대화가 곧 하나의 거대한 프롬프트**라는 뜻이다. 그 방대한 프롬프트를 혼자 쓰는 건 불가능하니까, 모델과 협력해서 함께 써 내려간 것이다.

플랜 모드, 플래닝, 다중 턴 대화는 전부 "내가 원하는 걸 나도 잘 못 쓰니까 모델과 같이 쓴다"의 다른 표현이다. → **세션·턴** 구조가 이 벽을 넘는다(2장).

### 한계 4 — 텍스트 밖의 행동을 사람이 대신해야 한다

단일 호출 모델은 텍스트만 출력한다. "기상청에 접속해서 날씨를 가져와라", "터미널에 이 명령을 쳐라" 같은 행동은 사람이 대신 해줘야 한다. 이러면 **모델이 생각하고 사람이 기계 노릇**을 하는 역전이 일어난다. 원래 기계가 실행하고 사람이 생각해야 하는데 반대가 된 것이다. → **도구 + 에이전트 루프**가 대행을 모델에게 돌려주어 이 역전을 바로잡는다.

## 필수 지식 (HOW) — 워크플로우 vs 에이전트

업계가 오래 혼란을 겪다가 합의한 정의가 있다. 이 구분선을 외우면 나머지 논의가 명료해진다.

> **제어 흐름(control flow)을 코드가 잡으면 워크플로우, 모델이 잡으면 에이전트다. 제어 흐름의 위치가 유일한 구분선이다.**

| | 워크플로우 (Workflow) | 에이전트 (Agent) |
|---|---|---|
| 흐름 제어 주체 | 개발자가 짠 코드 (고정 그래프) | 모델 (런타임에 결정) |
| 대표 도구/예시 | LangChain·LangGraph의 고정 파이프라인, n8n 매크로 | Claude Code, Codex |
| "더 반복할까? 그만할까?" | 코드가 미리 정해둠 | **모델이 매번 판단** |
| 장점 | 결정적·예측 가능 | 자율적·새 상황에 응용 가능 |
| 대가 | 유연성 없음 | 결정성 하락(뽑기·토큰 폭탄·예측 불가) |

**"에이전틱 AI"는 더 이상 모호한 마케팅 단어가 아니다.** 흐름을 모델이 제어하면 에이전트다 — 이 한 문장으로 합의됐다. 단일 응답이 아니라 여러 번 반복하되, **반복 횟수와 방법을 모델이 자율적으로 결정**하는 자율 의사결정권을 주면 그게 에이전틱 AI다.

### 워크플로우 패턴은 사라지지 않았다

프롬프트 체이닝(A의 출력→B의 입력), 라우팅(입력 분류→분기), 병렬화(독립 작업 동시 실행 후 취합) 같은 고전 워크플로우 패턴은 지금도 코드 안에 살아 있다. 흥미로운 역설: 요즘 "하네스(harness) 책"에 나오는 **서브에이전트 팀 구성·멀티에이전트 패턴은 대부분 여전히 워크플로우 패턴**이다. 즉 "판단자 2명 + 실행자 1명"처럼 개발자가 미리 짜둔 고정 구조를 따른다. 진짜 에이전트 패턴이라면 "네가 알아서 서브에이전트를 동원해서 걔네끼리 대화하게 만들어 문제를 풀어라"가 되어야 하지만, 아직 그 수준의 자율 하네스는 흔치 않다.

## 참고 — RLVR과 "알파고식" 창의적 해법 (배경 지식)

강의가 비결정성의 미래를 설명하며 든 배경이다. 최근 모델은 **RLVR(Reinforcement Learning with Verifiable Rewards, 검증 가능한 보상 기반 강화학습)**로 학습한다. 정답이 존재하는 문제(코딩이 대표적)를 모델이 높은 temperature로 다양하게 풀게 한 뒤, **정답만 맞으면 그 "창의적 궤적(trajectory)"을 학습 데이터로 되먹인다.** 사람이 준 데이터가 아니라 모델이 스스로 만들어낸 희한한 풀이가 점점 학습된다.

결과: 알파고가 바둑에서 인간이 안 두던 수를 두듯, 코딩 모델도 **인간의 해법 범주를 벗어난 방식**으로 문제를 풀 수 있게 된다. 강의의 전망은 이렇다 — 그냥 두면 우리가 리뷰할 수 없는 코드가 나올 수 있으므로, "인간이 읽기 쉬운 코드로 풀어달라"고 명시적으로 요구해야 하는 시대가 온다. 이는 정확한 미래 예측이 아니라 **비결정성이 왜 점점 심해지는지에 대한 강사의 해석**으로 받아들이면 된다.

## 우리 프로젝트와의 연결

에이전트를 직접 만들 때 첫 설계 결정은 "어디까지를 코드로 고정하고, 어디부터 모델에게 넘길 것인가"다. 이 결정이 곧 워크플로우와 에이전트의 경계를 긋는 일이며, 3장의 "도구 = 제어권" 논의로 직접 이어진다.
