# 03. 도구 = 모델 제어권의 범위

## 학습 목표

"도구를 어디까지 제공하는가 = 모델에게 제어권을 어디까지 넘기는가"라는 등식을 이해하고, 도구 설계의 세 축(전용 vs 범용, 도구 vs 스킬, 동기 vs 비동기)에서 각각 어떤 판단을 내려야 하는지 근거를 들어 설명한다.

## 선수 지식

- 2장의 확장 루프(서브에이전트 = 세션 생성 도구, 골 = 요청 큐 삽입 도구)

## 핵심 원리 (WHY) — 도구는 기능이 아니라 제어권이다

도구에 대한 선입견을 깨야 한다. 개발자 입장에서 **"어디까지를 도구로 만들까"는 "모델에게 어디까지 제어권을 넘길까"와 같은 질문**이다.

> **같은 기능을 코드에 가두면 사람이 워크플로우를 만드는 것이고, 도구로 제공하면 모델이 자율적으로 제어한다.**

이걸 잘 보여주는 예가 **요청 큐**다.

- **코드 방식(워크플로우):** 모델이 응답하는 중에 사용자가 프롬프트를 입력하면 대기열(큐)에 쌓아둔다. 모델 응답이 끝나면 코드가 큐를 검사해 항목이 있으면 새 요청으로 넣어 모델을 돌린다. 이 판정을 **코드가 확정적으로** 한다. → 워크플로우.
- **도구 방식(에이전트):** "요청 큐에 넣기"를 도구로 제공한다. 그러면 모델이 "이번 턴에서 해결 안 되니 다음 턴에 새 요청으로 시작해야겠다"고 판단해, 사람 대신 스스로 큐에 요청을 넣는다. → 응답 완료 후 새 턴이 자동 실행될지를 **모델이 통제**한다. **이것이 바로 골(2장)의 원리다.**

이 렌즈로 보면, 지금 UI나 파라미터로 제공되는 거의 모든 것을 도구로 뺄 수 있고, 뺄수록 모델의 제어 범위가 넓어진다:

| UI/파라미터 기능 | 도구로 주면 |
|---|---|
| 새 세션 열기 | 모델이 서브에이전트를 마음대로 열고 닫음 |
| 목표 설정 | 모델이 스스로 골을 설정 |
| 스킬/슬래시 커맨드 선택 | 모델이 스스로 스킬을 고름 |
| 모델 전환·컴팩션 | 모델이 스스로 모델을 바꾸고 컴팩션을 함 |
| 스케줄러 예약 | 모델이 "5분에 한 번씩 확인하겠습니다" 하고 스스로 예약 |
| 플러그인 설치 | 모델이 "이거 못 깔아서 깔고 쓰겠습니다" |

### 대기열 통합 — 제어권을 늘리면 큐가 늘어난다

요청 큐, 비동기 도구 대기열, 서브에이전트 응답 대기열… 제어권을 도구로 넘길수록 감시해야 할 대기열이 늘어난다. 그래서 최근 에이전트는 **대기열을 하나로 통합**한다. "감시할 게 있나 없나"만 보는 단일 감시 시스템을 두고, 큐 안의 **메시지 타입에 따라** 반응을 다르게 하는 식으로 구현한다. 안 그러면 코드가 대기열 지옥이 된다.

## 필수 지식 (HOW) — 도구 설계의 세 축

### 축 1 — 전용 도구 vs 범용 도구

현재 도구 추세의 양 극단이며, **클로드 코드와 코덱스가 정확히 반대편**에 있다.

| | 전용 도구 (Dedicated) | 범용 도구 (Generic) |
|---|---|---|
| 대표 | **Claude Code** — 파일 찾기만 해도 여러 도구를 줌 | **Codex** — 대부분 쉘(bash) 도구 하나로 통침 |
| 철학 | 용도별로 다양한 전용 도구 제공 | "터미널이면 다 되잖아" |
| 전제 | 약한 모델도 실수 적게 씀 | 문제를 터미널 명령으로 번역할 만큼 **모델이 강해야 함** |
| 방향성 | QN 코드·미스트랄 등은 여전히 도구를 많이 줌 | 오픈AI는 버전 올라갈수록 도구를 더 없애고 쉘로 통합 |

오픈AI가 **Terminal-Bench**를 미는 이유가 여기 있다 — 바이브 코딩 에이전트를 쉘 도구 통합으로 만들었기 때문에, "터미널을 얼마나 잘 쓰는가"가 자기들에게 결정적인 벤치마크다. (Terminal-Bench 2.0은 실제로는 Snorkel AI·스탠퍼드·Laude Institute가 공동 제작한 89개 터미널 태스크 벤치마크로, 컴파일·디버깅·시스템 관리 등 다단계 작업을 격리 컨테이너에서 검증한다.)

**전용 도구가 필요한 실전 근거 — `EditLine` vs `Edit`:**
- 클로드 코드의 `Edit` 도구는 `old_string`을 `new_string`으로 바꾼다. 그런데 파일 안의 `old_string`과 **완벽히 일치**하는 문자열을 줘야만 치환된다. 공백·탭 하나만 틀려도 실패한다.
- 클로드 같은 강한 모델은 이걸 할루시네이션 없이 해내지만, **로컬의 약한 모델**은 따옴표·스페이스 하나를 흘려서 편집이 실패한다.
- 그래서 나온 게 라인 기반 방식(`EditLine`): "0번째 줄부터 7번째 줄을 이걸로 대체해"는 완벽한 문자열 재현보다 난이도가 훨씬 낮아, 작은 모델도 실수를 거의 안 한다.

교훈: **약한 모델일수록 전용 도구가 실수를 줄인다. 터미널 하나로 비비려면 좋은 모델이 필요하다.**

> 각 모델은 자기 에이전트로 궤적 학습(RLVR)을 하기 때문에, 코덱스에 GPT가 아닌 클로드 모델을 넣으면 잘 안 맞고 그 반대도 마찬가지다. 궤적이 다르기 때문이다. 최적 성능은 **모델과 에이전트를 세트로 맞출 때** 나온다.

### 축 2 — 도구 vs 스킬 (그리고 그 통합)

같은 문제를 도구로도, 스킬로도 풀 수 있으면 **도구 설명(description)과 스킬 설명이 경합**한다. "디플로이할 때 이 도구를 써라"와 "디플로이할 때 이 스킬을 써라"가 둘 다 있으면 모델은 혼란에 빠진다.

원인은 **도구 설명의 빈약함**이다. 도구가 모델에게 줄 수 있는 정보는 짧은 description과 인자 설명이 전부다. 사용 예제·퓨샷·레퍼런스를 넣을 자리가 없고, description을 길게 쓰면 오히려 도구 선택이 더 어려워진다.

**최근 해법 — 통합(도구 + 스킬 조합):**
> 도구는 **터미널 하나만** 두고, 파일 수정·읽기 등 각각의 사용법은 전부 **스킬**로 기술한다.

스킬은 도구보다 훨씬 풍부하게 "이럴 때 발동해라", 사용 예제, 참조 스크립트를 담을 수 있다. 그래서 이 조합이 잘 먹힌다. 강사도 다음 에이전트는 "도구는 웹서치 같은 몇 개만 주고, 나머지는 터미널로 통친 뒤 전부 스킬로 기술"하는 방식을 고민 중이라고 밝혔다. **정답이 있는 게 아니라, 여러분의 에이전트가 도구를 어떻게 코디네이션할지 스스로 결정해야 하는 설계 축이다.**

### 축 3 — 도구 실행의 비동기성: 프로세스 vs 인메모리

**모든 도구 실행은 본질적으로 비동기다.** 우리가 동기적으로 대기(블로킹)하고 있을 뿐이다. 도구를 어디서 실행하느냐에 따라 트레이드오프가 갈린다.

| | 프로세스 실행 (별도 프로세스) | 인메모리 실행 (내장 함수) |
|---|---|---|
| 부하 | 프로세스 띄우고·종료하고·통신해야 함 | 변수만 주고받으면 됨 |
| 안전성 | **본체가 안전** — 도구가 실패·블로킹해도 에이전트 본체는 멀쩡 | 도구가 블로킹하면 **에이전트 전체가 늘어짐** |
| 직렬화 | 프로세스 통신은 텍스트라 중간 과정을 다 직렬화해야 함 | 직렬화 불필요 |
| 단일 스레드 위험 | — | Node 같은 싱글 이벤트 루프 기반은 특히 위험(다른 세션도 못 받음) |

강사는 **전부 프로세스로 구현**했다. 논리: bash는 어차피 내장 함수로 못 만들어 프로세스로 열려야 하는데, 그게 가장 많이 쓰는 도구다. 그렇다면 다른 도구만 인메모리 함수로 두는 게 무슨 의미가 있나? 게다가 도구가 터미널을 열어 무슨 짓(설치·삭제)을 할지 몰라 위험하다.

**프로세스 실행의 어려운 점 — 스트리밍 프로토콜:** 프로세스에 입력은 인자로 넘기면 되지만, 진행 상황 보고·중도 취소·중간 멈춤을 처리하려면 프로세스와 통신하는 프로토콜이 필요하다. 강사는 모든 스크립트가 공통으로 임포트하는 **`emit`** 개념을 만들어, 도구가 중간중간 진행 상황(`progress`)·에러·상태를 `print`로 보고하면 본체가 그걸 캡처해 클라이언트로 스트림 전송한다. "지금 경로를 리졸빙 중", "파일 읽는 중"을 사용자에게 실시간으로 보여주는 게 이 파이프라인이다. 제품 수준 에이전트는 이 진행 표시를 다 만들어야 한다.

## 필수 지식 (HOW) — 도구의 출력은 결과값만이 아니다 (부수 효과)

"날씨 도구가 서울 날씨를 응답으로 준다"는 순진한 그림은 옛날이야기다. 최근 도구는 결과값 외에 **부수 효과(side effect)**를 잔뜩 일으킨다:
- 스트리밍(진행 상황 실시간 전송)
- 대기 큐에 요청 삽입
- **컨텍스트에 별도의 사용자/시스템 프롬프트를 추가** ← 핵심
- 서브에이전트를 열어 도움을 받기

### 도구가 컨텍스트에 메시지를 끼워 넣는다

도구 호출 응답은 단순히 "도구 결과(tool_result) 하나"만 돌아오지 않는다. 리즈닝 + 어시스턴트 메시지 + 도구 호출이 복합적으로 오고, **도구가 결과값과 별도로 사용자 프롬프트나 시스템 프롬프트를 컨텍스트에 삽입**할 수 있다. 컨텍스트는 단조 증가하므로(2장), 도구가 여기에 몇 개든 추가로 끼워 넣을 수 있다.

### 도구가 LLM을 써야 할 때 — 또 세션을 연다

어떤 도구는 내부적으로 LLM을 써야 한다. 그때마다 별도 LLM API를 세팅하면 도구마다 토큰 비용을 또 낸다. 사용자는 보통 OpenAI 호환 API를 딱 하나만 세팅해 두므로, 도구는 **다시 세션을 열어** 처리한다(모든 기능이 세션에 있으니까). 즉 "도구가 LLM이 필요하다 → 세션을 연다 → 서브에이전트가 된다"로 자연스럽게 이어진다.

### 리마인더 (Reminder) — 약한 모델을 위한 부수 효과

단계별 수행 도구를 쓸 때, 로그가 길어지면 모델(GPT조차)이 **중간 단계를 까먹고 점프**하거나, 3단계를 안 하고 최종 응답으로 끝내버린다. 컨텍스트가 길어져 초반의 "3단계로 풀어라" 지시를 잊은 것이다.

해법: 도구가 현재 위치 근처에 **"이건 3단계 작업이고 지금 2단계다"라는 리마인더 메시지를 삽입**한다. 그러면 모델이 안 까먹고 순서대로 간다. 여러분이 바이브 코딩에서 단계가 하나씩 해결되는 걸 구경하는 게 이 리마인더 덕분이다. **모델이 약할수록 이런 중간 개입이 많이 필요하다**(6장으로 이어짐).

## 우리 프로젝트와의 연결

리마인더·프롬프트 리라이팅·가드레일 같은 중간 개입을 턴 루프 코드에 직접 박으면, 기능 하나 추가할 때마다 루프를 뜯어고쳐야 한다. 이걸 밖으로 빼는 장치가 **훅(hook)**이다 — 4장의 주제다.
