# 04. 훅(Hook) — 턴 루프를 건드리지 않고 기능을 붙였다 뗐다 하기

## 학습 목표

훅이 왜 필요한지(턴 루프 안정성)를 설명하고, 턴 루프의 어느 지점에 어떤 훅이 걸리는지 대표 사례로 말할 수 있다.

## 선수 지식

- 3장의 부수 효과(리마인더·프롬프트 리라이팅·가드레일) — 이것들이 훅으로 구현된다

## 핵심 원리 (WHY) — 왜 훅인가

훅을 쓰는 이유는 단 하나:

> **턴 루프를 큰 틀로 유지하고, 세세한 기능들은 전부 밖으로 빼기 위해서다.**

만약 리마인더·가드레일·반복 감지 같은 사소한 기능을 턴 루프 코드에 직접 박으면, 기능 하나 넣거나 뺄 때마다 메인 턴 루프를 뜯어고쳐야 한다. 그러면 코드가 순식간에 관리 불능이 된다. 그래서 **턴 루프의 여러 단계 사이사이에 이벤트(event)를 삽입하고, 각 이벤트에 등록된 훅들을 실행**하는 구조로 바꾼다. 기능을 넣었다 뺐다 하려면 훅으로 빼는 수밖에 없다.

핵심 성질:
- 훅은 일반적으로 **턴 루프를 중지시킬 수 있다.** (클로드 코드·코덱스에 훅을 걸면 작업 도중 턴을 멈출 수 있는 이유.)
- 하지만 중지시키지 않고 **메시지를 추가하거나 다른 부수 효과만 일으키는** 훅도 많다.
- **사용자 훅뿐 아니라 에이전트의 기본 기능 상당수도 훅으로 구현**된다. 즉 에이전트가 내장한 기본 훅이 먼저 걸려 있고, 그 위에 사용자 지정 훅이 추가로 붙는 구조다.

## 필수 지식 (HOW) — 턴 루프의 훅 지점들

강사가 자기 에이전트에 실제로 건 훅들을 순서대로 보면, 훅이 "이벤트 = 턴 루프 단계 사이사이"라는 게 드러난다. (에이전트 종류·모델 강도에 따라 걸리는 훅은 달라진다 — 이건 절대 사양이 아니라 예시다.)

| 훅 지점 | 이벤트 시점 | 대표적으로 하는 일 |
|---|---|---|
| **요청 접수 훅** (Request Received) | 사용자/모델 요청이 들어왔을 때 | 라우터 역할 — 더 진행할지 판단, **프롬프트 리라이팅**, 남은 컨텍스트를 보고 **컴팩션 판정** |
| **모델 전송 직전 훅** (before send) | 컨텍스트를 모델에 보내기 직전 | "프리픽스 깨 먹는 거 아니냐" 검사, 모델에 보내면 안 되는 내용 **가드레일** 검사 |
| **응답 스트리밍 훅** (streaming) | 스트림 응답이 오는 동안 | **스트림 가드** — 이상 감지, 특히 약한 모델의 **리즈닝 루프**(같은 말 반복) 감지 시 중간에 끊어버림 |
| **최종 응답 훅** (final response) | 최종 응답이 왔을 때 | "이 응답을 그냥 줘도 되나" 검사, 이 시점에 **컴팩션할지** 판정, 반복 실수하는 도구 호출의 **인자 보정**, 퍼미션 위반 도구 호출 차단 |
| **결과 수집 훅** (result collection) | 도구 호출 결과들을 모은 뒤 | **반복 감지** — "얘 똑같은 호출 또 하네", "한 짓 또 하는 거 같은데"를 LLM에게 판정시킴 |

훅으로 자주 구현되는 것들: 프롬프트 리라이터, 가드레일, **리마인더**(3장 — 약한 모델에 스킬 리스트를 몇 턴마다 다시 보여주기), 도구 라우팅.

### 두 가지 대표 가드레일 (출력 가드레일)

3장의 부수 효과와 연결되는 훅 기반 보안 장치:
- **프롬프트 리라이팅:** 애매하거나 보안에 걸리는 사용자 요청을 다시 쓰기로 교정.
- **출력 필터링:** 모델 출력을 믿을 수 없으니, `.env` 파일이나 토큰 같은 민감 정보가 밖으로 못 나가게 필터. 이런 보안 토큰 검사는 **모델로 판정하지 않고 그냥 정규식**을 돌려서 잡는 경우가 많다.

> **왜 정규식인가 — 휴먼 체크의 함정.** 강의는 "사람이 매번 퍼미션을 검수하는 보안 모델"을 강하게 비판한다. 휴먼 체크는 횟수가 많아지면 **100% 무력화**된다 — 사람은 인지·인내 한계 때문에 결국 "무조건 허용(Yes to all)"을 누른다. 그러면 보안은 무력화되고 책임만 사용자에게 전가된다("네가 부주의했잖아"). 그래서 에이전트를 만드는 우리는 **휴먼 체크가 아닌 다른 방식(정규식 기반 자동 검사, 리라이팅, 출력 필터)**을 직접 만들어야 한다.

## 필수 지식 (HOW) — 강한 모델일수록 훅을 뺀다

훅의 밀도는 모델 강도와 반비례한다:

> **모델이 후지면 많이 개입해야 하고(리마인더·스트림 가드·인자 보정), 모델이 좋으면 개입을 뺀다.**

오픈AI·클로드는 모델이 강력해지면서 이런 세세한 훅 개입을 점점 빼내고 있다 — 제어권을 더 넘겨도 부드럽게 전개되기 때문이다. 반대로 온프레미스 로컬 모델(6장)은 약해서 훅을 많이 걸어야 정상적으로 돌아간다. 그러니 **에이전트가 어떤 세세한 개입도 없이 매끄럽게 도는 것처럼 보인다면, 그건 그 뒤에서 엄청난 중간 개입이 일어나고 있거나(약한 모델) 모델이 그만큼 강한 것(강한 모델)이다.**

## 우리 프로젝트와의 연결

훅은 "제품 수준 에이전트"와 "개념 수준 에이전트"를 가르는 지점이다. 진행 상황 표시, 리즈닝 루프 차단, 퍼미션 강제, 반복 감지 — 사용자가 당연하게 여기는 이 모든 것이 훅으로 구현된다. 그리고 이걸 붙였다 뗐다 하려면 애초에 코드가 잘 격리되어 있어야 한다 — 그 격리 원리가 5장(폴더 격리)이다.
