# 06. 온프레미스 로컬 LLM 에이전트 — 200B 하한과 Q5 하한

## 학습 목표

기업 온프레미스 코딩 에이전트를 만들 때 부딪히는 하드웨어 제약(KV 캐시 → 동시 세션 수)을 계산하고, "왜 200B 이상, Q5 이상"이라는 두 하한선이 실무의 마지노선인지 원리와 함께 설명한다.

## 선수 지식

- 5장: 컨텍스트 크기 = KV 캐시 = VRAM 점유
- 4장: 약한 모델일수록 훅(리마인더 등) 개입이 많이 필요하다

## 핵심 원리 (WHY) — 왜 이걸 배우는가

강의가 코딩 에이전트를 직접 만드는 이유가 여기 있다. **온프레미스 로컬 LLM 기반의 회사 전용 코딩 에이전트 수요가 실제로 존재한다.** 기업은 H200 몇 장을 사서 사내에 로컬 LLM을 구축하고, 그 위에서 도는 전용 에이전트를 원한다(데이터 보안·규제 때문).

그런데 로컬 환경은 모델이 약하다. 그래서 **"로컬 LLM이 안 되는 게 아니라, 로컬 LLM의 특성을 반영한 에이전트가 없어서 안 되는 것"**이다. 클로드/오픈AI의 에이전트는 강력한 모델을 전제로 만들어져서, 약한 로컬 모델에 그대로 얹으면 잘 안 돈다. 리마인더·스트림 가드 같은 훅(4장)을 많이 걸어 컨텍스트를 계속 보강해 줘야 겨우 일관성 있게 돈다. 이 니즈를 채우는 에이전트를 만들 수 있다는 게 이 강의의 상업적 동기다.

## 필수 지식 (HOW) — KV 캐시 산수: 세션 몇 개나 열리나

암기할 하드웨어 숫자 하나: **NVIDIA H200 = 카드당 141GB VRAM(HBM3e).** (H100의 80GB에서 크게 늘어난 값이다.)

동시 세션 수 계산(강사의 온프레미스 실측 예시):

```
H200 노드 총 VRAM       ≈ 500GB        (H200 약 4장, 141GB × 4 ≈ 564GB급)
모델 적재(460B급, Q5)   ≈ 300GB        → 남는 VRAM ≈ 200GB
풀 컨텍스트 KV 세션 1개  > 10GB
동시 세션 수            ≈ 200GB / 10GB ≈ 20개
```

즉 **200GB로 열 수 있는 세션은 약 20개뿐**이다. 개발자 한 명이 보통 세션 2~3개를 여니까, **개발자 3명이 각 3세션이면 노드가 꽉 찬다.** KV 캐시가 VRAM을 잡아먹기 때문에 H200 노드의 겉보기 용량이 커 보여도 실제 동시성은 이렇게 빡빡하다. 이것이 5장에서 말한 "컨텍스트 크기 = 비용"의 온프레미스 버전이다.

## 필수 지식 (HOW) — 두 개의 마지노선

강사가 온프레미스 납품에서 얻은 두 개의 하한선. 둘 다 **제품 수준 코딩**이 가능한 최소 조건이다(잠깐 샘플 만드는 수준이 아니라).

### 하한 1 — 모델 크기: 200B를 넘어야 한다

> **제품 수준 코딩을 하려면 모델이 약 200B(파라미터)를 넘어야 한다.**

| 크기대 | 코딩 가능? | 예시 |
|---|---|---|
| 30B / 35B | ❌ 택도 없음 | (유행했던 소형 모델들) |
| ~120B | ❌ 안 됨 | gpt-oss-120B급, Nemotron급 |
| **~200B 이상** | ✅ 여기서부터 | MiniMax M2급(약 200~220B)이 진입점 |

작은 모델로 코딩이 될 거라 기대하지 마라 — 하네스를 아무리 잘 걸어도 제품 수준은 안 나온다. "된다"는 건 잠깐 샘플을 만드는 정도다.

### 하한 2 — 양자화: Q5 이상을 써야 한다

> **양자화(quantization)는 Q5 이상을 써야 한다. Q4는 아무리 큰 걸 써도 소용없다.**

**원리 — KL 발산(KL divergence) 그래프:** 양자화는 모델 가중치를 낮은 비트로 압축하는 것이다. 압축이 심하면 모델의 출력 분포가 원본에서 멀어진다. 원본 모델의 성향을 유지하려면 양자화 모델의 분포가 원본 분포로부터의 거리(KL 발산)가 **약 0.03 이내**에 들어와야 하는데:
- **Q4**는 이 벽을 넘지 못한다 — 아무리 큰 Q4를 써도 분포가 확 벌어져서 사실상 **다른 모델**이 된다. 도는 척하지만 오류가 엄청나고, 만드는 척하지만 다 버그다.
- **Q5**로 내려와야 원본 분포의 0.03 안에 들어와 원래 모델 성향이 나온다.

여러분이 로컬 모델을 쓰고 "성능이 안 나온다"고 느끼는 건 대개 **Q5 이하(Q4·Q3 등)를 썼기 때문**이다. 그건 쓰면 안 되는 모델이다. 어느 모델의 KL 그래프를 봐도 Q4→Q5 사이에 확연한 벽이 있다.

**결과 — Q5의 현실적 무게:** 200B 모델을 Q5로 양자화해도 약 **160GB**다. 그래서 128GB RAM을 가진 일반 가정용 컴퓨터에서는 돌릴 수 없다(GPU를 꽂고 램 128GB를 꽂아도 안 된다). RAM 256GB + 좋은 그래픽 카드는 되어야 한다. 참고로 gpt-oss-120B급을 Q5(약 88GB)로 4080(16GB VRAM) + CPU 128GB에 올리면 8~15 토큰/초로 돌긴 하지만 — 크기 하한(200B)에 못 미쳐 **코딩은 안 된다.**

> ⚠️ 여기 나오는 구체 모델명(MiniMax M2/M3, Nemotron, GLM, gpt-oss-120B)과 GB 수치는 강의 시점(2026-07-29)의 라이브 관찰이자 강사의 온프레미스 실측 경험이다. 자동 자막으로 옮겨져 모델명·수치에 오차가 있을 수 있으니, **"약 200B 이상 + Q5 이상"이라는 두 하한 원리**를 취하고 구체 모델은 직접 KL 그래프·VRAM 요구량을 확인해 검증하라.

## 정리 — 로컬 에이전트를 만든다는 것

1. **하드웨어 산수:** H200 141GB/장 → 노드 ~500GB → 모델 적재 후 남은 VRAM으로 KV 세션 수가 결정된다(약 20세션 = 개발자 3명 한계).
2. **모델 하한:** 200B 이상.
3. **양자화 하한:** Q5 이상(Q4는 다른 모델).
4. **에이전트 보완:** 약한 모델이므로 리마인더·스트림 가드 등 훅(4장)을 많이 걸어 컨텍스트를 지속 보강해야 일관성이 유지된다.

이 조건을 갖춘 에이전트는 클로드/오픈AI 계열을 커스터마이징하는 것보다 **직접 만드는 게 나을 수 있다**는 게 강사의 결론이다("커스터마이징하며 한 달 고생하다 보면 차라리 내가 만들지 싶어진다").

## 우리 프로젝트와의 연결

지식 자체는 AI가 제일 많이 갖고 있다. 우리가 못 만드는 건 "이게 대체 어떻게 생겼는지"에 대한 **개념**이 없어서다. 이 자료(1~6장)의 구성 요소 개념만 손에 쥐면, GPT와 상담해 바이브 코딩으로 에이전트를 만들 수 있다. 남는 차이는 오직 하나 — **격리를 잘한 구조로 리팩토링했느냐**가 지속적으로 유지보수 가능한 제품을 가르는 지점이다(5장으로 원점 회귀).
