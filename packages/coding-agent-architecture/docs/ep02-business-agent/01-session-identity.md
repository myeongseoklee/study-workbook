# 01. 세션의 정체 — 세션은 대화창이 아니라 KV 캐시 식별자다

## 학습 목표

"세션"이라는 말을 들을 때 화면의 대화창을 떠올리는 습관을 버리고, **모델 서버 쪽 KV 캐시를 가리키는 식별자**로 다시 정의한다. 이 정의가 왜 세션 수 = 메모리 비용인지, 왜 포크가 즉시 되는지, 왜 20분 뒤 재입장이 느린지를 한꺼번에 설명한다는 것을 이해한다.

## 선수 지식

- ep01의 "세션 = 모델과 함께 써 내려가는 거대한 프롬프트"라는 관점
- ep01의 KV 캐시가 VRAM을 잡아먹는다는 산수 (`must-memorize.md` 하드웨어 숫자)

## 핵심 원리 (WHY) — 세션은 UI 개념이 아니라 캐시 개념이다

강의가 먼저 깨는 오해가 있다.

> **"시중에 나와있는 에이전트 책들을 보고 도구 사용 좀 붙이면 바이브 코딩이 될 것 같지만 안 된다."**

안 되는 이유의 첫 번째가 세션이다. 도구 호출 루프는 만들 수 있어도, **세션을 무엇으로 볼 것인지**를 정하지 못하면 그 위의 모든 설계가 무너진다.

세션을 화면 단위(대화창 하나)로 보면 답이 안 나오는 질문들이 있다. 세션을 두 개 열면 왜 메모리가 두 배 드는가? 포크는 왜 즉시 되는가? 20분 쉬었다 돌아오면 왜 첫 응답이 느린가? 이 셋은 UI 관점에서 서로 무관해 보이지만, 세션을 **KV 캐시 식별자**로 보면 하나의 사실에서 파생된다.

> **세션의 정체는 모델이 실제로 들고 있는 KV 캐시의 식별 ID다. 캐시 ID가 달라지면 다른 세션이다.**

이유는 이렇다. 세션 두 개를 병렬로 진행하려면 KV 캐시도 두 세트가 필요하다. 한 세션은 대화가 이어져야 하므로 그 세션 몫의 캐시가 유지되어야 하고, 다른 세션은 다른 캐시를 쓴다. **캐시가 세션을 정의하는 것이지, 대화창이 세션을 정의하는 게 아니다.** 그래서 병렬 세션 수를 늘리면 KV 캐시 요구량이 그만큼 올라가고 메모리 사용량이 따라 오른다.

## 필수 지식 (HOW) — 식별 ID는 세 층에서 각각 필요하다

![세션처리 방법 08:15](assets/frames/t00-08-15.jpg)

강의는 식별 ID를 하나로 뭉뚱그리지 않고 세 층으로 나눈다. 각 층이 답하는 질문이 다르기 때문이다.

| 층 | 식별 ID가 가리키는 것 | 답하는 질문 |
|---|---|---|
| **모델의 KV 캐시** | 프리픽스 캐시를 유지하고, 나아가 캐시를 영속화·복원할 때 쓰는 고유 키 | "이 요청이 어느 캐시를 이어받는가" |
| **컨텍스트 구조체** | 그 ID에 쌓여 있는 컨텍스트 구조체에 접근할 권한 | "누가 이 대화 내용을 읽고 쓸 수 있는가" |
| **도구·메시지큐** | 도구 실행 결과나 큐 이벤트를 보고할 대상 ID | "이 결과를 어디로 돌려보내는가" |

**세 층이 왜 분리되어야 하는가**가 중요하다. 하나로 합치면 캐시가 만료됐을 때 대화 내용도 못 읽게 되고, 도구가 비동기로 늦게 끝났을 때 결과를 돌려보낼 곳이 사라진다. 도구 실행은 모델 추론보다 훨씬 오래 걸릴 수 있고(빌드·테스트), 그 사이 캐시는 내려갈 수 있다. **캐시의 생명주기와 대화의 생명주기와 작업의 생명주기가 서로 다르기 때문에** ID도 따로 필요하다.

## 필수 지식 (HOW) — 프리픽스 캐시와 영속화·복원

### 프리픽스 캐시가 성립하는 조건

컨텍스트가 **앞부분이 변하지 않고 뒤로만 자라는** 구조여야 프리픽스 캐시가 유효하다. 앞부분을 한 글자라도 고치면 그 뒤 캐시가 전부 무효가 된다. 그래서 에이전트의 컨텍스트는 단조 증가하는 불변 리스트로 설계된다 — 성능 취향이 아니라 캐시를 살리기 위한 구조적 요구다. (이 성질이 컴팩션을 어렵게 만든다 → 4장)

### 포크가 즉시 되는 이유 — 캐시 복사

클로드 코드의 포크 기능을 보면, 포크한 지점에서 바로 명령을 내릴 수 있다. 이전 컨텍스트를 이어받은 새 세션이 태어나는데, **그 앞까지의 KV 캐시를 처음부터 다시 만드는 게 아니라 이전 세션의 캐시를 복사해 온다.** 그래서 마치 캐시가 이미 잡혀 있는 것처럼 동작한다.

### 영속화·복원 — 20분 뒤 재입장이 느린 이유

VRAM에 KV 캐시를 계속 물려두면 메모리 소비가 너무 크다. 그래서 세션을 쓰지 않으면 **약 20분 뒤 캐시를 내린다.** 문제는 다시 들어왔을 때다. 캐시가 없는 상태에서 그 거대한 앞부분을 다시 처리해야 하므로 프롬프트 프로세싱이 오래 걸린다.

그래서 캐시를 내릴 때 **디스크에 직렬화해 저장**해 두고, 사용자가 돌아오면 그것을 KV 캐시로 다시 올린다. 이것이 클로드 코드의 캐시 영속화 기능이다.

> **정리하면 세션 하나의 실체는 이렇다:** VRAM 위의 KV 캐시 + 그 캐시를 가리키는 ID + (내려갔을 때) 디스크에 직렬화된 사본. 화면의 대화창은 이 실체를 사람에게 보여주는 껍데기일 뿐이다.

## 이 지식이 설계 판단에 쓰이는 자리

- **동시 세션 수를 제품 사양으로 정할 때**: 세션 수 × 세션당 KV 캐시가 곧 VRAM 요구량이다. 온프레미스 납품이라면 이 산수가 하드웨어 견적을 결정한다.
- **유휴 세션 정책을 정할 때**: 캐시를 언제 내리고, 내릴 때 직렬화할지 버릴지가 "재입장 지연 vs 디스크 사용량" 트레이드오프다.
- **컨텍스트 조립을 설계할 때**: 앞부분을 불변으로 유지해야 프리픽스 캐시가 산다. 기반 컨텍스트를 중간에 갱신하는 설계는 캐시를 통째로 버리는 설계다.

### ⚠️ 암기 필수

- [ ] **세션의 정체 = KV 캐시 식별 ID.** 캐시 ID가 다르면 다른 세션. 병렬 세션 수 = KV 캐시 세트 수 = 메모리 비용.
- [ ] **식별 ID는 세 층(KV 캐시 / 컨텍스트 구조체 접근권 / 도구·큐 보고 대상)으로 분리된다.** 생명주기가 서로 달라서 합칠 수 없다.
- [ ] **프리픽스 캐시는 "앞부분 불변"을 대가로 얻는 것이다.** 앞을 고치면 뒤 캐시가 전부 무효.
- [ ] **유휴 세션 캐시는 약 20분 뒤 내려간다.** 그래서 영속화(디스크 직렬화)와 복원이 필요하다.
- [ ] **포크 = KV 캐시 복사.** 재계산이 아니라 복사이므로 즉시 시작된다.
