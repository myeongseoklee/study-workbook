# 04. 컴팩션 — "언제"가 "어떻게"보다 어렵다

## 학습 목표

컴팩션을 "긴 대화를 요약하는 기능"이 아니라 **두 개의 독립된 난제**로 분해한다: 언제 트리거할지 판정하는 문제와, 무엇을 어떻게 버릴지 고르는 문제. 각 방식의 열화 메커니즘을 알고, 컴팩트가 불변 리스트와 만나면 왜 스냅샷 구분점이 되는지 이해한다.

## 선수 지식

- 3장: 기반 컨텍스트(고정) + 턴 로그(단조 증가) 구조
- 2장: 턴 로그가 이벤트 소싱에 가까운 append-only 리스트라는 성질
- ep01의 컨텍스트 희석·4시-7시 규칙 (컴팩션 후 품질이 떨어진다는 경험칙)

## 핵심 원리 (WHY) — 컴팩션은 피할 수 없고, 대상은 턴 로그다

컨텍스트 한계에 봉착하면 컴팩트는 **무조건** 일어난다. 대상은 턴 로그다 — 앞의 기반 컨텍스트는 건드리지 않는다(건드리면 프리픽스 캐시가 죽는다).

그런데 강의가 강조하는 건 "어떻게 요약하는가"가 아니다.

> **"컴팩트는 언제 판단하는 거야? 사용자 요청이 올 때 컴팩트하는 거야? 그럼 남은 컨텍스트가 이번 응답에 충분한지 아닌지 어떻게 판단했는데? 이번 응답이 얼마나 길어질 줄 알고?"**

이 질문이 핵심이다. 컴팩션은 **미래를 모르는 상태에서 내려야 하는 결정**이다.

## 필수 지식 (HOW) — 문제 1: 언제 트리거하는가

### 판정 지점을 어디에 둘 것인가

턴 안에는 컨텍스트가 늘어나는 지점이 여러 개 있다.

- 요청이 도착했을 때
- 도구를 호출했을 때
- 도구 호출 결과를 보고했을 때
- 최종 응답을 냈을 때

매 지점마다 컨텍스트를 계산하고 컴팩트 여부를 결정할 것인가? 그렇게 하지 않으면 이런 일이 생긴다 — **도구 호출이 엄청나게 몰리고 리즈닝이 길게 붙어 한 턴 안에서 컨텍스트를 다 소비**해 버리는데, 턴 시작 시점에만 판정했다면 그것을 예측할 수 없다.

### 판정하지 못하면 "잘림"이 일어난다

컨텍스트가 중간에 모자라면 잘림(truncation)이 발생한다. 이건 에이전트의 실수가 아니라 **추론 서버에 원래 있는 정책**이다.

| 잘림 정책 | 동작 | 바이브 코딩에서의 결과 |
|---|---|---|
| 롤링 윈도우 | 앞부분을 계속 뭉개면서 진행 | 초반 지시·규칙이 조용히 사라진다 |
| 중간 절단(truncate mid) | 중간에서 끊는다 | 맥락이 두 동으로 갈린다 |
| 정지(stop limit) | 리미트에 닿으면 거기서 끊어버린다 | 작업이 미완으로 종료된다 |

세 정책 모두 코딩 작업에는 치명적이다. **그래서 잘림에 도달하기 전에 컴팩트를 해야 한다.** 그런데 그 시점을 어떻게 계산하느냐가 앞의 문제로 되돌아온다.

### 80%가 최적인데, 80%를 어떻게 아는가

가장 좋은 시점은 컨텍스트가 **80% 찼을 때**다. 문제는 그 시점을 프로그램이 어떻게 아느냐다.

> **컨텍스트는 실제로 메모리를 쓴 양이 아니다. 모델에게 보내는 내용이 80% 찼는가의 문제다.** 즉 보낼 전체 메시지를 파싱해서 토큰 수를 세야 한다.

이것이 컴팩션 구현의 실제 작업이다: 매 판정 지점에서 전체 메시지의 토큰 수를 계산하고, 임계값과 비교하고, 이번 응답의 예상 길이를 감안해 여유를 남긴다.

## 필수 지식 (HOW) — 문제 2: 무엇을 어떻게 버리는가

네 가지 방식이 있고, 각각 다른 방식으로 정보를 잃는다.

### 방식 1. 요청·최종 응답만 남기기

턴 안의 이터레이션(도구 호출과 그 결과)을 제거한다. **컨텍스트에서 가장 큰 부피를 차지하는 게 도구 호출 부분**이라 효과가 크다.

한계: 요청과 응답만 남겨도 턴이 계속 쌓이면 다시 한계에 봉착한다. 결국 슬라이딩 윈도우로 앞부분을 버리게 된다.

### 방식 2. 모델에 의한 요약 (코덱스 방식)

모델에게 프롬프트로 요약을 시킨다. 열화 크기를 산수로 보면 심각하다.

> 262K 컨텍스트에서 기반이 약 5%, 턴 로그가 약 95%를 차지한다. 컴팩트하면 전체 10% 수준으로 줄어든다. 즉 **95%에 해당하는 내용을 5%로 압축**한 것이다. 얼마나 열화됐겠는가. 중요한 정보가 대량으로 분실된다.
>
> 게다가 **262K를 요약하는 과정 자체에 할루시네이션이 없을까?** 요약에 환각이 섞인 상태로 민감한 코딩 작업을 이어갈 수 있을까?

그래서 **요약 방식에 따라 바이브 코딩 성능이 완전히 달라진다.**

### 방식 3. 검색형 요약 (요즘 유행)

턴이 200개 있으면 **각 턴을 한 줄로만 요약**하고, 참조 ID를 붙인다. 상세 내용이 필요하면 모델이 **도구를 호출해 그 ID로 조회**한다.

방식 2보다 낫다. 요약 정보로 무슨 일이 있었는지 파악하고, 필요할 때만 상세를 가져오기 때문이다. 도구와 결합한 컴팩션이라는 점이 특징이다.

한계: 이것도 턴이 계속 쌓이면 한 줄 요약만으로도 커진다. 그래서 여기에도 슬라이딩 윈도우를 결합한다.

### 방식 4. 슬라이딩 윈도우 (위 방식들과 결합되는 보조 기법)

일정 크기를 넘으면 앞쪽을 잘라낸다. 단독으로 쓰이기보다 위 세 방식과 결합해 **크기를 일정하게 유지**하는 역할을 한다.

> **네 방식의 공통 구조**: 어떤 방식을 골라도 결국 슬라이딩 윈도우가 붙는다. 턴이 무한히 쌓이는 구조에서는 "압축률"만으로는 유한한 컨텍스트를 지킬 수 없기 때문이다.

## 필수 지식 (HOW) — 컴팩트 레코드와 불변 리스트

여기서 2장의 이벤트 소싱 성질과 충돌이 생긴다.

> 이벤트 소싱이라면 앞이 다 이어져서 현재가 만들어지는 것이다. **그런데 리스트 중간에 컴팩트 레코드가 등장하면 어떻게 되는가?**

답: 모델에게 보낼 때는 **컴팩트가 등장한 시점부터 아래로만** 보낸다. 즉 **컴팩트 레코드가 스냅샷 구분점**이 된다.

그리고 컴팩트는 한 번만 일어나지 않는다. 일어나고, 또 일어나고, 계속 일어난다. 그래서 스트림을 만들 때 규칙은 이렇다.

> **마지막 컴팩트 레코드 아래로만 컨텍스트를 구성한다.** 전체 로그에는 컴팩트 레코드가 여러 개 존재할 수 있다.

### 컴팩트 레코드 병합 — 열화 방지 기법

모델 요약 방식에는 추가 전략이 붙는다. **원래 RAG의 청크 병합에서 온 기법**이다.

앞의 컴팩트를 입력으로 삼아 다음 컴팩트를 만들고, 그 이전 컴팩트들을 모아 또 컴팩트를 만든다. 이렇게 **연속된 컴팩트 레코드를 병합 요약**하면 열화가 어느 정도 방지된다.

원리는 이렇다. 매번 원본 95%를 5%로 압축하면 정보가 계단식으로 소실되지만, 이전 요약들을 함께 입력에 넣으면 **초기 맥락이 여러 세대에 걸쳐 살아남을 확률**이 올라간다.

## 이 지식이 설계 판단에 쓰이는 자리

- **컴팩션 트리거를 구현할 때**: 판정 지점을 턴 시작 한 곳으로 두면 도구 폭주에 대응할 수 없다. 최소한 도구 결과 보고 지점을 포함해야 한다.
- **압축 방식을 고를 때**: 방식 2(모델 요약)는 구현이 가장 쉽고 품질 위험이 가장 크다. 상세 조회 도구를 만들 여력이 있으면 방식 3이 낫다.
- **로그 스토리지를 설계할 때**: 컴팩트 레코드가 여러 개 존재하고, 모델 입력은 마지막 것 아래만 쓴다 — 즉 **전체 로그는 보존하되 재생 범위만 잘라야 한다.** 로그를 실제로 지우는 설계는 되돌릴 수 없다.

### ⚠️ 암기 필수

- [ ] **컴팩션의 두 난제는 별개다: 트리거 시점 판정 / 압축 방식 선택.** 어려운 쪽은 "언제"다 — 이번 응답 길이를 모르는 상태에서 결정해야 한다.
- [ ] **컴팩트 대상은 턴 로그. 기반 컨텍스트는 건드리지 않는다** (프리픽스 캐시 보호).
- [ ] **최적 트리거 = 컨텍스트 80% 지점.** 단 "80%"는 메모리가 아니라 **보낼 메시지를 파싱한 토큰 수** 기준이다.
- [ ] **잘림 정책 3종(롤링 윈도우 / 중간 절단 / 정지)은 추론 서버에 원래 있다.** 셋 다 코딩에 치명적이므로 그 전에 컴팩트해야 한다.
- [ ] **모델 요약의 열화 산수: 262K 중 턴 로그 95% → 5%로 압축(전체 10% 잔존).** 여기에 요약 과정의 할루시네이션 위험이 겹친다.
- [ ] **검색형 요약 = 턴 한 줄 요약 + 참조 ID + 도구로 상세 조회.** 모델 요약보다 안전하나 슬라이딩 윈도우가 여전히 필요하다.
- [ ] **어떤 압축 방식이든 결국 슬라이딩 윈도우가 붙는다** — 압축률만으로는 무한 증가를 못 막는다.
- [ ] **컴팩트 레코드 = 스냅샷 구분점. 모델 입력은 마지막 컴팩트 아래로만 구성한다.** 전체 로그에는 여러 개가 존재한다.
- [ ] **컴팩트 레코드 병합(RAG 청크 병합 기법)으로 세대 간 열화를 완화한다.**
