# 05. 사람이 할 일 — 팀 운영 모델과 기술셋 전환

## 학습 목표

에이전트가 코딩을 대신하는 환경에서 **사람의 근무시간이 무엇으로 채워져야 하는지**를 구체적 산출물 수준으로 안다. 그리고 이번 변화가 왜 "기존 역량에 하나 추가"가 아니라 "기술셋 전체 교체"인지, 그 판단이 학습 계획에 어떤 차이를 만드는지 이해한다.

## 선수 지식

- 3·4장: 컨텍스트 조립과 컴팩션 — 좋은 계획 문서가 왜 성능에 직결되는지의 기술적 근거
- ep01의 "폴더 격리 = 최강 가드레일", 비결정성(뽑기) 개념

## 핵심 원리 (WHY) — 코딩은 이미 사람의 일이 아니다

강의는 자기 강의의 성격을 이렇게 정의한다.

> **"코딩은 어차피 바이브 코딩으로 한다. 그러면 강의에서 다뤄야 될 내용은 '코덱스에게 뭐라고 시킬지'에 대한 내용이 된다."**

이 문장이 이 장 전체의 전제다. 구현 능력이 아니라 **지시 설계 능력**이 병목이라는 관찰이고, 그 병목이 개인이 아니라 팀 단위에 있다는 주장으로 이어진다.

## 필수 지식 (HOW) — 하루 사이클: 낮에 계획, 밤에 실행, 아침에 리뷰

강의가 실제로 돌리는 사이클이다.

1. **퇴근 전까지 팀원들과 모여** 모델이 밤새 수행할 마일스톤·스프린트를 확정한다.
2. 밤새 에이전트가 작업한다. 커밋을 남기고 증거 리포트를 남긴다.
3. **오전에 출근해 다 같이 모여 리뷰**한다.

> **"근무시간에 해야 될 건 팀원들이 원탁에 모여서 이거(계획 문서) 만드는 거다. 왜냐하면 이 문서 혼자 보기 싫으니까."**

### 계획 문서에 반드시 들어가는 것

강의가 실제 프로토콜 마이그레이션 문서를 열어 보여준 항목들이다. 이 목록 자체가 체크리스트로 쓸 만하다.

| 항목 | 왜 필요한가 |
|---|---|
| **목적 기술** | 무엇을 위한 작업인지. 판단이 갈릴 때의 기준점 |
| **규칙 기술** | 지켜야 할 제약. 모델이 창의적으로 벗어나는 것을 막는다 |
| **마일스톤 공통 사이클** | 각 마일스톤을 어떤 순서로 전진할지 — 구현 전 기준 확인 → 검증 → 커밋·푸시 → 배포(배포 방식까지 명시) |
| **추론 게이트** | 통과 조건. 게이트를 몇 개 두고 무엇을 통과 기준으로 삼을지 |
| **로컬 테스트 규정** | 테스트를 어떻게 수행할지 |
| **완료 판정 기준** | "다 했다"를 무엇으로 판정할지 |
| **공통 추론 입력** | 모든 노드에서 동일하게 쓸 입력(프롬프트·동시 세션 수·최대 토큰·temperature·stream 여부 등) |
| **증거 저장 방법** | 결과를 어디에 어떤 형식으로 남길지 |
| **마일스톤 단계별 지시** | 0단계·1단계·2단계… 각각 무엇을 하고, 끝나면 **어디를 갱신할지** |

마지막 항목이 중요하다. "끝나면 이 문서의 여기를 갱신하라"는 지시가 있어야 아침에 리뷰할 대상이 생긴다. 밤새 작업의 결과가 커밋과 리포트로 문서에 누적된다.

## 필수 지식 (HOW) — 사무실 구조를 바꿔야 하는 이유

강의의 주장은 물리적 배치까지 내려간다.

> 현재 사무실은 **다들 벽을 보고 등을 지고 앉아 있다.** 이건 옛날에 사람이 개발할 때의 방식이다. 이제 벽 보고 일할 필요가 없다.
>
> 새 구조는 **원탁 + 컴퓨터 한 대 + 오퍼레이터 한 명.** 다 떠들고, 화면 같이 보면서 문서를 확정하고, 던지고, 정시 퇴근한다. 밤새 에이전트가 작업한다. 오전에는 모여서 리뷰한다.

근거는 생산성의 단위다.

> **"조직을 이렇게 바꾸지 않으면 개인 수준의 생산력밖에 못 갖는다. 팀 수준의 생산력은 다 거기서 나온다."**

반대로 흔한 실패 패턴은 이렇다.

> **"넌 너대로 구현해, 난 나대로 구현할게" — 이건 팀이 아니다.** 어차피 구현은 바이브 코딩이 빠르게 해줄 텐데, **뭘 시킬지를 각자 헤매면서 토큰만 낭비**하고 있다.

또 하나의 실패 패턴: **벽 보고 앉아 게임하다가 2시간에 한 번씩 명령 내리는 방식.** 이런 식으로는 작업이 진행되지 않는다.

> 혼자서 바이브 코딩이 가능하다는 생각은 착각이다. 혼자서는 **계획을 잘 세우지 못한다.** "그거 테스트할 때 이렇게 하면 좋겠는데" 같은 의견이 오갈수록 계획이 좋아진다.

## 핵심 원리 (WHY) — 기술셋 전환: 추가가 아니라 교체다

이 장의 두 번째 주제이자 강의의 가장 강한 메시지다. 비유가 정교하므로 그대로 따라간다.

> **여러분은 말을 중심으로 하는 운송업에서, 자동차를 중심으로 하는 운송업으로 넘어가는 중이다.**

말 운송업의 전문성은 무엇이었나. 말의 몸 상태를 보고 오늘 어느 속도로 달려야 최대 운행이 가능한지 판단하는 능력. 말굽을 관리하는 지식. **일종의 수의학과 결합된 지식 체계**다.

자동차 운송업에서 그 지식 체계는 **필요 없다.** 자동차가 오늘 퍼질지 고민하지 않고 그냥 부산에 갔다 온다. 고장은 수리업자를 부른다.

### 이전 변화들과 다른 점

> **"그전에 여러분이 겪었던 변화는 기존 위에 이렇게 추가해 가는 것이었다. 이번엔 그 동네가 다 전멸이다."**

이것이 이 비유의 핵심이다. 새 언어를 배우거나 새 프레임워크를 익히는 것은 기존 역량에 얹는 일이었다. 지금은 체계 전체가 대체된다.

> **"다 갖다 버린 사람만 전환된다."** 참조: 영화 「히든 피겨스」 — 컴퓨터가 등장하면서 수학자들이 코딩으로 업종을 전환하는 이야기.

### 오해하지 말아야 할 것

강의는 이 지점에서 조심스럽게 선을 긋는다.

> **"여러분이 뛰어난 엔지니어가 아닌 건 아니다. 엔지니어인데, 그냥 그 엔지니어를 이루고 있는 그 체계 전체가 필요 없어진 것뿐이다."**
>
> **"시대가 변한 게 아니라 기술셋의 요구사항이 바뀐 것이다. 거부하지 말고, 엔지니어로 남으려면 세트를 다시 갖추라."**

강의자 본인이 사례다. 작년 초반까지 AI 전문가가 아니었고, 그전에는 코틀린 전문가였다. 시장이 요구해서 기술셋 전체를 바꿨고, 바꾸지 않았으면 도태됐을 것이라고 말한다.

## 이 지식이 판단에 쓰이는 자리

- **팀 프로세스를 설계할 때**: 계획 문서 템플릿에 위 9개 항목이 들어가는지 점검한다. 특히 "완료 판정 기준"과 "증거 저장 방법"이 빠지면 아침 리뷰가 성립하지 않는다.
- **개인 학습 계획을 세울 때**: 기존 스택의 숙련도를 높이는 방향과 에이전트 시스템 구축 역량을 쌓는 방향 중 어디에 시간을 쓸지 결정한다. 강의의 입장은 후자이며, 근거는 "추가가 아니라 교체"다.
- **협업 도구를 고를 때**: 여러 클라이언트가 같은 세션을 함께 보는 요구가 여기서 나온다 (→ 2장의 스트림 서버가 필요한 조직적 이유).

### ⚠️ 암기 필수

- [ ] **사이클: 낮에 팀이 계획 문서 확정 → 밤에 에이전트 실행 → 아침에 팀이 리뷰.** 사람의 근무시간은 계획과 리뷰로 채워진다.
- [ ] **계획 문서 필수 항목 중 빠지기 쉬운 셋: 완료 판정 기준 / 증거 저장 방법 / 각 단계 종료 시 갱신할 위치.** 이게 없으면 리뷰 대상이 남지 않는다.
- [ ] **실패 패턴 = "각자 자기 것 구현" + "2시간에 한 번 명령".** 구현은 이미 빠르고, 병목은 지시 설계다.
- [ ] **혼자서는 계획을 잘 세우지 못한다** — 바이브 코딩은 팀 활동이다. 조직을 안 바꾸면 개인 수준 생산력에 갇힌다.
- [ ] **이번 변화는 추가가 아니라 교체다** (말 운송업 → 자동차 운송업). 기존 체계의 상당 부분이 무용해진다. 엔지니어 역량이 없어진 게 아니라 요구되는 세트가 바뀐 것.
