# 01. 계획표와 실제 — 어디까지 갔고 어디를 접었나

## 학습 목표

2강 계획표의 **하위 불릿 하나하나**가 3강에서 어떻게 됐는지 대조할 수 있다. 구현·부분·축소·변경·미구현을 구별하고, 접힌 것에 무엇이 남았는지 안다. 그리고 각 결정의 **뒤집기 비용**으로 자기 구현의 착수 순서를 정한다.

## 선수 지식

- 00장: 계획표 원문과 이 회차의 성격
- 2강 9장: 계획표의 각 항목이 왜 그 판정을 받았는지

## 핵심 원리 (WHY) — "만들었다"는 판정이 너무 거칠다

계획표에는 `→ 구현` / `→ 미구현` / `→ 간략하게 구현` 세 가지 판정만 있다. 그런데 실제로 만들어진 것을 하위 불릿과 맞춰 보면 이 셋으로는 안 잡히는 것이 나온다.

- 계획은 **개인별** 모델 할당인데 구현은 **조직별**이다 → 축소가 아니라 **변경**이다
- 계획은 "로그인 시 정보수집을 커스터마이즈"인데 구현은 헤더·쿠키 이름과 가입 필드까지다 → **부분**이다

이 차이가 중요한 이유는, 자기 구현을 하는 사람이 참조 구현을 보고 "이게 계획의 전부"라고 오해하면 **접힌 것을 접힌 줄 모르고 넘어가기** 때문이다. 그러면 나중에 그 자리를 못 찾는다.

그래서 이 장은 판정을 다섯으로 쪼갠다: **구현 / 부분 / 축소 / 변경 / 미구현.**

## 필수 지식 (HOW) — 항목별 대조

### 1. 인증인가 → 구현

| 계획표 하위 항목 | 3강 실제 | 판정 |
|---|---|---|
| 온프레미스 고려한 **자체 인증** | 이메일·비밀번호 계정. 마스터는 `.env`로 지정(DB 아님) | **구현** |
| 토큰기반 **세션키 발급** | 세션 키 발급 + 유휴 만료(7200초) | **구현** |
| 중앙에서 세션키 **모니터링 및 변경가능** | 세션 목록 화면, 강제 제거, 만료 기록 보관(86400초) | **구현** |
| 로그인 시 **다양한 정보수집 커스터마이즈** | 세션 헤더·쿠키 **이름** 설정 + 필수 가입 JSON | **부분** — 수집 **항목**을 고르는 UI는 나오지 않았다 |
| 인가권한 **중간 관리자 위임기능** | 조직 트리 + 책임자 범위(노드 단독 / 하위 계층 전체) + 재귀 위임 | **구현** |

**부분으로 남은 것**: 계획의 "다양한 정보수집"은 사내 IP·부서·사번·보안 프로그램 헤더처럼 **회사마다 다른 풋프린트**를 뜻한다(2강 9장). 3강이 만든 것은 그 값이 실릴 **통로**(헤더·쿠키 이름)와 가입 시 받을 필드이고, "이 회사는 이 항목을 남긴다"를 관리자가 정의하는 화면은 없다. 자기 구현에서 이 자리를 열어 두려면 감사 필드를 고정 스키마가 아니라 **확장 메타**로 받아야 한다.

### 2. 공유드라이브 설정기능 → 미구현 (계획대로)

계획도 미구현이었고 실제도 미구현이다. 다만 **접힌 채로 넘어간다**는 점이 중요하다 — 비즈니스 서버는 3강에서 닫히고 다음은 에이전트다.

자기 구현에서 남겨야 할 여지: 프로젝트 생성 경로를 코드에 고정하지 않는다. 사내 GitLab·GitHub Enterprise 연동이 붙을 자리다.

### 3. 모델라우터 → 간략하게 구현 (그리고 **변경**)

| 계획표 하위 항목 | 3강 실제 | 판정 |
|---|---|---|
| 에이전트가 사용할 모델의 **개인별** 할당정책 | **조직별** 할당 (조직 노드의 모델 탭) | **변경** |
| 로컬 llm 서비스와 **외부 모델 서비스 결합** | 엔드포인트를 여러 개 등록(사내 LM Studio + 유료 API 모두 가능) | **구현** |
| 개인별 **할당량에 따른 자동 전환정책** | 없음 | **미구현** |

**여기가 이 대조표의 핵심이다.** 계획의 단위는 개인이었는데 구현의 단위는 조직이 됐다. 강의는 조직별 통제를 "조직이 존재하는 큰 이유"로 설명하지만, 계획표 기준으로 보면 그것은 **다른 축**이다.

두 축의 차이:

| | 개인별 할당 | 조직별 할당 |
|---|---|---|
| 결정 주체 | 개인의 사용량·역할 | 조직 소속 |
| 필요한 것 | 사용량 집계, 소진 감지, 대체 모델 순위 | 조직 트리, 상속 규칙 |
| 해결하는 문제 | 토큰 예산 관리 (2강 7장의 핵심 요구) | 접근 권한 |

즉 3강은 **권한 축을 먼저 만들고 예산 축을 접었다.** 접은 쪽이 2강에서 "모델 라우터의 핵심 요구"라고 했던 것(엔터프라이즈 토큰 소진 시 사내 LLM 무중단 전환)이라는 점도 함께 기억할 것.

자기 구현에서 남겨야 할 여지: 프리셋을 해석하는 지점이 나중에 "할당량을 보고 다른 프리셋으로 떨어뜨리는" 자리가 된다. 그래서 모델 결정을 **호출 시점에 해석**하도록 두고, 계정에 미리 박아 두지 않는다.

### 4. 정보검색센터 → 미구현 (계획대로)

자기 구현에서 남겨야 할 여지: 저장소가 SQLite인데 벡터 검색이 붙으면 PostgreSQL + PGVector로 옮겨야 할 수 있다(2강 10장의 스택 선택). 그 전환 가능성을 배제하지 않는다.

### 5. 계획표에 없었는데 들어온 것

| 들어온 것 | 출처 |
|---|---|
| 모노레포 경계(`common`/`server`/`front`), 프로토콜 타입 위치 | 스킬 `monorepo-architecture-guard` |
| i18n 8개 언어 강제, 리소스 키 타입화 | 스킬 `i18n-resource-map` |
| 퍼미션 미들웨어 층(기본 거부) | 엔터프라이즈 관례 + 스킬 |
| 파일 400줄 상한, 5자리 포트, 볼륨 하나 | 스킬 `monorepo-architecture-guard`, `docker-compose-module-design` |
| 배포 검증·리포트 형식 | 스킬 `web-deploy-docker` |
| 날짜별 테스트 리포트 규정 | 테스트 규정 스킬 |

**요구사항이 아니라 스킬이 강제한 것**이다. 자기 구현을 할 때 계획표만 들고 시작하면 이 층이 비고, 그러면 에이전트가 만든 코드의 모양이 매번 달라진다(6장).

## 필수 지식 (HOW) — 결정 목록과 뒤집기 비용

계획표의 한 줄은 구현 단계에서 여러 결정으로 갈린다. 착수 순서의 기준은 "쉬운 것부터"가 아니라 **뒤집기 비용의 역순**이다 — 비싼 결정을 미루면 그때까지 쌓은 코드가 잘못된 가정 위에 선다.

| 결정 | 선택지 | 참조 구현의 선택 | 뒤집기 비용 |
|---|---|---|---|
| **계정 영구 키** | 이메일 / 사번 / 내부 불변 ID | 이메일 (문제를 인지하고 보류) | **매우 높음** — 감사 이력이 두 사람에게 섞이면 분리 근거가 없다 |
| **세션 토큰 성질** | 무상태 검증형 / 중앙 관리형 | 중앙 관리형 | **매우 높음** — 무상태면 "즉시 회수"가 성립하지 않아 계획의 `1-a`를 못 맞춘다 |
| **모델 할당 축** | 개인별 / 조직별 | 조직별 | **높음** — 축을 바꾸면 트리·상속·화면이 함께 움직인다 |
| **조직 루트 개수** | 단일 / 복수 | 복수(`parentId: string \| null`) | **매우 높음** — 단일 전제는 스키마·쿼리·권한 판정에 퍼진다 |
| **관리자 권한 범위** | 노드 단독만 / 노드+하위 전체 | 둘 다 | **높음** — 단독만 두면 새 노드마다 재부여가 필요하다 |
| **모노레포 경계** | 2분할 / 도메인 3분할 | `common`·`server`·`front` | **매우 높음** — 프로토콜 위치가 바뀌면 양쪽 import가 전부 움직인다 |
| **i18n 도입 시점** | 나중에 / 처음부터 | 처음부터 8개 언어 | **매우 높음** — 뷰에 리터럴이 박힌 뒤 외부화는 전면 작업 |
| **퍼미션 배치** | 엔드포인트별 / 미들웨어 한 층 | 미들웨어, 기본 거부 | **높음** — 나중에 모으려면 모든 라우트 재검토 |
| **필수 가입 필드** | — | 정책으로 지정 | **높음** — 나중에 받기 시작한 필드는 기존 계정에 없다 |
| 마스터 지정 | DB / 환경변수 | 환경변수, 콤마 복수 | 낮음 — 재기동만 |
| 저장소 | SQLite / PostgreSQL | SQLite, 볼륨 하나 | 중간 — 배포·백업 절차가 바뀐다 |
| 모델 등록 단위 | 모델 / 프리셋 | 프리셋 | 높음 — 모델 단위면 용도별 설정을 못 담는다 |
| 유휴·보관 시간 | — | 7200 / 86400 | 낮음 — 설정값 |
| 포트·파일 상한 | — | 5자리 / 400줄 | 낮음 |

**매우 높음 다섯**을 먼저 앉아서 정해야 한다: 계정 영구 키 / 세션 토큰 성질 / 조직 루트 개수 / 모노레포 경계 / i18n 도입 시점. 나머지는 만들어 가며 정해도 된다.

## 이 지식이 판단에 쓰이는 자리

- **참조 구현을 볼 때**: 화면에 있는 것을 계획의 전부로 보지 않는다. `부분`·`축소`·`변경`을 찾아 그 자리에 무엇이 남았는지 확인한다.
- **자기 구현을 시작할 때**: 뒤집기 비용 "매우 높음" 다섯을 먼저 확정한다.
- **축이 바뀐 것을 발견했을 때**: 모델 할당의 개인별↔조직별처럼, 축이 다르면 필요한 데이터와 해결하는 문제가 달라진다. 축소로 착각하고 넘기면 원래 요구가 사라진다.
- **범위를 닫을 때**: 접은 항목마다 "남겨야 할 여지"를 적는다.

### ⚠️ 암기 필수

- [ ] **판정은 다섯이다: 구현 / 부분 / 축소 / 변경 / 미구현.** `구현`과 `미구현`만으로 보면 접힌 것을 접힌 줄 모르고 지나간다.
- [ ] **계획은 모델 할당이 `개인별`인데 구현은 `조직별`이다 — 축소가 아니라 축의 변경이다.** 조직별은 권한 축, 개인별은 예산 축(토큰 소진 시 무중단 전환)이고 후자가 2강이 말한 핵심 요구였다.
- [ ] **"로그인 정보수집 커스터마이즈"는 부분 구현이다** — 값이 실릴 통로(헤더·쿠키 이름)는 만들었지만 **수집 항목을 정의하는 화면**은 없다. 감사 필드를 확장 메타로 받아 자리를 열어 둔다.
- [ ] **착수 순서는 뒤집기 비용의 역순.** 매우 비싼 다섯: **계정 영구 키 / 세션 토큰 성질 / 조직 루트 개수 / 모노레포 경계 / i18n 도입 시점.**
- [ ] **계획표에 없던 구조 규칙은 스킬이 강제한 것이다** — 계획표만 들고 시작하면 그 층이 비고, 에이전트 산출물의 모양이 매번 달라진다.
