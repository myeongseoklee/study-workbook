# 01. 저장소와 계정 — SQLite로 충분한 이유, 그리고 이메일을 믿으면 안 되는 이유

## 학습 목표

사내 비즈니스 서버의 저장소를 무엇으로 고를지 판단 기준을 갖는다. 계정 식별자로 회사 이메일을 쓸 때 생기는 함정과, 마스터 계정을 DB 밖에 두는 이유를 설명할 수 있다.

## 선수 지식

- 2강 6장: 온프레미스 = 외부 인증(구글 로그인) 불가 → 자체 인증이 강제된다
- 이 장의 대상은 **관리 서버의 저장소**다. 에이전트가 쓰는 세션 저장소·벡터DB는 별개다

## 핵심 원리 (WHY) — 규모가 아니라 배포 형태가 저장소를 정한다

기본값은 SQLite다.

> 사내에서 비즈니스용으로 쓸 거면 **어지간히 대규모로 배포할 게 아니면 그냥 SQLite 써도 충분**하다. 좀 더 가야 된다 그러면 그때 PostgreSQL 깔고 쓰면 된다.

판단이 "데이터가 많냐"가 아니라 **"어떻게 배포되냐"**에 걸려 있다는 점이 중요하다. 온프레미스 관리 서버는 고객사마다 한 벌씩 들어가고, 동시 사용자는 회사 인원 규모이며, 설치가 쉬워야 한다. 이 조건에서 별도 DB 서버는 **관리 대상만 하나 더 늘린다.**

실제 배포 형태가 그 선택을 뒷받침한다.

![docker-compose.yml — 볼륨 하나, 5자리 포트 11:24](assets/frames/t00-11-24.jpg)

볼륨이 `admin_data:/app/data` **하나뿐**이다. SQLite 파일과 서버가 저장할 것들이 전부 이 디렉토리 안으로 들어간다.

> 볼륨은 요거 하나만 잡아 주면 되거든요. 여기에 SQLite도 저장하고 기타 서버가 저장해야 될 것들 저장하죠.

백업이 "이 디렉토리 하나"가 되는 것이 온프레미스 납품에서 실제로 큰 이점이다.

### 파일시스템 + JSON은 왜 안 되나

에이전트류를 만들 때 흔히 택하는 방식인데, 강의는 두 가지 이유로 거부한다.

> 폴더 나눠 가지고 JSON 쓰는 걸로는 **한계가 금방 와요.** 폴더·파일은 금방 지저분해지기도 하고, **파일 액세스에 대한 동시성은 더 나쁘기** 때문에.

두 번째가 결정적이다. 여러 요청이 같은 JSON을 읽고 쓰면 잠금을 직접 구현해야 하는데, 그건 이미 DB가 하는 일이다. SQLite는 파일 하나라는 배포 이점을 유지하면서 그 문제를 넘긴다.

## 필수 지식 (HOW) — 회사 이메일은 고유 식별자가 아니다

계정은 이메일·비밀번호로 정의했다. 그런데 여기에 함정이 있다.

> 회사 이메일은 그 사람이 **퇴사하면 없어져야 되거든요.** 그래서 이 이메일이 고유하지가 않아요. 그 사람 퇴사하고 나면 **똑같은 이메일을 신입사원이 다시 받아요.** 많은 회사가 그래요.

`kim@example.com`이 김 대리였다가 다음 해 다른 김 대리가 된다. 이메일을 계정의 **영구 키**로 쓰면 두 사람의 이력이 한 계정에 섞인다. 감사 로그가 목적인 시스템에서 이건 치명적이다 — "누가 무엇을 했나"의 '누가'가 무너진다.

강의는 이 문제를 지금은 열어 두지만("나중에 문제가 되긴 하는데 지금은 이 정도로만"), **문제가 있다는 사실 자체를 짚고 넘어간다.** 설계에서 이 인식이 갖는 값은 크다. 나중에 사번·사원 고유 ID 같은 불변 키를 도입할 자리를 미리 알아 두는 것과, 이메일이 영원할 거라 믿고 외래키를 박아 두는 것은 마이그레이션 비용이 완전히 다르다.

## 필수 지식 (HOW) — 마스터 계정은 DB에 없다

관리자 권한 중 최상위인 마스터 계정은 **데이터베이스가 아니라 환경변수**로 정해진다.

> 얘는 슈퍼 계정인데, **DB상에 있는 데이터로 슈퍼 계정인 걸 알아낸 게 아니라 Docker를 띄울 때 환경으로 지정**하게 돼 있어. 그러니까 **DB로도 얘를 조작할 수 없는 거지.** 마스터 계정에 대한 권한은 `.env` 파일에 있기 때문에 Docker 띄울 때 확정돼요.

같은 결정이 구현 지시에도 그대로 나온다.

> 마스터 이메일은 **DB 설정이 아니라 환경변수에서만 읽도록** 하겠습니다.

이 배치가 사는 이유는 **공격면이 다르기 때문**이다. DB에 마스터 플래그가 있으면, DB에 쓰기 권한을 얻은 사람은 누구나 자기를 마스터로 만들 수 있다. 환경변수에 있으면 그러려면 **서버를 재기동할 권한**이 필요하다 — 그건 이미 인프라 접근 권한이고, 감사 대상이 다르다.

대가도 분명하다.

> 어떤 계정을 마스터로 띄우고 싶으면 **서버를 완전히 재기동해야 돼.**

마스터는 자주 바뀌지 않으므로 이 대가는 싸다. 대신 **여러 명을 콤마로 넣을 수 있게** 해서 다른 문제를 막는다 (→ 3장의 승인자 단일화 위험).

## 이 지식이 판단에 쓰이는 자리

- **온프레미스 제품의 저장소를 고를 때**: 동시 사용자와 배포 편의를 먼저 본다. 규모가 커지면 그때 PostgreSQL로 간다.
- **계정 스키마를 짤 때**: 이메일을 표시·로그인 수단으로 쓰되 **영구 키로 쓰지 않는다.** 재사용되는 값에 이력을 매달지 않는다.
- **권한 최상위를 설계할 때**: 데이터로 승격 가능한 권한과, 인프라 접근이 있어야만 바꿀 수 있는 권한을 나눈다. 후자를 하나는 둔다.

### ⚠️ 암기 필수

- [ ] **사내 비즈니스 서버의 기본 저장소는 SQLite.** 대규모 배포가 아니면 충분하고, 필요해지면 PostgreSQL로 간다. 판단 기준은 데이터 양이 아니라 **배포 형태**다.
- [ ] **파일시스템+JSON은 쓰지 않는다** — 금방 지저분해지고 **동시성이 더 나쁘다**(잠금을 직접 만들게 된다).
- [ ] **회사 이메일은 고유하지 않다** — 퇴사자의 주소를 신입이 다시 받는다. 이메일을 계정의 영구 키로 쓰면 두 사람의 이력이 한 계정에 섞인다.
- [ ] **마스터 계정은 DB가 아니라 환경변수(.env)로 지정한다** → DB를 조작해도 마스터가 될 수 없고, 바꾸려면 서버 재기동이 필요하다. 콤마로 여러 명을 지정한다.
