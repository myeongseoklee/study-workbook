# 03. 위임과 조직 — 계획표 1-c의 구현체

## 학습 목표

**조직 트리가 독립 기능이 아니라 `인가권한 중간 관리자 위임기능`의 구현체**임을 이해한다. 위임을 성립시키려면 무엇이 필요한지 역으로 짚고, 조직도 설계에서 가장 흔한 실수를 피한다.

## 선수 지식

- 01장: 조직이 계획표의 독립 항목이 아니라는 대조 결과
- 2강 9장: "중간관리자 위임이 있으면 관리자 페이지가 로그인 주체에 따라 달라진다"

## 핵심 원리 (WHY) — 위임을 만들려면 조직이 필요하다

2강이 요구한 것은 조직도가 아니라 **위임**이었다.

> AX팀이 이걸 다 하지 않는다. 팀장에게 "네 팀 애들은 네가 알아서 해"라고 **위임하는 기능**이 필요하다. (2강)

여기서 "네 팀 애들"이 문제다. 위임을 구현하려면 **위임의 범위를 표현할 단위**가 있어야 하고, 그 단위가 조직이다. 계정에 `role: manager`만 붙이면 "무엇의 매니저인가"를 말할 수 없다.

그래서 순서가 이렇다.

```
위임 요구  →  범위 단위 필요  →  조직 트리
                              →  범위 종류(노드 단독 / 하위 전체)
                              →  위임 사슬(누가 누구를 임명하나)
```

조직을 "회사 조직도를 보여주는 화면"으로 이해하면 이 인과가 끊긴다. 3강에서 조직 노드가 **정보 / 멤버 / 모델** 세 탭을 갖는 것도 여기서 나온다 — 위임의 대상이 멤버 관리와 모델 통제이기 때문이다.

## 필수 지식 (HOW) — ① 루트를 하나로 만드는 것이 가장 흔한 실수다

강의가 직접 지목한다.

> 조직도 만들 때 **가장 많이 한 실수가 루트를 하나밖에 안 되게 만드시는 건데 그러시면 안 돼요.** 진짜 실무에서는 **조직의 루트가 여러 개 있을 수 있어.** 이게 아예 **지사 A, 지사 B**가 될 수 있잖아요.

왜 하나로 만들기 쉬운가. 조직도를 "회사"의 그림으로 생각하면 회사는 하나이므로 루트도 하나가 된다. 하지만 시스템이 담아야 하는 것은 회사가 아니라 **관리 단위의 집합**이다 — 지사·법인·인수한 자회사·프로젝트 조직이 서로의 하위가 아니면서 나란히 존재한다.

그리고 **비대칭**이 결정을 강제한다. 복수를 허용하면 루트가 하나인 회사도 아무 불편이 없다. 반대로 하나로 제한한 뒤 둘이 되면 스키마·쿼리·트리 UI·권한 판정·상속 로직을 전부 고친다. 한쪽 실수는 비싸고 다른 쪽은 공짜이므로 **기본값이 정해져 있다.**

타입이 그 결정을 담는다.

```ts
export type Organization = {
  id: string;
  name: string;
  parentId: string | null;   // null = 루트. 그런 노드가 여럿인 것을 막을 근거가 없다
  color: OrganizationColor;
  icon: OrganizationIcon;
  createdAt: string;
};
```

## 필수 지식 (HOW) — ② 권한 범위가 두 종류여야 위임이 산다

![노드 설정 — 정보·멤버·모델 탭 38:00](assets/frames/t00-38-00.jpg)

> 이 노드에다가 **어드민을 부여**하잖아요. 그럼 이 계정이 **멤버 승인을 할 수도 있고 모델을 컨트롤할 수도 있게** 되는 권한을 줄 수도 있고요. **어드민 하면 얘 하이어라키의 모든 노드에 어드민이 될 수 있게끔** 할 수도 있고 — **이 두 가지를 제공**해 주는 거예요.

| 범위 | 의미 | 누구 |
|---|---|---|
| **노드 단독** | 그 노드에서만 관리자 | 팀장 — 자기 팀만 |
| **하위 계층 전체** | 그 노드와 모든 후손 | 본부장·지사장 |

하위 전체가 없으면 위임이 성립하지 않는다. 지사장에게 권한을 주려고 노드마다 개별 부여하면 **조직을 새로 만들 때마다 다시 부여**해야 하고, 그러면 권한이 조직 변경을 따라오지 못한다. 하위 전체 범위는 **미래에 생길 노드**까지 포함한다.

그리고 위임은 재귀적이다. 구현 지시에 이렇게 적혀 있다.

> 조직의 **책임자는 마스터 관리자가 임명**할 수 있으며, 책임자는 다시 **자신의 권한에 따라 노드 또는 하위 노드 전체에 대해 책임자를 지정**할 수 있다.

두 가지가 함께 있다 — 사슬이 뻗는다는 것과, **자기 권한을 넘지 못한다**는 것. 팀장이 본부 전체 관리자를 임명할 수는 없다. 이 제약이 없으면 위임이 권한 상승 경로가 된다.

이것이 승인자 단일화 문제의 구조적 답이기도 하다(2장의 마스터 복수 지정과 짝).

## 필수 지식 (HOW) — ③ 위임의 대상: 멤버와 모델

노드의 세 탭 중 **모델 탭**이 계획표 3번과 만나는 자리다.

> 이 조직이 **사용할 모델을 지정**하게 돼. 그렇게 하면 **이 조직에 속해 있는 애들은 싹 다 이것밖에 못 쓰게** 되는 거야. **내가 이렇게 다 지정해 줘야지만 쓸 수 있는 거지.**

기본값이 **거부**다. 열어 두고 막는 방식이면 새 모델을 등록할 때마다 전 조직에 열린다 — 모델은 곧 비용(VRAM·토큰)이다. 4장에서 이 축이 계획표의 "개인별"과 어떻게 다른지 다룬다.

멤버 할당은 이메일로 계정을 찾아 노드에 붙이는 방식이다. 여기서도 2장의 함정이 이어진다 — 멤버십이 이메일 문자열을 참조하면 퇴사·재입사에서 어긋난다.

## 필수 지식 (HOW) — ④ 색상·아이콘이 요구사항이었던 이유

사소해 보이는데 강의가 굳이 짚는다.

> 이런 사소한 기능들이 이제 **편리성을 가져오게 되죠. 조직이 커지면.** 이것도 다 괜히 만든 게 아닙니다. **회사 부서 아이콘 뭐 이런 거 해 달라고 그래 가지고** 이거 다 만들어 놓은 거란 말이죠.

조직이 수십 개가 되면 이름만으로는 트리에서 눈이 길을 잃는다. 실사용에서 올라온 요구라는 점이 기억할 부분이다 — 위임 구조를 만들면 **관리 화면을 쓰는 사람이 늘어나고**, 그때부터 이런 요구가 들어온다.

## 이 지식이 판단에 쓰이는 자리

- **"조직 관리 기능을 만들어 달라"를 받았을 때**: 먼저 위임 요구가 있는지 묻는다. 위임이 없으면 조직 트리는 표시용이고, 있으면 권한 판정의 뼈대다.
- **조직도를 설계할 때**: 루트 복수를 기본으로. 비대칭이라 선택의 여지가 없다.
- **권한을 배치할 때**: 범위를 노드 단독/하위 전체로 나누고, 위임자가 자기 권한을 넘지 못하게 막는다.
- **자원 접근을 통제할 때**: 기본 거부. 지정하지 않은 조직이 전부 쓰게 되면 통제가 아니다.

### ⚠️ 암기 필수

- [ ] **조직 트리는 독립 기능이 아니라 `인가권한 중간 관리자 위임`의 구현체다.** 위임에는 범위를 표현할 단위가 필요하고 그것이 조직이다.
- [ ] **조직 루트는 여러 개일 수 있다**(지사 A·지사 B). 하나로 제한하는 것이 **가장 흔한 실수**이고, 복수 허용은 공짜인데 제한은 전면 수정이라 **비대칭이 기본값을 정한다.**
- [ ] **권한 범위 2종(노드 단독 / 하위 계층 전체)이 있어야 위임이 산다** — 하위 전체가 **나중에 생기는 노드**까지 포함하기 때문이다.
- [ ] **위임은 재귀적이되 자기 권한을 넘지 못한다.** 이 제약이 없으면 위임이 권한 상승 경로가 된다.
- [ ] **조직별 모델 접근은 기본 거부.** 지정하지 않으면 못 쓴다 — 모델은 비용이다.
