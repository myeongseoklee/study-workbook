# 07. 빌드 사이클 — 쪼개서 시키고, 확인하고, 남긴다

## 학습 목표

큰 기능을 어떤 입자로 쪼개 지시하는지, 시킨 것이 됐는지 어떻게 확인하는지, 그 결과를 어디에 남기는지 안다. 이 사이클이 자기 구현에서 돌려야 하는 바퀴다.

## 선수 지식

- 05·06장: 지시의 내용(스킬)과 그것이 강제하는 규칙
- 이 장은 그 지시를 **어떤 단위로 던지고 어떻게 회수하는가**를 다룬다
- 1강 5장: 폴더 격리 — 같은 원리가 시간축에 적용된다

## 핵심 원리 (WHY) — 세션의 크기가 되돌리기 단위를 정한다

큰 기능을 한 번에 시키지 않는다. 세션 목록이 그 증거다.

![Codex 세션 목록 — 작업 단위로 쪼갠 지시 36:06](assets/frames/t00-36-06-sessions.jpg)

아래에서 위로 읽으면 실제 순서가 된다.

```
Scaffold admin web service      ← 스킬로 골격 생성
어드민 좌측메뉴 기본 구조
조직 및 마스터관리자 기능 추가
서브카피를 버전 표시로 변경
링커 프론트엔드 테마 적용
데이터 프리로딩 및 응답 개선
노드 모달 정보·멤버 탭 개편
조직도 관리자 권한 적용
노드 색상과 타이틀 반영 수정
모델 엔드포인트 메뉴 추가
Fix missing account menus
엔드포인트 저장 동작 수정
노드 모델 탭 및 서버 관리
노드 모델 탭 추가               ← 최근
```

**읽어 낼 것은 입자 크기다.** "어드민 사이트 만들어"가 아니라 "노드 모달의 정보·멤버 탭 개편", "노드 색상과 타이틀 반영 수정"처럼 **한 화면의 한 부분**이 한 세션이다.

이 크기가 두 가지를 정한다.

1. **뽑기가 미치는 범위** — 세션이 작으면 잘못됐을 때 영향 범위도 작다 (폴더 격리를 시간축에 적용한 것)
2. **되돌리기 단위** — 세션 제목이 곧 되돌릴 수 있는 최소 단위가 된다

그리고 목록 자체가 **작업 이력**이 된다. `Fix missing account menus` → `엔드포인트 저장 동작 수정`처럼 수정 세션이 섞여 있는 것을 보면, 한 번에 완성되지 않았고 그것이 정상이라는 것도 읽힌다.

시작은 스캐폴딩이다.

> 처음에는 **제 스킬로 스캐폴딩을 쭉 시킵니다.** 스킬이 있기 때문에 한 번에 쭉 만들어 내거든요. 그리고 기본적인 내용을 지시해요.

## 필수 지식 (HOW) — ① 검증: 내장 브라우저가 비용을 바꿨다

> 예전에는 그게 다 **Playwright 기반**으로 저도 엄청 꼼꼼하게 했었는데요, 이제는 그냥 **Codex 내장 브라우저가 짱**이에요. **이젠 더 이상 크롬도 필요 없어.** 헤드리스 브라우저도 필요 없어. 그냥 지시가 이거야 — **"내장 브라우저에서 스샷 떠"** 그러면 얘가 다 하거든요.

부수 효과가 실무적으로 크다.

> 더 이상 크롬으로 **포커스를 뺏지도 않고 제 마우스를 건들지도 않아요.**

기존 헤드리스 자동화의 비용은 스크립트 작성만이 아니었다 — 시나리오를 코드로 옮기고, 셀렉터가 바뀌면 고치고, 실행 중엔 화면을 내줘야 했다. 내장 브라우저는 그 과정을 **자연어 지시 + 결과 보고**로 바꾼다.

그리고 강의자가 낸 과제가 "**스크린샷 공유**"였던 것과 이어진다(00장). 검증 산출물이 스크린샷이므로 공유가 곧 검증 공유다.

> 이 나중에 이거 볼 때도 되게 좋아요. 왜냐면 **모든 걸 문서로 안 보고 스샷으로 보고**되니까.

## 필수 지식 (HOW) — ② 배포 검증은 스킬이 형식으로 못박는다

수동 확인에 맡기지 않는다. `web-deploy-docker` 스킬이 배포의 성공 조건과 보고 형식을 정한다.

![web-deploy-docker — 리포트 형식 강제 33:15](assets/frames/t00-33-15.jpg)

> Config is validated before refresh. An invalid `docker compose config` fails the deploy with its own reason instead of surfacing later as a container error.
>
> The published port is verified. An empty port mapping, a port of `0`, and an `invalid IP:0` mapping are **failures, not warnings.**
>
> Health is verified over the published port. **Do not assume `127.0.0.1` is the Docker host**; try the valid host candidates. **A deploy that never proved a response is not a successful deploy.**
>
> The run is idempotent. An unchanged service is reported as `already-current` **instead of being rebuilt.**
>
> Everything lands in one report block. **A deploy that succeeds silently cannot be reviewed.**

그리고 형식이 파싱 가능하게 고정돼 있다.

```
deploy-report-begin
result:  status=<ok|failed> services=<...> compose=<refreshed|already-current|failed>
time:    total=<n>ms resolve=<n>ms install=<n>ms build=<n>ms compose=<n>ms verify=<n>ms
verify:  <one line per service and per health probe>
changed: files_edited=<...>
deploy-report-end
```

> **Base the final answer on that block** and carry its four summary lines into the answer.

이 마지막 문장이 환각 방지 장치다. 모델이 "배포 성공했습니다"라고 요약하는 대신 **실제 출력 블록에 근거하게** 묶는다. 그리고 `Do not assume 127.0.0.1`은 04장의 Docker localhost 함정을 스킬 층에서 막은 것이다.

## 필수 지식 (HOW) — ③ 테스트 층위: 인수 우선과 그 전제

> 여러분들이 **코드상의 인수 테스트나 이런 거 다 옛날 방식**이야. **처음부터 인수 테스트만 돌려도 된다고. AI가 단위 테스트를 실패하면 뭐 어쩔 건데? 다시 뽑기로 코드 짜 가지고 단위 테스트 통과시킨 것뿐이잖아.** 그러니까 **뽑기로 인수 테스트를 통과하는 게 낫단 말이지.**

논리를 풀면 이렇다. 단위 테스트의 전통적 가치 중 **"실패 위치를 좁혀 준다"**가 에이전트 앞에서 값이 떨어진다 — 좁혀 줘도 에이전트는 그 지점을 **다시 생성**할 뿐이고, 통과한 결과가 "옳아서 통과"인지 "그 테스트만 만족"인지 구별되지 않는다. 같은 뽑기라면 **사용자가 실제 겪는 경로**를 판정 대상으로 두는 편이 낫다.

**전제를 함께 봐야 한다.** 강의가 만든 것은 CRUD 관리 화면이고, 그 영역에서는 인수 경로가 곧 기능의 전부다. 반면 순수 로직이 두꺼운 영역 — 이 레포의 과제들처럼 컴팩션 트리거 판정, 조직 트리 권한 해석, 키셋 감사 — 에서는 단위 테스트가 **명세 그 자체**로 기능한다. 실패 위치를 좁히려고 쓰는 게 아니라 **무엇을 만들지 정의하려고** 쓴다.

정리하면 교훈은 "단위 테스트를 버려라"가 아니라 **"테스트의 층위를 목적으로 고르라"**다.

## 필수 지식 (HOW) — ④ 남기기: 날짜별 리포트

> 저는 **테스트 규정이 있거든요.** 얘네들이 다 어디에 쌓이냐면 **날짜별로 쌓이게** 돼 있어요. **무슨 짓을 했는지 시간대별로 다 남아.** 테스트 리포트 작성이 다 되고, **뭘 페일했는지 뭘 성공했는지** 다 남게 돼 있거든요. 이것도 스킬로 돼 있어.

세션 로그로 충분하지 않은 이유를 강의가 직접 말한다.

> 그래서 나중에 뭘 했는지 **저 세션 같은 거 안 뒤지고 이거 그냥 볼 때도 많아요.**

세션 로그는 대화 전체다 — 시도·실패·수정이 뒤섞여 길다. 테스트 리포트는 **결과만** 날짜별로 정렬돼 있어 "이 기능이 언제부터 동작했나", "무엇이 실패했었나"를 빨리 찾는다. 그리고 **세션이 사라져도 남는다.**

이 발상은 06장과 한 쌍이다 — 규칙에 검사를 붙이고(06), 검사 결과를 날짜별 산출물로 남긴다(07). 둘 다 **에이전트의 작업을 사후에 검증 가능하게** 만드는 장치다.

## 이 지식이 판단에 쓰이는 자리

- **기능을 지시할 때**: 화면 하나가 아니라 **화면의 한 부분**을 한 세션으로 잡는다. 세션 제목이 되돌리기 단위가 된다.
- **UI를 검증할 때**: 헤드리스 스크립트를 짜기 전에 내장 브라우저 + 스크린샷으로 시작한다.
- **배포를 맡길 때**: 성공의 정의를 문장으로 못박고(응답을 증명하지 못한 배포는 성공이 아니다) 리포트 형식을 고정한다.
- **테스트 층위를 고를 때**: 사용자 경로가 곧 기능인 영역은 인수, 판정 기준이 명확한 순수 로직은 단위(명세로서).
- **이력을 남길 때**: 세션 로그에 의존하지 않고 결과만 담은 날짜별 산출물을 만든다.

### ⚠️ 암기 필수

- [ ] **한 세션 = 한 작업 단위(화면의 한 부분).** 세션 크기가 **뽑기의 영향 범위와 되돌리기 단위**를 정한다 — 폴더 격리를 시간축에 적용한 것.
- [ ] **내장 브라우저가 인수 검증 비용을 바꿨다** — Playwright·헤드리스·별도 크롬이 불필요하고 포커스·마우스를 빼앗지 않는다. 지시는 "내장 브라우저에서 스샷 떠"로 끝난다.
- [ ] **배포 성공의 정의를 못박는다: "응답을 증명하지 못한 배포는 성공이 아니다", "조용히 성공한 배포는 리뷰할 수 없다".** 빈 포트 매핑·`0`·`invalid IP:0`은 경고가 아니라 **실패**다.
- [ ] **출력 형식을 `key=value`로 고정하고 최종 답변을 그 블록에 묶는다** — 보고와 실제가 어긋날 수 없게.
- [ ] **에이전트 앞에서 단위 테스트의 "실패 위치 좁히기" 값이 떨어진다** — 좁혀 줘도 다시 뽑을 뿐이다. **단 전제는 순수 로직이 얇은 CRUD·화면 영역**이고, 판정 기준이 명확한 로직에는 단위 테스트가 **명세**로 남는다.
- [ ] **테스트 리포트를 날짜별 산출물로 남긴다** — 세션 로그는 시도·실패가 섞여 길지만 리포트는 결과만 정렬돼 있고 **세션이 사라져도 남는다.**
