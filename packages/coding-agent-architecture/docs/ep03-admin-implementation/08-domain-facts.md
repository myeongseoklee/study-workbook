# 08. 도메인 사실 — 모든 결정의 근거가 되는 환경 조건

## 학습 목표

이 영역(사내 온프레미스 관리 서버)을 다룰 때 **알고 있어야만 결정이 성립하는 사실**들을 한자리에 모아 둔다. 기술 선택이 아니라 환경의 성질이므로, 모르면 결정 자체를 못 한다.

## 선수 지식

- 01~07장 전체. 이 장은 그 결정들의 **근거 목록**이고 새 내용을 도입하지 않는다
- 자기 구현을 설계할 때 이 표만 따로 열어 대조하면 된다

## 핵심 원리 (WHY) — 결정이 아니라 조건이다

앞 장들의 결정은 대부분 "이게 더 좋아서"가 아니라 **"환경이 그러니까"** 내려졌다. 헤더 이름을 설정으로 뺀 것은 설계 취향이 아니라 사내 방화벽이 헤더를 감시하기 때문이고, 이메일을 영구 키로 못 쓰는 것은 회사가 주소를 재사용하기 때문이다.

그래서 자기 구현을 할 때 순서가 이렇게 된다.

```
환경 사실 확인  →  결정  →  지시(스킬)  →  검증
```

사실을 건너뛰고 결정하면 참조 구현을 베끼는 것이 되고, 자기 고객사 조건이 다를 때 그 차이를 발견하지 못한다.

## 필수 지식 (HOW) — 사내망·보안

| 사실 | 무엇을 강제하나 | 어디서 |
|---|---|---|
| **사내 보안 방화벽이 L7에서 헤더를 감시·삽입·차단한다** | 세션 헤더·쿠키 이름을 설정으로 빼고 **보안팀 승인을 일정에 넣는다.** 설치 당일에 발견하면 늦다 | 02장 |
| **쿠키 자동 전송은 브라우저뿐** | 모바일 앱용 헤더 경로가 함께 필요하다 (같은 토큰, 두 통로) | 02장 |
| **로그인 풋프린트 요구가 회사마다 크게 다르다** (사내 IP·부서·사번·지급 노트북 보안 코드) | 감사 필드를 고정 스키마가 아니라 **확장 메타**로 받는다 | 02장 |
| **온프레미스는 외부 인증(구글 로그인)이 불가** | 자체 인증·세션 발급을 직접 만든다 | 2강 6장 |
| **RHEL 엔터프라이즈 + 사내 보안은 컨테이너를 차단한다** | Docker 전제를 고객사별로 확인한다. 네이티브 설치형이 필요할 수 있다 | 2강 8장 |
| **온프레미스는 타임 서버가 없어 컴퓨터 시간을 믿어야 한다** | 라이센스라면 시간 조작 방어가 필수 | 2강 8장 |

## 필수 지식 (HOW) — 조직과 사람

| 사실 | 무엇을 강제하나 | 어디서 |
|---|---|---|
| **회사 이메일은 퇴사 후 재사용된다** | 이메일은 영구 키가 될 수 없다. 감사·멤버십은 계정 ID를 참조한다 | 02장 |
| **사내망 안에 협력업체·인턴·타 부서·퇴사 예정자가 있다** | 사내망 위치는 신원 증명이 아니므로 가입에 승인 정책이 필요하다 | 02장 |
| **조직의 최상위가 여러 개일 수 있다** (지사·법인·인수한 자회사) | 루트 복수를 기본으로. 제한은 전면 수정, 허용은 공짜 | 03장 |
| **승인자가 휴가 가면 가입이 멈춘다** — 조직에서 흔한 일 | 마스터 복수 지정 + 재귀 위임 | 02·03장 |
| **AX팀이 전사 관리를 다 하지 않는다** | 중간관리자 위임이 필수이고, 그러면 **관리자 화면이 로그인 주체에 따라 달라진다** | 03장 |
| **조직이 커지면 이름만으로 트리에서 길을 잃는다** | 색상·아이콘 같은 표시 속성이 실사용 요구로 올라온다 | 03장 |
| **인사DB 조회는 연동 작업이다** | 사번 필터는 IP 필터보다 착수 비용이 크다. "조건 하나 추가"가 아니다 | 02장 |

## 필수 지식 (HOW) — 인프라·운영

| 사실 | 무엇을 강제하나 | 어디서 |
|---|---|---|
| **서버가 죽는 원인 1위는 로그 적재** | 세션·감사 기록 보관 기간을 **처음부터** 설정으로 뺀다 | 02장 |
| **Docker 컨테이너 안의 `localhost`는 컨테이너 자신** | 호스트 서비스 URL에 `localhost`를 쓰지 않는다. **개발 중엔 통했기 때문에 배포 후에만 깨진다** | 04·07장 |
| **네 자리 포트(3000·8080·5432)는 다른 서버와 충돌한다** | 5자리 대역으로 통일하면 여러 프로젝트를 동시에 띄울 수 있다 | 06장 |
| **적재된 모델에서 모달리티가 제거될 수 있다** | 모달리티는 이름으로 추론 불가, 등록 시 지정 | 04장 |
| **작은 모델은 리즈닝 루프에 빠진다** | `repeat_penalty`를 처방으로 준다. 리즈닝 옵션을 끄는 선택지도 있다 | 04장 |
| **회사가 모델을 지정해 내려준다** (산업용) | 개인이 고르는 구조가 아니다. 모델 접근은 기본 거부 | 03·04장 |

## 필수 지식 (HOW) — 에이전트에게 맡길 때

| 사실 | 무엇을 강제하나 | 어디서 |
|---|---|---|
| **모델은 애매한 지시를 자기에게 유리하게 해석한다** | 위반의 지위를 못박는다 — `violation, not a to-do` / `failures, not warnings` | 05장 |
| **키 맵이 없으면 모델은 키를 지어내거나 그럴싸한 것을 복사한다** | 권고가 아니라 **불가능**하게 만드는 장치를 둔다. 그리고 틀린 키는 **에러가 아니라 조용한 빈칸**이다 | 05·06장 |
| **모델은 일반 코딩 지식을 이미 안다** | 스킬에 일반론을 적으면 기반 컨텍스트 예산만 먹는다 (`Skip generic coding knowledge`) | 05장 |
| **단위 테스트 실패는 에이전트에게 "다시 뽑기"일 뿐이다** | 사용자 경로를 판정 대상으로 두되, 순수 로직에는 단위 테스트를 **명세**로 쓴다 | 07장 |
| **뽑기(비결정성)는 격리 없이 전역에 퍼진다** | 폴더·파일·세션을 잘게 나눠 영향 범위를 좁힌다 | 06·07장 |
| **세션 로그는 시도·실패가 섞여 길다** | 결과만 담은 날짜별 리포트를 따로 남긴다 | 07장 |

## 이 지식이 판단에 쓰이는 자리

- **자기 구현을 시작할 때**: 이 표를 훑어 **자기 고객사 조건과 다른 줄**을 찾는다. 다른 줄이 있으면 그에 걸린 결정을 다시 내려야 한다.
- **견적을 낼 때**: "조건 하나 추가"처럼 보이는 것(사번 필터)이 실제로는 연동 작업인지 확인한다.
- **고객사 방문 전에**: 사내망·보안 절의 여섯 줄을 체크리스트로 쓴다. 헤더 이름 협의와 컨테이너 차단 여부가 특히 늦게 발견되면 비싸다.

### ⚠️ 암기 필수

- [ ] **순서는 환경 사실 → 결정 → 지시 → 검증이다.** 사실을 건너뛰고 결정하면 참조 구현을 베끼는 것이 되고, 조건이 다를 때 그 차이를 발견하지 못한다.
- [ ] **가장 늦게 발견되면 비싼 둘: 사내 방화벽의 헤더 감시(설치 당일 막힘) / 컨테이너 차단(배포 형태 전면 변경).**
