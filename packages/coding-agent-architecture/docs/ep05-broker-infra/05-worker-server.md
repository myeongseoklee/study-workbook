# 05. 워커 서버 — 기능을 추가한다는 것이 워커를 하나 더 띄운다는 뜻이 된다

## 학습 목표

워커가 무엇을 모르는지, 그 무지가 왜 "기존 코드를 한 줄도 안 건드리고 기능을 추가한다"로 이어지는지 설명할 수 있게 된다.

## 선수 지식

- 2장 — 한 요청이 도는 다섯 걸음
- 3장 — `set_vt` → `delete`의 신뢰 보정
- 4강 8장(워커 풀 정책, 취소는 코드 구조의 성질)

## 핵심 원리 (WHY) — 워커는 이 동네를 모른다

> 워커 서버는 아예 **이 동네를 몰라. 관심이 없어. 클라이언트도 관심이 없어** 얘는. 여기서 지가 작업할 거 있나 하고 읽어보고서 "아 이 이벤트 내가 처리해야겠는데" 그러면 가져가. 가져가면 지가 일을 다 하고서 완료해서 **결과물이 들어있는 이벤트를 다시 여기 등록하면서 가져갔던 작업을 이때 지우는** 거지. `[20:30–21:30]`

워커에게 세상은 큐 하나다. 클라이언트도, 브로커도, 소켓도 존재하지 않는다. 이 무지가 세 가지를 동시에 만든다.

| 워커가 모르는 것 | 그래서 생기는 것 |
|---|---|
| 요청을 누가 보냈는지 | 워커는 **상태 없는 프로세스**가 된다 → 교체·증설이 자유롭다 |
| 결과를 누구에게 보낼지 | **대기가 사라진다** — 놓기만 하면 끝이다 |
| 통신을 어떻게 하는지 | 워커 코드에 네트워크 코드가 없다 → **구현이 쉬워진다** (10장) |

## 필수 지식 (HOW) — 관심사별 배치가 곧 기능 배치다

> PGMQ에 있는 수많은 이벤트 중에 **워커 서버별로 지가 처리하고 싶은 것만** 처리한단 말이야. 1번 워커 서버는 이벤트 타입 1번부터 5번까지 처리하는데 2번 워커 서버는 이벤트 타입 A부터 Z까지 처리한단 말이야. `[17:30–18:00]`
>
> 끝없이 PGMQ에 새로운 타입의 이벤트를 넣으면 **기존에 아무런 아키텍처나 코드 한 줄 안 건드리고** 그 새로운 이벤트를 처리하는 **워커 서버만 추가**합니다. `[18:00–18:30]`

여기서 나오는 성질이 이 아키텍처의 실질적 이득이다.

| 하고 싶은 것 | 무엇을 하나 | 무엇을 안 건드리나 |
|---|---|---|
| 처리량 늘리기 | 같은 타입 워커를 여러 대 | 전부 |
| 새 기능 붙이기 | 새 타입 워커 한 대 + 클라이언트 쪽 해석 | 브로커 · PGMQ · 기존 워커 |
| 무거운 작업 격리 | 그 타입 워커만 큰 머신으로 | 전부 |
| 기능 끄기 | 그 타입 워커를 내린다 | 전부 (이벤트는 큐에 쌓인다) |

**마지막 줄에 함정이 있다.** 워커를 내리면 그 타입 이벤트는 처리되지 않은 채 큐에 남는다. 가시성 타임아웃이 반복해서 만료되며 계속 재배정 대상이 되므로, 기능을 진짜로 끄려면 **생산 쪽(클라이언트가 그 이벤트를 만드는 것)을 먼저 막아야** 한다. 소비만 끄는 것은 정지가 아니라 적체다.

## 필수 지식 (HOW) — 워커는 어디에 있어도 된다

> 이 워커도 이벤트 종류별로 수많은 워커를 둘 수 있고 **머신도 갈릴 수 있고 어차피 네트워크니까.** 여기도 다 다른 인스턴스로 머신을 갈릴 수가 있습니다. **PGMQ조차도 마찬가지예요.** `[21:30–22:00]`

워커의 유일한 의존은 "PGMQ에 접속할 수 있다"이다. 그래서 배치가 자유롭고, 4강 8장의 워커 풀(한 프로세스 안의 스레드 풀)과 이 장의 워커 서버(별도 프로세스·머신)가 **같은 개념의 두 축척**이 된다.

| 축척 | 무엇 | 한계 |
|---|---|---|
| 워커 스레드 (4강 8장) | 한 프로세스 안에서 진짜 병렬 | 메모리 격리 → 직렬화 비용 |
| 워커 서버 (이 장) | 프로세스·머신 단위 | 네트워크 비용, 배포 대상 증가 |

**둘 중 어디로 쪼갤지는 "무엇을 넘겨야 하는가"가 정한다.** 큰 인메모리 객체를 넘겨야 하면 스레드 쪽이 유리하고, 이벤트 봉투만 넘기면 되면 서버로 쪼개도 손해가 없다. 이 아키텍처는 후자를 전제로 설계되어 있다 — 오가는 것이 작은 이벤트뿐이기 때문이다.

## 필수 지식 (HOW) — 완료 처리는 "등록 + 삭제"가 한 쌍이다

> 결과물이 들어있는 이벤트를 다시 여기 등록하면서 **가져갔던 작업을 이때 지우는** 거지. `[21:00–21:30]`

순서가 중요하다. **새 이벤트를 먼저 쓰고, 그다음에 원본을 지운다.**

| 순서 | 중간에 죽으면 | 결과 |
|---|---|---|
| **등록 → 삭제** (채택) | 결과는 나갔는데 원본이 남는다 | 다른 워커가 재처리 → **중복** → 멱등이 흡수 |
| 삭제 → 등록 | 원본은 사라졌는데 결과가 안 나간다 | **유실** — 복구 경로가 없다 |

4강 6장의 "삭제 시점" 규칙이 완료 처리에서도 그대로 적용된다. 그리고 PGMQ에서는 이 둘을 **한 트랜잭션으로 묶을 수 있다**(3장) — 그러면 중복조차 줄어든다. 전용 브로커였다면 불가능한 선택지다.

### ⚠️ 암기 필수

- [ ] **워커는 클라이언트도 브로커도 통신 방법도 모른다.** 아는 것은 큐 하나뿐이고, 그래서 상태가 없고 교체·증설이 자유롭다
- [ ] 🔴 **기능 추가 = 새 타입 워커 한 대.** 브로커·PGMQ·기존 워커의 코드를 건드리지 않는다
- [ ] **워커를 내리는 것은 기능을 끄는 것이 아니라 적체시키는 것이다.** 진짜로 끄려면 생산 쪽을 먼저 막는다
- [ ] 🔴 **완료 처리는 "결과 등록 → 원본 삭제" 순서.** 뒤집으면 중복 대신 유실이 남고, 유실은 복구 경로가 없다
- [ ] **스레드로 쪼갤지 서버로 쪼갤지는 "무엇을 넘겨야 하는가"가 정한다.** 큰 인메모리 객체면 스레드, 작은 봉투면 서버

## 이 지식이 설계 판단에 쓰이는 자리

이벤트 기반 시스템에 기능을 붙일 때 확인할 것이 정해진다.

1. **새 이벤트 타입을 도입하는가, 기존 타입에 필드를 더하는가?** 새 타입이면 워커만 추가하면 되고, 필드 추가면 기존 워커와 클라이언트를 모두 고쳐야 한다. **후자가 훨씬 비싸다**
2. **이 워커가 죽으면 큐가 얼마나 빨리 차는가?** 생산 속도 × 평균 처리 시간으로 대략 나온다. 이 값이 큐 크기를 넘으면 워커 사망이 곧 전체 장애가 된다
3. **완료 처리의 두 연산이 한 트랜잭션인가?** 아니라면 그 사이에서 중복이 나온다는 것을 멱등 쪽에 명시적으로 알려 둔다
