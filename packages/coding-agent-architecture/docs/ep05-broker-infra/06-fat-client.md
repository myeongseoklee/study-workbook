# 06. 팻 클라이언트 — 서버가 단순해진 만큼 클라이언트가 두꺼워진다

## 학습 목표

이 아키텍처에서 클라이언트가 두꺼워지는 것이 부작용이 아니라 **필연**임을 설명할 수 있게 된다. 그리고 그 두께가 아키텍처 채택을 막는 실제 장벽이라는 것, 그런데 지금은 그 장벽이 낮아지고 있다는 관찰까지 잡는다.

## 선수 지식

- 2장 — 이벤트 타입이 곧 주소
- 4강 2장(CPS) — 클라이언트도 서버가 된다는 대목

## 핵심 원리 (WHY) — 페이로드만 오면 해석은 받는 쪽 몫이다

> 자기가 원하는 이벤트 채널에 있는 이벤트를 브로커한테 받으면 **그 이벤트 가지고 뭘 할지는 다 클라이언트에 구현되어 있어야 돼요.** 어떻게 보면 헤비 클라이언트야. 신 클라이언트가 아니라고. 왜냐하면 이 이벤트 브로킹 시스템에서는 클라이언트가 결국에는 **페이로드가 담겨있는 이벤트만 받는단 말이지.** 그 페이로드로 받아온 이벤트를 어떻게 처리할지는 다 클라이언트 책임이란 말이야. 그러니까 **팻 클라이언트가 될 수밖에 없는 거죠.** `[15:30–16:00]`

**"될 수밖에 없다"는 표현이 정확하다.** 서버가 상대를 모르기로 한 순간(1장), 서버는 상대에 맞춘 화면을 만들 수 없다. 만들려면 상대를 알아야 하고, 알면 상태가 생기고, 상태가 생기면 증설이 막힌다. 그러므로 **서버의 무지와 클라이언트의 두께는 같은 결정의 양면이다.**

| 서버가 보내는 것 | 클라이언트가 하는 것 |
|---|---|
| 렌더링된 HTML | 표시만 (신 클라이언트) |
| **이벤트 페이로드** | **해석 · 상태 조립 · 렌더링 전부** (팻 클라이언트) |

## 필수 지식 (HOW) — 두꺼워진 대가로 서버가 얻는 것

> HTML 같은 그런 거의 하드코어한 렌더링 로직이 다 포함되어 있는 걸 줄 필요도 없고 **그냥 이벤트 페이로드만 던지면 클라이언트가 알아서 하라는 건데. 당연히 좋겠죠.** `[16:30–17:00]`

서버 쪽 이득이 셋이다.

| 이득 | 왜 |
|---|---|
| 전송량이 작다 | 렌더링 결과가 아니라 데이터만 간다 |
| 서버가 화면을 모른다 | 화면이 바뀌어도 서버를 안 고친다 |
| **브로커가 무상태로 남는다** | 개인화할 것이 없으니 세션별 상태가 필요 없다 |

세 번째가 실질이다. 앞의 둘은 일반적인 API 설계의 이득이지만, 세 번째는 **4장의 확장성이 성립하는 전제**다.

## 필수 지식 (HOW) — 채택을 막는 것은 서버가 아니라 배포다

이 아키텍처가 대규모에 적합한데도 기업 시스템에서 드문 이유가 여기 있다.

> 초대형 규모의 시스템들은 이벤트 브로킹 시스템으로 만드는 게 제일 합리적인데 **많은 엔터프라이즈 시스템에서 그렇게 하기가 어려운 이유는** 그거죠. **팻 클라이언트를 만들어야 된다는 거죠.** 팻 클라이언트를 만들면 **웹에서 배포하기 어렵다**는 거. 그리고 앱 입장에서는 **앱 유지 보수비가 많이 드니까** 어떻게든 신 클라이언트를 만들려는 요즘 유행 때문에 그랬는데… `[19:00–19:30]`

| 팻 클라이언트의 비용 | 무엇이 어려워지나 |
|---|---|
| 번들이 커진다 | 웹 첫 로딩, 캐시 무효화 |
| 로직이 분산된다 | 같은 규칙을 서버·클라이언트 양쪽에 둘 위험 |
| **버전이 갈린다** | 사용자가 옛 클라이언트를 들고 있으면 이벤트 해석이 어긋난다 |
| 유지보수가 늘어난다 | 플랫폼별 클라이언트마다 해석 로직 |

세 번째가 가장 아프다. 이벤트 타입이 계약인데(4강 7장) 계약의 한쪽이 사용자 기기에 있으므로, **계약을 바꾸려면 배포가 끝나기를 기다려야 한다.** 서버만 고쳐서 되돌릴 수 있는 결정이 아니게 된다.

## 필수 지식 (HOW) — 그런데 지금은 유행이 되돌아왔다

> 요즘 신 클라이언트 추세에 비하면… **요즘 신 클라이언트 추세 맞아요? 이거 어마무시한 팻 클라이언트잖아. 코덱스, 클로드 코드 이런 애들 전부 다 엄청나게 팻 클라이언트잖아.** 얘네 다 러스트나 되게 큰 코드베이스로 돼 있단 말이야. `[16:00–16:30]`
>
> 유행은 돌고 돌아와서 **다시 팻 클라이언트 시대로 돌아오고 있기 때문에 괜찮아요.** `[19:30]`

**관찰의 값어치는 "코딩 에이전트가 이미 팻 클라이언트다"라는 사실에 있다.** 터미널에 설치되는 큰 바이너리를 사용자가 이미 받아들이고 있다면, 팻 클라이언트의 배포 장벽은 이 도메인에서 이미 지불된 비용이다. 즉 **에이전트 제품에서는 이 아키텍처의 최대 단점이 무료가 된다.**

이 판단은 도메인에 묶여 있으므로 그대로 옮기면 안 된다. 사내 웹 대시보드처럼 "URL만 주면 끝"이 요구인 제품에서는 장벽이 그대로 남는다.

### ⚠️ 암기 필수

- [ ] 🔴 **서버의 무지와 클라이언트의 두께는 같은 결정의 양면이다.** 서버가 상대를 모르기로 하면 상대에 맞춘 화면을 만들 수 없다
- [ ] **팻 클라이언트의 가장 아픈 비용은 번들 크기가 아니라 버전 분기다** — 계약의 한쪽이 사용자 기기에 있어 되돌리기가 어렵다
- [ ] **이 아키텍처의 채택 장벽은 서버 난이도가 아니라 클라이언트 배포다**
- [ ] **코딩 에이전트 도메인에서는 그 장벽이 이미 지불돼 있다** — 사용자가 큰 로컬 바이너리를 이미 설치하고 쓴다

## 이 지식이 설계 판단에 쓰이는 자리

이벤트 기반 구조를 제품에 얹을지 판단할 때 **배포 제약에서 시작하는 편이 빠르다.**

1. **클라이언트를 강제 업데이트할 수 있는가?** 가능하면(설치형 CLI·데스크톱 앱) 계약 변경이 감당된다. 불가능하면(웹·모바일 스토어) 이벤트 타입에 버전을 넣고 **구형 해석 경로를 유지할 각오**를 해야 한다
2. **같은 규칙이 서버와 클라이언트 양쪽에 생기지 않는가?** 생긴다면 그 규칙은 이벤트 페이로드에 결과로 실어 보내는 편이 낫다
3. **첫 로딩 시간이 제품 지표인가?** 그렇다면 팻 클라이언트의 이득이 상당 부분 상쇄된다
