# 07. 애플리케이션이란 이벤트 타입 협약이다 — 그래서 인프라는 다시 안 만든다

## 학습 목표

이 회차의 결론을 한 문장으로 잡는다. "애플리케이션을 만든다"가 이 구조에서 무엇을 뜻하는지 정의하고, 왜 인프라가 고정 자산이 되는지, 그 주장이 어디까지 참인지까지 안다.

## 선수 지식

- 2장 — 무지의 배치
- 5장 — 기능 추가 = 워커 추가
- 6장 — 클라이언트가 계약의 다른 한쪽이라는 사실

## 핵심 원리 (WHY) — 애플리케이션의 정의가 바뀐다

> 이 아키텍처 내에서 애플리케이션을 구현한다는 건 뭐예요? **클라이언트와 워커 서버 간의 특정 이벤트 타입을 인식하는 협약**을 맺었다는 거잖아. 이 둘 사이에 **이벤트 프로토콜이 성립했을 뿐**이지 이벤트 브로커나 MQ는 아예 어떤 이벤트인지조차도 관심이 없어. `[24:00–24:30]`

보통 "애플리케이션"은 서버와 클라이언트와 DB를 합친 것이다. 여기서는 다르다.

| | 애플리케이션에 속하는 것 | 인프라에 속하는 것 |
|---|---|---|
| 무엇 | 이벤트 타입 정의 · 워커 구현 · 클라이언트 해석 | 브로커 · PGMQ · 소켓 처리 · 신뢰 보정 |
| 누가 바꾸나 | 제품 팀 | **아무도** |
| 몇 개 있나 | 애플리케이션 수만큼 | **하나** |

> **여기는 영원히 재사용이다.** 영원히 재사용이야. 건들 것도 없단 말이죠. 그래서 이거를 한 판만 만들어놓으면 그다음은 이 시스템에 맞는 인터페이스에 맞춰서 얘만 만들고 얘만 만들면 항상 애플리케이션이 계속 만들어지겠죠. `[24:30–25:00]`

## 필수 지식 (HOW) — 더 센 주장: 인프라 인스턴스도 공유된다

코드 재사용이 아니라 **운영 중인 인스턴스의 재사용**이라는 점이 이 주장의 핵심이다.

> 더 무서운 게 뭐예요? **애플리케이션 종류가 여러 개가 늘어나도 이벤트 브로커와 PGMQ는 심지어 계속 똑같은 걸 유지해도 돼.** (…) 코드만 일치한다는 게 아니야. **이 인프라를 그대로 이용해서 1번 애플리케이션 운영해도 되고 2번 애플리케이션은 그 인프라로 똑같이 운영해도 된단 말이야.** 왜냐하면 워커만 달라지는 거니까. `[25:00–25:30]`
>
> 어떻게 보면 **사내의 모든 솔루션은 이 서버 군에다 다 밀어넣을 수도 있어.** 저는 요즘 그렇게 만들어요. `[25:30]`

**성립 근거는 2장의 무지다.** 브로커와 PGMQ가 이벤트의 의미를 모르므로, 서로 무관한 애플리케이션의 이벤트가 같은 큐를 지나가도 아무 일이 일어나지 않는다. 타입이 다르면 다른 채널이고, 다른 채널이면 서로 안 보인다.

## 필수 지식 (HOW) — 이 주장이 참인 범위

"영원히 재사용"은 강한 문장이므로 조건을 붙여 두어야 한다. 강의는 인프라 층이 애플리케이션을 모른다는 데까지 말했고, **모른다고 해서 영향이 없는 것은 아니다.**

| 공유해도 무관한 것 | 공유하면 서로 영향을 주는 것 |
|---|---|
| 이벤트의 의미 · 처리 로직 | **큐 테이블의 물리적 용량과 IO** |
| 워커의 구현·배포 주기 | **PGMQ 인스턴스의 커넥션 수** |
| 클라이언트의 화면 | **브로커 프로세스의 메모리·소켓 한도** |
| 애플리케이션별 장애 | **DB 장애 — 전부가 함께 멈춘다** |

**즉 논리적 격리는 완전하고 물리적 격리는 없다.** 사내 전체를 한 군집에 얹으면 폭발 반경이 사내 전체가 된다. 그래서 강의가 함께 준 수단이 있다 — 이벤트 타입에 따라 **PGMQ 인스턴스 자체를 나누는 것**(4장, `[14:00–14:30]`). 물리적 격리가 필요해지는 지점에서 쓰는 다이얼이 이미 설계 안에 있는 셈이다.

정리하면 이렇게 읽는 것이 정확하다.

> **재사용되는 것은 "설계와 코드"이고, 인스턴스 공유는 규모가 허락하는 동안의 선택지다.** 규모가 커지면 타입 기준으로 쪼개면 되고, 쪼개도 애플리케이션 코드는 그대로다.

## 필수 지식 (HOW) — 웹소켓이 이 이야기를 현실로 만들었다

> 요즘 다 웹소켓 되잖아요. 다 웹소켓을 연결하면 그만이거든요. 그래서 일반적인 테이블을 쓰는 거는 백엔드 서버가 있지, HTTP 통신하는. 근데 **주요한 애플리케이션 서버는 그냥 다 이벤트 브로커 웹소켓을 껴서 똑같은 인프라 위에서 워커들만 다르게 배치**해가지고 많은 애플리케이션을 그냥 만들어버려. `[25:30–26:00]`

여기서 두 종류의 트래픽이 갈린다. 이 구분이 실무에서 바로 쓰인다.

| 성격 | 경로 | 예 |
|---|---|---|
| 짧고 동기적이고 CRUD | 평범한 HTTP 백엔드 | 로그인, 목록 조회, 설정 저장 |
| 길고 비동기적이고 진행 상황이 있는 것 | **이벤트 브로커** | 에이전트 턴, 배치 작업, 스트리밍 |

**전부를 이벤트로 바꾸려 하지 않는다는 것이 요점이다.** 로그인 하나를 이벤트로 만들면 얻는 것 없이 왕복만 늘어난다.

### ⚠️ 암기 필수

- [ ] 🔴 **이 구조에서 "애플리케이션을 만든다" = 클라이언트와 워커 사이에 이벤트 타입 협약을 맺는다.** 브로커·MQ는 그 협약을 모른다
- [ ] 🔴 **인프라는 코드도 인스턴스도 재사용된다** — 애플리케이션이 늘어도 브로커·PGMQ는 같은 것을 쓴다. 근거는 "중간 계층이 의미를 모른다"
- [ ] ⚠️ **논리적 격리는 완전하지만 물리적 격리는 없다.** 용량·커넥션·DB 장애는 공유된다. 필요해지면 **이벤트 타입 기준으로 PGMQ를 쪼갠다**
- [ ] **전부를 이벤트로 바꾸지 않는다.** 짧고 동기적인 CRUD는 HTTP 백엔드에 남기고, 길고 진행 상황이 있는 것만 브로커로 보낸다

## 이 지식이 설계 판단에 쓰이는 자리

"사내 공용 이벤트 인프라"를 제안할 때 미리 정해 두어야 하는 것이 셋이다.

1. **어느 트래픽이 들어오고 어느 트래픽이 안 들어오는가?** 기준이 없으면 CRUD까지 밀려 들어와 왕복만 늘어난다
2. **쪼개는 기준을 언제 발동하는가?** "큐 지연이 N초를 넘으면 그 타입을 별도 PGMQ로 옮긴다" 같은 수치 기준을 미리 적어 둔다. 사고가 난 뒤에 정하면 이미 늦다
3. **누가 이벤트 타입을 소유하는가?** 타입이 계약이므로 이름 충돌과 하위 호환이 조직 문제로 올라온다. 네임스페이스 규칙을 첫날 정한다

3번을 미루면 인프라 공유의 이득을 **타입 충돌 조정 비용**이 잠식한다. 기술적으로는 아무 문제가 없는데도 그렇게 된다.

> 원본 근거 — 발화 `[23:30–26:00]`
