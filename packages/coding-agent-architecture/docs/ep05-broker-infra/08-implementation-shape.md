# 08. 실제로 도는 물건의 모양 — 도커 한 통, Express 하나, 라이브러리 하나

## 학습 목표

앞 장들의 설계가 실제 배치에서 어떤 모양이 되는지 잡는다. 특히 **하나의 Express가 웹 백엔드와 이벤트 브로커를 겸한다**는 선택과 **`agent` 패키지가 순수 라이브러리라는 경계**의 근거를 설명할 수 있어야 한다.

## 선수 지식

- 2강 10장(기술 스택) — 터보 모노레포·단일 Express 결정
- 3강 — 어드민에서 계정·조직·모델을 배정하는 화면
- 도커 기본 (컨테이너·볼륨·환경 변수)

## 핵심 원리 (WHY) — 실행 환경이 도커라는 사실이 사용자 경험을 정한다

> 지금 버전은 여러분의 PC에서 도는 게 아니기 때문에 **프로젝트 폴더도 PC에 설치될 수가 없겠죠.** (…) 이 프로젝트가 구동하고 있는 이 파일 어디다 썼어? 라고 물어보면 당연히 **도커 안에 썼겠지.** 서버가. **모든 프로젝트 파일은 다 도커 안에 써집니다.** `[29:30–30:00]`

**이것은 구현 세부가 아니라 제품 성격이다.** 코딩 에이전트가 웹에서 돌면 작업 결과물이 사용자 기기에 없다. 그러면 사용자는 결과를 어떻게 가져가는가 — 이 질문이 곧바로 따라오고, 5강 시점의 답은 **도커 볼륨**이다.

| 무엇 | 어디 |
|---|---|
| 워크스페이스(볼륨) | 컨테이너 밖 호스트에 마운트 |
| 세션 하나 | 워크스페이스 아래 **폴더 하나 = 프로젝트 루트 하나** |
| 프로젝트 파일 | 그 세션 폴더 안 |

> 요게 볼륨이야. 요게 이제 워크스페이스, 즉 **프로젝트의 루트 폴더**인 거죠. 이 루트 폴더의 세션마다 이런 식으로 자기 프로젝트 파일 공간이 생겨나는 거죠. 도커 안에. (…) **세션 하나가 프로젝트가 돼서** 그 밑에서 이제 파일을 만들고 있는 거죠. `[32:30–33:00]`

**"세션 하나 = 프로젝트 하나"가 이 시점의 격리 단위다.** 2강에서 세션이 KV 캐시 식별자였고, 여기서는 **파일 시스템 격리 단위**까지 겸한다. 세션이라는 개념에 책임이 하나 더 붙은 셈이다.

## 필수 지식 (HOW) — 하나의 Express가 셋을 겸한다

> 하나의 익스프레스 서버에서 둘 다 처리하기 때문에 익스프레스 서버가 **소켓 서버로서의 이벤트 브로커 역할도 하고 프론트의 백엔드 역할도 한꺼번에** 하기 때문에 **포트가 하나밖에 필요 없어서** 포트 하나로 이제 다 처리를 하는 거죠. `[30:00–30:30]`
>
> 저 같은 경우에는 이 프론트엔드도 따로 서버 안 띄우고 저 익스프레스 서버가 **프론트엔드도 서빙하고 백엔드도 서빙하고 동시에 웹소켓 서버를 서빙**한단 말이야. `[35:30–36:00]`

한 프로세스가 셋을 한다: 정적 프론트엔드 서빙 · HTTP 백엔드 · 웹소켓 이벤트 브로커.

| 얻는 것 | 잃는 것 |
|---|---|
| 포트 하나 — 방화벽·프록시 설정이 단순 | 셋의 부하가 한 프로세스에 섞인다 |
| CORS 문제가 없다 | 하나가 죽으면 셋이 같이 죽는다 |
| 배포 단위가 하나 | 브로커만 따로 증설하려면 분리부터 해야 한다 |

**이 선택은 온프레미스 납품과 짝이다.** 고객사 방화벽 안에 물건을 넣을 때 열어야 할 포트가 하나뿐이라는 것은 실제로 큰 값어치를 갖는다. 반대로 4장에서 본 "브로커를 수십 대로 늘린다"를 하려면 이 통합을 되돌려야 한다 — **지금은 개념 증명이므로 합쳐 두었고, 분리 지점이 어디인지는 이미 알고 있는 상태**로 읽는 것이 맞다.

## 필수 지식 (HOW) — `agent`는 순수 라이브러리이고 그 경계가 중요하다

모노레포 안에서 패키지의 성격이 둘로 갈린다.

> 지금 이 `packages`의 성격을 보면 **도메인이 붙은 애들은 `apps`에 실제로 그런 앱이 존재하고**, 이 앱에 있는 코어 로직을 `packages`에서 관리하려고 (…) 근데 그에 비해서 **이 `agent`는 순수한 라이브러리예요.** `[44:00–44:30]`
>
> 사실 여기 있는 `packages`에 있는 이 `agent`는 **완전 독립적인 라이브러리예요.** 얘 의존성을 보면 완전한 외부 의존성만 있잖아. 이거 완전히 뚝 떼어서 그냥 **라이브러리 하나랍니다. 다른 데 써도 돼.** `[43:30–44:00]`

| 패키지 성격 | 무엇 | 판별법 |
|---|---|---|
| **도메인 패키지** | `apps/`의 특정 앱에 딸린 코어 로직 | 그 앱이 없으면 의미가 없다 |
| **순수 라이브러리** (`agent`) | 브로커 구현 + 워커 인터페이스 | **의존성이 전부 외부다** |

**"의존성이 전부 외부인가"가 실행 가능한 판별식이다.** 사내 패키지를 하나라도 import하면 그것은 이미 이 제품에 묶인 코드이고, 다른 프로젝트로 떼어 갈 수 없다. 7장의 "인프라는 영원히 재사용"이 코드 수준에서 지켜지는 자리가 정확히 여기다 — **재사용 가능하다고 말하려면 의존성 그래프가 그것을 증명해야 한다.**

## 필수 지식 (HOW) — 라이브러리가 주는 것과 주지 않는 것

> `agent` 라이브러리가 보면 **브로커를 제공하고요. 브로커는 거의 완성되어 있는 거잖아. 가져다 쓰기만 하면 되잖아.** (…) 나머지 **워커에 대한 인터페이스만 제공하면 된단 말이에요. 워커는 구현체가 아니라** 이런 기본적인 워커 구현체, 워커 스레드를 어떻게 운영할 건지 — worker thread pool 어떻게 운영할 것인지에 대한 **기본 구현체만 주고** 실제로는 요거를 이제 구현을 해야 되는 거지. 각 애플리케이션에서. `[34:00–34:50]`

| 라이브러리가 주는 것 | 애플리케이션이 만드는 것 |
|---|---|
| 브로커 구현 (Express에 끼우면 소켓 서버가 된다) | 이벤트 타입 정의 |
| 워커 스레드 풀 운영의 기본 구현체 | **각 타입의 실제 처리 로직** |
| 워커 인터페이스 | 클라이언트의 해석·화면 |

**경계가 7장의 정의와 정확히 일치한다.** 라이브러리는 "의미를 모르는 부분"을 전부 가져가고, 애플리케이션에는 "의미를 아는 부분"만 남는다. 설계에서 그은 선이 패키지 경계로 그대로 내려온 것이다.

## 필수 지식 (HOW) — 코드 구성

> `common`에 보면 **프로토콜 정의**되어 있어서 여기에서 얘가 주고받는 **이벤트 타입들을 다 정의**를 이렇게 했겠죠. 그리고 여기에 **세션 정의**하고. `[36:30–37:00]`
>
> 서버 쪽 구현을 보면 LLM 쪽에 대한 지식이 필요하니까 **chat completion 어떻게 쓸 건지**에 대한 지식이나 **턴 루프 어떻게 운영할 건지**, 계속 이벤트 주고받는 걸로 돼 있죠. **세션 관리** 어떻게 할 건지, **DB** 어떻게 쓸 건지, 세션 정보 어떻게 불러올 건지. `[37:00–37:30]`

그리고 어드민 설정이 실제로 런타임에 작동한다 — 3강에서 만든 것이 여기서 쓰인다.

> 이 어드민에 써 있는 모델을 할당했기 때문에 걔가 이제 그 계정에 들어간 거야. (…) **이 계정에 조직을 할당하지 않으면 모델을 기본적으로 할당하는 애가 바로 들어가거든요.** `[31:30–32:30]`

어드민 계정 자체는 DB가 아니라 환경 변수에 있다 — 3강에서 정한 그대로다.

> 제가 어드민 계정은 **도커에 설정**한다고 전에 한번 말씀드렸죠. 누가 어드민이냐고 물어보면 **환경 변수에 설정**한다고 했죠. `[1:09:00–1:09:30]`

### ⚠️ 암기 필수

- [ ] **서버가 도커에서 돌면 작업 결과물이 사용자 기기에 없다.** 볼륨 마운트가 그 간극을 메우는 유일한 통로다
- [ ] **세션 하나 = 워크스페이스 아래 폴더 하나 = 프로젝트 루트 하나.** 세션이 KV 캐시 식별자(2강)에 더해 **파일 시스템 격리 단위**까지 겸한다
- [ ] **하나의 Express가 프론트 서빙 · HTTP 백엔드 · 웹소켓 브로커를 겸한다.** 얻는 것은 포트 하나, 잃는 것은 브로커만 따로 증설할 자유
- [ ] 🔴 **순수 라이브러리의 판별식은 "의존성이 전부 외부인가"다.** 사내 패키지를 하나라도 import하면 그 코드는 이미 이 제품에 묶여 있다
- [ ] **라이브러리는 "의미를 모르는 부분"을 전부 가져간다** — 브로커 구현과 워커 스레드 풀 기본 구현체. 애플리케이션에는 각 타입의 실제 처리 로직만 남는다

## 이 지식이 설계 판단에 쓰이는 자리

모노레포에서 패키지를 나눌 때 기준이 흐려지기 쉽다. 이 회차가 준 기준은 하나로 요약된다.

1. **이 패키지를 떼어서 다른 제품에 넣을 수 있는가?** 그 답을 의견이 아니라 **`package.json`의 의존성 목록**으로 확인한다
2. **못 떼어낸다면 그것이 의도인가?** 도메인 패키지는 못 떼는 것이 정상이다. 문제는 라이브러리라고 부르면서 못 떼는 경우다
3. **합쳐 둔 프로세스를 나중에 나눌 지점을 알고 있는가?** 개념 증명 단계에서 합치는 것은 정당한 선택이고, **나눌 선을 모르는 채 합치는 것**이 문제다
