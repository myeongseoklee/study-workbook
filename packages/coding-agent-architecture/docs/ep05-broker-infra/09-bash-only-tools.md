# 09. 도구를 bash 하나로 좁히고, 넓히는 일은 스킬에게 맡긴다

## 학습 목표

"도구를 많이 주면 유능해진다"는 직관이 왜 뒤집히는지 설명할 수 있게 된다. 그리고 도구·스킬·CLI 셋이 각각 어떤 자리를 맡는지 구분할 수 있어야 한다.

## 선수 지식

- 1강 3장(도구 = 제어권 / 전용 vs 범용) — 이 장은 그 트레이드오프에서 한쪽을 **실제로 골라 본** 기록이다
- 1강 4장(훅)

## 핵심 원리 (WHY) — 도구 수는 능력이 아니라 제어권 배분이다

1강에서 이미 두 방향이 있다고 했다. 5강은 그중 한쪽을 실제로 택한다.

> 전에 말했던 그 **도구 구현에 두 가지 방향**이 있다고 했죠. **코덱스는 셸로 다 처리**하는데 **앤트로픽 애들은 엄청 많이 도구를 준다**고. 그래서 저도 이번 거는 **bash로만 도구를 주고요.** `[39:00]`
>
> 요즘은 다 터미널 벤치 돌릴 정도로 **도구 사용할 때 터미널 사용에 대해서 많이 학습하고 나오잖아요.** 제 생각에는 **쓸데없이 많은 도구를 주는 거보다** 이번에는 bash만 쓰는 애를 만들어 써보려고 해요. `[40:00]`

**근거가 "요즘 모델은 터미널을 잘 쓴다"는 관찰이다.** 즉 이 선택은 모델 역량에 대한 베팅이고, 모델이 약하면 반대 방향(전용 도구 다수)이 옳다. 1강의 트레이드오프가 그대로 살아 있다 — **전용 도구는 약한 모델의 실수를 줄이고, 범용 셸 하나로 비비려면 강한 모델이 필요하다.**

## 필수 지식 (HOW) — 셋으로 나뉜 자리

도구를 하나로 줄이면 나머지 기능은 어디로 가는가. 강의는 셋으로 나눈다.

| 층 | 무엇 | 언제 쓰나 |
|---|---|---|
| **도구(tool)** | `bash` 하나 | 모델이 직접 호출하는 유일한 통로 |
| **스킬(skill)** | *"파일을 찾을 땐 이런 스킬을 써라"* | 절차·관례를 문장으로 주는 것 |
| **전용 CLI** | 내밀한 기능을 커맨드로 감싼 것 | 셸에서 부를 수 있게 만든 능력 |

> 이번 에이전트는 **bash만 넣어줄 거거든요. 나머지는 다 스킬로 때울 거야.** "파일을 찾을 땐 이런 스킬을 써라, 파일을 쓸 때는 이런 스킬을 써라." 그리고 이제 내밀한 어떤 기능이 필요하면 걔를 **커맨드 프롬프트용 CLI 툴로 만들어서 제공**하지. `[38:30–39:00]`
>
> 나머지들은 더 유연하게 **스킬로 기능들을 제공하는 거죠.** "파일 찾을 때는 스킬에 있는 이 스크립트로 bash로 돌려라." `[40:00–40:30]`

**세 층의 차이는 "무엇이 모델의 스키마에 들어가는가"다.**

| | 스키마에 올라오나 | 늘리면 무엇이 늘어나나 |
|---|---|---|
| 도구 | **올라온다** | 매 요청의 고정 토큰 · 선택지 혼란 |
| 스킬 | 안 올라온다 (필요할 때 읽힌다) | 파일 · 문서 |
| CLI | 안 올라온다 | 설치물 |

도구를 하나로 줄이면 **매 요청에 실리는 고정 비용이 최소가 되고**, 능력은 스킬과 CLI로 얼마든지 늘릴 수 있다. 이것이 이 선택의 실질적 이득이다.

## 필수 지식 (HOW) — bash 도구의 실체

> 지금 bash 툴 실행하는 거 보면 **spawn 뜨는 거 보이시죠. spawn은 Node.js에서 프로세스 띄우는 거거든요.** 그래서 bash 프로세스 띄우고 — 저는 도커니까 도커는 기본적으로 리눅스 환경이니까 **bash가 무조건 있잖아요** — 이거 띄워서 이 프로세스 하에서 이제 **프라미스로 말아서 비동기로 처리해서 타임아웃 처리도 하고 finish 처리도 하고 표준 입출력 통해서 메시지 주고받고** 이렇게 하는 거죠. `[39:00–39:30]`

정리하면 도구 하나의 구현이 이 정도다.

```
모델이 bash 도구 호출
   ↓
Node.js spawn 으로 bash 프로세스 생성
   ↓  표준 입출력으로 주고받음
Promise 로 감싸 비동기 처리
   ↓
타임아웃 처리 · 종료 처리
   ↓
결과를 모델에게 반환
```

**도커 전제가 여기서 값을 한다.** 실행 환경이 리눅스 컨테이너로 고정돼 있으므로 "bash가 있는가"를 따질 필요가 없다. 8장에서 본 도커 전제가 도구 설계까지 단순하게 만든 것이다. 반대로 사용자 PC에서 도는 에이전트였다면 셸 종류·경로·인코딩을 전부 다뤄야 한다.

## 필수 지식 (HOW) — 5강 시점에 없는 것

> 아직 **스킬 같은 건 구현도 안 되고 훅도 구현 안 되죠.** 이런 것들은 이제 차근차근 고급 기능 구현이라는 편에서 실제로 하나씩 하나씩 구현을 해보겠습니다. **이거 아직 멀었어.** `[40:30–41:00]`

**설계는 정해졌고 구현은 없다.** 그래서 이 장은 "이렇게 만들었다"가 아니라 "이렇게 만들기로 했다"로 읽어야 한다. 스킬을 어떻게 로딩하고 언제 컨텍스트에 넣을지 — 그 결정들은 아직 남아 있다.

### ⚠️ 암기 필수

- [ ] **도구 수는 능력이 아니라 제어권 배분이다.** 전용 도구 다수는 약한 모델의 실수를 줄이고, 셸 하나는 강한 모델을 전제한다
- [ ] 🔴 **도구·스킬·CLI를 가르는 기준은 "모델의 스키마에 올라오는가"다.** 도구만 올라오므로 도구를 늘리면 매 요청의 고정 비용과 선택지 혼란이 함께 늘어난다
- [ ] **bash 하나 + 스킬로 넓히기 = 고정 비용을 최소화하면서 능력은 무한히 늘리는 배치**
- [ ] **bash 도구의 실체는 `spawn` + Promise + 타임아웃 + 표준 입출력이다.** 실행 환경이 컨테이너로 고정돼 있어 셸 존재를 따질 필요가 없다

## 이 지식이 설계 판단에 쓰이는 자리

에이전트에 새 능력을 붙일 때 순서가 생긴다.

1. **이것이 매 요청마다 후보로 보여야 하는가?** 아니라면 도구가 아니라 스킬이다. 대부분은 "아니오"다
2. **모델이 인자를 정확히 맞춰야 하는가?** 그렇다면 전용 도구의 스키마 검증이 값을 한다. 셸 명령 문자열은 검증이 없다
3. **우리 모델이 이 정도 터미널 조작을 안정적으로 하는가?** 온프레미스에서 작은 모델을 쓴다면 답이 달라진다 — **이 선택은 모델 등급에 딸려 있다**

3번이 중요하다. 같은 제품을 강한 클라우드 모델과 작은 로컬 모델로 모두 굴려야 하면, **도구 구성이 모델에 따라 달라져야 할 수도 있다.**
