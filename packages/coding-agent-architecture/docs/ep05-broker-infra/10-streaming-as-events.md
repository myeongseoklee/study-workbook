# 10. 스트리밍은 기능이 아니라 이벤트를 자주 넣는 일이다

## 학습 목표

이 아키텍처에서 스트리밍이 어떻게 성립하는지 그릴 수 있게 된다. 그리고 "워커가 통신을 모른다"는 성질이 구현 난이도에 실제로 어떤 차이를 만드는지 — 그리고 그 대신 무엇이 공짜가 아닌지 — 를 안다.

## 선수 지식

- 5장 — 워커는 결과를 "누구에게"가 아니라 "어디에" 놓는다
- 4장 — 브로커가 로그를 커서로 따라 읽는다
- 9장 — bash 도구가 표준 출력을 계속 뱉는다

## 핵심 원리 (WHY) — 통신을 모르는 것이 구현을 쉽게 만든다

> 뭐 지가 하고 싶은 게 있으면 **이벤트로 말아서 여기 넣는 것밖에 안 하는 거야.** 여기 구현이 되게 쉬워져. 워커 구현이. 이런 애들 다 모르니까. 몰라. 관심 없어. (…) **AI 쓰면 스트리밍 데이터가 들어왔든, 도구 쓰면서 표준 출력이 들어왔든 아무 생각도 없어. 그냥 다 이벤트로 여기다 쏘는 거야.** 그러니까 구현이 쉬워. `[42:30–43:30]`

**서로 다른 출처의 진행 상황이 하나의 동작으로 수렴한다.** 이것이 이 설계의 실질적 이득이다.

| 무엇이 발생하나 | 워커가 하는 일 |
|---|---|
| LLM이 토큰 스트림을 보냈다 | 이벤트로 말아 큐에 넣는다 |
| bash가 표준 출력 한 줄을 뱉었다 | 이벤트로 말아 큐에 넣는다 |
| 도구가 에러를 냈다 | 이벤트로 말아 큐에 넣는다 |
| 턴이 끝났다 | 이벤트로 말아 큐에 넣는다 |

워커 코드에는 소켓도, 연결 관리도, "이 사용자가 아직 붙어 있나" 확인도 없다. **네 가지 사건이 코드에서 같은 모양이 된다.**

## 필수 지식 (HOW) — 스트리밍의 경로

> 중간중간에 이 출력을 준 거를 **이벤트로 말아서** 얘한테 꽂으면, 이 이벤트가 클라이언트가 원하는 이벤트면 이벤트 브로커가 가져가고 이걸 얘한테 쏘는 걸 **계속 반복해서** 이쪽에 스트리밍이 일어나는 거란 말이지. **스트리밍 원리가 그거야.** `[42:00–42:30]`

```
LLM / bash  ──(부분 출력)──▶  워커  ──(이벤트 write)──▶  PGMQ
                                                          │
                                                    (커서 tail)
                                                          ▼
클라이언트  ◀──(소켓 push)──  이벤트 브로커
```

**스트리밍이 별도 기능이 아니다.** 한 번에 하나씩 오던 결과 이벤트를 여러 개로 쪼개 넣는 것뿐이고, 나머지 경로는 이미 있는 것을 그대로 쓴다. 4장에서 결과 경로를 **로그 tail**로 잡아 둔 것이 여기서 값을 한다 — 커서 기반이라 이벤트가 촘촘히 들어와도 브로커끼리 경합하지 않는다.

## 필수 지식 (HOW) — 그런데 아직 없다

이 대목을 빼면 자료가 사실과 어긋난다. 5강 시점에서 스트리밍은 **설계만 있고 구현이 없다.**

> 지금 이 bash 도구의 실제 실행을 보면 (…) 얘 out을 보면 **`onData`를 받아서 표준 출력에다가 이렇게 넣기만 하지 스트리밍이 되는 것도 아니고**, 얘가 중간에 스트리밍 이벤트를 받을 때마다 이벤트를 생성해서 PGMQ에 넣어줘야지만 그거를 이벤트 브로커가 들고 가서 클라이언트한테 스트리밍하면서 "아 지금 bash가 실행 중입니다, bash가 무슨 커맨드를 보내는데 이랬대요 저랬대요" 이런 게 준비가 될 거 아니에요. **그런 기능은 하나도 없잖아요. 그거 다 만들어야 돼. 공짜가 아니야.** `[41:00–41:30]`

**"공짜가 아니야"가 이 장의 정직한 결론이다.** 아키텍처가 스트리밍을 **가능하게** 만든 것이지 **제공한** 것이 아니다. 실제로 해야 할 일이 남아 있다.

| 남은 일 | 왜 사소하지 않은가 |
|---|---|
| 부분 출력마다 이벤트 생성 | 이벤트 수가 폭증한다 — 배치·스로틀 정책이 필요하다 |
| 이벤트 타입 설계 | "부분 출력"과 "완료"가 다른 타입이어야 클라이언트가 구분한다 |
| 순서 보장 | 4강 3장의 `sequence`가 여기서 실제로 필요해진다 |
| 클라이언트의 조립 | 부분들을 이어 붙여 화면을 만드는 로직 (6장의 두께) |

첫 줄이 특히 그렇다. 토큰 하나마다 이벤트를 만들면 큐가 곧바로 병목이 된다. **스트리밍을 붙이는 순간 "이벤트 하나의 알갱이 크기"라는 새 설계 변수가 생긴다.**

## 필수 지식 (HOW) — 프로세스 통신은 단방향이다

> bash하고 워커 사이에 프로세스 통신을 하잖아요. 얘가 **끝없이 통신할 수 있어. 계속 출력을 줄 수… 통신은 아니고 1방향이죠.** `[42:00]`

도구에서 워커로 오는 흐름은 단방향(출력)이다. 그래서 진행 상황은 흘려보낼 수 있지만, **실행 중인 명령에 개입하는 것**(중단·입력 주입)은 별도의 장치가 필요하다. 4강 8장의 결론이 여기 붙는다 — **취소 가능성은 런타임 기능이 아니라 코드 구조의 성질이다.**

### ⚠️ 암기 필수

- [ ] 🔴 **스트리밍은 별도 기능이 아니라 결과 이벤트를 잘게 쪼개 자주 넣는 것이다.** 경로는 이미 있는 것을 그대로 쓴다
- [ ] **워커가 통신을 모르기 때문에 LLM 스트림·도구 출력·에러·완료가 코드에서 같은 모양이 된다**
- [ ] ⚠️ **아키텍처는 스트리밍을 가능하게 했을 뿐 제공하지 않았다.** 이벤트 생성·타입 설계·순서 보장·클라이언트 조립이 남는다
- [ ] 🔴 **스트리밍을 붙이는 순간 "이벤트 하나의 알갱이 크기"가 새 설계 변수로 등장한다.** 토큰마다 이벤트를 만들면 큐가 병목이 된다
- [ ] **도구 → 워커는 단방향이다.** 진행 상황은 흘려보내지만 실행 중 개입은 별도 장치가 필요하다

## 이 지식이 설계 판단에 쓰이는 자리

진행 상황을 사용자에게 보여줘야 하는 기능을 붙일 때 물을 것.

1. **한 이벤트에 얼마를 담을 것인가?** 토큰 단위인지, 줄 단위인지, 100ms 배치인지. 이 결정 하나가 큐 부하와 체감 반응성을 동시에 정한다
2. **부분과 완료를 다른 타입으로 둘 것인가?** 같은 타입에 플래그를 넣으면 클라이언트가 매번 분기해야 하고, 중간 이벤트를 놓쳤을 때 복구가 어려워진다
3. **순서가 어긋나면 무엇이 깨지는가?** 텍스트 이어 붙이기라면 치명적이다. 이때 4강의 `sequence`가 장식이 아니라 필수가 된다
