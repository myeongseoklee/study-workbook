# 11. 모델을 고르기 전에 알아야 하는 세 가지 해부학 — MTP · QAT · 멀티모달

## 학습 목표

로컬 모델 카탈로그를 읽을 때 이름과 크기만 보지 않게 된다. 같은 이름에 왜 크기가 여러 개인지, 왜 어떤 4비트는 쓸 만하고 어떤 4비트는 못 쓰는지, 그리고 **원본이 멀티모달인데 튜닝본은 아닐 수 있는** 이유를 설명할 수 있어야 한다.

## 선수 지식

- 1강 6장(온프레미스 로컬 LLM) — 200B·Q5 하한, KV 캐시
- 2강 1장(세션의 정체 = KV 캐시) — 12장에서 다시 쓰인다

## 핵심 원리 (WHY) — 모델 파일은 한 덩어리가 아니다

이 장의 셋은 서로 다른 이야기처럼 보이지만 하나의 사실에서 나온다. **모델 파일은 여러 부품의 묶음이고, 부품은 따로 붙이고 뗄 수 있다.**

| 부품 | 무엇 | 떼면 |
|---|---|---|
| 본체 웨이트 | 언어 모델 | — |
| **MTP 웨이트** | 다음 토큰 여러 개를 앞질러 제안하는 별도 모델 | 속도가 준다 |
| **이미지·오디오 인코더** | 멀티모달 입력을 처리하는 타워 | **텍스트 전용 모델이 된다** |

그래서 카탈로그에서 같은 이름·같은 양자화인데 크기가 다른 파일을 보게 되고, 그 차이가 성능 차이가 아니라 **부품 구성의 차이**인 경우가 많다.

## 필수 지식 (HOW) — MTP와 추측 디코딩

**추측 디코딩(speculative decoding)**은 작고 빠른 모델이 다음 토큰 여러 개를 미리 제안하고, 본체 모델이 그것을 **한 번에 검증**하는 기법이다. 검증은 생성보다 싸므로 제안이 맞을수록 빨라진다. 제안자로 별도의 작은 모델(draft model)을 쓰는 방식과, 본체에 딸린 전용 웨이트를 쓰는 방식이 있고 후자를 **MTP(Multi-Token Prediction)**라 부른다.

> MTP가 있는 모델들은 스페큘러티브 디코딩 할 때… **MTP도 별도의 모델이에요.** 모델 뒤에 붙어 있는 스페큘러티브를 하기 위한 **별도의 웨이트**거든요. `[46:30–47:00]`
>
> 보통 똑같은 양자화 모델 받아도 **MTP가 붙어 있으면 더 커요. 보통은 0.2GB에서 1GB까지** 클 때도 있고. `[47:30]`

**설정은 둘이다** — 한 번에 몇 개를 제안할지(최대·최소)와, 어느 정도 비슷하면 채택할지(임계).

> 보통 **맥스 2, 민 0**으로 놓으시면 돼요. **2 이상 해보면 비용만 많이 증가**하고. `[48:00]`

왜 많이 제안하는 것이 손해인가 — **앞에서부터 채택되기 때문이다.**

> 한 번에 몇 개씩 토큰을 추천할래, 이거야. (…) 이 추천이 많아져 봤자 **5개를 추천했으면 추천한 것 중에 첫 번째 거에서 까이면 이 4개를 다 버려야 돼요.** (…) 앞에서부터 까인단 말이야. 그럼 뒤가 다 버려져야 돼. `[48:30–49:00]`

```
제안 5개:  [t1][t2][t3][t4][t5]
t1 거부  →  t2~t5는 t1을 전제로 만든 것이므로 전부 무효
           →  5개 만든 비용 중 4개가 낭비
```

**기대 이득이 제안 길이에 선형으로 늘지 않는다.** 각 토큰의 채택 확률을 p라 하면 k개를 다 쓸 확률은 대략 pᵏ로 줄어드는 반면 비용은 k에 비례해 는다. 그래서 최적 k가 작다 — 실무에서 2~3이다.

**채택 임계는 품질을 파는 다이얼이다.**

> 0.75는… 이게 성능을 높이려면 여기를 4로 두고 (…) **출력 품질은 낮아지고 속도는 빨라지거든요.** (…) **0.75면 원래 모델을 100으로 봤을 때 75%만 비슷하면 채택하겠다**는 거거든요. 그러면 최악의 성능에서는 **75%의 품질밖에 안 나올 수도 있는 거야.** `[48:30]` `[49:00–49:30]`

그리고 기대치를 낮춰 둔다.

> 요런 것들을 조정하면 약간 빨라져요. **기대하신 거 "좀 두 배 빨라져" 이런 거 없고요. 10%, 20% 약간 빨라지고 이 정도가 거의 최선의 옵션이에요.** `[49:30]`

> **설정 이름은 도구·버전에 따라 다르다.** LM Studio는 추측 디코딩을 사이드바에서 초안 모델 선택으로 노출하고, MTP 초안 길이 관련 설정은 버전에 따라 이름과 위치가 바뀐다 ([공식 문서](https://lmstudio.ai/docs/app/advanced/speculative-decoding)). **외울 것은 필드 이름이 아니라 "길이는 짧게, 임계는 함부로 낮추지 않는다"는 규칙이다.**

## 필수 지식 (HOW) — QAT와 PTQ

양자화에는 순서가 다른 두 방식이 있다.

| | **PTQ** (post-training quantization) | **QAT** (quantization-aware training) |
|---|---|---|
| 언제 양자화하나 | 학습이 끝난 모델을 나중에 낮은 정밀도로 변환 | **학습 중에 양자화 오차를 흉내 내며** 학습 |
| 모델이 아는 것 | 반올림 오차를 겪어 본 적이 없다 | 오차에 견디도록 가중치가 자리 잡았다 |
| 4비트 품질 | 저비트로 갈수록 뚜렷하게 떨어진다 | 같은 4비트에서 눈에 띄게 낫다 |
| 크기 선택 | 2·3·4·5·6·8비트 등 자유롭게 | **정해진 것만** (보통 4·8비트) |

> QAT 붙은 애들은 **양자화 사이즈가 정해져 있어요. 4비트, 8비트 이렇게 딱 정해져 있어. 3비트, 2비트 이런 거 없고.** 왜냐하면 QAT라는 건 **모델을 처음부터 학습시킬 때 양자화를 고려해서 학습시키는** 애들이야. PTQ라는 애들은 보통 우리가 알고 있는 양자화 모델은 **멀쩡한 모델을 양자화시키는** 거거든요. `[50:00–50:30]`

**크기 선택지가 좁은 것이 결함이 아니라 방식의 귀결이다.** 학습 시점에 목표 비트를 정해 놓았으므로 임의 비트로 다시 뽑을 수가 없다.

품질은 어느 정도인가 — 강의자는 조심스럽게 말한다.

> 양자화했음에도 불구하고 원래 모델하고 성능이 비슷하게 나올 리가 있냐? 없지만 아무튼 꽤 높은 성능이 나와. **PTQ보다는 높게 나와요. 똑같은 4비트라도 훨씬 더 높게** 성능이 잘 나오는 거죠. `[50:30]`
>
> **6비트에서 8비트 정도의 성능이 나오는 것 같더라고요. 그것도 모델 따라 달라요.** (…) 안 그랬으면 세상이 다 이 QAT 양자화 모델이었겠지. 근데 실제로는 **잘 안 돼. 성능이 그렇게까지 좋지 않아요. 자랑하는 것만큼.** `[52:00]`

**"자랑하는 것만큼은 아니다"를 함께 외운다.** QAT라고 적혀 있으면 같은 비트의 PTQ보다는 낫다고 보되, 한 단계 위 비트와 같다고 가정하지는 않는다.

> **외부 근거**: Google은 2026년 6월 Gemma 4 계열의 QAT 체크포인트를 공개하면서 Q4_0 형식과 모바일 전용 형식을 함께 배포했고, QAT 결과가 표준 PTQ 기준선보다 전반적 품질이 높다고 밝혔다 ([공식 블로그](https://blog.google/innovation-and-ai/technology/developers-tools/quantization-aware-training-gemma-4/)). **"QAT는 같은 비트에서 PTQ보다 낫다"는 방향은 공개 자료로 뒷받침되고, "몇 비트에 해당하는가"는 모델마다 다르다.**

## 필수 지식 (HOW) — 멀티모달은 별도 모듈이다

이 대목이 실무에서 가장 자주 사람을 놀라게 한다.

> 이게 그 모델이 원래 원본 모델이 멀티모달을 지원한다고 해도 **멀티모달은 별도의 모듈이에요. 별도의 모듈이야.** `[58:30]`
>
> 원래 얘가 31B 모델인데 이 중에 **오디오 인코더 파라미터가 300M이고 비디오 인코더 파라미터는 150M**이라고. (…) **이걸 배제하면 텍스트 전용 모델이 되는 거야.** 그러니까 이거 튜닝하는 애들이 모델을 다시 재튜닝하면서 **멀티모달 기능을 삭제할 수도 있단 말이지. 얼마든지.** `[59:00]`
>
> 안에 보면 **이미지 타워하고 오디오 타워하고 따로 있어서 빼면 빼져요.** 그래서 원래 모델이 멀티모달을 지원해도 튜닝하면서 **얼마든지 빼거나 없앨 수도 있고.** `[59:30]`

> 위 파라미터 수치는 강의자가 화면의 모델 카드를 읽은 예다 `[59:00]`. **외울 것은 수치가 아니라 "인코더가 본체와 분리되어 표기되고, 튜닝본에서 빠질 수 있다"는 구조다.**

**그리고 이것이 코딩 에이전트에서는 치명적이다.**

> 이 단점이 뭐냐면 이 놈은 망치만 있고 **눈깔이 없잖아요. 멀티모달이 아니야. 이미지가 안 돼. 그래서 스크린샷 던지기가 안 되는 게 바이브 코딩한테 나쁜 점**인데… `[45:00]`
>
> 그러면 우리 바이브 코딩으로 만들 때 **스크린샷 던지기가 안 되잖아. 너무 괴롭잖아.** `[56:00–56:30]`

**"스크린샷을 던질 수 있는가"가 코딩 에이전트 모델 선택의 1차 필터다.** UI를 보고 고치는 작업이 코딩 에이전트 사용의 큰 몫이므로, 텍스트 성능이 아무리 좋아도 여기서 걸리면 후보에서 빠진다. 그리고 원본이 멀티모달이어도 **튜닝본은 확인해 봐야 한다.**

## 필수 지식 (HOW) — 튜닝본을 읽는 법

카탈로그의 상당수가 소수의 베이스 모델을 튜닝한 것이다.

> 특별한 모델이 아니고요. **아키텍처를 보면** 뭐다? (…) **모의(MoE) 모델 기반의 아키텍처를 튜닝한 모델일 뿐이야. 이게 튜닝 업체야.** `[56:30–57:00]`
>
> 이렇게 수동 튜닝하는 애들은 **뭔가 이빨이 빠져 있어.** `[58:30]`

그래서 카드에서 확인할 것이 정해진다.

| 확인 항목 | 왜 |
|---|---|
| **아키텍처** | 무엇을 튜닝한 것인지 — 베이스의 성질을 물려받는다 |
| **인코더 유무** | 멀티모달이 남아 있는지 |
| **MTP 동봉 여부** | 같은 이름의 파일 크기 차이를 설명한다 |
| **QAT 표기** | 같은 비트에서 품질 기대치를 올려 잡을 근거 |
| **아이콘 표기** | 리즈닝 · 도구 사용 특화 · 멀티모달 여부가 뱃지로 표시되는 카탈로그가 많다 `[56:00]` |

### ⚠️ 암기 필수

- [ ] 🔴 **모델 파일은 본체 + MTP 웨이트 + 인코더 타워의 묶음이다.** 같은 이름·같은 비트인데 크기가 다르면 대개 부품 구성 차이다
- [ ] **MTP 초안 길이는 2 정도가 최선.** 앞에서부터 채택되므로 첫 토큰이 거부되면 뒤가 전부 버려진다 — 비용은 k에 비례하고 이득은 pᵏ로 줄어든다
- [ ] **채택 임계(예: 0.75)를 낮추면 속도는 오르고 품질이 그만큼 내려간다.** 최악의 경우 원 모델 대비 그 비율까지 떨어질 수 있다
- [ ] **추측 디코딩의 현실적 기대치는 10~20%다.** 두 배는 없다
- [ ] 🔴 **QAT는 학습 시점에 양자화를 고려한 것이라 비트 선택지가 좁다(보통 4·8).** 같은 비트의 PTQ보다 낫지만 **한 단계 위 비트와 같다고 가정하지 않는다**
- [ ] 🔴 **멀티모달은 별도 모듈이라 튜닝본에서 빠질 수 있다.** 원본이 멀티모달이어도 그 튜닝본은 아닐 수 있다
- [ ] **코딩 에이전트 모델 선택의 1차 필터는 "스크린샷을 던질 수 있는가"다**

## 이 지식이 설계 판단에 쓰이는 자리

온프레미스 납품에서 모델 후보를 좁힐 때 순서가 있다.

1. **멀티모달인가** — 아니면 코딩 에이전트 후보에서 제외 (그 튜닝본까지 확인한다)
2. **도구 사용에 특화됐는가** — 9장에서 도구를 bash 하나로 좁혔다면 터미널 조작 능력이 곧 제품 품질이다
3. **QAT가 있는가** — 있으면 같은 VRAM에서 한 단계 나은 품질을 기대할 근거가 생긴다
4. **MTP가 동봉되는가** — 붙이면 0.2~1GB 더 쓰고 10~20% 빨라진다. **VRAM이 빠듯하면 이 교환이 성립하지 않는다**

4번은 12장의 용량 산수와 직접 부딪힌다. 속도를 위해 1GB를 쓰는 것이 옳은지는 남은 여유가 정한다.
