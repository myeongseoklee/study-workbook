# 00. 개요 — CloudFormation 템플릿 두 장을 끝까지 읽기

## 이 자료가 목표로 하는 상태

당신 앞에 YAML 파일 두 개가 있다. 하나는 약 570줄로 서비스 하나를 통째로 세우고, 다른 하나는 약 100줄로 배포 권한만 만든다. 지금은 `!Ref`가 무슨 뜻인지, `TargetGroup`이 왜 필요한지, 롤이 왜 두 개인지 모르는 상태다.

이 자료를 끝내면 다음이 가능해진다.

1. **모든 줄을 소리 내어 설명할 수 있다.** "이 리소스는 무엇이고, 없으면 무엇이 깨지는가"에 답할 수 있다.
2. **속성값의 근거를 말할 수 있다.** `MinimumHealthyPercent: 100`이 왜 100인지, `deregistration_delay`를 왜 30초로 줄였는지, `TreatMissingData: breaching`이 왜 저 알람에만 붙었는지.
3. **바꿔도 되는 것과 건드리면 안 되는 것을 구분할 수 있다.** 어떤 속성은 값만 바뀌고, 어떤 속성은 리소스를 삭제·재생성하며, 어떤 속성은 실서비스를 멈춘다.
4. **증상에서 원인을 역추적할 수 있다.** "태스크가 unhealthy로 계속 교체된다", "`/health`는 200인데 API는 500이다", "스택 삭제가 멈췄다" 같은 상황에서 어디를 볼지 안다.

## 무엇을 모르는지부터 정리

"뭘 모르는지 모른다"는 상태의 정체는 보통 **층이 섞여 있어서** 생긴다. 이 템플릿에는 성격이 다른 일곱 층이 한 파일에 들어 있고, 각 층은 다른 회사가 만든 다른 서비스다.

| 층 | 답해야 하는 질문 | 문서 |
|---|---|---|
| **선언 도구** | 이 YAML은 누가 읽고 무엇을 하는가? 두 번 실행하면? | [01](01-iac-and-cloudformation.md) |
| **네트워크** | 이 컨테이너는 어느 IP를 갖고, 누가 말을 걸 수 있는가? | [02](02-network-vpc-sg.md) |
| **트래픽 입구** | 외부 요청이 컨테이너까지 어떻게 도달하는가? | [03](03-alb-and-target-group.md) |
| **실행 기반** | 컨테이너를 누가 언제 몇 개 띄우고, 배포 중 무슨 일이 일어나는가? | [04](04-ecs-fargate.md) |
| **권한** | 누가 무엇을 할 수 있는가? 롤이 왜 세 개인가? | [05](05-iam-roles.md) |
| **비밀** | 값을 코드에 두지 않고 어떻게 컨테이너에 넣는가? | [06](06-secrets.md) |
| **관측** | 뭔가 잘못됐을 때 어떻게 아는가? | [07](07-observability.md) |
| **배포** | 코드가 이미지가 되고 서비스가 되는 경로는? | [08](08-deploy-pipeline.md) |

이 순서에는 이유가 있다. 네트워크를 모르면 ALB의 `Subnets`가 왜 public이고 서비스의 `Subnets`는 왜 private인지 알 수 없고, ALB를 모르면 헬스체크가 두 곳(ALB와 컨테이너)에 있는 이유를 알 수 없고, IAM을 모르면 시크릿 주입이 실패하는 이유를 알 수 없다. **아래층을 건너뛰면 위층은 암기가 된다.**

## 로드맵

```
01 IaC·CloudFormation      ← 선언형이라는 발상, 스택, 교체(replacement), 참조 함수
        ↓
02 네트워크 (VPC·서브넷·SG) ← 트래픽이 지나갈 길과 문
        ↓
03 ALB·타겟그룹             ← 문 앞의 안내원, 그리고 "건강하다"의 정의
        ↓
04 ECS Fargate              ← 컨테이너를 대신 돌려주는 서비스, 무중단 교체의 산수
        ↓
05 IAM 롤                    ← 실행 롤 / 태스크 롤 / 배포 롤이 나뉘는 이유
        ↓
06 시크릿                    ← 환경변수 평문과 Secrets Manager 참조의 갈림길
        ↓
07 관측·알람                 ← 침묵을 이상으로 볼 것인가
        ↓
08 배포 파이프라인           ← ECR, OIDC, 그리고 장기 키를 없애는 방법
        ↓
90 암기 카드 → 91 용어집 → 92 워크북
```

## 예상 시간

| 단계 | 분량 | 예상 |
|---|---|---|
| 01~08 지식 문서 정독 | 8개 문서 | 4~6시간 |
| 90 암기 카드 회수 연습 | 카드 29장 | 1~2시간 |
| 92 워크북 서술형 | 회수 29 + 판단 7 + 재현 3 | 3~4시간 |
| 코딩 과제 5종 (`src/`) | 파일 5개, 판정 146항목 | 3~5시간 |

한 번에 다 하지 않아도 된다. **01~04까지만 읽어도 템플릿의 절반은 읽힌다.** 05~08은 "왜 이 값이어야 하는가"를 채우는 층이다.

## 읽는 방법

각 문서는 같은 구조다.

- **핵심 원리 (WHY)** — 이 층이 왜 존재하는가. 여기를 이해하면 나머지는 유도된다.
- **필수 지식 (HOW)** — 구체적 동작 방식과 속성의 의미.
- **⚠️ 암기 필수** — 검색할 여유가 없을 때 필요한 것만. 전체의 10~20%로 제한했다.
- **자가 진단** — 답이 막히면 그 절을 다시 읽으라는 신호.

암기 카드([90](90-must-memorize.md))는 각 문서의 "암기 필수"를 판단 단위로 묶은 것이고, 워크북 파트 1([92](../workbook/92-workbook.md))은 그 카드 29장과 1:1로 대응한다. 즉 **90을 덮고 92를 풀 수 있으면 이 자료의 목표에 도달한 것이다.**

코딩 과제 5개는 `src/`에 있고 **무엇을 만들지는 `tests/`가 정의한다.** 명세를 먼저 읽고 스켈레톤을 채운 뒤 돌리면 통과/실패로 확인되므로 "이해한 것 같다"에서 멈추지 않는다. 참고 구현(`solutions/`)은 통과한 뒤에 연다.

```bash
pnpm test 04-01        # 한 과제만 (패키지 디렉토리에서)
pnpm test            # 전체
```

용어가 막히면 [91 용어집](91-glossary.md)을 본다. AWS 어휘는 약어가 많고(ARN·ENI·ACM·OIDC·CIDR·LCU) 이름이 내용을 설명해주지 않는 경우가 많아서, 레이어별로 묶어 정리해 뒀다.

## 학습 대상 템플릿

이 자료는 실제 운영 중인 ECS Fargate 스택 두 장을 교재로 쓴다.

| 파일 | 크기 | 담는 것 |
|---|---|---|
| `orders-server-multi-env.cfn.yaml` | 약 570줄, 리소스 18종 | 로그 그룹 · 시크릿 · IAM 롤 2종 · 보안 그룹 5종 · ALB · 타겟그룹 · 리스너 · WAF 연결 · 클러스터 · 태스크 정의 · 서비스 · 알람 3종 |
| `orders-server-iam-deploy-roles.cfn.yaml` | 약 100줄, 리소스 1종 | GitHub Actions가 OIDC로 맡아 쓰는 배포 롤 |

### ⚠️ 식별자는 예시값으로 치환했다

**이 자료의 모든 식별자는 문서용 예시값이다.** 실제 계정 ID·공인 IP·리소스 ID·도메인·서비스명이 아니다.

| 이 자료의 값 | 정체 |
|---|---|
| `111122223333` | AWS 문서가 쓰는 예시 계정 ID |
| `203.0.113.10` · `198.51.100.20` | RFC 5737이 문서용으로 예약한 대역 |
| `subnet-0aaa1111…` · `sg-0db1111…` · `vpc-0abc1234…` | 형식만 맞춘 가짜 ID |
| `orders-server` · `orders-dev` | 서비스명·클러스터명 |
| `*.example.com` · `repo:my-org/orders-server` | 도메인·리포지토리 |

**자기 템플릿과 대조할 때는 이 값들을 자기 조직의 값으로 읽으라.** 배울 것은 값이 아니라 구조와 판단 근거이므로, 치환은 학습 가치를 줄이지 않는다.

이렇게 하는 이유는 **학습 자료가 공유되기 쉽기 때문이다.** 노션에 올리고, 팀에 링크를 주고, 나중에 공개 레포로 옮기는 일이 흔하다. 계정 ID·고정 공인 IP·리소스 ID·OIDC 신뢰 대상이 한 문서에 모여 있으면 그것만으로 정찰 정보가 된다 — 특히 이 자료처럼 "ALB가 `internet-facing`이고 허용 IP는 이 둘뿐"이라는 설명이 함께 있을 때는 표적이 좁혀진다. 실제 값이 필요한 사람은 이미 그 계정에 접근할 수 있으므로, 문서에 둘 이유가 없다.

이 두 파일은 **DEV 환경만** 지원한다(`AllowedValues: [dev]`). TEST/STAGE/PROD는 아직 열리지 않았고, 그 사실 자체가 여러 값의 근거다 — 태스크 1개, 로그 7일, DB 비밀번호 평문 파라미터, Fargate Spot 100%는 모두 "개발 환경이니까" 성립하는 선택이다. 운영 환경에서 같은 값을 쓰면 안 되는 이유는 각 문서에서 짚는다.
