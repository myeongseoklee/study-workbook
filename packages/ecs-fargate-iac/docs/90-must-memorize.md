## 1군. CloudFormation의 기본값과 교체 (문서 [01](01-iac-and-cloudformation.md))

### 카드 1 — `DeletionPolicy`를 안 쓰면?

**앞** 리소스에 `DeletionPolicy`를 지정하지 않고 스택을 지우면 그 리소스는?

**뒤** **삭제된다.** 기본값이 `Delete`다. 예외는 RDS 클러스터와 `DBClusterIdentifier`가 없는 RDS 인스턴스로, 기본값이 `Snapshot`이다.

**왜** 기본값을 반대로 알고 있으면 지우면 안 되는 것을 지운다. 그리고 Secrets Manager는 CloudFormation 삭제 시 **복구 대기 기간 없이 즉시 삭제**되므로 되돌릴 수 없다.

### 카드 2 — 고정 `Name`을 언제 피하는가

**앞** 어떤 리소스에 고정 이름(`Name`·`GroupName`)을 주면 안 되는가? 대신 무엇으로 식별하는가?

**뒤** **교체(replacement)를 유발할 수 있는 속성을 가진 리소스** — ALB(`Scheme`), 보안 그룹(`GroupDescription`) 등. 교체는 "새것 생성 → 옛것 삭제" 순서라 고정 이름이 겹쳐 실패한다. 식별은 **`Name` 태그**로 한다(태그는 중복 허용, 변경 시 교체 없음).

**왜** 이름 충돌이 업데이트 실패 → 롤백 → 롤백 중 또 다른 충돌의 연쇄를 만든다. 반대로 IAM 롤·알람은 다른 스택이나 사람이 이름으로 지목해야 하므로 고정 이름을 준다.

### 카드 3 — `Retain`의 대가

**앞** `DeletionPolicy: Retain`이 붙고 이름이 고정된 리소스가 있는 스택을 지웠다가 같은 템플릿으로 다시 만들면?

**뒤** **남아 있는 리소스와 이름이 충돌해 스택 생성이 실패한다.** 재생성 전에 잔존 리소스를 조회하고 값을 살릴지 정리할지 먼저 정한다.

**왜** 실패가 스택 생성 초반에 일어나 원인이 드러나지 않는다. 그리고 `DeletionPolicy`만 걸고 `UpdateReplacePolicy`를 빼면 교체 시에는 옛 리소스가 삭제된다 — 둘은 서로를 대신하지 못한다.

## 2군. 네트워크 (문서 [02](02-network-vpc-sg.md))

### 카드 4 — public 서브넷의 정의

**앞** 서브넷이 public인지 private인지는 무엇으로 결정되는가?

**뒤** **라우팅 테이블에 인터넷 게이트웨이로 가는 경로(`0.0.0.0/0 → igw-…`)가 있는지.** 이름·태그와 무관하다. NAT를 가리키면 나가기만 가능한 private이다.

**왜** "public 서브넷에 뒀는데 인터넷이 안 된다"의 대부분이 라우팅 미확인이다. 그리고 private 서브넷 + `AssignPublicIp: DISABLED` 조합에서 NAT나 VPC 엔드포인트가 없으면 **이미지 pull과 로그 전송이 모두 실패**한다.

### 카드 5 — 보안 그룹의 두 성질

**앞** 보안 그룹은 상태를 기억하는가? 새로 만든 보안 그룹의 인바운드·아웃바운드 기본값은?

**뒤** **상태를 기억한다(stateful)** — 요청 방향만 열면 응답은 자동으로 통과한다. 기본값은 **인바운드 전부 거부 / 아웃바운드 전부 허용**. 단 `SecurityGroupEgress`를 한 번이라도 쓰면 전체 허용이 사라지고 적은 것만 남는다.

**왜** 상태 저장을 모르면 응답용 이그레스를 넣으려다 필요 이상으로 넓게 연다. 기본값 비대칭을 모르면 이그레스를 조이는 순간 시작되는 조용한 차단을 예상하지 못한다.

### 카드 6 — 연결에 필요한 규칙

**앞** A에서 B로 트래픽이 가려면 어떤 규칙이 필요한가?

**뒤** **A의 이그레스 허용 + B의 인그레스 허용, 양쪽 모두.**

**왜** 인그레스만 확인하고 "규칙 있는데 왜 안 돼"에서 멈추는 것이 흔하다. 전용 보안 그룹은 아웃바운드가 전부 열려 있어 문제가 안 되지만, **이그레스가 제한된 공용 보안 그룹을 재사용하면** 여기서 막힌다.

### 카드 7 — `/health`는 200인데 API가 500

**앞** `/health`는 200을 반환하는데 비즈니스 API만 500이다. 무엇을 먼저 의심하는가?

**뒤** **이그레스 차단.** 헬스체크가 DB·캐시 같은 외부 의존을 확인하지 않으면 그 통신이 막혔어도 200이 나온다.

**왜** 배포가 성공으로 판정되고 원인이 애플리케이션 코드로 오인된다. 실제로 이 조합이 발생한 사례가 있었고, 보안 그룹 이그레스 규칙 두 건 추가로 해결됐다. 진단은 ECS Exec로 컨테이너에 들어가 목적지 포트로 연결을 시도해 본다.

### 카드 8 — 수동 보안 그룹 규칙이 만드는 문제

**앞** DB 인그레스 규칙을 콘솔·CLI로 수동 추가하면 나중에 무엇이 막히는가?

**뒤** **스택 삭제가 `DependencyViolation`으로 멈춘다.** 그 규칙이 서비스 보안 그룹을 참조하는데 CloudFormation은 규칙의 존재를 모른다. 규칙도 `AWS::EC2::SecurityGroupIngress`로 관리한다.

**왜** 멈춘 삭제를 푸는 데 사람 시간이 들고, 공용 보안 그룹을 건드려야 하므로 다른 서비스 영향 확인까지 필요하다.

## 3군. ALB와 헬스체크 (문서 [03](03-alb-and-target-group.md))

### 카드 9 — `SslPolicy` 기본값 함정

**앞** CloudFormation으로 HTTPS 리스너를 만들면서 `SslPolicy`를 생략하면 어떤 정책이 적용되는가?

**뒤** **`ELBSecurityPolicy-2016-08`** — TLS 1.0과 1.1을 허용하는 구식 정책. **콘솔에서 만들면 최신 정책이 붙어서 차이를 인지하기 어렵다.** 항상 명시한다(예: `ELBSecurityPolicy-TLS13-1-2-2021-06` = TLS 1.3 + 1.2만).

**왜** 보안 점검에서 지적받을 때까지 발견되지 않는다. 정책 이름의 `TLS13-1-2`는 "TLS 1.3 지원 + 최소 버전 1.2"로 읽는다.

### 카드 10 — 장애 감지 시간 계산

**앞** `HealthCheckIntervalSeconds: 30`, `UnhealthyThresholdCount: 3`이면 태스크가 죽은 뒤 ALB가 트래픽을 끊기까지 최대 몇 초인가? 복귀는?

**뒤** **비정상 판정 = 30 × 3 = 최대 90초.** 복귀 = `Interval` × `HealthyThresholdCount` = 30 × 2 = 최대 60초.

**왜** "장애 후 몇 초 동안 요청이 죽은 태스크로 가는가"를 즉답해야 한다. 줄이면 감지가 빨라지지만 일시적 지연에 건강한 태스크가 쫓겨난다 — 감지 속도와 안정성의 트레이드오프에 공짜가 없다.

### 카드 11 — 등록 해제 지연 기본값

**앞** 타겟그룹의 등록 해제 지연 기본값은? 너무 짧게 잡으면?

**뒤** **300초.** 짧게 잡으면 처리 중인 요청이 잘려 **클라이언트가 500번대 오류를 받는다.** 적정값은 "가장 느린 정상 요청이 끝나는 시간".

**왜** 기본값을 모르면 배포가 느린 원인을 찾지 못한다. 태스크마다 최대 5분을 기다리므로 배포가 10분 이상 걸릴 수 있다.

### 카드 12 — ALB 503의 의미

**앞** ALB가 503을 반환한다. 원인의 범위는?

**뒤** **healthy 타겟이 하나도 없다.** 원인은 항상 타겟 쪽 — 태스크 미기동 / 헬스체크 실패 / 서비스 보안 그룹이 ALB를 막음.

**왜** 장애 중 가장 빠른 분기점이다. 504는 태스크가 응답하지 않는 것, 502는 유효하지 않은 응답, 503은 보낼 곳이 없는 것이다.

### 카드 13 — HEAD 헬스체크 함정

**앞** 컨테이너 헬스체크에 `wget --spider`를 쓰면 왜 위험한가?

**뒤** **`--spider`는 HEAD 요청**이고, `app.get('/health')`로 등록한 라우트는 HEAD를 잡지 않아 인증 미들웨어로 흘러 **401**이 된다 → unhealthy 오판 → 배포 실패. `wget -q -O /dev/null`로 GET을 쓴다.

**왜** 브라우저로는 200이 나와서 원인을 찾기 어렵다. ALB 타겟 헬스체크는 항상 GET이므로 컨테이너 헬스체크도 GET으로 맞춰 두 판정을 일치시킨다.

## 4군. ECS와 Fargate (문서 [04](04-ecs-fargate.md))

### 카드 14 — Fargate CPU·메모리 조합

**앞** `Cpu: 512`에서 허용되는 메모리 값은? `Memory: 512`는 되는가?

**뒤** **512(.5 vCPU) → 1 GB, 2 GB, 3 GB, 4 GB만.** `Memory: 512`는 **안 된다** — 512 MiB는 `Cpu: 256`에서만 가능하다.

**왜** 조합을 틀리면 태스크 정의 등록 자체가 실패한다. `TaskMemory`에 `AllowedValues`가 없으면 CloudFormation 검증을 통과해 AWS API 호출 단계에서 실패하므로 실패 지점이 늦다.

### 카드 15 — 배포 중 태스크 수 계산

**앞** `DesiredCount`, `MinimumHealthyPercent`, `MaximumPercent`로 배포 중 태스크 수 범위를 구하는 식은?

**뒤**
```
최소 유지 = ceil(DesiredCount × MinimumHealthyPercent / 100)   ← 올림
최대 허용 = floor(DesiredCount × MaximumPercent / 100)         ← 내림
```
방향이 다르다: **최소는 올려서 가용성을 지키고, 최대는 내려서 비용 한도를 지킨다.**

**왜** 이 계산으로 무중단 여부가 결정된다. `DesiredCount: 4` + 50/100이면 최소 2·최대 4로 여유 용량 없이 2개씩 교체하고, 100/200이면 최소 4·최대 8로 새것을 먼저 띄운다.

### 카드 16 — 롤링 배포 기본값과 교착

**앞** 롤링 업데이트의 두 퍼센트 기본값은? `DesiredCount: 1`에서 `MaximumPercent: 100`이면?

**뒤** 기본값은 **`MinimumHealthyPercent: 100` / `MaximumPercent: 200`**(레플리카 서비스). `DesiredCount: 1` + `MaximumPercent: 100`은 **교착** — 최소 1·최대 1이라 하나도 멈출 수 없고 하나도 시작할 수 없다. ECS가 "설정 때문에 태스크를 멈추거나 시작할 수 없다"는 이벤트를 낸다.

**왜** 실제로 자주 나는 실수이고 증상이 "배포가 멈춤"이라 원인이 안 보인다. `DesiredCount: 1`에서 무중단을 원하면 `MaximumPercent`는 반드시 200이어야 한다.

### 카드 17 — 서킷 브레이커 임계값

**앞** 배포 서킷 브레이커의 실패 임계값 계산식은? `DesiredCount: 1`이면?

**뒤** **`clamp(0.5 × DesiredCount, 최소 3, 최대 200)`** (기본 `BOUNDED_PERCENT`, 기본 비율 50%). `DesiredCount: 1` → 0.5 → **최소값에 걸려 3**. 기본 동작에서는 건강한 태스크가 하나 뜨면 실패 카운트가 0으로 초기화된다.

**왜** "몇 번 실패하면 포기하나"를 알아야 배포 실패 판정 시점을 예측한다. `DesiredCount: 25`면 13, `400`이면 최대값 200에 걸린다.

### 카드 18 — 첫 배포의 롤백 불가

**앞** 첫 배포가 실패했는데 서킷 브레이커가 롤백하지 않는다. 왜인가? 예방책은?

**뒤** 롤백 대상은 **`COMPLETED` 상태의 배포**이고 첫 배포에는 그것이 없다 → 배포가 그대로 멈춘다. 게다가 CloudFormation 스택 롤백이 **로그 그룹까지 삭제**해 실패 원인이 담긴 로그가 사라진다. 예방: 첫 배포는 **`DesiredCount: 0`으로 인프라만 세운 뒤 `1`로 올리는 2단계**로.

**왜** 원인을 조사할 유일한 자료가 사라지는 상황이라 되돌릴 수 없다.

### 카드 19 — Fargate Spot의 조건

**앞** Fargate Spot의 할인율, 회수 시 경고 시간과 신호, `stopTimeout` 기본값은? 태스크 1개 서비스에서 회수되면?

**뒤** **최대 70% 할인. 2분 경고**(EventBridge 이벤트 + 컨테이너에 **SIGTERM**). `stopTimeout` **기본 30초, 최대 120초**. 태스크 1개면 용량이 생길 때까지 **서비스가 멈추고, 일반 Fargate로 자동 대체되지 않는다.**

**왜** SIGTERM을 처리하지 않으면 30초 뒤 SIGKILL로 잘린다. 운영에서 Spot을 쓰려면 `Base`로 최소 개수를 일반 용량에 확보하고 초과분만 Spot으로 돌려야 한다.

### 카드 20 — ECS Exec의 세 제약

**앞** ECS Exec 권한은 어느 롤에 넣는가? 함께 쓸 수 없는 설정과, 도는 태스크에 대한 제약은?

**뒤** **태스크 롤**(`ssmmessages:CreateControlChannel`·`CreateDataChannel`·`OpenControlChannel`·`OpenDataChannel`) — 컨테이너 안에서 채널을 열기 때문. **`readonlyRootFilesystem`과 함께 쓸 수 없다**(SSM 에이전트가 파일을 만들어야 함). **도는 태스크에 나중에 켤 수 없다** — 새 배포가 필요하다.

**왜** 장애 대응 중에 켜려 하면 조사 대상 태스크가 교체되어 사라진다. 미리 켜 두는 것이 진단 통로를 남기는 방법이다.

## 5군. IAM (문서 [05](05-iam-roles.md))

### 카드 21 — 롤의 두 문서

**앞** IAM 롤에 붙는 두 문서는 각각 무엇을 정하는가? AccessDenied가 났을 때 어느 쪽을 먼저 보는가?

**뒤** **신뢰 정책(`AssumeRolePolicyDocument`) = 누가 맡을 수 있나** / **권한 정책(`Policies`·`ManagedPolicyArns`) = 맡으면 무엇을 할 수 있나.** 맡을 자격이 없으면 권한 목록은 볼 기회조차 없으므로 **신뢰 정책을 먼저** 확인한다. 오류 발생 단계도 다르다 — 신뢰 정책 거부는 `AssumeRole` 시점, 권한 부족은 실제 API 호출 시점.

**왜** 신뢰 정책 문제인데 권한 정책을 뒤지면 원인을 찾지 못한다.

### 카드 22 — 실행 롤과 태스크 롤의 경계

**앞** 실행 롤과 태스크 롤을 가르는 기준은? 컨테이너 안 코드는 어느 쪽을 쓰는가?

**뒤** **시점이다.** 실행 롤 = 컨테이너를 **띄우기 전·중**에 ECS·Fargate 에이전트가 쓴다(ECR pull, 로그 스트림 생성, 시크릿 값 읽어 주입). 태스크 롤 = 컨테이너가 **돌고 있는 동안** 안의 코드가 쓴다. **컨테이너는 실행 롤 자격증명에 접근할 수 없다.** 두 롤의 신뢰 정책은 똑같이 `ecs-tasks.amazonaws.com`이고, 태스크 정의의 `ExecutionRoleArn`/`TaskRoleArn` 자리가 역할을 정한다.

**왜** 권한을 어느 롤에 넣을지 판단하는 유일한 기준이다. 합치면 애플리케이션 취약점으로 실행 롤 권한까지 넘어간다.

### 카드 23 — 관리형 정책의 빈틈

**앞** 실행 롤에 `AmazonECSTaskExecutionRolePolicy`를 붙였는데 태스크가 `ResourceInitializationError: unable to pull secrets`로 죽는다. 원인은?

**뒤** **그 관리형 정책에는 `secretsmanager:GetSecretValue`가 없다.** 태스크 정의에서 시크릿을 참조하면 인라인 정책으로 직접 추가해야 한다. (고객 관리 KMS 키를 쓰면 `kms:Decrypt`도 필요하다.)

**왜** 정책 이름이 "TaskExecutionRolePolicy"라서 실행 롤에 필요한 모든 것이 들어 있을 것처럼 읽힌다. 증상이 이미지 문제로 오인돼 이미지를 다시 빌드하며 시간을 잃는다.

### 카드 24 — `PassRole`

**앞** 배포 파이프라인이 `RegisterTaskDefinition`에서 AccessDenied를 받는다. 어느 권한인가? 함께 걸어야 하는 조건은?

**뒤** **배포 롤의 `iam:PassRole`.** 태스크 정의에 실행 롤·태스크 롤 ARN이 들어가므로 "롤을 서비스에 넘기는" 별도 권한이 필요하다. **`Condition: iam:PassedToService = ecs-tasks.amazonaws.com`**을 함께 걸어 다른 서비스(Lambda·EC2)로 넘기는 경로를 막는다.

**왜** 오류 메시지가 **넘겨질 롤**의 이름을 언급해서 엉뚱한 롤(실행 롤·태스크 롤)의 정책을 뒤지게 만든다. 조건이 없으면 자기 권한보다 강한 권한을 우회 획득하는 경로가 남는다.

## 6군. 시크릿 (문서 [06](06-secrets.md))

### 카드 25 — 주입 시점과 갱신

**앞** `Secrets`로 주입된 값은 언제 해석되는가? 시크릿 값을 갱신하면 도는 컨테이너는?

**뒤** **컨테이너 시작 시점에 한 번만.** 갱신해도 도는 컨테이너는 옛 값을 들고 있다 → **`aws ecs update-service --force-new-deployment`**로 태스크를 새로 띄워야 반영된다.

**왜** "값을 바꿨는데 왜 안 바뀌지"에서 오래 머문다. 이 성질 때문에 **회전이 필요한 값은 환경변수만으로 표현할 수 없고**, 앱이 저장소에 직접 쓰는(`PutSecretValue`) 구조가 필요해진다.

### 카드 26 — 빈 시크릿과 블록 수정 금지

**앞** 시크릿 초기값을 빈 문자열이 아니라 표식 문자열로 두는 이유 두 가지는? 값 주입 후 그 리소스 블록을 고치면?

**뒤** (1) **버전(값) 없는 시크릿은 `secrets:` 해석이 실패해 태스크가 기동하지 못한다** — 운영 중 업데이트면 곧 장애. (2) 표식은 **미주입 상태를 드러내** 진단을 한 걸음으로 만든다. 주입 후 `Description` 같은 다른 속성만 고쳐도 CloudFormation이 `UpdateSecret`에 **`SecretString`(표식)을 함께 실어 실제 값이 되돌아갈 수 있다** → **어떤 속성도 수정하지 않는다.**

**왜** 사람의 재로그인이 필요한 값이면 소실 복구가 비싸다. 값을 꼭 바꿔야 하면 변경 후 다시 주입한다.

## 7군. 알람 (문서 [07](07-observability.md))

### 카드 27 — `TreatMissingData`

**앞** `TreatMissingData` 기본값과 그 결과는? 지표 성격에 따라 무엇을 골라야 하는가?

**뒤** 기본값은 **`missing`** → 전부 결손이면 **`INSUFFICIENT_DATA`**이고, 이건 `ALARM`이 아니라서 **알림이 발동하지 않는다.**

```
정상일 때 항상 데이터가 오는가?
  ├─ 예 (연속 지표: healthy 호스트 수, 실행 중 태스크 수) → breaching
  └─ 아니오 (이벤트 지표: 5xx 건수, 스로틀 건수)          → notBreaching
```

**왜** 태스크 전멸처럼 **가장 심각한 상황이 지표를 멈추게 하는데**, 기본값이면 그때 조용하다. 반대로 이벤트 지표에 `breaching`을 붙이면 **에러가 없는 평온한 시간에 계속 울려** 사람이 알람을 끄게 된다. 참고: 실제 데이터가 `EvaluationPeriods`만큼 모이면 결손 설정은 쓰이지 않는다.

## 8군. 배포 (문서 [08](08-deploy-pipeline.md))

### 카드 28 — OIDC `sub` 조건

**앞** OIDC 신뢰 정책에서 `sub` 조건을 빼면 무엇이 가능해지는가? `sub`의 두 형식과 `aud` 값은?

**뒤** **GitHub의 아무 리포지토리나 그 롤을 맡을 수 있다** — 롤 ARN은 비밀이 아니므로 ARN만 알면 된다. `aud`는 **`sts.amazonaws.com`**.

```
환경 스코프:  repo:OWNER/REPO:environment:ENV_NAME
브랜치 스코프: repo:OWNER/REPO:ref:refs/heads/BRANCH
```

워크플로에는 **`permissions: id-token: write`**가 필요하다(없으면 토큰 자체를 못 얻는다).

**왜** 이 한 줄 누락이 계정 침해로 직결된다. 환경 스코프가 나은 이유는 GitHub 환경에 승인 규칙을 걸 수 있어 통제가 양쪽에서 걸리기 때문이다.

### 카드 29 — 태그 전략과 다이제스트 고정

**앞** 가변 태그(`dev`)만 쓰면 무엇이 막히는가? 같은 태그에 새 이미지를 push하면 도는 서비스는?

**뒤** **롤백 대상을 지목할 수 없다** — 옛 이미지가 태그를 잃고 `<untagged>`가 된다. 그래서 불변 태그(`dev-<git-sha>`)를 함께 push한다. 그리고 **ECS는 태스크 정의의 태그를 다이제스트로 고정**하므로 같은 태그에 push해도 도는 서비스는 바뀌지 않는다 → `--force-new-deployment` 필요.

**왜** 롤백이 필요한 순간에 지목할 대상이 없다. 그리고 "push했는데 안 바뀌네"의 원인이 다이제스트 고정이다(이 동작이 서비스 안 모든 태스크의 이미지 일관성을 보장한다).

## 카드가 아닌 것 — 외우지 않아도 되는 것

우선순위를 지키기 위해 무엇을 빼는지도 적어 둔다.

| 항목 | 왜 안 외우는가 |
|---|---|
| `!Ref`가 리소스 타입별로 반환하는 값 | 규칙이 없다. 각 리소스 타입 문서의 "Return values"를 **찾아본다** |
| CloudWatch 지표 이름과 디멘션 조합 | 서비스마다 다르고 문서에 표로 있다 |
| 정책 액션 이름 전체 목록 | 서비스 권한 레퍼런스에서 찾는다 |
| ALB 보안 정책별 암호 스위트 목록 | 정책 이름 규칙(`TLS13-1-2` = 1.3 지원 + 최소 1.2)만 알면 된다 |
| Fargate 시간당 단가 | 리전·시점마다 바뀐다. **Spot이 최대 70% 싸다는 관계만** 기억한다 |
| CLI 명령의 정확한 플래그 | `--help`로 확인한다 |
