# 06. 커맨드 패턴과 재수화 — 애그리게이트 루트는 Invoker다

## 학습 목표

재수화(rehydration)가 성립하기 위해 애그리게이트에 걸리는 **구조적 제약**을 안다. 그 제약이 왜 커맨드 패턴으로 귀결되는지, 리플레이 중과 평시의 동작이 어디서 갈리는지 설명할 수 있다.

## 선수 지식

- 05장: 명령과 이벤트의 구별, 이벤트 연쇄
- 03장: 불변식이 애그리게이트 루트에 사는 방식
- 커맨드 패턴을 몰라도 된다 — 이 문서가 필요한 만큼만 다룬다

## 핵심 원리 (WHY) — 재수화가 메서드를 금지한다

이벤트 소싱의 목적 중 하나가 이벤트로부터 상태를 복원하는 것이다. 그런데 그 목적이 애그리게이트의 설계를 강하게 제약한다.

> 이 전략은 궁극적으로는 **애그리게이트에 메서드가 없다는 뜻이야. 이벤트를 수신하는 메서드 외에는 없다는 얘기야.** 왜? **나의 모든 행동이 이벤트로 규정되는** — 안 그러면 어떻게 재수화가 되겠어?

논리를 확인해 보자.

> 어떤 애그리게이트 루트가 **일반 메서드를 세 번 호출하고 이벤트 수신을 네 번 해서** 현재 상태가 만들어졌으면 — **재수화됩니까? 안 되죠.** 모든 상태가 이벤트로부터 만들어졌어야 재수화가 될 거 아니에요.

그래서 결론이 이렇게 좁혀진다.

```
재수화 가능 ⟺ 현재 상태가 오직 이벤트(커맨드)의 적용 결과다
           ⟹ 상태를 바꾸는 공개 메서드가 있으면 안 된다
           ⟹ 입구는 "커맨드를 받는 메서드" 하나
```

## 필수 지식 (HOW) — 두 가지 구현 수준

책과 실무 구현이 다른 지점이다.

> 책에서는 **봐주는 거예요.** 메서드 n개에 해당되는 n종류의 명령이 존재한다 — 그러니까 `add`, `remove` 이렇게 전개해 가고 있죠. 근데 **궁극적으로 구현하면 메서드가 하나예요.** 명령을 받아들이는 메서드 하나가 **명령에 따라서 분기해서 처리할 뿐이야.** 이게 더 강력하게 제약을 걸어서 **무조건 재수화 가능한 객체**를 만들게 됩니다.

| | 메서드 n개 (책) | 메서드 1개 (궁극) |
|---|---|---|
| 읽기 쉬움 | 좋다 | 분기 덩어리가 된다 |
| 재수화 보장 | 개발자가 지켜야 한다 | **구조가 강제한다** |
| 실수 여지 | 상태 바꾸는 메서드를 몰래 추가 가능 | 추가할 자리가 없다 |

이 선택이 "코드의 의사 결정"이라고 강의자는 말한다 — 정답이 아니라 **얼마나 강제할 것인가**의 문제다.

## 필수 지식 (HOW) — 그 구조의 이름은 커맨드 패턴이다

> 궁극적으로 메서드를 없애고, 오직 이벤트라고 해도 좋고 **외부의 구상 객체로 내부의 상태를 변경해 가는 패턴** — 이걸 디자인 패턴 중에 **커맨드 패턴**이라고 부릅니다.
>
> 어떻게 보면 **이벤트 소싱을 해주는 애그리게이트 루트는 커맨드 패턴에 나오는 Invoker로 볼 수 있어요.**

그리고 실무적 이득이 하나 붙는다.

> 리플렉션 안 쓰고 어떻게 하나? **다 커맨드 패턴 쓰면 됩니다.**

즉 "이벤트 타입 → 핸들러" 매핑을 리플렉션이나 애노테이션 스캔으로 풀지 않고, 커맨드 객체와 Invoker의 협력으로 푼다.

## 필수 지식 (HOW) — Invoker의 구조

강의자가 코틀린으로 전개한 골격을 개념만 남겨 옮기면 이렇다.

**보유 상태**: 적용된 커맨드들의 리스트. (원래 커맨드 패턴의 Invoker도 커맨드 배열을 갖는다.)

**save** — 스토어로 넘기고 자기 것은 비운다.

> 현재 커맨드를 리스트로 복사본 하나 넘겨 주고, 넘겨 줬으니까 **플러시됐으니 내 커맨드는 클리어**시켜야겠죠. 그럼 내가 넘겨준 저 커맨드로 **어떻게 저장하는지는 스토어가 알아서 할 일이고 내 관심사는 아니고.**

**restore** — 바깥에서 커맨드 리스트를 받아 복원한다. 단 전제가 있다.

> 근데 **커맨드가 비어 있지 않아? 그럼 이미 커맨드에 뭐가 있는 거니까 restore가 불가능하죠.** 얘는 새 객체가 아닌 거야.

즉 **이미 상태가 있는 객체에는 복원할 수 없다.** 이것을 실패로 알린다. (강의자는 예외를 던지는 대신 `Boolean`을 돌려주는 취향을 밝힌다 — "거의 모든 언어에서 공통으로 쓸 수 있어서".)

**리플레이 플래그** — 여기가 이 패턴의 핵심 분기다.

> 재수화라는 마크를 true로 달아줬어요. … **재수화가 켜져 있으면 커맨드를 넣지 않고** 쭉 커맨드를 dismiss 해주는 거죠.

왜 필요한가. 리플레이 중에 적용한 커맨드를 다시 리스트에 쌓으면, 다음 `save`에서 **같은 이벤트가 두 번 저장**된다. 즉 리플레이가 이벤트 로그를 오염시킨다.

```
평시   : on(cmd) → 적용 성공 → 커맨드를 리스트에 쌓는다   (다음 save 대상)
리플레이: on(cmd) → 적용 성공 → 쌓지 않는다              (이미 로그에 있다)
```

**커맨드와 Invoker의 핑퐁** — 분기를 어느 쪽이 하느냐의 문제다.

> 커맨드 객체가 `invoke`하다가 Invoker를 주면 Invoker가 `invoke`를 부르는 거예요. … 통신 방법이 **커맨드에 있는 invocation을 하면 Invoker에 있는 invocation을 부르는** 식이지.

Invoker 쪽은 추상 메서드로 남겨 자식(구체 애그리게이트)이 "이 커맨드가 오면 무엇을 할지"를 정한다.

## 필수 지식 (HOW) — 불변식은 여전히 루트에 산다

재수화 구조를 갖췄어도 03장의 원칙은 그대로다. 강의자의 장바구니 예시에서 `remove`가 그것을 보여준다.

> `remove`는 신경 써서 구현해 봤어요. **productNumber로 remove할 수 있는데, remove하기 전에 적어도 아이템이 한 개 이상은 남아 있어야 지울 수 있어** — 요게 바로 그겁니다. **도메인 불변식.** 이게 애그리게이트 루트가 지고 있게 돼요.

그리고 왜 내부 객체를 외부에 노출하지 않는지가 여기서 확정된다.

> **아이템을 바깥에 노출할 수 없는 이유가 바로 이거예요.** 카트를 통하지 않고 아이템을 함부로 삭제하거나 등록하면 안 되는 거지. 왜냐면 **불변식 적용 대상이 카트**기 때문에. 우리는 이 카트를 애그리게이트 루트라고 부르고, 애그리게이트 루트는 **트랜잭션 일관성을 보장한다.**

불변식을 코드에 배치하는 방법이 하나가 아니라는 점도 짚어 둔다.

> 개입시키는 방법은 여러 가지가 있어요. **before/after consistency**로 불변식을 쫙 만들어 놓고 앞뒤로 한 번씩 돌려서 안 되면 취소하는 방법도 있고, **불변식을 각각의 로직에 나눠서 따로따로 넣어주는** 방법도 있고.

## 이 지식이 판단에 쓰이는 자리

- **이벤트 소싱을 도입할 때**: 애그리게이트에 상태를 바꾸는 공개 메서드를 남겨두면 **재수화가 조용히 깨진다.** 입구를 하나로 좁히는 것이 그 방어다.
- **리플레이를 구현할 때**: 리플레이 중 커맨드를 다시 쌓지 않는 분기를 반드시 둔다. 없으면 로그가 중복된다.
- **restore를 설계할 때**: 이미 상태가 있는 객체에 복원을 허용하지 않는다. 새 객체에만 복원한다.
- **리플렉션·애노테이션 스캔을 쓰려 할 때**: 커맨드 패턴으로 대체 가능한지 먼저 본다.

### ⚠️ 암기 필수

- [ ] **재수화가 가능하려면 현재 상태가 오직 이벤트의 적용 결과여야 한다** → 상태를 바꾸는 공개 메서드가 있으면 안 되고, 입구는 **커맨드를 받는 메서드 하나**다.
- [ ] **이벤트 소싱의 애그리게이트 루트 = 커맨드 패턴의 Invoker.** 리플렉션 없이 이벤트 디스패치를 푸는 방법이 이것이다.
- [ ] **리플레이 중에는 적용한 커맨드를 다시 쌓지 않는다** — 쌓으면 다음 save에서 같은 이벤트가 중복 저장돼 로그가 오염된다.
- [ ] **restore는 빈 객체에만 가능하다.** 이미 커맨드가 쌓인 객체는 복원 대상이 아니다.
- [ ] **save는 복사본을 넘기고 자기 리스트를 비운다** — 어떻게 저장할지는 스토어의 관심사다.
- [ ] **불변식은 여전히 애그리게이트 루트가 진다.** 그래서 내부 객체를 외부에 노출하지 않는다 — 노출하면 불변식을 우회한다.
