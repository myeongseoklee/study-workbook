# 11. PostgreSQL을 브로커로 — PGMQ

## 학습 목표

이 문서는 **강의 밖의 보강**이다. 08장의 채널 정책이 실제 도구에서 어떤 이름으로 나타나는지 보고, "카프카 대신 PostgreSQL 확장"이라는 선택이 무엇을 얻고 무엇을 포기하는지 판단할 수 있게 한다.

## 선수 지식

- 08장: 발행-구독의 주인공은 채널이고, 브로커 설정은 채널 정책의 목록이라는 결론
- 05장: 팩트 이벤트는 확정 후에 발급해야 한다는 요구 — 이 문서의 트랜잭션 절이 그 요구와 만난다

## 핵심 원리 (WHY) — 왜 RDB를 브로커로 쓰나

이 문서를 붙인 계기는 다른 강의 시리즈의 한 문장이다.

> PGVector는 원래 PostgreSQL에 벡터 익스텐션 꽂은 거거든요. **여기다가 카프카를 대신한 이벤트 스트림 플러그인도 꽂을 거예요.** 이걸 베이스로 해서 돌릴 거고요. — 코딩 에이전트 시리즈 2강

온프레미스 납품에서 이 선택이 갖는 값은 분명하다. 카프카를 추가하면 **운영 대상이 하나 더 늘고**, 고객사 보안 심사와 설치 절차도 함께 늘어난다. 이미 PostgreSQL이 있다면 그 안에서 큐를 해결하는 편이 싸다.

**PGMQ**(PostgreSQL Message Queue)가 그 도구다. 외부 워커나 별도 프로세스 없이 **순수 SQL 객체로 구현된** 경량 메시지 큐이고, AWS SQS·RSMQ와 비슷한 시맨틱을 제공한다. ([공식 저장소](https://github.com/pgmq/pgmq))

## 필수 지식 (HOW) — 핵심 시맨틱: Visibility Timeout

PGMQ의 중심 개념은 하나다.

**VT(visibility timeout)** — 메시지를 읽으면 지정한 초 동안 **다른 소비자에게 보이지 않는다.** 그 시간 안에 삭제하거나 보관하지 않으면 **자동으로 다시 나타난다.**

이 하나가 두 가지를 동시에 해결한다.

| 문제 | VT가 어떻게 푸나 |
|---|---|
| 두 소비자가 같은 메시지를 처리 | 읽은 순간 감춰지므로 중복 소비를 막는다 |
| 소비자가 처리 중 죽음 | VT가 지나면 다시 보이므로 **메시지가 유실되지 않는다** |

즉 "처리 완료를 명시적으로 알려야 사라진다"는 구조다. 09장의 표현을 빌리면 — **한 번 달성되면 잊는** 시스템이 아니라, 달성을 확인받기 전까지 붙잡고 있는 쪽이다.

주요 연산은 넷이다.

| 연산 | 뜻 |
|---|---|
| `read` | 메시지를 읽고 VT를 건다 |
| `pop` | 읽고 즉시 삭제 (VT 없음) |
| `delete` | 완전히 제거 |
| `archive` | **보관 테이블로 이동** |

## 필수 지식 (HOW) — archive가 이벤트 소싱과 만나는 지점

`archive`가 이 문서를 이 패키지에 넣은 이유다.

삭제 대신 보관 테이블로 옮기면 메시지가 **남는다.** 그리고 남은 것은 다시 읽을 수 있다 — 06장의 재수화가 요구하는 것이 정확히 이것이다. 이벤트 로그가 남아 있어야 상태를 복원할 수 있다.

정리하면 이렇게 대응한다.

| 이 패키지의 개념 | PGMQ에서 |
|---|---|
| 채널 (08장) | 큐 / 토픽 패턴 라우팅 |
| 팩트 이벤트를 남긴다 (05장) | `archive`로 보관 테이블에 적재 |
| 재수화 (06장) | 보관된 메시지를 다시 읽어 재생 |
| 순서 보장이 필요한 구간 | FIFO 큐 (메시지 그룹 키) |
| 팬아웃 (08장) | 토픽 와일드카드 패턴 구독 |

## 필수 지식 (HOW) — 얻는 것과 포기하는 것

**얻는 것**

- **운영 대상이 늘지 않는다.** PostgreSQL 하나로 큐까지 처리한다 — 온프레미스에서 특히 크다
- **트랜잭션 안에서 발행할 수 있다.** 이것이 05장의 요구와 직결된다. 업무 데이터 저장과 이벤트 발행이 **같은 트랜잭션**에 들어가면, "확정되지 않은 사실을 이벤트로 발급"하는 실수가 구조적으로 막힌다. 별도 브로커를 쓸 때 이 문제를 풀려고 **아웃박스 패턴**을 도입하는데, 큐가 같은 DB에 있으면 그 패턴이 필요 없어진다
- 백업·복구·권한 관리가 DB 절차에 흡수된다

**포기하는 것**

- **스트리밍 처리량.** PGMQ는 스트리밍보다 **작업 큐**에 맞춰져 있다. 카프카급 처리량·보존·파티셔닝을 기대하는 자리에는 맞지 않는다
- DB가 병목이면 큐도 함께 병목이 된다 — 부하가 한 자원에 모인다
- 카프카 생태계(스트림 처리·커넥터·컨슈머 그룹 도구)를 쓸 수 없다

**언어 클라이언트**는 Rust·Python이 공식이고, Go·Java·Kotlin·Node.js/TypeScript 등 20여 개가 커뮤니티 지원이다. PostgreSQL 14~18을 지원한다.

## 필수 지식 (HOW) — 설치

Docker 이미지가 가장 간단하다.

```bash
docker run -d --name pgmq-postgres \
  -e POSTGRES_PASSWORD=postgres -p 5432:5432 \
  ghcr.io/pgmq/pg18-pgmq:v1.10.0
```

그다음 확장을 켠다.

```sql
CREATE EXTENSION pgmq;
```

확장 설치가 막힌 환경(관리형 DB 등)에서는 **SQL 파일만 실행하는 방식**도 제공된다 — 확장 권한 없이도 쓸 수 있다는 뜻이고, 이것이 온프레미스·관리형 양쪽에서 값을 한다.

> **버전·이미지 태그는 확인 시점(2026-08) 기준이다.** 최신 값은 공식 저장소를 본다.

## 이 지식이 판단에 쓰이는 자리

- **브로커를 추가할지 결정할 때**: 이미 PostgreSQL이 있고 요구가 **작업 큐**라면 확장으로 끝날 수 있다. 스트리밍이 필요하면 카프카를 본다.
- **"확정 후 발급"을 보장해야 할 때**: 큐가 같은 DB에 있으면 **같은 트랜잭션**으로 묶을 수 있고, 아웃박스 패턴이 불필요해진다.
- **온프레미스 납품을 준비할 때**: 운영 대상 개수가 곧 설치·심사 비용이다. 하나로 줄이는 선택의 값이 여기서 커진다.
- **재생이 필요할 때**: 삭제 대신 `archive`를 쓴다 — 보관된 메시지가 재수화의 입력이 된다.

### ⚠️ 암기 필수

- [ ] **PGMQ = PostgreSQL 확장으로 구현된 경량 메시지 큐**(SQS류). 외부 워커·별도 프로세스가 없다.
- [ ] **핵심은 VT(visibility timeout)** — 읽으면 일정 시간 감춰지고, 그 안에 delete/archive 하지 않으면 **다시 나타난다.** 중복 소비와 소비자 사망을 한 개념으로 막는다.
- [ ] **`archive`는 삭제가 아니라 보관 테이블로 이동**이므로 **재생이 가능하다** — 이벤트 소싱의 재수화와 직결된다.
- [ ] **같은 DB에 큐가 있으면 업무 저장과 이벤트 발행을 한 트랜잭션에 묶을 수 있다** → "확정되지 않은 사실을 발급"하는 실수가 구조적으로 막히고 **아웃박스 패턴이 불필요**해진다.
- [ ] **포기하는 것은 스트리밍 처리량**이다. PGMQ는 작업 큐용이고, DB가 병목이면 큐도 함께 병목이 된다.
