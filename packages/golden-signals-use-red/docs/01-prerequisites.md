# 01. 선수 지식 — 신호를 읽기 전에 알아야 하는 다섯 가지

## 학습 목표

이 파일을 읽으면 뒤 문서에서 설명 없이 쓰는 다섯 개념(SLI/SLO, 백분위수, 누적 히스토그램, 큐와 사용률, 자원)의 뜻을 정확히 말할 수 있다. 이미 아는 개념은 건너뛰어도 된다.

## 1. SLI · SLO · SLA — 셋이 다른 것

| 용어 | 무엇인가 | 형태 |
|---|---|---|
| **SLI** (Service Level Indicator) | 서비스 품질을 재는 **측정값** | "성공 요청 비율", "p99 응답 시간" |
| **SLO** (Service Level Objective) | 그 측정값에 대한 **내부 목표** | "p99 응답 시간 ≤ 300ms를 30일 중 99.9%" |
| **SLA** (Service Level Agreement) | 목표를 못 지켰을 때의 **계약상 배상** | "월 가용성 99.5% 미달 시 요금 10% 환급" |

세 개를 섞으면 판단이 흐려진다. **SLI는 사실이고, SLO는 우리가 정한 선이며, SLA는 돈이다.** 이 자료에서 "실패"라고 부르는 것 중 하나는 SLO를 기준으로만 정의된다([07](07-slo-and-error-budget.md) § 정책적 실패). SLA는 이 자료의 범위 밖이다.

SLO가 없으면 "느리다"는 말이 판단이 되지 못한다. 300ms가 느린지 빠른지는 시스템이 대답할 수 없고, 우리가 정해야 한다.

## 2. 백분위수 — p99가 뜻하는 것

**p99 = 전체 요청을 응답 시간 순으로 줄 세웠을 때, 하위 99% 지점의 값.** "요청 100개 중 가장 느린 1개를 뺀 나머지가 이 값 안에 들어온다"는 뜻이다.

읽는 법에서 가장 흔한 오해는 방향이다.

- **틀림**: "p99가 5초면 사용자 1%가 5초를 기다린다" → 정확히는 **1%가 5초 이상**을 기다린다. 5초는 그 1%의 *하한*이고, 그중 누군가는 30초를 기다리고 있다
- **틀림**: "p50이 좋으면 서비스가 건강하다" → p50은 절반의 이야기이고, 나머지 절반은 아무것도 말하지 않는다

그래서 실무에서는 p50(중앙값)·p95·p99·p99.9를 **함께** 본다. p50은 "평상시 체감", p99는 "가장 아픈 사람들의 하한", 둘의 간격은 "분포가 얼마나 벌어졌는가"를 말한다.

**평균(mean)은 백분위수가 아니다.** 평균은 모든 값을 더해 개수로 나눈 것이라, 극단값 하나가 전체를 끌어올릴 수도 있고 다수에 묻혀 사라질 수도 있다. 어느 쪽인지 평균만 봐서는 알 수 없다 — 이것이 [05](05-percentiles-and-histograms.md)의 주제다.

## 3. 누적 히스토그램 — 지표 시스템이 실제로 저장하는 형태

모니터링 시스템은 모든 요청의 응답 시간을 다 저장하지 않는다. 그러면 저장 비용이 요청 수에 비례해 폭발한다. 대신 **경계값을 미리 정해 두고 "그 경계 이하가 몇 건인지"만 센다.**

```
le=0.1  → 1200건   (100ms 이하 요청 누적 1200건)
le=0.3  → 1900건   (300ms 이하 요청 누적 1900건)  ← 0.1~0.3 구간은 700건
le=1.0  → 1980건
le=+Inf → 2000건   (전체 요청 수)
```

`le`는 *less or equal*이고, 각 버킷은 **누적**이다. 그래서 `le=+Inf`가 항상 전체 건수다. 이 구조에서 분위수를 구하는 것은 계산이 아니라 **추정**이며, 오차의 크기가 버킷 폭에 묶인다. 이것도 [05](05-percentiles-and-histograms.md)에서 다룬다.

## 4. 큐 · 사용률 · 대기 시간 — 왜 셋을 같이 보나

- **사용률(utilization, ρ)** — 자원이 일하고 있던 시간의 비율. 0~1(또는 0~100%)
- **큐(queue)** — 자원이 지금 처리할 수 없어서 밀려 대기 중인 일감
- **대기 시간(wait)** — 큐에 앉아 있던 시간. 요청의 응답 시간은 `대기 시간 + 처리 시간`이다

핵심은 이 셋이 **선형 관계가 아니라는** 것이다. 사용률이 50%에서 60%로 오를 때 대기 시간이 늘어나는 폭과, 90%에서 95%로 오를 때 늘어나는 폭이 전혀 다르다. 이 비선형성이 "자원은 100%가 되기 전에 이미 무너진다"의 수학적 근거이고, [06](06-saturation-and-queueing.md)에서 식으로 확인한다.

## 5. 자원(resource)이란 무엇인가 — USE를 읽기 위한 정의

USE Method에서 **자원은 "서비스 요청을 처리하는 물리적 서버의 기능 구성요소"**다. Brendan Gregg의 원문 표현으로는 *"all physical server functional components (CPUs, disks, busses, ...)"* ([USE Method](https://www.brendangregg.com/usemethod.html)).

즉 자원 목록은 이렇게 나온다: CPU, 메모리, 네트워크 인터페이스, 스토리지 장치, 스토리지 용량, 컨트롤러, 인터커넥트.

**소프트웨어 구성요소도 자원이 될 수 있지만 범위가 좁다.** Gregg는 이 방법이 *"usually applies to smaller components of software, not entire applications"* — 뮤텍스 락, 스레드 풀, 프로세스/스레드 용량 같은 **작은 것**에 적용된다고 명시한다. "결제 서비스"는 USE의 자원이 아니다. 그것을 보는 것이 RED의 일이다([04](04-red-method.md)).

이 경계를 처음부터 잡아두지 않으면 "USE를 마이크로서비스에 적용해 보자"는 잘못된 시도로 시간을 쓴다. 실제로 RED가 만들어진 계기가 그것이었다.
