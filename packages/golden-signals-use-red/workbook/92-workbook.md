## 파트 1. 회수 연습 (자료를 덮고)

> 정답: [93-solutions.md](93-solutions.md) 파트 1. 문항은 `docs/90-must-memorize.md`의 카드 1~16과 1:1 대응한다.

**1-1.** 세 프레임워크(Four Golden Signals · USE · RED)의 **저자와 보는 대상**을 각각 쓰고, 각각이 대답하는 질문을 한 문장으로 써라.

**1-2.** Four Golden Signals 네 개를 쓰고 각각을 한 줄로 정의하라. 원문에서 이 넷의 적용 대상을 한정하는 표현은 무엇이며, 그 한정어가 왜 중요한가?

**1-3.** USE의 세 항목을 쓰고 각각의 **표현 단위**를 대라. 그리고 세 항목의 **판정 기준이 서로 다르다** — 각각의 기준을 쓰라.

**1-4.** RED의 세 항목을 쓰고, Golden Signals의 어느 신호가 빠졌는지, **왜 뺐는지**를 답하라.

**1-5.** 레이턴시에 평균을 쓰면 안 되는 이유를 구체적 수치 예로 설명하라. 좋은 SLI와 나쁜 SLI를 각각 한 줄로 써라.

**1-6.** 성공 레이턴시와 실패 레이턴시를 분리하는 이유를 쓰라. 분리와 동시에 SRE Book이 주는 **반대 방향의 주의**는 무엇인가?

**1-7.** 에러의 세 종류를 쓰고, 각각이 어디서 잡히는지 대라. 셋 중 가장 위험한 것은 무엇이며 왜인가?

**1-8.** Utilization의 두 가지 정의를 쓰고, 각각에서 100%가 무엇을 뜻하는지 답하라. 이 구분이 실무에서 사고를 만드는 구체적 사례를 하나 대라.

**1-9.** "5분 평균 CPU 사용률 20%"인 서버에서 p99가 튀고 있다. 어떻게 이런 일이 가능한지 설명하고, 그래서 무엇을 별도로 재야 하는지 답하라.

**1-10.** p99 = 1초인 서버 100개에 팬아웃하는 요청이 있다. 1초를 넘기는 사용자 요청의 비율을 계산식과 함께 쓰라. 이 계산이 뜻하는 것을 한 문장으로 요약하라.

**1-11.** `avg(p99)`가 틀린 값인 이유를 인스턴스 두 개짜리 예로 설명하라. 올바른 계산 순서는 무엇이고, Summary와 Histogram 중 어느 것이 그것을 가능하게 하는가?

**1-12.** 누적 히스토그램에서 φ 분위수를 구하는 절차 네 단계를 쓰라. 이 값의 **오차가 무엇에 묶이는지**, 그리고 그 오차를 줄이는 실무 규칙 하나를 답하라.

**1-13.** 사용률 ρ에서의 지연 배수 식을 쓰고, ρ = 50 / 80 / 90 / 95%의 배수를 대라. 그리고 "허용 지연 배수 k"에서 목표 사용률을 역산하는 식을 쓰라.

**1-14.** 에러 예산의 정의를 쓰고, 99.9% SLO의 30일 예산을 **분 단위로** 계산하라. 소진율의 정의식과 고갈 시간 계산식을 쓰고, 소진율 10과 1,000일 때의 고갈 시간을 답하라.

**1-15.** 99.9% SLO에 권장되는 다중 창·다중 소진율 알림 **세 규칙**을 표로 재현하라(긴 창 / 짧은 창 / 소진율 / 심각도). 짧은 창의 길이 규칙과 **역할**을 답하라.

**1-16.** 인과 사슬을 순서대로 쓰고, 그 사슬이 성립하는 **전제**를 답하라. 전제가 깨지는 대표 사례와, 그때 하면 안 되는 조치를 하나 대라.

## 파트 2. 판단 문제 (시나리오)

> 해설: [93-solutions.md](93-solutions.md) 파트 2. 각 문항에 **선택과 근거**를 모두 적어라.

**2-1.** 새벽 3시에 호출을 받았다. 대시보드에서 관측된 것은 다음과 같다.

```
Traffic     : 평상시와 동일 (변화 없음)
Saturation  : CPU 35%, 메모리 40% (평상시와 동일)
Latency p99 : 200ms → 4,200ms (20분 전부터)
Errors      : 0.1% → 12% (12분 전부터)
```

무엇을 원인 방향으로 보고, 어떤 순서로 확인하겠는가? 그리고 **이 상황에서 인스턴스를 2배로 늘리면** 무슨 일이 일어나는가?

**2-2.** 동료가 대시보드를 개선해 왔다. "CPU·메모리 그래프를 서비스별로 40개 붙였고, 알림은 CPU 80%로 통일했습니다."

이 대시보드가 놓치는 것을 세 가지 대고, 각각을 어떻게 교정할지 쓰라. 그리고 "CPU 80% 통일"이 특히 위험한 이유를 [06](../docs/06-saturation-and-queueing.md)의 계산으로 설명하라.

**2-3.** 두 서비스의 지연 SLO를 정한다. (A) 상품 검색 API — p50 40ms, 타임아웃 1초. (B) 리포트 생성 API — p50 3초, 타임아웃 30초.

각각의 목표 사용률을 정하고 근거를 대라. 두 서비스에 같은 "CPU 80% 알림"을 적용하면 어느 쪽에서 무슨 문제가 생기는가?

**2-4.** SLO를 "p99 응답 시간 ≤ 300ms"로 잡았다. 히스토그램 버킷은 `[0.1, 0.25, 0.5, 1.0, +Inf]`다.

(a) 이 구성에서 SLO 판정에 어떤 문제가 있는가? (b) 오차의 크기를 구체적으로 계산해 보이라(모든 관측이 0.25~0.5 구간에 몰린 경우). (c) 어떻게 고칠 것이며, SLO 문장 자체를 어떻게 다시 쓰면 더 나은가?

**2-5.** 팀이 "에러율 5% 초과 30분 지속이면 호출"이라는 알림을 쓰고 있다. SLO는 99.9%, 기간은 30일이다.

(a) 완전 장애(에러율 100%)가 났을 때 이 알림이 뜨기까지 예산의 몇 %를 소비하는가? (b) 반대로 임계값을 "1분간 1%"로 낮추면 어떤 문제가 생기는가? (c) 두 실패가 **같은 원인**에서 온다는 것을 설명하고, 소진율 알림이 그것을 어떻게 고치는지 쓰라.

**2-6.** 마이크로서비스 40개짜리 시스템에 RED를 도입하려 한다. 동료가 "일단 트래픽 많은 5개에만 붙이고 효과를 보자"고 제안한다.

이 제안을 평가하라. RED의 실제 산출물이 무엇인지에 근거해 답하고, 만약 점진 도입을 하더라도 **무엇은 처음부터 전면 통일해야 하는지** 대라.

**2-7.** 큐 컨슈머의 대시보드가 이렇다: `Rate 1,000/s · Errors 0% · Duration p99 12ms`. 전부 초록이다. 그런데 사용자는 "주문 확인 메일이 3시간 뒤에 온다"고 항의한다.

무슨 일이 일어나고 있는가? 어떤 지표를 추가해야 하는가? 이 사례가 RED의 어떤 전제를 드러내는가?

**2-8.** NVMe SSD를 쓰는 DB 서버에서 `iostat`이 `%util 100%`를 보고한다. 동료가 "디스크가 병목이니 더 빠른 디스크로 바꾸자"고 한다.

이 판단이 왜 근거가 부족한지 설명하고, 무엇을 대신 봐야 하는지 대라. 그리고 만약 실제로 디스크가 병목이라면 어떤 값이 그것을 말해 주는가?

**2-9.** 결제 API가 잘못된 금액을 반환하는 버그가 3일간 프로덕션에 있었다. 모든 대시보드는 그 3일간 초록이었고, 고객 문의로 발견됐다.

(a) 어떤 종류의 실패였는가? (b) 왜 어떤 지표도 반응하지 않았는가? (c) 다음에 같은 종류를 잡으려면 무엇을 만들어야 하는가? (d) 이 실패를 에러 예산에 넣으려면 무엇이 필요한가?

**2-10.** 세 프레임워크를 전부 도입한 팀에서, 장애 조사가 USE 체크리스트까지 내려갔고 모든 자원이 초록이었다. 조사를 여기서 끝내도 되는가? 근거를 원저자의 문장으로 대고, 다음에 무엇을 볼지 답하라.

## 파트 3. 코딩 과제 — 작은 모니터링 시스템 만들기

> 참고 구현: `solutions/{과제번호}/`. **먼저 열지 마라** — 열면 과제가 독해로 바뀐다.
> 명세는 `tests/{과제번호}/index.test.ts`이고, 그것을 **먼저 읽는 것이 순서다.**

일곱 과제가 하나의 파이프라인을 이룬다. 순서대로 풀면 신호 추출부터 알림·트리아지까지 조립된다.

```
  02-01  신호 추출기         ──┐
  05-01  히스토그램 분위수   ──┤
  06-01  목표 사용률         ──┼──▶  08-01  인과 사슬 트리아지
  07-01  소진율 알림         ──┘            (앞의 값들이 모여 판단이 되는 자리)

  03-01  USE 진단기          ────▶  자원 쪽 분기 — 어느 자원이 병목인가
  04-01  RED 집계기          ────▶  서비스 쪽 분기 — 어느 서비스가 문제인가
```

**3-1. 네 신호 추출기** — 과제 `02-01`

요청 이벤트 스트림에서 Golden Signals를 뽑는다. 세 종류의 실패를 분류하고, 성공/실패 레이턴시를 분리한다.

```bash
node .claude/skills/study-progress/scripts/progress.js start golden-signals-use-red 02-01
cd .sol/golden-signals-use-red/02-01/packages/golden-signals-use-red
pnpm test 02-01
```

가장 틀리기 쉬운 곳: **범주별 카운트와 에러율의 분자가 다르다.** 그리고 레이턴시 분리 기준에 세 범주 중 어느 둘이 들어가는지.

읽을 문서: `docs/02-golden-signals.md` § Errors, § Latency

**3-2. USE 진단기** — 과제 `03-01`

자원별 U/S/E 샘플을 판정하고 무엇을 먼저 볼지 순서를 낸다.

가장 틀리기 쉬운 곳: **세 항목의 임계 규칙이 다르다**(70 / 0 / 증가 중). 그리고 `null`(관측 공백)을 정상으로 처리하지 않는 것.

읽을 문서: `docs/03-use-method.md` § 해석 규칙

**3-3. RED 집계기** — 과제 `04-01`

스팬 목록에서 서비스별 Rate·Errors·Duration을 만들고, 동형성이 깨진 곳을 찾는다.

가장 틀리기 쉬운 곳: `percentile`의 **off-by-one**. 그리고 행 정렬 기준이 심각도가 아닌 이유.

읽을 문서: `docs/04-red-method.md` § 측정 지점

**3-4. 히스토그램 분위수** — 과제 `05-01`

누적 버킷에서 선형 보간으로 분위수를 추정하고, 여러 인스턴스의 버킷을 합친다.

가장 틀리기 쉬운 곳: **구간 건수는 누적의 차다**(그 버킷의 누적이 아니다). 첫 버킷의 하한, `+Inf` 버킷 안에 분위수가 있을 때의 처리, `+Inf` 버킷이 없는 입력.

읽을 문서: `docs/05-percentiles-and-histograms.md` § 손으로 해 보기

**3-5. 목표 사용률 계산기** — 과제 `06-01`

사용률 ↔ 지연 배수를 양방향으로 계산하고, 목표까지 필요한 용량 배수를 낸다.

가장 틀리기 쉬운 곳: ρ ≥ 1과 ρ < 0의 처리. `capacityFactorFor`에서 **비율의 방향**.

읽을 문서: `docs/06-saturation-and-queueing.md` § 목표 사용률을 역산한다

**3-6. 소진율 알림** — 과제 `07-01`

에러율을 소진율로 바꾸고, 두 창을 함께 보아 발화를 결정한다. 표준 세 규칙을 상수로 채우는 것도 과제의 일부다.

가장 틀리기 쉬운 곳: 고갈 시간에서 **소진율이 분모에 온다.** 그리고 두 창이 **모두** 참일 때만 발화한다는 조건.

읽을 문서: `docs/07-slo-and-error-budget.md` § 다중 창·다중 소진율 알림

**3-7. 인과 사슬 트리아지** — 과제 `08-01`

네 신호 시계열에서 무엇이 먼저 움직였는지 찾아 원인 방향과 조치를 낸다.

가장 틀리기 쉬운 곳: 기준선을 **앞 구간으로만** 만드는 것(전체 평균을 쓰면 스파이크가 자기를 정상으로 만든다). σ = 0의 처리. 동점일 때 사슬 앞쪽을 고르는 것.

읽을 문서: `docs/02-golden-signals.md` § 인과 사슬 / `docs/08-composing-the-three.md`

**자주 나오는 오해 패턴** — 위 표를 채운 뒤 자기 답이 이 중 어디에 해당하는지 표시해 보라.

1. **방향 뒤집기** — 고갈 시간에 소진율을 곱한다 / `capacityFactorFor`의 비율을 뒤집는다 / Latency 증가를 Saturation의 결과가 아니라 원인으로 읽는다
2. **경계 처리 누락** — `>` 대 `>=`(정책적 실패, 사용률 70%) / off-by-one(`percentile`) / 첫 버킷의 하한
3. **분모 착각** — 에러율의 분자를 범주 합으로 쓴다 / 히스토그램 구간 건수를 누적으로 쓴다 / Rate와 Errors를 다른 관측 지점에서 센다
4. **없음을 정상으로 읽기** — `null` 관측을 ok로 / 측정값 없는 알림 규칙을 통과로 / `+Inf` 버킷 없는 히스토그램을 계산
5. **전제 무시** — 인과 사슬을 모든 장애에 적용 / `%util`을 병렬 자원에 적용 / RED를 큐 컨슈머에 적용 / USE 초록을 "문제 없음"으로 결론
