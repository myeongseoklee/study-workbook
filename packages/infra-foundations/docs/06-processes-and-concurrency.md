# 06. 프로그램은 어떻게 여러 일을 처리할까 — 프로세스·대기·동시성

## 출발 상황과 선수 지식

[01장](01-computers-and-programs.md)의 CPU·메모리·프로세스와, [03장](03-dns-and-http.md)의 요청·응답을 알고 시작한다. 주문 앱 하나에 손님 세 명의 요청이 거의 동시에 들어왔다고 하자. 한 요청이 저장을 기다리는 동안 다른 요청도 처리할 수 있을까?

## 1. CPU를 쓰는 시간과 기다리는 시간

연필 가격에 수량을 곱하는 것은 CPU가 명령을 수행하는 계산이다. 다른 컴퓨터에 재고를 물은 뒤 답을 기다리는 것은 다른 종류의 시간이다. 기다리는 동안 주문 요청이 끝나지는 않았지만, 내 CPU가 계속 계산해야 하는 것은 아니다.

디스크나 네트워크처럼 데이터를 외부와 주고받는 작업을 **입출력(I/O)**이라고 한다. 느린 요청의 시간을 계산과 입출력 대기로 나누면 왜 CPU가 낮아도 서비스가 느릴 수 있는지 설명할 수 있다.

## 2. 운영체제는 실행할 차례를 배정한다

한 CPU 코어가 명령을 실행할 수 있는 양에는 한계가 있다. 여러 프로세스가 실행을 원하면 운영체제가 차례를 배정한다. 이 배정을 **스케줄링**이라고 한다.

프로세스가 외부 응답을 기다려 지금 계산할 수 없다면, 운영체제는 실행 가능한 다른 작업에 CPU를 줄 수 있다. 사용자는 여러 프로그램이 동시에 움직이는 것처럼 볼 수 있다.

실제로 같은 시각에 여러 명령 흐름을 실행하려면 여러 CPU 코어 같은 실행 자원이 필요하다. **동시성**은 여러 일을 진행 중으로 다루는 성질이고, **병렬성**은 실제로 같은 시간에 일을 실행하는 성질이다.

## 3. 작은 시간표로 차이를 보기

다음 시간과 작업량은 설명용 가정이다. A 요청은 1단계에서 계산하고, 2~4단계 동안 외부 답을 기다린 뒤 5단계에 마무리한다.

| 단계 | A 요청 | 다른 요청 B |
|---|---|---|
| 1 | CPU로 계산 | 아직 시작하지 않음 |
| 2 | 외부 응답 대기 | CPU로 계산 가능 |
| 3 | 외부 응답 대기 | 다른 작업 수행 가능 |
| 4 | 외부 응답 대기 | 다른 작업 수행 가능 |
| 5 | 응답을 받아 마무리 | 실행 자원에 따라 차례 조정 |

A의 대기를 처리할 수 있도록 실행 구조를 만들면 그동안 B를 진행할 수 있다. 하지만 A가 1~5단계 내내 CPU 계산을 해야 한다면 같은 실행 자원에서 시간을 저절로 겹칠 수는 없다.

## 4. 스레드는 프로세스 안의 실행 흐름이다

한 프로세스 안에 여러 실행 흐름을 둘 수 있다. 이 실행 흐름을 **스레드**라고 한다. 스레드들은 프로세스의 메모리와 자원을 공유한다.

공유는 편리하지만 주의가 필요하다. 두 스레드가 같은 재고 값을 읽고 동시에 하나씩 줄이면 서로의 변경을 덮을 수 있다. 이런 **동시 접근**을 조정하는 장치 중 하나가 잠금이다. 잠금은 특정 작업 구간에 들어갈 차례를 조정해 동시에 부딪히지 않게 한다. 실제 데이터 예제는 09장에서 살펴본다.

프로세스는 별도의 메모리 상태를 가진다는 01장의 설명과 비교하자. 스레드끼리의 공유와 서로 다른 프로세스의 데이터 교환은 다른 상황이다.

## 5. 비동기는 기다림을 다루는 방식이다

어떤 작업이 끝날 때까지 그 실행 흐름이 기다리는 방식을 **동기 방식**이라고 부를 수 있다. 작업을 요청한 뒤 다른 일을 진행하고, 완료 통지를 받으면 이어서 처리하는 방식은 **비동기 방식**이다.

예를 들어 A의 저장을 요청하고 B의 검증을 처리하다가, A 저장 완료가 알려지면 A 응답을 마무리할 수 있다. 다만 실행 구조가 그런 순서를 지원해야 한다. 함수 이름에 async를 붙이는 것만으로 오래 걸리는 계산이 별도 CPU에서 실행되지는 않는다.

Node.js의 **이벤트 루프**는 준비된 작업과 완료 통지를 받아 처리 흐름을 이어가는 구조다. 그 흐름에서 긴 동기 계산을 계속하면 다른 요청의 처리도 밀릴 수 있다. 이 교재에서는 특정 런타임의 함수를 외우기보다 계산과 대기, 이어 실행할 흐름을 구분한다.

## 6. 대기 중에도 메모리는 필요하다

A가 외부 답을 기다릴 때도 어떤 주문인지와 이어 할 작업을 기억해야 한다. 그래서 대기 요청이 늘면 들고 있는 상태와 메모리가 늘 수 있다.

설명용으로 요청 하나가 50 KiB를 유지하고 2,000개가 기다린다고 가정하면, 그 상태만 `50 × 2,000 = 100,000 KiB`, 약 97.7 MiB다. 1 KiB는 1,024바이트, 1 MiB는 1,024 KiB다. 실제 프로세스에는 다른 사용량도 더해진다.

따라서 “CPU가 낮으니 아무 부담이 없다”는 판단은 부족하다. CPU 사용, 기다리는 작업 수, 메모리 보유를 따로 관찰해야 한다.

## 7. 종료 요청과 강제 종료

운영체제는 프로세스에 **시그널**이라는 알림을 보낼 수 있다. `SIGTERM`은 종료 요청이다. 프로그램은 처리기를 작성해 이 알림을 받고 진행 중 작업을 정리할 수 있다.

`SIGKILL`은 잡거나 무시할 수 없는 강제 종료다. 정리 코드를 실행할 기회를 주지 않는다. 정리할 기회가 있어도 무한히 기다릴 수는 없으므로 실제 실행 환경은 종료 제한 시간을 둘 수 있다.

손님에게 답을 보내는 중인 서버를 교체할 때 이 차이가 중요하다. 어떻게 종료를 요청하고 얼마나 기다릴지는 13장에서 배운다.

## 직접 관찰하기

다음 명령은 macOS·Linux의 일반 셸 기준이다. `sleep 120`은 120초 동안 기다리는 프로그램이다. 다른 사람의 프로세스에는 종료 신호를 보내지 않는다.

```bash
sleep 120 &
study_sleep_pid=$!
ps -p "$study_sleep_pid" -o pid=,ppid=,stat=,comm=
kill -TERM "$study_sleep_pid"
wait "$study_sleep_pid"
```

`&`는 기다리지 않고 백그라운드에서 시작하라는 셸 문법이다. `$!`는 방금 시작한 자식의 PID다. **PID**는 실행 중인 프로세스를 구분하는 번호다. `ps`는 그 프로세스를 보여 주고, `kill -TERM`은 종료 요청을 보낸다. `wait`는 자식이 끝날 때까지 기다리고 종료 결과를 받는다.

정상적으로 TERM으로 끝났어도 `wait`는 0이 아닌 상태를 줄 수 있다. 이 실습에서 확인한 것은 자기 자식의 실행과 종료다. 웹 요청 보존까지 검증한 것은 아니다.

## 꼭 기억할 것

- **카드 07:** 요청의 시간에는 계산과 대기가 함께 있다. 비동기는 대기 중 다른 일을 진행하게 할 수 있지만 계산 자원을 저절로 늘리지 않는다.

## 자가 진단

<details><summary>CPU가 낮은데 주문 응답이 느릴 수 있는 이유 두 가지는?</summary>

외부 응답이나 디스크를 기다릴 수 있고, 잠금이나 사용할 자원의 차례를 기다릴 수도 있다. 요청이 끝나지 않았다는 사실과 CPU가 계산 중이라는 사실은 다르다.
</details>

<details><summary>스레드 두 개가 같은 재고 변수를 건드릴 때 왜 조정이 필요할까?</summary>

같은 메모리를 공유하므로 서로 오래된 값을 읽거나 변경을 덮을 수 있다. 작업 순서를 조정할 수단이 필요하다.
</details>

<details><summary>SIGTERM을 보낼 수 있으니 어떤 장애에서도 정리 코드가 실행될까?</summary>

그렇지 않다. 강제 종료나 호스트 장애에는 정리할 기회가 없을 수 있다.
</details>
