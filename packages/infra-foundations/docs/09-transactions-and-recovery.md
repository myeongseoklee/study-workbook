# 09. 재고와 주문을 함께 바꾸기 — 트랜잭션·동시성·복구

## 이 장에서 배울 것

함께 확정할 변경의 범위를 정하고, 동시 주문을 DB가 조정하는 과정을 따라간다. 변경 기록과 커밋 상태로 장애 뒤 데이터를 복구하는 원리를 설명하고, 복제·백업이 대비하는 실패를 구분한다.

## 출발 상황과 선수 지식

[08장](08-storage-and-databases.md)의 테이블·SQL·DB 연결과 메모리 버퍼를 사용한다. 연필 재고가 하나 남았다. 주문을 받으면 재고를 줄이고 주문 행을 만들어야 한다. 중간에 앱이 죽거나 두 손님이 동시에 주문하면 어떻게 될까?

DB마다 구현은 다르다. 이 장의 구체적인 동시 실행·복구 예는 PostgreSQL을 기준으로 설명한다. 설치나 실행은 필요하지 않다. SQL은 처리 의도를 읽는 예다.

## 1. 순서만 바꿔서는 중간 실패를 없애지 못한다

재고를 1에서 0으로 줄인 뒤 주문 42를 추가하려는데 앱이 종료되면 재고만 줄어들 수 있다. 반대로 주문을 먼저 추가하면 재고를 줄이기 전에 죽어 주문만 남을 수 있다. 두 작업의 순서를 바꾸는 것으로는 “둘 다 반영하거나 둘 다 반영하지 않는다”는 요구를 만족하지 못한다.

**트랜잭션**은 함께 확정할 DB 작업의 단위다. 단위 안의 변경을 모두 반영하거나 모두 취소하는 성질이 **원자성**이다. 원자성은 작업이 물리적으로 한순간에 실행된다는 뜻이 아니다. 중간 작업이 여럿이어도 확정 결과를 반쪽으로 남기지 않는다는 뜻이다.

앱이 시작을 요청하고 여러 SQL을 수행한 뒤 **커밋**으로 확정을 요청한다. 도중에 실패하면 **롤백**으로 그 단위의 변경을 취소한다. 이 상태는 특정 DB 연결에 속하므로 같은 연결에서 절차를 이어야 한다.

## 2. 재고 차감과 주문 기록을 어떤 단위로 묶을까

다음은 앱과 DB가 협력하는 절차다. 들여쓴 설명까지 포함한 의사 절차이며, 그대로 실행할 SQL 스크립트는 아니다.

```text
같은 DB 연결에서 BEGIN으로 시작
UPDATE products
  SET stock = stock - 1
  WHERE product_id = 7 AND stock >= 1;
변경된 행 수가 0이면 ROLLBACK하고 품절 응답
변경된 행 수가 1이면 orders에 주문 42를 INSERT
INSERT까지 성공하면 COMMIT
중간 오류가 나면 ROLLBACK
```

`BEGIN`은 시작, `UPDATE`는 기존 행의 변경, `INSERT`는 새 행 추가다. 조건부 UPDATE는 “재고가 있을 때 하나 줄여라”를 DB가 한 작업으로 판단하게 한다. **변경된 행 수를 확인하지 않고 무조건 주문을 추가하면 품절 주문을 막지 못한다.**

주문 추가가 실패해 롤백되면 같은 트랜잭션의 재고 차감도 확정되지 않는다. 반대로 커밋이 확정되면 두 변경을 함께 확정된 결과로 다룬다. 통신이 끊겨 커밋 응답을 못 받았다면 DB에서 실제로 확정했는지는 다시 확인해야 한다. 이 경우는 11장과 이어진다.

## 3. 트랜잭션 두 개가 있으면 동시 주문도 자동으로 맞을까

트랜잭션은 필요하지만, 이름만 붙이면 모든 동시 실행 오류가 사라지는 것은 아니다. 다음은 읽은 값을 앱에서 계산해 그대로 덮어쓰는 가상 절차다.

| 순서 | 요청 A의 기억 | 요청 B의 기억 | DB 재고 | 확정한 주문 수 |
|---|---|---|---|---|
| 1. A가 읽음 | 1 | 없음 | 1 | 0 |
| 2. B가 읽음 | 1 | 1 | 1 | 0 |
| 3. A가 자기 계산 0을 저장하고 주문 확정 | 0 | 여전히 1 | 0 | 1 |
| 4. B도 자기 계산 0을 저장하고 주문 확정 | 0 | 0 | 0 | 2 |

DB의 값이 바뀌어도 B의 메모리에 복사해 둔 1은 자동으로 바뀌지 않는다. 각 트랜잭션이 자체 변경을 함께 확정하더라도, 동시에 읽고 판단한 결과가 업무 요구에 맞는지는 별도로 조정해야 한다. 이것이 **격리**의 문제다.

## 4. 조건부 UPDATE를 두 요청이 동시에 실행하면

PostgreSQL의 Read Committed 격리에서 같은 재고 행을 바꾸는 사례를 따라가자. 앞의 조건부 UPDATE와 주문 추가를 각각 한 트랜잭션으로 묶었다고 가정한다.

1. A가 재고 1인 행을 갱신하면서 충돌하는 다른 변경이 동시에 진행하지 못하도록 행의 잠금을 유지한다.
2. B도 같은 행을 갱신하려 하면 A의 트랜잭션 종료를 기다릴 수 있다. 기다림은 B가 CPU로 재고를 계속 계산한다는 뜻이 아니다.
3. A가 주문을 추가하고 커밋한다. 재고는 0으로 확정된다.
4. B는 변경된 행에 `stock >= 1` 조건을 다시 확인한다. 이제 거짓이므로 변경 행 수가 0이고 주문을 추가하지 않는다.

A가 롤백했다면 재고 1을 기준으로 B가 변경을 진행할 수 있다. DB는 단순히 “한 번 읽은 값대로 나중에 써라”를 수행하는 것이 아니라, 같은 행의 경쟁과 조건 재평가를 조정한다. 다른 격리 수준에서는 충돌 오류가 나서 트랜잭션을 다시 시도해야 할 수도 있다.

잠금도 비용이 있다. 트랜잭션 안에서 외부 배송 응답까지 오래 기다리면 다른 재고 갱신이 막힐 수 있다. 서로 다른 순서로 여러 행을 잠그면 서로의 잠금 해제를 기다리는 **교착 상태**도 생길 수 있다. DB는 이를 감지해 한 트랜잭션을 실패시키기도 하므로 오류와 재시도를 설계해야 한다.

[PostgreSQL 격리 규칙](https://www.postgresql.org/docs/current/transaction-iso.html)과 [잠금](https://www.postgresql.org/docs/current/explicit-locking.html)을 이 예의 기준으로 삼았다.

## 5. 다른 요청에는 어느 시점의 값이 보일까

변경할 때마다 모든 읽기를 막으면 읽는 요청도 줄을 길게 선다. PostgreSQL은 **MVCC**, 즉 여러 버전의 행과 트랜잭션 정보를 이용하는 동시성 제어를 사용한다. 읽는 요청은 자신에게 보이는 시점의 버전을 선택해, 다른 트랜잭션이 바꾸는 중인 미확정 값을 그대로 읽지 않게 한다.

이때 읽기에 사용할 데이터 상태의 기준을 **스냅샷**이라고 한다. 사진 파일을 매 질의마다 복사한다는 뜻은 아니다. 어떤 트랜잭션의 변경을 보이게 할지 판단하는 기준이다. 일반적인 데이터 읽기와 쓰기의 충돌을 줄이지만, 같은 행을 동시에 변경하는 작업의 잠금까지 사라지는 것은 아니다.

| 격리 수준 | 이 장에서 구분할 핵심 |
|---|---|
| Read Committed | 문장 시작 전 확정된 데이터를 읽는다. 같은 트랜잭션의 다음 조회는 더 최근 변경을 볼 수 있다 |
| Repeatable Read | 트랜잭션의 스냅샷을 유지해 반복 조회의 기준을 안정시킨다. 모든 업무 경쟁을 자동 제거하지는 않는다 |
| Serializable | 결과가 트랜잭션들을 하나씩 실행한 것과 같도록 보장한다. 충돌로 실패한 작업을 다시 실행해야 할 수 있다 |

격리를 강하게 한다는 것은 모든 작업이 실제로 한 줄로만 실행된다는 뜻은 아니다. 허용할 결과를 더 엄격하게 제한한다는 뜻이다. [MVCC 설명](https://www.postgresql.org/docs/current/mvcc-intro.html)을 참고했다.

## 6. 메모리에서 바꾼 여러 페이지를 어떻게 장애 뒤에도 남길까

재고 페이지는 저장했지만 주문 페이지는 저장하기 전에 전원이 꺼질 수도 있다. 두 페이지를 같은 순간에 장치에 쓰는 것에만 의존하면 복구가 어렵다. PostgreSQL은 변경을 설명하는 기록인 **WAL(Write-Ahead Log)**을 데이터 페이지보다 먼저 영속 저장하는 원칙을 사용한다.

동기 커밋으로 영속 기록을 기다리는 사례는 다음과 같다. 저장 장치가 영속 쓰기 완료를 올바르게 보장하며, 데이터와 WAL이 보존되는 장애 범위를 가정한다.

| 단계 | 기억하거나 기록한 것 | 의미 |
|---|---|---|
| 변경 진행 | 재고·주문의 새 버전과 변경을 재현할 WAL | 아직 이 트랜잭션이 확정된 것은 아님 |
| 커밋 요청 | 필요한 WAL과 커밋 기록을 영속 저장 | 장애 뒤 확정 변경을 판별·복구할 근거 확보 |
| 성공 응답 | 앱이 커밋 결과를 받음 | 앱이 업무 성공을 알릴 근거 |
| 나중의 페이지 기록 | 바뀐 데이터 페이지도 저장 | 모든 페이지를 커밋 순간마다 쓰는 부담을 줄임 |

장애 뒤에는 WAL로 필요한 데이터 페이지 변경을 재현하고 트랜잭션의 확정 상태를 판단한다. 미확정 트랜잭션의 행 버전은 확정된 업무 결과로 보이지 않는다. 따라서 디스크 쓰기가 중간에 끊겨도 재고만 확정된 상태를 손님에게 보여 주지 않도록 복구할 수 있다.

**WAL이 원자성과 영속성의 전부는 아니다.** 행 버전·트랜잭션 상태·잠금 등과 함께 작동한다. 모든 DB가 같은 구현을 쓰는 것도 아니다. 비동기 커밋처럼 영속 기록 전에 성공을 반환하는 설정은 장애 때 최근 성공 작업을 잃을 수 있으므로, 설정을 무시하고 “커밋이면 어떤 장애에도 절대 보존”이라고 단정하면 안 된다.

[WAL 원리](https://www.postgresql.org/docs/current/wal-intro.html), [동기·비동기 커밋](https://www.postgresql.org/docs/current/wal-async-commit.html)을 참고했다.

## 7. ACID를 재고 예제로 연결하기

트랜잭션의 성질을 **ACID**라고 묶어 부른다. 이름을 외우기보다 서로 다른 요구임을 구분하자.

- **원자성(Atomicity):** 재고 차감과 주문 추가를 반쪽만 확정하지 않는다.
- **일관성(Consistency):** 제약과 올바른 작업으로 유효한 상태에서 유효한 상태로 옮긴다. DB가 “팔 수 없는 상품” 같은 모든 업무 규칙을 저절로 아는 것은 아니다.
- **격리(Isolation):** 동시 트랜잭션이 서로 어떤 변경을 보고 어떤 간섭을 허용하는지 정한다.
- **영속성(Durability):** 확정된 변경을 정한 장애·설정의 보장 안에서 유지한다.

`order_id`가 중복되면 안 된다는 것은 DB의 유일성 제약으로 표현할 수 있다. 하지만 주문을 전혀 추가하지 않는 앱을 DB가 알아서 고쳐 주지는 않는다. 올바른 트랜잭션 범위와 업무 로직을 정하는 책임은 앱 설계에 있다.

## 8. 내 DB 밖의 결제는 왜 롤백되지 않을까

외부 결제 회사가 결제를 확정한 뒤 내 DB의 주문 추가가 실패했다고 하자. 내 DB는 자기 트랜잭션의 변경을 취소할 수 있지만 다른 회사가 이미 실행한 효과까지 제어하지 않는다.

결제 상태 조회, 같은 결제 의도의 중복 방지, 취소·환불 같은 별도 절차가 필요하다. 이미 실행된 효과를 다른 작업으로 상쇄하는 것을 **보상**이라고 부른다. DB 롤백과 달리 보상도 지연되거나 실패할 수 있다. 함께 확정할 수 있는 경계를 먼저 정해야 하는 이유다.

## 9. 복제와 백업은 어떤 실패를 복구할까

**복제**는 변경을 다른 노드에도 전달해 사본을 유지한다. 비동기 복제는 주 노드가 성공을 반환한 뒤 사본이 따라올 수 있어 전환 시 최신 데이터가 부족할 수 있다. 동기 복제는 정해진 사본의 확인을 기다리는 만큼 지연·가용성의 조건이 달라진다. 구체적 보장은 복제 계약에 달려 있다.

복제는 현재 상태를 여러 곳에 두는 방법이다. 실수로 지운 주문도 복제될 수 있으므로 과거 상태 복구를 대신하지 않는다. **백업**과 그 뒤의 변경 기록을 보존하면 백업 시점부터 원하는 복구 시점까지 재현하는 방식을 구성할 수 있다. WAL도 데이터와 함께 모두 사라지면 그 장치만으로 복구할 수 없다.

**RPO**는 허용할 데이터 손실 시간, **RTO**는 복구까지 허용할 시간의 목표다. 가정상 12시에 사고가 났고 마지막 복구 가능 시점이 11시 50분이면 10분의 데이터가 빠질 수 있다. 복구가 12시 40분에 끝나면 중단 뒤 40분이 걸렸다. 목표와 실제 측정 결과를 비교해야 한다.

백업이 존재하는 것만으로 복구 성공을 판단하지 않는다. 별도 환경에 복원해 데이터와 앱 동작을 확인하고, 복원·연결 전환·검증까지 얼마나 걸리는지 측정한다. [백업](https://www.postgresql.org/docs/current/backup.html), [RPO·RTO](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-objectives.html)를 참고했다.

## 꼭 기억할 것

- **카드 10:** 트랜잭션은 정한 경계 안의 변경을 함께 확정하거나 취소한다. 내 DB 밖의 결제 효과까지 자동으로 되돌리지는 않는다.

</details>

<details><summary>데이터 페이지가 아직 모두 기록되지 않아도 확정 변경을 복구할 수 있는 이유는?</summary>

영속 저장된 WAL에 필요한 변경과 커밋의 근거가 있기 때문이다. 재시작 때 변경을 재현하고 확정 상태를 판단한다. 이 설명은 WAL과 저장 장치가 보존되는 장애 범위를 전제로 한다.
</details>

<details><summary>같은 트랜잭션의 조회 결과가 달라지면 언제나 DB 오류일까?</summary>

아니다. Read Committed에서는 두 문장 사이에 다른 트랜잭션이 커밋하면 다음 문장이 그 변경을 볼 수 있다. 어떤 격리 약속을 선택했는지 먼저 확인한다.
</details>

<details><summary>잘못된 삭제가 복제됐다면 정상인 복제본만으로 삭제 전 주문을 되찾을 수 있을까?</summary>

현재 상태의 복제본에도 삭제가 반영됐을 수 있다. 삭제 전 백업과 필요한 변경 기록, 복원 절차가 있는지 확인해야 한다.
</details>
