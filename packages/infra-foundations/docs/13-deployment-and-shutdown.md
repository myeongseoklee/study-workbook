# 13. 주문을 받으면서 앱을 바꾸기 — 배포와 정상 종료

## 이 장에서 배울 것

빌드한 산출물이 실제 사용자 요청을 받기까지의 단계를 연결한다. 배포 중 최소 처리 용량과 새·기존 요청의 수명을 계산하고, 누가 어떤 신호로 교체를 진행·중단하는지 설명한다.

## 출발 상황과 선수 지식

[07장](07-containers-and-images.md)의 이미지, [10장](10-scaling-and-state.md)의 여러 앱과 입구 서버를 알고 시작한다. 주문 앱 v1에 기능을 추가해 v2를 만들었다. 손님이 주문하는 동안 어떻게 바꿀까?

## 1. 빌드와 배포를 나누어 보기

**빌드**는 소스 코드와 의존성에서 실행할 산출물을 만드는 과정이다. 소스 코드는 개발자가 작성한 프로그램의 표현이며, 산출물은 실행 파일이나 컨테이너 이미지 등이 될 수 있다.

**배포**는 그 산출물과 설정을 실행 환경에 적용하는 과정이다. 이미지를 만들었다고 손님이 쓰는 앱이 이미 바뀐 것은 아니다. 실행과 트래픽 전달이 새 대상으로 이어져야 한다.

**버전**은 서로 다른 코드와 산출물을 구분하기 위한 표시다. 어떤 소스에서 어떤 이미지를 만들고 어디에 언제 적용했는지 연결해 기록하면 문제를 좁히기 쉽다.

### 배포 파이프라인은 어떤 것을 넘겨줄까

반복할 작업을 정해진 단계로 이어 자동 수행하는 절차를 **파이프라인**이라고 한다. 코드 변경을 검사하고 테스트한 뒤 산출물을 만들고 저장소에 올리며, 배포 단계가 그 산출물과 실행 설정을 선택하도록 구성할 수 있다.

중간에 같은 이름으로 다시 빌드하면 검사한 것과 운영에서 실행한 것이 달라질 수 있다. 그래서 소스 버전·이미지 다이제스트·실행 설정·배포 시각을 연결한다. 07장에서 태그와 실제 콘텐츠를 나눈 이유다. 검사 통과는 검사한 범위의 근거이며, 운영의 네트워크·권한·데이터 호환성까지 자동 검증했다는 뜻은 아니다.

## 2. 모두 끄고 다시 켜면 생기는 빈 구간

앱 A와 B가 v1으로 주문을 받고 있다고 하자. 둘을 모두 종료한 뒤 v2를 실행하면 그 사이에 요청을 받을 앱이 없을 수 있다. 앱 시작과 초기화에도 시간이 걸린다.

초기화는 설정을 읽고 필요한 연결과 내부 데이터를 준비하는 작업이다. 프로세스가 생겼다는 사실만으로 이 준비가 끝났다고 말할 수 없다.

## 3. 새 대상을 먼저 준비하는 점진 교체

일부씩 순서대로 교체하는 방법을 **롤링 배포**라고 한다. 다음은 여유 자원으로 새 앱 C를 먼저 실행하는 가상 과정이다.

| 단계 | A | B | C | 새 요청을 받을 수 있는 대상 |
|---|---|---|---|---|
| 시작 | v1 처리 중 | v1 처리 중 | 없음 | A, B |
| C 시작 | v1 처리 중 | v1 처리 중 | v2 초기화 중 | A, B |
| C 준비 확인 | v1 처리 중 | v1 처리 중 | v2 준비됨 | A, B, C |
| A 교체 시작 | 새 배정 중단·기존 요청 마무리 | v1 처리 중 | v2 처리 중 | B, C |
| A 종료 | 종료 | v1 처리 중 | v2 처리 중 | B, C |

남은 대상도 같은 원리로 교체할 수 있다. 임시로 더 많은 실행 자원이 필요하고 v1·v2가 잠시 공존한다. 두 버전이 같은 데이터와 요청을 해석할 수 있는지도 확인해야 한다.

### 교체를 진행하는 주체와 용량의 조건

실행 관리자는 원하는 버전과 개수를 받아 새 인스턴스를 만들고 상태를 관측하며 이전 인스턴스를 줄인다. 사람은 진행 조건과 중단 기준을 정하고, 자동화는 그 조건을 적용한다. “새 버전을 원한다”는 선언과 현재 모든 요청이 그 버전에서 처리되는 시점 사이에는 여러 단계가 있다.

설명용으로 앱 하나가 현재 요청을 초당 60건 처리하고 유입이 초당 90건이라고 하자. 최소 두 개의 준비된 앱이 필요하다. A를 먼저 끄고 C가 준비되길 기다리면 남은 B의 용량 60건을 넘어 대기가 쌓일 수 있다. C를 먼저 준비하면 교체 중 용량을 유지하기 쉽지만 CPU·메모리와 DB 연결의 임시 증가를 감당해야 한다.

처리량 숫자는 선형 계산을 위한 가정이다. 실제로는 새 버전의 처리 능력과 공통 DB 병목도 확인한다. 준비에 실패한 C를 계속 추가하면서 A·B를 줄이면 안 되는 이유를 용량과 상태로 설명할 수 있어야 한다.

## 4. 살아 있음과 준비됨은 다른 질문이다

**살아 있음(liveness)**은 이 프로세스를 계속 유지할지 판단하는 관점이다. **준비됨(readiness)**은 지금 새 요청을 맡겨도 되는지 판단하는 관점이다.

필수 설정을 아직 읽는 중인 앱은 살아 있지만 준비되지 않았을 수 있다. 이때 새 요청을 보내면 실패할 수 있다. 입구 서버나 실행 관리자가 상태를 확인하는 요청을 **헬스 체크**라고 한다.

헬스 체크 경로가 응답했다는 사실과 실제 주문 업무가 정상이라는 사실도 구분한다. 준비 판정에 무엇을 포함할지는 앱의 처리 조건에 따라 정한다.

외부 DB가 잠시 느려졌다고 앱을 계속 재시작하면 DB가 고쳐지는 것은 아니다. 오히려 초기화와 연결 재수립을 반복해 회복을 늦출 수 있다. 검사 실패 시 트래픽에서 뺄지, 재시작할지, 기다릴지를 구분한다.

## 5. 새 요청을 멈추어도 기존 요청은 남는다

A로 새 요청을 보내지 않기로 했어도 A가 이미 받은 주문은 처리 중일 수 있다. 입구에서 새 배정을 멈추고 기존 연결·요청을 마무리하는 과정을 **드레이닝**이라고 부른다.

단순히 A를 즉시 강제 종료하면 저장 중이던 요청이나 보내는 중이던 응답이 끊길 수 있다. 11장의 불확실한 결과가 다시 생길 수 있는 순간이다.

**정상 종료**는 앱이 종료 요청을 받아 진행 중 일을 마무리하고 자원을 정리하는 절차다. 06장에서 배운 SIGTERM 처리기가 여기에 연결된다.

### 입구와 앱이 각각 멈춰야 하는 것

입구는 A를 새 배정 후보에서 빼고, 앱 A는 종료 단계임을 알고 새 작업 수락을 멈추며 진행 중 작업 수를 추적해야 한다. 등록 해제와 설정 전파에는 시간이 걸릴 수 있고, 재사용 중인 연결의 처리 방식도 제품에 따라 다르다. 한 지점의 설정 변경만으로 그 순간부터 아무 새 요청도 오지 않는다고 가정하지 않는다.

A는 이미 받은 주문의 저장·응답을 마친 뒤 연결 풀과 열린 자원을 정리하고 종료할 수 있다. 큐 소비자라면 새 메시지 수신을 멈추고 처리 중 메시지를 완료 확인하거나 재처리 가능하게 남기는 절차가 필요하다. HTTP 서버의 연결 닫기만으로 모든 백그라운드 일이 마무리되는 것은 아니다.

SIGTERM을 누가 실제 앱에 전달하는지도 확인한다. 컨테이너의 시작 프로그램이 셸이고 신호를 앱에 전달하지 않으면 앱의 종료 처리기가 실행되지 않을 수 있다. “신호가 컨테이너에 갔다”와 “앱이 신호를 처리했다”를 나누어 관찰한다.

## 6. 시간 제한을 서로 맞추기

설명용으로 A가 받은 요청의 남은 처리 시간이 12초라고 하자. 앱이 정리하려 해도 실행 환경이 5초 뒤 강제로 끝내면 그 요청을 끝내지 못할 수 있다.

실제 앱에서 필요한 처리 시간과 입구의 드레이닝 시간, 앱의 종료 대기, 실행 환경의 강제 종료 제한이 맞는지 확인한다. 12초나 5초는 권장값이 아니라 충돌을 보여 주는 예다.

긴 연결과 백그라운드 작업은 짧은 조회 요청보다 오래 남을 수 있다. 종료 전에 완료할지, 다른 실행자가 다시 처리할지, 중간 상태를 저장할지 업무별로 정한다. 갑작스러운 호스트 장애에는 정상 종료 기회 자체가 없을 수 있다.

## 7. 코드 롤백은 무엇을 되돌리는가

**롤백**은 변경을 이전 상태로 되돌리는 것이다. 앱 배포에서 이전 이미지를 다시 실행하는 것이 한 예다. v2에 문제가 발견되면 v1으로 새 트래픽을 돌릴 수 있도록 준비한다.

하지만 앱을 되돌린다고 이미 보낸 영수증이나 확정된 주문이 저절로 취소되지는 않는다. DB 구조를 바꿨다면 이전 앱이 그 구조를 읽을 수 있어야 한다. 이 문제는 14장에서 따로 다룬다.

### 교체 방식은 무엇을 더 준비하고 무엇을 되돌릴까

롤링 배포는 일부씩 교체하므로 버전 공존을 다뤄야 한다. **블루·그린 배포**는 기존 환경과 새 환경을 나란히 준비한 뒤 입구를 전환하는 방식이다. 되돌릴 기존 환경을 남기기 쉽지만 두 환경을 유지하는 자원이 필요하고, 공통 DB의 변경은 별도 문제다.

카나리는 일부 요청으로 새 버전을 검증하는 노출 방식이다. 롤링이나 별도 환경과 조합할 수 있다. 방식 이름보다 동시에 유지할 용량, 버전 공존 기간, 트래픽을 되돌릴 방법, 이미 실행한 데이터 효과를 무엇으로 복구할지를 판단한다.

## 8. 배포 성공을 무엇으로 확인할까

배포 도구가 “새 앱 실행 완료”라고 알려 주는 것은 실행 관리의 결과다. 손님이 실제로 주문할 수 있는지는 사용자 요청과 업무 결과로 확인해야 한다.

작은 범위의 새 버전에 요청을 보내고 오류·지연·주문 결과를 관찰한 뒤 범위를 넓힐 수 있다. 이렇게 일부에 먼저 노출해 확인하는 접근을 **카나리 배포**라고 부른다.

어느 관찰에서 다음 교체를 멈추고 언제 되돌릴지 미리 정한다. 배포 후의 관측 방법은 15장에서 구체적으로 배운다.

### 언제 다음 대상을 교체해도 될까

새 버전이 충분한 시간 동안 요청을 받아도 오류율과 지연, 주문 생성 결과가 정한 범위에 있는지 확인한다. 전체 평균만 보면 소수의 새 버전 오류가 가려질 수 있어 버전별로 비교한다. 관찰 시간과 허용 범위는 실제 트래픽·위험·목표에 맞춰 정한다.

문제가 생겼을 때 추가 교체를 멈추고 이전 대상으로 새 요청을 돌릴 수 있어야 한다. 새 버전에서 이미 확정한 주문은 사라지지 않으므로 데이터 호환성이 이 절차를 뒷받침해야 한다. 재현할 때는 C의 준비 실패와 A 종료 중 요청을 각각 넣어, 어떤 신호가 다음 행동을 바꾸는지 확인한다.

## 꼭 기억할 것

- **카드 14:** 새 대상이 준비된 뒤 요청을 옮기고, 이전 대상의 새 요청 배정을 멈춘 뒤 진행 중 일을 마무리한다. 프로세스 실행·준비·드레이닝·종료는 다른 사건이다.
