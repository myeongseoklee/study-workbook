# 16. 연결할 수 있으면 무엇이든 해도 될까 — 인증과 권한

## 이 장에서 배울 것

로그인부터 다음 요청의 신원 확인·주문 권한 검사까지 이어지는 과정을 설명한다. 증표의 위조 방지와 내용 암호화를 구분하고, 앱·배포 기반의 역할과 임시 자격증명이 사용되는 순서를 이해한다.

## 출발 상황과 선수 지식

[05장](05-routing-and-access.md)의 네트워크 허용과 [10장](10-scaling-and-state.md)의 로그인 세션을 알고 시작한다. 손님과 관리자는 같은 주문 서버에 접속한다. 하지만 손님에게 다른 사람의 주문 삭제 기능까지 허용해서는 안 된다. 네트워크 연결만으로 이 차이를 표현할 수 있을까?

## 1. 누구의 요청인가와 무엇을 허용할까

**인증(authentication)**은 요청한 주체가 누구인지 확인하는 절차다. **인가(authorization)**는 그 주체에게 어떤 작업을 허용할지 판단하는 절차다. 주체는 사람뿐 아니라 실행 중인 앱이나 배포 자동화일 수도 있다.

손님이 로그인에 성공했다고 하자. 서버는 그 손님이 누구인지 알 수 있다. 그렇다고 모든 주문을 삭제할 권한이 생기는 것은 아니다. 자기 주문을 읽을 수 있는지, 취소 가능한 상태인지 등을 추가로 판단한다.

공개 상품 목록처럼 인증 없이 허용할 기능도 있다. 중요한 것은 모든 요청에 같은 절차를 강제하는 것이 아니라, 각 작업을 어떤 주체와 조건에 허용하는지 정하는 것이다.

## 2. 비밀번호와 키는 무엇을 증명할까

**자격증명(credentials)**은 신원을 확인하는 데 쓰는 정보다. 비밀번호, 비밀키, 적절한 절차로 발급한 토큰 등이 예다. 외부에 알려지면 다른 사람이 그 주체처럼 행동할 수 있어 보호해야 한다.

**토큰**은 서버가 발급하거나 신뢰하는 방식으로 만든 증표다. 브라우저가 다음 요청에 증표를 보내고 서버가 유효성을 확인하는 방식으로 사용할 수 있다. 모든 토큰이 같은 형식이나 검증 방법을 쓰지는 않는다.

10장의 세션 식별자도 다음 요청을 사용자 상태와 연결하는 한 방법이다. 요청에 이름 문자열만 써 보냈다고 그 이름의 사용자라고 믿어서는 안 된다. 그 정보를 믿을 수 있는 확인 절차가 필요하다.

### 로그인 이후에도 서버는 어떻게 사용자를 알아볼까

HTTP 연결이 같다는 것만으로 사용자가 인증되지는 않는다. 공유 세션 방식의 기본 흐름은 다음과 같다.

1. 손님이 HTTPS로 로그인 정보를 보낸다. 서버는 등록한 계정과 비밀번호 검증 정보를 대조한다.
2. 성공하면 추측하기 어려운 세션 식별자 S를 만들고, S와 사용자·만료 시각 등을 서버의 세션 저장소에 연결한다.
3. 브라우저에 쿠키로 S를 전달한다. 다음 주문 요청에서 브라우저가 해당 쿠키를 보낸다.
4. 서버는 S가 존재하고 유효한지 확인해 요청의 사용자를 정한다. 이 값을 요청 본문의 임의 사용자 이름으로 대체하지 않는다.
5. 주문을 읽거나 취소하기 전에 그 사용자의 권한과 주문 상태를 검사한다.

비밀번호를 원문 그대로 보관하면 DB 유출이 곧 비밀번호 유출이 된다. 비밀번호 전용 해시 함수는 원래 비밀번호를 쉽게 역산하지 못하도록 검증값을 만들며, 로그인 때 같은 방식으로 검증한다. 사용자별 무작위 값인 **솔트**를 함께 사용하면 같은 비밀번호의 결과가 같아지는 것을 피하고 미리 계산한 공격을 어렵게 할 수 있다. 빠른 일반 해시 한 번과 비밀번호 저장용 설계는 다르다.

세션 S가 탈취되면 만료·폐기되기 전까지 사용자를 사칭하는 데 악용될 수 있다. 그래서 전송 보호와 쿠키의 접근·전송 범위, 만료·로그아웃 처리가 필요하다. 식별자를 단순히 숫자로 붙였다는 이유로 안전한 인증 증표가 되는 것은 아니다. [인증](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [세션](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [비밀번호 저장](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)의 저자 문서를 참고했다.

### 서명한 토큰을 쓰면 무엇이 달라질까

다른 방식으로는 발급자가 사용자·만료 등의 정보를 담아 서명한 토큰을 주고 서버가 신뢰하는 발급자의 검증 키로 서명을 확인할 수 있다. 서버 저장소의 식별자만 조회하는 방식과 달리, 증표 안의 정보를 신뢰할 수 있는지 암호학적으로 확인하는 것이다. 발급자와 사용할 서비스, 만료 등도 의도한 계약과 맞아야 한다.

**서명은 내용 암호화와 다르다.** 서명된 JWT 같은 형식은 내용이 읽힐 수 있으므로 비밀번호를 넣어도 숨겨진다고 생각하면 안 된다. 또 서명이 유효해도 현재 계정이 정지됐거나 권한이 바뀌었을 수 있다. 즉시 폐기가 필요한지, 만료까지 허용하는지에 따라 추가 상태 조회가 필요할 수 있다. 토큰은 모든 권한 판단을 없애는 장치가 아니다. [JWT 표준](https://www.rfc-editor.org/rfc/rfc7519)을 참고했다.

## 3. HTTPS가 확인하는 상대와 손님 로그인은 다르다

04장의 일반적인 웹 TLS 연결에서는 브라우저가 접속한 서버를 인증서로 확인했다. 이는 “내가 연결한 쪽이 이 도메인의 서버인가?”에 관한 확인이다.

문구점 서버가 손님에게 “당신은 어느 사용자이며 이 주문을 읽어도 되는가?”를 판단하는 로그인과 인가는 별도다. HTTPS를 사용한다고 모든 사용자에게 모든 기능을 허용하는 것은 아니다.

반대로 사용자 인증이 있어도 전송 보호를 없애면 자격증명과 내용이 노출될 수 있다. 서로 다른 경계가 각자의 문제를 푼다.

## 4. 권한은 주체·작업·대상·조건으로 읽는다

권한 규칙을 이해할 때 다음 질문을 적어 보면 좋다.

| 질문 | 문구점의 예 |
|---|---|
| 누가 | 주문 앱의 실행 주체 |
| 무엇을 | 객체 읽기 |
| 어디에 | 상품 사진 저장소의 특정 범위 |
| 어떤 조건으로 | 서비스에 필요한 접근일 때 |

상품 사진을 읽는 앱이 모든 백업을 삭제할 필요는 없다. 필요한 작업과 대상 범위만 허용하는 원칙을 **최소 권한**이라고 한다.

규칙을 표현한 문서를 **정책(policy)**이라고 부를 수 있다. 실제 허용 여부는 여러 정책과 조건을 종합해 판단할 수 있으므로 정책 이름만 보고 결론을 내리지 않는다.

### 권한 검사는 어디에서 어떤 값을 신뢰해야 할까

손님 A가 `/orders/42`를 요청했다고 하자. 서버는 인증된 주체 A를 얻고, 주문 42의 소유자와 현재 상태를 읽고, “A가 이 주문을 조회·취소할 수 있는가”를 판단한다. URL의 주문 번호를 43으로 바꿨다는 이유로 다른 손님 주문이 보이면 안 된다.

요청 본문에 `user_id=B`라고 적은 것을 그대로 신원으로 믿으면 누구나 남을 사칭할 수 있다. 브라우저에서 버튼을 숨겨도 직접 요청할 수 있으므로 서버가 매 요청의 대상에 권한을 적용해야 한다. 인가는 신뢰할 수 있게 확인한 주체와 실제 자원을 결합하는 단계다.

## 5. 실행하는 주체가 다르면 필요한 권한도 다르다

새 이미지를 등록하고 앱을 교체하는 배포 자동화와, 실행 후 상품 사진을 읽는 주문 앱은 다른 일을 한다. 같은 관리자 자격증명을 둘에 나누어 줄 필요는 없다.

실행 주체가 맡을 수 있는 권한 묶음을 **역할(role)**로 나눌 수 있다. AWS에서는 누가 그 역할을 맡을 수 있는지 정하는 신뢰 정책과, 역할을 맡은 뒤 무엇을 할 수 있는지 정하는 권한 정책을 구분한다.

역할을 맡아 일정 기간만 유효한 임시 자격증명을 얻도록 구성할 수 있다. 이 방식은 장기 비밀키를 앱 파일에 넣어 배포하는 부담을 줄일 수 있다. 자격증명의 공급과 갱신은 실행 환경의 지원 방식에 따라 확인한다.

### 역할 이름과 실제 자격증명은 어떻게 연결될까

AWS의 한 역할 사용 흐름에서는 호출자가 역할을 맡겠다고 요청하고, AWS STS가 요청 주체와 신뢰·허용 조건을 검증한 뒤 유효 기간이 있는 자격증명을 발급한다. **STS**는 임시 자격증명을 발급하는 AWS 서비스다. 역할 이름만 알고 있다는 사실로 권한을 얻는 것은 아니다.

앱은 그 자격증명으로 AWS API 요청에 서명하고 AWS는 주체와 적용 정책을 확인해 허용 여부를 판단한다. 요청 서명은 증표를 요청 내용에 연결하는 것이며, HTTPS의 전송 암호화를 대체하지 않는다. 실행 환경과 SDK가 자격증명을 공급·갱신하도록 구성할 수 있어 장기 키를 코드에 복사하지 않아도 된다.

권한을 허용하는 정책이 하나 보인다고 항상 성공하는 것은 아니다. 다른 적용 정책의 명시적 거부나 권한 경계 등의 제한을 함께 평가할 수 있다. 먼저 실제 호출 주체와 작업·자원을 확인한 뒤 거부가 만들어진 지점을 찾는다. [역할 사용](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-api.html), [정책 평가](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html)를 참고했다.

## 6. 네트워크·클라우드 API·DB 권한을 구분하기

방화벽은 통신을 허용할지 판단한다. 연결에 성공한 뒤 AWS API나 DB가 요청자의 자격과 작업 권한을 다시 검사할 수 있다.

예를 들어 앱에서 DB 주소로 접속은 되지만 DB 사용자에게 주문 테이블 조회 권한이 없으면 질의가 거부될 수 있다. 반대로 DB 계정 권한은 맞아도 네트워크 길이 없으면 접속부터 하지 못한다.

“권한 오류”라는 한 표현으로 덮지 말고 어느 주체의 어떤 요청을 누가 거부했는지 구분한다. 응답의 오류, 실제 요청 주체, 관련 정책이 다음 확인의 근거다.

## 7. 비밀을 코드 밖에서 공급하는 이유

자격증명을 코드 파일이나 이미지에 넣으면 복사본과 배포 산출물에 비밀이 함께 남는다. 대신 비밀을 보관하는 별도 수단에서 실행 시 공급하도록 만들 수 있다. 이런 민감한 설정값을 **시크릿**이라고 부른다.

환경변수로 주입한다고 누구에게도 보이지 않는 것은 아니다. 프로세스나 진단 정보에 접근하는 권한도 관리해야 한다. 로그에 전체 자격증명을 출력하면 저장 위치를 옮긴 효과가 사라질 수 있다.

비밀 값을 바꾸었을 때 앱이 즉시 새 값을 사용하는지도 공급 방식에 달려 있다. 시작 때 한 번 읽은 값을 계속 보유한다면 다시 읽거나 재실행해야 할 수 있다.

## 권한을 배포와 연결하기

배포가 시작되기 전의 다운로드 실패와, 앱 실행 뒤의 데이터 접근 거부는 서로 다른 주체의 작업일 수 있다. 어떤 프로그램이 어느 자격증명으로 요청했는지 먼저 적는다.

다음 장의 ECS 실행 역할과 태스크 역할을 이 관점으로 읽으면 이름을 외우는 대신 왜 역할이 나뉘었는지 설명할 수 있다.

## 꼭 기억할 것

- **카드 17:** 인증은 주체 확인, 인가는 작업 허용 판단이다. 네트워크 도달·TLS 상대 확인·앱 사용자 권한은 서로 대신하지 않는다.

</details>

<details><summary>로그인 토큰의 서명이 맞으면 주문 42 삭제를 바로 허용해도 될까?</summary>

서명은 발급된 내용이 위조되지 않았는지 확인하는 근거다. 의도한 발급자·사용 대상·만료 등을 검증하고, 현재 주체에게 주문 42를 삭제할 권한과 업무 조건이 있는지도 판단해야 한다. 서명이 내용을 비밀로 만드는 것도 아니다.
</details>
