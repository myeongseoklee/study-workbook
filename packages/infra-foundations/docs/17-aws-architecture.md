# 17. 이제 AWS 이름을 읽어 보기 — 한 주문 서비스의 구성

## 이 장에서 배울 것

AWS 서비스를 역할에 대응하는 데서 나아가, 태스크가 만들어지고 교체되는 과정을 설명한다. 준비를 위한 API 호출 경로와 사용자 요청 경로를 나누고, 각 단계의 주소·주체·데이터 수명을 연결한다.

## 출발 상황과 선수 지식

[01장](01-computers-and-programs.md)부터 [16장](16-identity-and-permissions.md)까지의 개념을 사용한다. 실제 운영 계정은 조사하지 않았다. 이 장의 구성은 공통 원리를 연결하는 가상 예이며, 그대로 만들라는 구축 지시가 아니다.

## 1. 클라우드는 무엇을 제공하는가

**클라우드**는 필요한 컴퓨팅·저장·네트워크 등의 자원을 서비스로 제공받아 사용하는 방식이다. 직접 컴퓨터를 구매하고 설치하는 대신 제공자의 자원을 정해진 방식으로 사용할 수 있다. AWS는 이런 서비스를 제공하는 플랫폼 중 하나다.

제공자가 많이 관리하는 서비스도 있지만, 앱 코드와 업무 요구까지 대신 정해 주지는 않는다. 누가 운영체제를 관리하고, 누가 앱과 데이터를 책임지는지 서비스별로 확인한다.

가격과 최신 한도는 여기서 외우지 않는다. 필요한 역할을 먼저 설명하고 그 역할을 구현할 서비스의 조건과 비용을 확인하는 순서가 좋다.

## 2. 실행할 곳 — EC2, ECS, Fargate

**EC2**는 가상 서버를 제공한다. 07장에서 배운 VM에 운영체제를 실행하고 앱을 올리는 방식과 연결된다. 사용자에게는 운영체제와 실행 관리 등의 책임이 남는다.

**ECS**는 컨테이너로 묶은 작업을 실행하고 서비스를 관리하는 체계다. 어떤 이미지와 설정, 자원으로 실행할지 적는 것을 **태스크 정의**, 그 정의를 바탕으로 실제 실행하는 단위를 **태스크**라고 한다.

원하는 수만큼 태스크를 유지하고 교체하도록 **서비스**를 구성할 수 있다. 태스크를 실행할 컴퓨팅 자원으로 EC2나 Fargate 같은 방식을 선택할 수 있다.

**Fargate**는 컨테이너 실행을 위한 서버 관리 부담을 줄이는 방식이다. 사용자는 여전히 이미지, CPU·메모리 요구, 앱 설정, 준비와 종료, 데이터 보관을 정해야 한다. ECS와 Fargate를 같은 역할의 두 이름으로 외우지 않는다.

### “태스크 두 개를 유지하라”는 요청 뒤에 일어나는 일

서비스에 원하는 개수 2와 태스크 정의를 지정했다고 하자. ECS의 스케줄러는 현재 실행 상태와 원하는 상태의 차이를 보고 필요한 태스크를 시작한다. 하나가 멈추면 새 태스크를 만들어 개수를 맞추려 한다. 이처럼 원하는 상태를 유지하도록 실행을 조정하는 것을 **오케스트레이션**이라고 한다.

개수만 맞추면 충분한 것은 아니다. 컴퓨팅 자원과 네트워크를 준비하고, 이미지를 가져오고, 설정·시크릿을 공급하고, 컨테이너를 시작하고, 준비 상태를 확인해야 사용자 요청을 받을 수 있다. 잘못된 시작 명령으로 계속 죽는 태스크를 교체한다고 코드 오류가 고쳐지는 것은 아니다.

관리 구성을 바꾸는 API 호출과 실제 주문을 처리하는 HTTP 요청은 다른 경로다. 전자를 **제어 평면**, 후자를 **데이터 평면**이라는 관점으로 구분할 수 있다. 예를 들어 배포자는 ECS에 새 정의를 적용하지만 손님의 주문 요청이 매번 ECS 관리 API를 통과하는 것은 아니다. [ECS 서비스](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_services.html)를 참고했다.

## 3. 주소와 길 — VPC, 서브넷, 경로

**VPC**는 AWS에서 구성하는 가상 네트워크다. 주소 범위와 그 안의 서브넷, 경로 등을 정한다. 05장의 주소 묶음과 다음 전달 규칙을 적용하는 자리다.

인터넷과 통신하기 위한 **인터넷 게이트웨이** 경로를 둘 수 있다. 사설 주소의 앱이 시작한 외부 연결에는 **NAT gateway**를 사용하는 구성이 가능하다. AWS 서비스별로 VPC 엔드포인트라는 별도 접근 경로를 사용할 수도 있다.

**보안 그룹**은 자원의 네트워크 인터페이스에 적용하는 통신 허용 규칙이다. 상태를 추적하므로 허용된 연결의 응답도 구분한다. 서브넷 수준의 **네트워크 ACL**은 상태를 추적하지 않는 정책으로 읽는다.

이름이 public인 서브넷에 두었다고 모든 조건이 완료되지는 않는다. 실제 공인 주소와 경로, 정책, 수신 상태를 함께 확인한다.

### Fargate의 앱은 어떤 주소로 통신할까

여기서는 IPv4 기반의 Fargate 태스크를 예로 든다. 태스크에는 가상 네트워크 인터페이스인 **ENI**와 사설 IP가 제공된다. 태스크를 교체하면 새 태스크의 IP가 달라질 수 있으므로 앱의 한 IP를 영구 주소로 외우는 방식은 맞지 않는다.

같은 태스크에 속한 컨테이너는 네트워크를 공유해 localhost로 통신할 수 있다. 서로 다른 태스크는 별도 네트워크 끝점이므로 localhost가 상대 태스크를 뜻하지 않는다. 07장의 격리 범위는 “컨테이너라는 이름이 다르면 무조건 모두 별도”로 외우는 대신 실제 공유 단위를 확인해야 한다.

또 앱이 시작되기 전에 이미지 저장 서비스인 **ECR**의 이미지와 필요한 시크릿을 가져오는 경로가 필요하다. 프라이빗 서브넷이라는 이유로 아무 통신도 못 하게 두면 준비 단계부터 막힐 수 있다. 인터넷 경유 경로나 필요한 AWS 서비스용 VPC 엔드포인트 등을 구성하고, 서비스별 경로·DNS·정책을 맞춰야 한다. 엔드포인트 하나가 모든 외부 통신을 대신하지 않는다. [Fargate 네트워크](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html)를 참고했다.

## 4. 손님의 입구 — Route 53과 ALB

**Route 53**은 DNS 등을 관리하는 서비스다. 문구점 이름이 어떤 접속 대상을 가리키는지 설정하는 데 사용할 수 있다.

**ALB**는 HTTP 계열 요청을 여러 대상으로 전달하는 로드밸런서다. 요청을 받는 프로토콜과 포트의 설정을 **리스너**, 전달 후보들의 묶음을 **타깃 그룹**이라고 한다.

ALB가 HTTPS 요청을 받아 TLS를 끝내고 앱으로 새 연결을 만들 수 있다. 그러면 인증서는 손님과 ALB 사이에 쓰이고, ALB와 앱 사이는 별도로 프로토콜과 보호 방식을 정한다.

헬스 체크로 대상 상태를 판단할 수 있지만 제품의 예외 동작도 확인해야 한다. 예를 들어 ALB는 등록 대상이 모두 비정상이면 fail-open으로 라우팅할 수 있다. 13장의 개념을 특정 제품의 절대 보장으로 바꾸어 읽지 않는다.

### 요청 규칙과 대상 등록은 어떻게 이어질까

이 예에서 ALB의 HTTPS 리스너는 443번에서 손님 연결을 받는다. 리스너 규칙은 호스트·경로 같은 조건을 보고 전달할 타깃 그룹을 고른다. 타깃 그룹에는 실제 앱의 접속 대상과 포트가 연결된다. ECS 서비스와 연동하면 시작한 태스크를 대상으로 등록하고 종료할 태스크를 해제하도록 관리할 수 있다.

예를 들어 내부 앱은 3000번에서 받으므로 손님→ALB의 443 연결과 ALB→앱의 3000 연결은 다르다. 앱의 통신 규칙은 그 구간을 허용해야 하고, ALB 헬스 체크의 경로·포트가 앱의 준비 응답과 맞아야 한다. DNS 레코드, 리스너, 타깃 등록, 실제 수신은 각각 다른 상태다.

## 5. 남겨 둘 데이터 — RDS, S3, EBS

**RDS**는 관리형 관계형 DB 서비스다. 표와 질의, 트랜잭션을 쓰는 주문 데이터에 연결해 생각할 수 있다. 사용자는 스키마·질의·권한·용량과 복구 목표를 여전히 판단한다.

**S3**는 객체 저장소다. 상품 사진과 영수증 파일을 키로 보관하는 예를 떠올릴 수 있다. **EBS**는 블록 저장소다. 가상 서버에 저장 장치처럼 연결해 사용하는 예와 이어진다.

셋은 같은 일을 하는 상표 세 개가 아니다. DB 행의 규칙, 객체 API, 블록 장치라는 서로 다른 역할이다. 저장 서비스의 이름만으로 데이터 수명과 복구 목표가 자동 결정되지는 않는다.

## 6. 누가 요청하는가 — 실행 역할과 태스크 역할

**IAM**은 AWS 주체의 작업 권한을 관리하는 서비스다. 16장에서 배운 주체·자격증명·작업·대상을 적용한다.

ECS의 **실행 역할**은 태스크를 준비하는 실행 기반이 쓰는 권한이다. 저장된 이미지를 가져오고 지정된 로그·시크릿 관련 작업을 하는 데 쓰일 수 있다. ECR에서 이미지를 받는 것이 예다.

**태스크 역할**은 실행된 앱 코드가 AWS 서비스를 호출할 때 쓸 권한이다. 주문 앱이 S3의 영수증을 읽는 것이 예다.

이미지 다운로드 단계의 실패와 앱 실행 뒤의 AccessDenied를 같은 주체의 사건으로 합치지 않는다. AccessDenied는 접근이 거부됐다는 응답이다. 실제 호출 주체와 관련 IAM·리소스·암호화 키 정책 등을 확인한다.

### 권한과 네트워크는 둘 다 맞아야 한다

실행 역할에 이미지 읽기를 허용해도 이미지 저장 서비스까지 길이 없으면 다운로드가 실패한다. 반대로 길은 있어도 실행 역할의 권한이 없으면 API가 거부할 수 있다. 앱이 쓰는 태스크 역할에 S3 읽기를 허용해도 앱이 다른 자격증명을 사용하거나 버킷 등 다른 적용 정책이 거부하면 실패할 수 있다.

진단에서는 “어떤 단계에서 어떤 프로그램이 어느 자격으로 어디에 요청했는가”를 먼저 적는다. 시작 전 다운로드·시크릿 주입과, 시작 뒤 앱의 상품 사진 접근을 분리하면 권한을 엉뚱한 역할에 더하는 실수를 줄일 수 있다. [실행 역할](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_execution_IAM_role.html), [태스크 역할](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html)을 참고했다.

## 7. 한 요청을 끝까지 따라가기

다음은 역할 연결을 위한 가상 경로다. 특정 프로토콜 선택을 운영 권장안으로 제시하는 것은 아니다.

| 순서 | 발생하는 일 | 앞에서 배운 원리 |
|---|---|---|
| 1 | 손님이 문구점 도메인의 주소 정보를 조회 | DNS |
| 2 | 손님과 ALB가 HTTPS 연결을 준비 | TCP·TLS·포트 |
| 3 | ALB가 준비된 앱 태스크로 요청 전달 | 프록시·부하 분산 |
| 4 | 앱이 DB 연결을 빌려 재고·주문 변경 | 연결 풀·트랜잭션 |
| 5 | 앱이 저장 결과를 확인해 응답 | 커밋·업무 결과 |
| 6 | 응답이 ALB를 거쳐 손님에게 전달 | 요청과 응답의 여러 연결 |

각 연결에는 경로와 통신 허용이 필요하다. DB 사용자의 권한과 앱의 AWS API 권한은 또 다른 경계다. 앱 프로세스·컨테이너를 교체해도 주문 데이터는 정한 저장소에 남아야 한다.

## 8. 여러 개를 어디에 둘 것인가

**리전**은 AWS의 지리적 서비스 영역이고, **가용 영역(AZ)**은 리전 안에서 구분된 배치 경계다. 10장의 “같이 실패하는 범위”로 생각하면 된다.

앱을 여러 가용 영역에 나눠도 공통 DB나 필수 외부 서비스가 실패하면 전체 업무에 영향이 있을 수 있다. 개수만 세지 말고 각 의존성의 복구 방식과 전환 시간을 확인한다.

## 9. 구성과 관측도 관리 대상이다

**CloudWatch**는 로그·지표·경보 등을 다루는 서비스다. 무엇을 수집하고 어떤 사용자 목표로 경보할지는 15장의 질문으로 정한다.

네트워크와 실행 구성을 코드로 선언해 관리하는 것을 **IaC**, 즉 인프라를 코드로 관리한다고 부른다. **CloudFormation**은 그런 선언을 적용하는 AWS 도구 중 하나다. 파일을 리뷰하고 변경 계획을 확인하면 무엇이 교체·삭제될지 파악하는 데 도움이 된다.

도구가 적용에 성공했다는 사실과 사용자가 정상 주문했다는 사실은 마지막까지 구분한다.

### 선언 파일을 바꾸면 실제 자원은 어떻게 바뀔까

CloudFormation 템플릿은 원하는 자원과 속성, 자원 간 참조를 선언한다. 이를 함께 관리하는 단위를 **스택**이라고 한다. 변경 시 어떤 자원은 속성만 수정되고 어떤 자원은 새로 만들어 교체되거나 삭제될 수 있다. 파일의 한 줄 수정과 운영 자원의 변화 크기는 비례하지 않는다.

**변경 세트(change set)**는 적용 전에 추가·수정·삭제·교체 영향을 검토하는 수단이다. DB 같은 영속 자원의 교체라면 이름만 새로 만드는 것과 데이터·접속 대상을 옮기는 일은 별도다. 변경 계획이 생성됐다는 사실도 적용 성공이나 주문 성공을 보장하지 않는다. [변경 세트](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-changesets.html)를 참고했다.

## 배포 한 번을 앞의 원리로 재구성하기

배포 자동화가 이미지 콘텐츠를 고정하고 새 태스크 정의를 적용한다. ECS는 새 실행을 준비하고, Fargate의 네트워크와 실행 기반이 이미지·설정을 가져오며 앱을 시작한다. 준비가 확인된 대상에 ALB가 요청을 보내고 이전 대상을 등록 해제·드레이닝·종료한다.

새 태스크는 외부 DB에서 기존 주문을 읽고 필요한 API를 자기 역할로 호출한다. 관측에서는 버전별 오류·지연·업무 결과를 확인한다. 이 흐름의 어느 지점에서도 CPU·연결·저장·권한·버전 호환성이라는 앞 장의 원리가 사라지지 않는다. 플랫폼이 바뀌면 각 역할을 맡는 제품과 설정을 다시 대응시키면 된다.

<details><summary>ECS와 Fargate는 같은 역할의 서비스일까?</summary>

ECS는 태스크와 서비스 실행을 관리하고, Fargate는 그 컨테이너를 실행할 컴퓨팅 방식 중 하나다. 태스크 정의와 앱 동작은 사용자가 정한다.
</details>

<details><summary>ALB가 HTTPS를 받으면 ALB에서 앱으로 가는 구간도 자동으로 HTTPS일까?</summary>

아니다. 별도의 연결이므로 그 구간의 프로토콜과 보호 방식을 확인해야 한다.
</details>

<details><summary>이미지 다운로드 실패와 앱의 S3 읽기 실패는 어느 역할부터 구분할까?</summary>

실행 기반의 작업에는 실행 역할, 앱의 API 호출에는 태스크 역할을 중심으로 실제 요청 주체와 오류를 확인한다.
</details>

<details><summary>원하는 태스크 개수는 2인데 새 태스크가 시작 전에 계속 실패한다. 어떤 준비 단계를 나누어 확인할까?</summary>

컴퓨팅·네트워크 준비, 이미지 경로와 실행 역할, 시크릿 공급, 시작 명령·설정, 실제 수신과 헬스 체크를 나누어 확인한다. 스케줄러가 교체를 시도한다는 사실만으로 이 조건들이 모두 충족된 것은 아니다.
</details>
