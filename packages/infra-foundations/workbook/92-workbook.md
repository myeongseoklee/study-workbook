# 워크북 — 처음 배운 인프라 원리를 써 보기

## 사용법

본문을 덮고 자기 말로 답한다. 문장 표현이 해설과 같아야 하는 것은 아니다. 누가 무엇을 하고 중간 상태가 어떻게 달라지는지 설명해 본다. [해설](93-solutions.md)은 먼저 답을 적은 뒤 연다.

회수 연습은 [암기 카드 18개](../docs/90-must-memorize.md)와 순서대로 대응한다. 판단 문제와 재현 과제는 본문에서 배운 상황을 조금 바꾼 것이다. 수량과 시간은 모두 문제의 가정이며 운영 권장값이 아니다.

답은 원본 교재에 쓰지 않는다. 레포 `README.md` 규약 4의 별도 worktree를 사용하고 개인 오답은 `.study-log/`에 남길 수 있다. 자동 채점 코딩 과제는 없다.

## 파트 1. 회수 연습

답을 비교할 때: [93-solutions.md](93-solutions.md) 파트 1.

**1-1.** 주문 수량 계산, 처리 중인 주문 값, 내일 다시 읽을 주문 기록을 각각 컴퓨터의 어느 역할과 연결할까? 전원을 껐을 때의 차이도 설명하라.

**1-2.** 저장된 같은 주문 프로그램을 두 번 실행했다. 두 실행이 처리 중인 주문도 반드시 같을까? 프로그램과 프로세스를 써서 설명하라.

**1-3.** 같은 IP의 주문 앱은 3000번, 관리자 앱은 4000번에서 기다린다. 손님 요청을 어느 앱에 전달할지 무엇으로 구분할까? 앱이 미리 준비할 일도 쓰라.

**1-4.** DNS에서 이름의 주소를 얻었다. 왜 아직 상품 조회가 끝난 것은 아닐까? DNS와 HTTP가 맡는 일을 나누어 설명하라.

**1-5.** `ORDER42`의 뒷부분이 먼저 도착했다. 순서를 다루는 것과 내용을 남이 못 읽게 하는 것은 각각 어떤 역할인가? 주문 저장 성공도 함께 보장할까?

**1-6.** 목적지까지 경로를 추가했는데 연결은 안 된다. 라우팅과 방화벽의 역할을 구분하고 왕복 통신에 필요한 나머지 조건을 쓰라.

**1-7.** A 요청이 외부 답을 기다리는 동안 B 계산을 진행하는 것과, 긴 계산 두 개를 동시에 실행하는 것은 왜 다른가? 비동기의 의미를 설명하라.

**1-8.** 같은 이미지에서 A와 B 컨테이너를 만들었다. A의 메모리와 업로드 파일이 B에도 자동으로 있는가? 이미지·실행·파일 수명을 나누어 설명하라.

**1-9.** 주문 앱을 종료하고 새로 실행해도 어제 주문을 읽으려 한다. 작업 중 상태와 영속 데이터는 어떻게 나누어야 할까?

**1-10.** 재고 차감과 주문 추가를 함께 확정하려면 어떤 개념이 필요한가? 내 DB의 취소가 외부 결제도 자동 취소하는지 설명하라.

**1-11.** 앱을 두 개로 늘릴 때 요청을 반씩 보내는 것 외에 무엇을 더 확인할까? 세션·공통 DB·장애 범위 중 구체적 예를 들어 설명하라.

**1-12.** 주문 응답이 시간 초과됐다. 서버에서 가능한 상태 두 가지 이상을 쓰고, 재시도에 필요한 결과 확인·중복 방지·횟수와 시간 제한을 설명하라.

**1-13.** 상품 조회 캐시와 영수증 작업 큐는 각각 어떤 문제를 풀까? 캐시의 오래된 값과 큐의 재전달이 만드는 결과도 쓰라.

**1-14.** 새 앱 실행, 준비 확인, 이전 앱 새 배정 중단, 기존 요청 마무리, 종료는 왜 다른 사건인가? 한 주문이 진행 중인 예로 설명하라.

**1-15.** 옛 앱이 읽는 열을 첫 배포에서 지우면 왜 위험할까? 새 열 추가부터 옛 열 제거까지 필요한 근거를 설명하라.

**1-16.** 평균 지연과 CPU만으로 느린 주문의 원인을 알 수 있을까? 메트릭·로그·추적으로 각각 어떤 질문에 답할지 쓰라.

**1-17.** 로그인에 성공한 손님이 다른 사람의 주문을 삭제할 수 있는가? 인증·인가·네트워크 통신 허용을 나누어 설명하라.

**1-18.** 앱 실행 전 이미지 다운로드와 실행 후 S3 읽기는 왜 다른 주체의 작업인가? ECS 실행 역할과 태스크 역할을 연결하라.

## 파트 2. 상황을 바꿔 판단하기

답을 비교할 때: [93-solutions.md](93-solutions.md) 파트 2. 결론만 쓰지 말고 어떤 관찰과 원리가 그 결론을 지지하는지 적는다.

**2-1.** 친구는 자기 컴퓨터에서 `127.0.0.1:3000`으로 주문 앱을 열었다. 나는 내 컴퓨터에서 똑같은 주소를 입력했는데 친구 앱이 나오지 않는다. 왜 이런 결과가 가능한지 설명하고, 친구 앱에 접속하려면 어떤 주소·수신·경로·허용을 확인할지 쓰라.

**2-2.** 상품 소개는 하루에 한 번 바뀌지만 재고는 주문마다 바뀐다. 둘 다 1시간 캐시에 저장해 주문 확정까지 그대로 쓰자는 제안이 있다. 어떤 부분을 나누어 판단할지 근거를 쓰고, 오래된 값을 허용해도 되는 반대 조건도 제시하라.

**2-3.** 앱 네 개가 각자 최대 20개 DB 연결을 가진다. 열두 개로 늘리려 한다. 전후의 최대 연결 수를 계산하고 왜 실제 연결 수와는 다를 수 있는지 설명하라. 앱 계산이 병목인 경우와 DB 대기가 병목인 경우의 증설 판단을 나누라.

**2-4.** 재고 1을 A와 B가 모두 읽고 각자 0을 저장한 뒤 주문을 만든다. 결과 재고가 음수는 아닌데 손님 두 명에게 주문 성공이 표시됐다. 어느 순서에서 문제가 만들어졌는지 설명하고, 읽은 값을 따로 판단하는 방식의 한계를 쓰라.

**2-5.** 소비자는 영수증을 보냈지만 큐에 완료 확인을 보내기 전에 종료됐다. 큐가 같은 메시지를 다시 전달했다. 왜 중복 발송이 가능한지와 업무를 한 번만 처리하려면 어떤 식별·기록·외부 계약이 필요한지 설명하라.

**2-6.** A 앱의 새 요청 배정을 멈췄다. A에는 남은 처리 시간이 12초인 주문이 있는데 실행 환경은 5초 뒤 강제 종료한다. 앱에 SIGTERM 처리기가 있으니 괜찮다는 주장에 동의하는지, 시간과 진행 상태를 근거로 답하라.

**2-7.** 배포 후 사용자가 느리다고 한다. 어떤 요청의 기록은 입력 검증 10 ms, 연결 풀 대기 90 ms, DB 질의 40 ms, 응답 만들기 10 ms다. 먼저 확인할 지점을 고르고, 이 한 표만으로 아직 확정할 수 없는 원인도 쓰라.

## 파트 3. 관찰·재현 과제

해설과 판정 예: [93-solutions.md](93-solutions.md) 파트 3. 앞의 두 과제는 macOS·Linux의 일반 셸 기준이다. 운영 계정과 서비스는 사용하지 않는다. 도구나 접근 권한이 없으면 임의 설치·우회 대신 그 제한을 기록하고 다음 과제로 넘어가도 된다.

**3-1. 이름 조회와 HTTP 응답 구분하기**

다음 명령을 실행하고 결과에서 주소 조회 상태, HTTP 상태 줄, 헤더, 본문을 찾아 분리해 기록하라. `dig`는 DNS를 조회하고 `curl`은 요청을 보내는 도구다. `-i`는 응답 헤더를 함께 보이고, timeout 옵션의 숫자는 초 단위 한도다.

```bash
dig example.com A
dig study.invalid A
curl -i --connect-timeout 3 --max-time 10 https://example.com/
curl -i --connect-timeout 3 --max-time 5 https://study.invalid/
```

프록시나 조직의 네트워크 정책에 따라 관찰이 달라질 수 있다. 특정 IP·시간·본문이 같아야 한다고 가정하지 않는다.

- [ ] DNS 상태와 HTTP 상태를 다른 칸에 기록했다.
- [ ] 성공한 응답에서 헤더와 본문을 구분했다.
- [ ] 실패가 어느 단계에서 관찰됐는지 출력으로 설명했다.
- [ ] 관찰과 원인 추정을 구분했다.
- 막히면: [03장](../docs/03-dns-and-http.md), [04장](../docs/04-tcp-and-tls.md). 예상 20~30분은 저자의 추정이다.

**3-2. 내 프로세스의 수명 관찰하기**

[06장](../docs/06-processes-and-concurrency.md)의 `sleep` 실습을 실행한다. 각 명령의 뜻을 먼저 설명한 뒤 자기 자식의 PID·명령 이름·종료 상태를 기록하라. 실행한 자식만 정리한다.

- [ ] `&`와 `$!`의 의미를 설명했다.
- [ ] 종료 전에 `ps`에서 자기 자식의 명령 이름을 확인했다.
- [ ] 그 자식에만 TERM을 보냈고 남아 있지 않은지 확인했다.
- [ ] 이 관찰로 웹 주문의 정상 종료까지 검증한 것은 아니라는 범위를 설명했다.
- 막히면: [06장](../docs/06-processes-and-concurrency.md). 예상 15~20분은 추정이다.

**3-3. 두 주문의 실행 순서를 종이에 재현하기**

처음 재고는 1이다. 먼저 “A 읽기, B 읽기, A 쓰기, B 쓰기, 각각 주문 추가”의 각 단계에서 A가 기억한 값·B가 기억한 값·DB 재고·주문 수를 표로 채우라. 다음에는 A가 읽고 변경을 끝낸 뒤 B가 새로 읽는 순서로 바꾸어 비교하라. B는 재고가 0이면 주문을 거절한다는 조건이다.

- [ ] 프로세스가 읽어 기억한 값과 DB의 현재 값을 별도 열에 두었다.
- [ ] 두 순서의 최종 주문 수 차이를 설명했다.
- [ ] 필요한 조정의 대상이 읽기·판단·변경의 관계임을 설명했다.
- [ ] 조건부 변경과 주문 기록을 묶는 개선 절차를 말로 적었다.
- 막히면: [09장](../docs/09-transactions-and-recovery.md). 예상 25~35분은 추정이다.

**3-4. 교체 중인 앱과 주문을 한 표에 놓기**

v1 앱 A·B가 주문을 받는다. 새 v2 앱 C는 시작 뒤 초기화가 필요하다. A에는 남은 12초의 주문이 있다. 데이터의 열 이름도 바꾸려 한다. 시간 순서 표에 각 앱의 버전·준비 여부·새 요청 허용·진행 중 주문·읽고 쓰는 열을 적고 전환을 설계하라. 실제 제품의 기본 제한 값은 모른다고 가정한다.

- [ ] 실행과 준비 확인을 구분했다.
- [ ] 새 요청 배정과 기존 주문 마무리를 구분했다.
- [ ] 종료 제한에 필요한 정보와 가정을 표시했다.
- [ ] 호환 버전과 되돌릴 수 있는 시점을 구체적으로 정했다.
- [ ] 사용자 성공·지연으로 다음 단계 진행 여부를 판단할 근거를 적었다.
- 막히면: [13장](../docs/13-deployment-and-shutdown.md)~[15장](../docs/15-observability-and-capacity.md). 예상 40~60분은 추정이다.
