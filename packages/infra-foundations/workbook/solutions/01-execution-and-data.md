# 회수 해설 — 실행·통신·데이터

[문제](../92-workbook.md)를 먼저 풀고 비교한다. [채점 안내](../93-solutions.md)의 도움 사용 구분을 따른다. 문장 일치가 아니라 필수 근거를 대조한다.

### 1-1

**확인할 능력:** 계산·작업 상태·보존할 기록을 구분한다.

- [ ] 수량 비교·계산을 CPU의 명령 실행에 연결했다.
- [ ] 처리 중 값과 내일 읽을 기록을 서로 다른 수명의 공간에 연결했다.
- [ ] 전원 종료 뒤 RAM만의 값은 유지되지 않는 이유를 설명했다.

**성립하는 답의 예:** CPU는 수량 비교·계산 명령을 실행하고, 메모리는 처리 중인 주문 값을 둔다. 내일 읽을 주문은 전원 종료 후에도 남는 저장소에 기록해야 한다. RAM만의 값은 전원을 껐다 켜도 그대로 남지 않는다.

**오개념 교정:** “주문 계산이 끝났으니 주문 기록도 남았다” → 실행 중 값의 변경과 영속 저장은 별개다. 메모리에서 계산한 뒤 오래 남길 기록을 저장해야 한다.
📍 되짚기: [01장 §1. 명령을 수행하는 CPU](../../docs/01-computers-and-programs.md#1-명령을-수행하는-cpu).

### 1-2

**확인할 능력:** 프로그램 파일과 실행 상태를 구분한다.

- [ ] 같은 명령 파일을 여러 실행이 사용할 수 있다고 설명했다.
- [ ] 각 프로세스의 입력·작업 중 메모리가 다를 수 있다고 설명했다.

**성립하는 답의 예:** 같은 명령 파일을 실행해도 프로세스별로 입력과 작업 상태가 다를 수 있다. A가 처리하는 주문이 B의 메모리에 자동으로 나타나지는 않는다. 파일과 실행 중 상태를 나누어 설명하면 된다.

**오개념 교정:** “같은 프로그램을 켰으니 메모리도 같다” → 같은 명령을 실행하는 것과 같은 작업 상태를 갖는 것은 다르다. 프로세스별 메모리는 자동 공유되지 않는다.
📍 되짚기: [01장 §6. 저장된 프로그램과 실행 중인 프로세스](../../docs/01-computers-and-programs.md#6-저장된-프로그램과-실행-중인-프로세스).

### 1-3

**확인할 능력:** 주소·포트와 앱의 수신 준비를 연결한다.

- [ ] 같은 IP에서도 목적지 포트로 통신 끝점을 구분했다.
- [ ] 주문 앱의 주소·3000번 수신과 관리자 앱의 4000번 수신을 구분했다.
- [ ] 실행 코드의 존재와 바인딩·수신 대기 준비가 다름을 설명했다.

**성립하는 답의 예:** 목적지 포트로 통신 끝점을 구분한다. 주문은 해당 주소의 3000번에 수신 대기하는 앱으로 연결돼야 한다. 코드에 주문 기능이 있다는 사실만으로 네트워크 수신이 시작되지는 않는다.

**오개념 교정:** “컴퓨터에 주문 코드가 있으면 어느 포트로 보내도 된다” → 운영체제가 해당 주소·포트의 소켓으로 전달할 준비가 돼야 한다. 업무 코드가 존재하는 것만으로 수신 소켓이 생기지 않는다.
📍 되짚기: [02장 §5. 컴퓨터에 도착한 뒤 어느 프로그램에 줄까](../../docs/02-addresses-and-packets.md#5-컴퓨터에-도착한-뒤-어느-프로그램에-줄까).

### 1-4

**확인할 능력:** 이름 조회와 업무 요청을 분리한다.

- [ ] DNS 결과가 이름의 주소 등 접속 정보임을 설명했다.
- [ ] HTTP가 요청·응답의 형식과 의미를 정한다고 설명했다.
- [ ] 조회 뒤 연결·요청·서버 처리·응답이 남아 있음을 순서로 연결했다.

**성립하는 답의 예:** DNS는 이름의 주소 등 접속 정보를 찾는다. 실제 연결과 HTTP 요청 전달, 서버의 업무 처리와 응답은 뒤에 남는다. HTTP는 요청과 응답의 형식·의미를 약속한다.

**오개념 교정:** “DNS가 응답했으니 상품 조회도 성공했다” → 이름의 정보를 얻은 것과 주문 서버가 상품 질의를 처리한 것은 다른 사건이다. DNS 서버는 상품 내용을 반환하는 업무 서버가 아니다.
📍 되짚기: [03장 §7. 이름 찾기와 HTTP 요청은 다른 사건이다](../../docs/03-dns-and-http.md#7-이름-찾기와-http-요청은-다른-사건이다).

### 1-5

**확인할 능력:** 바이트 전달·전송 보호·업무 결과를 구분한다.

- [ ] 바이트 위치와 수신 상태로 순서를 복구하는 역할을 TCP에 연결했다.
- [ ] 상대 검증과 내용 보호의 역할을 TLS에 연결했다.
- [ ] 두 준비의 성공이 DB 주문 커밋을 증명하지 않음을 설명했다.

**성립하는 답의 예:** TCP는 바이트 위치와 수신 상태를 관리해 원래 순서로 읽게 한다. TLS는 상대 확인과 통신 보호를 맡는다. 둘의 성공만으로 서버 앱이 주문을 커밋했는지는 알 수 없다.

**오개념 교정:** “HTTPS 연결이 됐으니 주문도 저장됐다” → 연결과 암호 보호는 바이트 교환을 준비한다. 주문을 읽고 저장하는 앱·DB의 결과는 별도로 확인한다.
📍 되짚기: [04장 §한 요청에서의 위치와 배포와의 연결](../../docs/04-tcp-and-tls.md#한-요청에서의-위치와-배포와의-연결).

### 1-6

**확인할 능력:** 왕복 경로·허용·수신을 따로 확인한다.

- [ ] 라우팅의 다음 전달 결정과 방화벽의 허용 판단을 구분했다.
- [ ] 응답의 주소·포트와 반환 경로·허용도 확인했다.
- [ ] 대상 주소·포트에서 앱이 실제 수신 중인지 포함했다.

**성립하는 답의 예:** 라우팅은 목적지에 대한 다음 전달을 고르고 방화벽은 통신을 허용할지 판단한다. 반환 경로와 응답 허용, 실제 목적지 주소·포트의 수신도 맞아야 한다. 길을 추가하는 것만으로 모든 조건이 바뀌지는 않는다.

**오개념 교정:** “기본 경로를 추가하면 통신도 모두 허용된다” → 경로 선택은 허용 판단을 대신하지 않는다. 요청뿐 아니라 응답이 돌아오고 앱이 수신해야 왕복 통신이 된다.
📍 되짚기: [05장 §반환 패킷은 어느 포트로 오는가](../../docs/05-routing-and-access.md#반환-패킷은-어느-포트로-오는가).

### 1-7

**확인할 능력:** 대기를 겹치는 것과 계산 병렬화를 구분한다.

- [ ] A의 입출력 대기 중 CPU가 다른 일을 진행할 수 있다고 설명했다.
- [ ] 비동기가 완료 통지 뒤 후속 처리를 이어가는 방식임을 설명했다.
- [ ] 긴 계산 두 개의 실제 동시 실행에는 실행 자원이 필요하다고 구분했다.

**성립하는 답의 예:** 대기 중인 A가 CPU를 계속 쓰지 않을 때 그 자원으로 B를 진행할 수 있다. 긴 계산 두 개를 실제 같은 시각에 하려면 실행 자원이 필요하다. 비동기는 완료 통지 뒤 이어 처리하는 방식이며 CPU 자체를 늘리지 않는다.

**오개념 교정:** “async를 붙이면 계산 속도가 두 배가 된다” → 비동기는 기다림을 다루는 방식이다. CPU 자원을 새로 만들지 않으며 한 실행 흐름의 긴 계산은 다른 준비 작업을 밀 수 있다.
📍 되짚기: [06장 §이벤트 루프는 멈춘 요청을 어떻게 이어 갈까](../../docs/06-processes-and-concurrency.md#이벤트-루프는-멈춘-요청을-어떻게-이어-갈까).

### 1-8

**확인할 능력:** 이미지와 실행별 상태·파일 수명을 구분한다.

- [ ] 이미지는 템플릿이며 A·B는 별도 실행 상태라고 설명했다.
- [ ] A의 메모리와 쓰기 계층 파일이 B에 자동 복사되지 않음을 설명했다.
- [ ] 공유·보존할 데이터에는 적절한 외부 저장소와 연결이 필요하다고 설명했다.

**성립하는 답의 예:** 이미지는 템플릿이며 A와 B는 별도 실행 상태다. A의 쓰기 계층 파일도 B로 자동 복사되지 않는다. 공유·보존할 데이터는 적절한 외부 저장 공간과 연결을 마련해야 한다.

**오개념 교정:** “이미지가 같으니 A가 업로드한 파일도 B에 있다” → 읽기 전용 이미지 계층과 각 컨테이너의 변경은 구분된다. 볼륨 등 공유 저장소를 명시적으로 연결한 경우와도 나눠야 한다.
📍 되짚기: [07장 §6. 같은 컨테이너 재시작과 새 컨테이너 교체](../../docs/07-containers-and-images.md#6-같은-컨테이너-재시작과-새-컨테이너-교체).

### 1-9

**확인할 능력:** 앱과 영속 데이터의 수명을 분리한다.

- [ ] 앱 종료와 함께 사라질 수 있는 실행 상태를 구분했다.
- [ ] 어제 주문은 영속 저장소에 남겨야 함을 설명했다.
- [ ] 새 앱도 같은 업무 기록을 찾아 읽을 주소·접근 조건이 필요하다고 연결했다.

**성립하는 답의 예:** 프로세스 메모리의 작업 중 상태와 오래 남길 주문 기록을 분리한다. 새 앱도 기록을 찾아 읽도록 저장 위치와 접근 방식을 마련해야 한다. 앱 실행 수명과 데이터 수명은 다르다.

**오개념 교정:** “앱을 다시 실행하면 예전 메모리가 돌아온다” → 새 실행은 새 작업 상태로 시작한다. 오래 남길 사실을 별도로 기록하고 새 실행이 읽어야 한다.
📍 되짚기: [08장 §1. 프로그램이 사라져도 남아야 할 사실](../../docs/08-storage-and-databases.md#1-프로그램이-사라져도-남아야-할-사실).

### 1-10

**확인할 능력:** 함께 확정할 변경과 외부 효과의 경계를 정한다.

- [ ] 재고 차감과 주문 추가를 같은 DB 트랜잭션으로 묶었다.
- [ ] 커밋·롤백과 전부 반영 또는 취소의 관계를 설명했다.
- [ ] 별도 외부 결제는 이 롤백에 자동 포함되지 않는다고 설명했다.

**성립하는 답의 예:** 함께 바뀌어야 할 변경을 트랜잭션으로 묶는다. 커밋하면 확정하고 실패 시 그 단위를 롤백한다. 외부 결제가 같은 DB 트랜잭션에 자동 참여하지 않으므로 결과 조회나 취소 절차는 별도다.

**오개념 교정:** “내 DB를 롤백하면 외부 결제도 취소된다” → 다른 회사가 확정한 효과는 내 DB 트랜잭션의 제어 범위 밖이다. 상태 조회·취소·보상 같은 별도 계약이 필요하다.
📍 되짚기: [09장 §8. 내 DB 밖의 결제는 왜 롤백되지 않을까](../../docs/09-transactions-and-recovery.md#8-내-db-밖의-결제는-왜-롤백되지-않을까).
