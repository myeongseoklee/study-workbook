# 회수 해설 — 협력·배포·운영

[문제](../92-workbook.md)를 먼저 풀고 비교한다. [채점 안내](../93-solutions.md)의 도움 사용 구분을 따른다. 문장 일치가 아니라 필수 근거를 대조한다.

### 1-11

**확인할 능력:** 요청 분배 외의 확장 조건을 설명한다.

- [ ] 분배 외에 상태 공유·공통 의존성·장애 경계 중 하나 이상의 구체적 문제를 골랐다.
- [ ] 그 문제가 생기는 처리 과정이나 실패 사례를 설명했다.
- [ ] 제안한 대응이 성립하는 조건과 남는 의존성을 설명했다.

**성립하는 답의 예:** 세션을 예로 들면 A에서 로그인한 식별자 S가 다음 요청에 B로 갈 수 있다. S의 사용자 정보를 A 메모리에만 두면 B는 찾지 못한다. A가 공유 저장소에 세션을 기록하고 B도 같은 S를 조회하게 만들면 특정 앱에 묶이지 않는다. 이 대응에는 저장소 접근·가용성, 세션의 만료·폐기 관리가 필요하다. 요청을 분배한 것만으로 이런 공유가 생기지는 않는다.

공통 DB 예도 인정한다. 각 앱의 연결 풀이 늘어 전체 연결 수가 커질 수 있으므로 앱별 최대값과 앱 수를 함께 계산하고 DB의 연결·처리 여유를 확인한다. 장애 경계 예라면 같은 호스트의 앱들이 함께 실패할 수 있음을 밝히고 배치를 분산하되 공통 의존성이 남는지 설명할 수 있다. 세 예를 모두 나열할 필요는 없다.

**오개념 교정:** “앱 수만 늘리면 메모리와 DB 처리 능력도 같이 늘어난다” → 요청을 나누는 기능은 세션을 공유하거나 공통 DB를 증설하지 않는다. 선택한 문제의 실제 공유 범위와 병목을 확인해야 한다.
📍 되짚기: [10장 §6 총 연결](../../docs/10-scaling-and-state.md#6-앱을-늘리면-db-연결도-늘-수-있다), [10장 §7 장애 경계](../../docs/10-scaling-and-state.md#7-여러-개와-서로-다른-장애-경계), [10장 §5. 무상태 앱의 뜻](../../docs/10-scaling-and-state.md#5-무상태-앱의-뜻).

### 1-12

**확인할 능력:** 결과 불확실성을 유지하며 재시도를 설계한다.

- [ ] 미수신·처리 중·완료 후 응답 유실 중 두 가지 이상을 구분했다.
- [ ] 같은 업무 의도 식별과 결과 확인·중복 방지를 연결했다.
- [ ] 재시도 횟수·전체 시간·부하 제한이 필요하다고 설명했다.

**성립하는 답의 예:** 요청 미수신·처리 중·처리 완료 후 응답 유실 등이 가능하다. 원래 의도 식별자로 결과를 확인하거나 안전하게 다시 요청할 계약이 필요하다. 중복 효과를 막고 총 횟수·전체 시간·백오프·지터로 추가 부하도 제한한다.

**오개념 교정:** “타임아웃이면 저장이 실패했으니 새 주문으로 보내면 된다” → 호출자의 기다림 종료는 서버의 미처리 증명이 아니다. 같은 의도를 추적하고 결과와 중복 효과를 함께 관리해야 한다.
📍 되짚기: [11장 §2. 서버는 저장했는데 손님은 모를 수 있다](../../docs/11-timeouts-and-retries.md#2-서버는-저장했는데-손님은-모를-수-있다).

**후속 복습의 기준:**
- [ ] 남은 전체 예산을 600 ms로 계산했다.
- [ ] 각 시도의 한도를 새로 주어 전체 약속을 넘길 수 있음을 설명했다.
- [ ] 첫 시도의 결과 확인·같은 의도 식별과 중복 방지는 시간 예산과 별도라고 설명했다.

남은 예산은 1,000−300−100=600 ms다. 새로 1,000 ms를 주면 전체 한도를 넘길 수 있다. 남은 예산 안에서 다음 시도·추가 대기를 배치하거나 중단한다. 첫 시도가 확정됐는지는 여전히 별도이므로 같은 의도로 결과를 확인하고 중복 효과를 막아야 한다.

### 1-13

**확인할 능력:** 캐시와 큐의 이점·비용을 대응시킨다.

- [ ] 캐시를 원본 결과 재사용과 오래된 값의 문제에 연결했다.
- [ ] 큐를 작업 전달·완료 지연·처리 속도 차이에 연결했다.
- [ ] 재전달이 중복 업무를 만들 수 있다고 설명했다.

**성립하는 답의 예:** 캐시는 결과를 재사용해 DB 읽기 등을 줄이지만 원본 변경 후 오래된 값을 줄 수 있다. 큐는 일을 넘겨 처리 시점을 나누지만 완료 지연과 적체가 생길 수 있다. 처리 후 ack 전 실패로 재전달되면 중복 업무도 다뤄야 한다.

**오개념 교정:** “큐에 넣었으니 영수증 발송은 완료됐다” → 큐 접수와 소비자의 업무 완료는 다른 사건이다. 처리·확인 사이 실패로 재전달될 수 있다.
📍 되짚기: [12장 §4. 주문 응답 전에 영수증 발송까지 끝내야 할까](../../docs/12-caches-and-queues.md#4-주문-응답-전에-영수증-발송까지-끝내야-할까).

### 1-14

**확인할 능력:** 앱 교체에서 요청 수명을 보존한다.

- [ ] 실행 시작과 초기화·준비 완료가 다르다고 설명했다.
- [ ] 새 요청 배정 중단 후에도 진행 중 주문이 남는다고 설명했다.
- [ ] 대체 대상 준비와 종료 제한 안의 마무리를 시간 순서로 연결했다.

**성립하는 답의 예:** 프로세스가 생겨도 초기화는 끝나지 않았을 수 있다. 새 요청 배정을 멈춰도 기존 주문은 남는다. 준비된 대체 대상으로 새 요청을 옮기고, 기존 일을 종료 제한 안에 마무리할 절차가 필요하다.

**오개념 교정:** “새 배정을 멈췄으니 이전 앱은 즉시 강제 종료해도 된다” → 이미 받은 요청과 연결은 남을 수 있다. 새 유입과 진행 중 작업을 별도로 관리해야 한다.
📍 되짚기: [13장 §5. 새 요청을 멈추어도 기존 요청은 남는다](../../docs/13-deployment-and-shutdown.md#5-새-요청을-멈추어도-기존-요청은-남는다).

### 1-15

**확인할 능력:** 버전 공존과 데이터 전환 순서를 설명한다.

- [ ] 옛 독자·작성자가 옛 열에 의존하므로 먼저 지우면 안 됨을 설명했다.
- [ ] 추가·호환 쓰기·백필 검증·읽기 전환을 연결했다.
- [ ] 옛 사용과 지원할 롤백 필요가 사라진 근거 뒤에 제거한다고 설명했다.

**성립하는 답의 예:** 공존 중인 옛 앱과 롤백 대상이 옛 열을 사용할 수 있다. 새 열 추가, 호환 작성자 전환, 기존 데이터 채움과 검증, 새 읽기 전환을 거친다. 옛 소비자와 롤백 필요가 사라졌다는 근거 뒤에 제거한다.

**오개념 교정:** “v2 코드가 준비됐으니 옛 열은 바로 삭제해도 된다” → v1과 배치·관리 도구가 남을 수 있고 이전 앱으로 돌아갈 수도 있다. 전환 중의 독자·작성자까지 확인해야 한다.
📍 되짚기: [14장 §1. 실행 중인 코드도 DB 구조에 기대고 있다](../../docs/14-schema-and-rollback.md#1-실행-중인-코드도-db-구조에-기대고-있다).

### 1-16

**확인할 능력:** 기록 수단과 측정 경계로 원인 후보를 좁힌다.

- [ ] 메트릭·로그·추적이 각각 집계·사건·작업 구간에 답한다고 설명했다.
- [ ] 평균은 일부 긴 지연을 감출 수 있다고 설명했다.
- [ ] CPU가 낮아도 풀·입출력 대기로 느릴 수 있다고 설명했다.

**성립하는 답의 예:** 메트릭은 언제 어느 범위가 나빠졌는지, 로그는 어떤 요청에 무슨 사건이 있었는지, 추적은 그 요청이 어느 구간에 시간을 썼는지 돕는다. 평균에 긴 요청이 가려질 수 있고 CPU가 낮아도 대기할 수 있다.

**오개념 교정:** “평균 지연과 CPU가 낮으니 모든 사용자에게 정상이다” → 집계는 분포와 대기 구간을 감출 수 있다. 요청별 기록과 측정 경계를 함께 확인한다.
📍 되짚기: [15장 §5. 평균만으로는 긴 기다림이 가려질 수 있다](../../docs/15-observability-and-capacity.md#5-평균만으로는-긴-기다림이-가려질-수-있다).

### 1-17

**확인할 능력:** 주체 확인과 자원별 허용을 분리한다.

- [ ] 인증은 주체 확인이라고 설명했다.
- [ ] 인가에는 실제 대상 주문·허용 작업·업무 조건 확인이 필요하다고 설명했다.
- [ ] 네트워크 허용이나 TLS 서버 확인이 사용자 업무 권한을 대신하지 않음을 설명했다.

**성립하는 답의 예:** 인증 성공은 주체를 확인했다는 뜻이다. 다른 사람 주문 삭제를 허용할지는 인가가 판단한다. 방화벽의 통신 허용이나 TLS의 서버 확인도 이 업무 권한을 대신하지 않는다.

**오개념 교정:** “로그인했으니 URL의 주문 번호만 바꾸어도 삭제할 수 있다” → 로그인은 다른 사람의 주문에 대한 권한을 주지 않는다. 서버가 확인된 주체와 실제 대상의 관계를 검사해야 한다.
📍 되짚기: [16장 §권한 검사는 어디에서 어떤 값을 신뢰해야 할까](../../docs/16-identity-and-permissions.md#권한-검사는-어디에서-어떤-값을-신뢰해야-할까).

### 1-18

**확인할 능력:** 실행 기반과 앱의 AWS 호출 주체를 구분한다.

- [ ] 시작 전 이미지 가져오기를 실행 기반의 작업으로 구분했다.
- [ ] 실행 후 앱의 S3 읽기를 앱 코드의 호출로 구분했다.
- [ ] 실행 역할·태스크 역할을 해당 주체에 대응시키고 실제 오류 주체를 확인했다.

**성립하는 답의 예:** 태스크를 준비하는 실행 기반과 실제 업무를 수행하는 앱은 다르다. 다운로드에는 실행 역할, 앱의 AWS API 호출에는 태스크 역할을 중심으로 실제 요청 주체와 오류를 확인한다.

**오개념 교정:** “앱의 S3 읽기가 거부되면 실행 역할에 권한을 추가한다” → 태스크를 준비하는 기반과 실행된 앱이 쓰는 역할은 다르다. 실제 호출 주체를 먼저 확인해야 한다.
📍 되짚기: [17장 §6. 누가 요청하는가 — 실행 역할과 태스크 역할](../../docs/17-aws-architecture.md#6-누가-요청하는가--실행-역할과-태스크-역할).
