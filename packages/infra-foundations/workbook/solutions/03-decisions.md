# 판단 해설 — 조건과 근거

[문제](../92-workbook.md)를 먼저 풀고 비교한다. [채점 안내](../93-solutions.md)의 도움 사용 구분을 따른다. 문장 일치가 아니라 필수 근거를 대조한다.

### 2-1

**확인할 능력:** 루프백과 외부 수신 조건으로 접속 실패를 좁힌다.

- [ ] 각 컴퓨터의 127.0.0.1이 서로 다른 자기 자신이라고 설명했다.
- [ ] 친구의 도달 가능한 실제 주소와 앱 바인딩·수신을 확인했다.
- [ ] 왕복 경로·통신 허용을 구분해 다음 확인을 제시했다.

**성립하는 답의 예:** 내 컴퓨터의 루프백은 내 네트워크 환경의 자기 자신이다. 친구의 루프백과 같은 컴퓨터를 뜻하지 않는다. 친구 앱에 도달할 실제 주소와 수신 바인딩, 연결 경로와 왕복 허용을 확인한다. 같은 URL 문자열만 비교해서 앱 결함으로 단정하지 않는다.

**오개념 교정:** “같은 URL이 안 되니 친구 앱 코드가 고장 났다” → 문자열이 같아도 루프백이 가리키는 실행 환경은 다르다. 먼저 어느 컴퓨터의 끝점에 연결했는지 확인한다.
📍 되짚기: [02장 §7. 내 컴퓨터 안에서만 시험하기](../../docs/02-addresses-and-packets.md#7-내-컴퓨터-안에서만-시험하기).

### 2-2

**확인할 능력:** 캐시 최신성 요구와 갱신 경쟁을 판단한다.

- [ ] 상품 소개와 주문 확정 재고의 최신성 요구를 나눴다.
- [ ] A의 옛 읽기→B의 변경·삭제→A의 캐시 채움 순서로 오래된 값 재등장을 설명했다.
- [ ] 쓰기 뒤 삭제의 한계와 오래됨을 허용할 반대 조건을 함께 설명했다.

**성립하는 답의 예:** 소개 문구와 주문 확정의 최신 재고는 요구가 다르다. 오래된 재고만으로 주문을 확정하면 품절 뒤에도 판매할 수 있다. 제시한 경쟁에서는 B가 캐시를 지운 뒤 A가 예전 가격을 다시 채우므로, 쓰기 뒤 삭제만으로 즉시 최신성을 보장하지 못한다.

만료는 재사용을 제한하지만 원본 읽기와 캐시 쓰기의 동시성을 없애지 않는다. 잠깐 오래된 상품 설명·미리 보기에는 캐시를 쓸 수 있고, 확정은 기준 저장소에서 검증하는 등 요구를 나눌 수 있다. 어떤 경로를 허용할지는 최신성 계약으로 정한다.

**오개념 교정:** “DB 변경 뒤 캐시를 지웠으므로 새 값만 나온다” → 원본 읽기와 캐시 쓰기 사이에 다른 변경이 끼면 이전 결과가 다시 저장될 수 있다. 삭제 명령 하나로 동시성까지 사라지지 않는다.
📍 되짚기: [12장 §DB를 바꾸고 캐시를 지워도 오래된 값이 다시 들어갈 수 있다](../../docs/12-caches-and-queues.md#db를-바꾸고-캐시를-지워도-오래된-값이-다시-들어갈-수-있다).

### 2-3

**확인할 능력:** 앱 증설의 최대 연결 수와 병목을 비교한다.

- [ ] 앱 측 최대 연결 합계를 80개와 240개로 계산했다.
- [ ] 최대치와 실제 사용 수가 다르고 다른 사용자의 연결도 있음을 설명했다.
- [ ] 앱 계산 병목과 공통 DB·풀 대기 병목에서 증설 효과를 나눴다.

**성립하는 답의 예:** 최대 합계는 80개에서 240개로 늘어난다. 실제 수는 풀 사용량과 수명 등에 따라 최대치보다 작을 수 있고 다른 서비스의 연결도 별도다. 앱 계산이 병목이고 의존성에 여유가 있으면 증설이 도움 될 수 있다. DB나 풀 대기가 병목이면 더 압박할 수 있어 질의·반환·잠금을 먼저 살핀다.

**오개념 교정:** “앱을 세 배 늘리면 DB 처리 능력도 세 배다” → 각 앱의 풀이 늘어도 공통 DB의 처리 능력은 그대로일 수 있다. 연결 증가가 대기와 경쟁을 키울 수 있다.
📍 되짚기: [10장 §6. 앱을 늘리면 DB 연결도 늘 수 있다](../../docs/10-scaling-and-state.md#6-앱을-늘리면-db-연결도-늘-수-있다).

### 2-4

**확인할 능력:** 공유 재고의 읽기·판단·쓰기 경쟁을 재현한다.

- [ ] A·B가 모두 1을 기억한 시점을 짚었다.
- [ ] 각자 0을 쓰면 최종 재고 0인데 주문 둘이 되는 과정을 설명했다.
- [ ] 읽기·판단·변경 사이의 경쟁을 조정해야 함을 설명했다.

**성립하는 답의 예:** 둘 다 재고 1을 읽은 뒤 자기 계산 결과 0을 쓰므로, 재고는 0인데 주문은 둘이 된다. 읽기·판단·변경 사이에 다른 요청이 끼어든 결과다. 조건부 변경의 성공 여부를 확인하고 주문 기록까지 트랜잭션으로 묶는 등 동시 접근을 조정해야 한다.

**오개념 교정:** “재고가 음수가 아니므로 초과 판매가 아니다” → 같은 하나를 두 요청이 각각 팔아도 덮어쓰기로 0이 남을 수 있다. 최종 숫자만으로 주문과 재고의 관계를 검증할 수 없다.
📍 되짚기: [09장 §3. 트랜잭션 두 개가 있으면 동시 주문도 자동으로 맞을까](../../docs/09-transactions-and-recovery.md#3-트랜잭션-두-개가-있으면-동시-주문도-자동으로-맞을까).

### 2-5

**확인할 능력:** 업무 기록·발행 의도·외부 효과의 실패 경계를 나눈다.

- [ ] A에서 주문과 발행 의도를 같은 DB에 함께 기록해야 누락 재시도가 가능함을 설명했다.
- [ ] B의 발송 후 확인 전 실패는 아웃박스로 없어지지 않는다고 설명했다.
- [ ] 메시지 식별·완료 기록·외부 제공자의 중복 방지·조회 계약을 연결했다.

**성립하는 답의 예:** A에서는 주문과 “발행할 메시지”를 같은 DB 트랜잭션으로 남기는 아웃박스가 도움이 된다. 발행자가 중단돼도 미발행 기록이 남아 다시 보낼 수 있다. 주문과 발행 의도를 따로 확정한 실패 구간을 줄이는 것이다.

B는 이미 외부 발송이 끝났지만 큐는 완료를 모르는 상태다. 아웃박스도 발행 후 완료 기록 전에는 중복 발행할 수 있어 이 문제를 없애지 않는다. 안정적인 메시지·업무 식별자와 완료 기록, 외부 발송자의 멱등·결과 조회 계약을 연결해야 한다. 로컬 DB에 완료를 먼저 썼다는 사실만으로 외부 발송의 성공까지 보장하면 안 된다.

**오개념 교정:** “아웃박스를 쓰면 영수증도 반드시 한 번만 발송된다” → 아웃박스는 업무와 발행 의도의 기록을 묶는다. 발행·외부 처리·완료 확인 사이의 중복 가능성은 계속 남는다.
📍 되짚기: [12장 §주문은 저장했는데 큐에 넣기 전에 앱이 죽으면](../../docs/12-caches-and-queues.md#주문은-저장했는데-큐에-넣기-전에-앱이-죽으면).

**후속 복습의 기준:**
- [ ] DB에 발행할 기록이 남아 다시 시도할 수 있음을 설명했다.
- [ ] 큐에 이미 도착한 메시지가 다시 발행될 수 있음을 설명했다.
- [ ] 소비자의 업무 효과는 식별·멱등 처리·외부 계약으로 별도 조정한다고 설명했다.

DB에는 미발행으로 보이는 아웃박스 기록이 남아 발행자가 다시 시도할 수 있다. 큐는 이미 첫 메시지를 받았으므로 동일 업무 메시지가 중복 도착할 수 있다. 아웃박스가 막는 기록 누락과 소비자 효과를 한 번으로 제한하는 일은 다르며, 안정적인 식별자와 소비자의 처리·외부 효과 계약이 필요하다.

### 2-6

**확인할 능력:** 정상 종료의 의도와 실제 시간 한도를 비교한다.

- [ ] 12초 남은 요청을 5초 안에 끝낼 수 있다는 주장의 모순을 짚었다.
- [ ] SIGTERM 처리 기회와 강제 종료 제한이 별개임을 설명했다.
- [ ] 요청 상한·드레이닝·앱 대기·실행 제한을 맞추거나 재처리 계약이 필요하다고 제시했다.

**성립하는 답의 예:** 동의할 수 없다. 정리할 기회가 있어도 남은 요청 12초보다 강제 종료까지의 5초가 짧다. 실제 처리 상한과 드레이닝·앱 대기·런타임 제한을 맞추거나 재개·재시도 가능한 작업 계약이 필요하다.

**오개념 교정:** “SIGTERM 처리기가 있으니 종료 한도는 상관없다” → 정리 코드도 실행할 시간이 필요하다. 강제 종료 시점이 먼저 오면 남은 처리가 끊길 수 있다.
📍 되짚기: [13장 §6. 시간 제한을 서로 맞추기](../../docs/13-deployment-and-shutdown.md#6-시간-제한을-서로-맞추기).

### 2-7

**확인할 능력:** 측정한 대기 구간에서 다음 가설을 고른다.

- [ ] 가장 긴 구간인 연결 풀 대기 90 ms를 질의 40 ms와 구분했다.
- [ ] 연결 점유·반환·대기 수 등 가설을 구분할 다음 관찰을 제안했다.
- [ ] 한 표만으로 누수·DB 용량·모든 사용자 원인을 확정하지 않았다.

**성립하는 답의 예:** 가장 긴 구간은 90 ms의 연결 풀 대기다. 연결을 왜 오래 기다렸는지 실제 사용·반환·다른 요청의 점유를 본다. 한 표만으로 누수나 느린 질의, DB 용량 부족을 확정하지는 못한다. 사용자 전체에 같은 원인이 있는지도 다른 표본으로 확인한다.

**오개념 교정:** “DB라는 이름이 들어가니 DB 서버 CPU부터 증설하면 된다” → 연결을 얻기 전 대기와 질의 실행은 다르다. 점유·반환과 실제 DB 작업을 나눠 확인해야 한다.
📍 되짚기: [15장 §4. 추적은 한 요청이 쓴 시간을 구간별로 연결한다](../../docs/15-observability-and-capacity.md#4-추적은-한-요청이-쓴-시간을-구간별로-연결한다).

### 2-8

**확인할 능력:** TCP 연결 확인에 필요한 정보를 설명한다.

- [ ] SYN+ACK를 보낸 것과 상대가 서버 번호를 받은 것을 구분했다.
- [ ] 마지막 유효 ACK 없이 오래된 SYN을 현재 연결로 오인할 수 있음을 설명했다.
- [ ] TCP 상태 확인과 사용자 인증·주문 커밋이 별개임을 설명했다.

**성립하는 답의 예:** 서버는 클라이언트가 제시한 시작 번호를 받았고 자기 번호를 보냈지만, 상대가 서버의 시작 정보를 받았는지는 아직 확인하지 못했다. 오래된 SYN만 늦게 도착한 경우도 현재 요청으로 오해할 수 있다. 새 서버 번호에 대한 유효한 ACK를 요구해 그 SYN 하나로 연결을 확정하지 않게 한다.

이 교환은 바이트 전송을 위한 상태 동기화다. 사용자 신원·권한이나 DB 커밋을 증명하지 않는다. TLS의 서버 인증과 앱의 로그인·업무 처리는 별도다.

**오개념 교정:** “세 번 왕복하니 양쪽 사용자와 주문 성공도 확인됐다” → 기본 절차는 세 메시지 교환으로 번호와 연결 상태를 맞춘다. 사용자 인증과 DB 작업의 성공을 확인하는 절차가 아니다.
📍 되짚기: [04장 §두 번째에서 바로 끝내면 왜 부족할까](../../docs/04-tcp-and-tls.md#두-번째에서-바로-끝내면-왜-부족할까).
