# 재현 해설 — 상태와 실패 시점

[문제](../92-workbook.md)를 먼저 풀고 비교한다. [채점 안내](../93-solutions.md)의 도움 사용 구분을 따른다. 문장 일치가 아니라 필수 근거를 대조한다.

### 3-1

**확인할 능력:** 관찰 출력과 원인 추정을 구분한다.

- [ ] 실제 출력에서 DNS 상태와 HTTP 상태를 다른 단계로 기록했다.
- [ ] 응답이 있으면 헤더·본문을 나누고 없으면 없는 응답을 만들어 내지 않았다.
- [ ] 접근 제한·프록시 등 확인하지 못한 범위와 원인 가설을 표시했다.

**성립하는 답의 예:** 정상적인 직접 조회 환경에서는 example.com의 DNS 응답과 HTTPS 응답을 볼 수 있다. study.invalid는 실패 예시를 위한 예약 이름이다. DNS의 NXDOMAIN과 HTTP의 상태 코드는 서로 다른 단계의 응답이다. 프록시가 대신 HTTP 오류를 줄 수도 있으므로 실제 출력을 읽는다.
실패한 요청은 헤더·본문이 없을 수도 있다. 그때 없는 HTTP 응답을 지어내지 않고 도구가 보고한 오류와 진행 단계를 기록하면 된다.

도구나 네트워크가 없어 실행하지 못했다면 관찰 수행은 미확인으로 남긴다. 본문으로 설명한 지식과 실제 출력을 확인한 사실을 나누어 기록한다.

**오개념 교정:** “실패 사이트니까 HTTP 404가 출력됐다고 적는다” → 이름 조회부터 실패하면 HTTP 응답이 없을 수 있다. 실제 도구 출력에 없는 상태를 추정해 기록하지 않는다.
📍 되짚기: [03장 §7. 이름 찾기와 HTTP 요청은 다른 사건이다](../../docs/03-dns-and-http.md#7-이름-찾기와-http-요청은-다른-사건이다).

### 3-2

**확인할 능력:** TCP 상태와 바이트 위치를 계산해 재현한다.

- [ ] 세 메시지의 방향·플래그·양방향 SEQ·ACK와 상태를 표에 적었다.
- [ ] SYN은 번호 한 칸을 쓰고 순수 ACK는 쓰지 않는 규칙을 적용했다.
- [ ] 앞부분 유실 때와 복구 뒤의 수신 버퍼·누적 ACK를 계산했다.
- [ ] 세 번째 ACK 유실 때 클라이언트와 서버의 상태를 구분했다.
- [ ] TCP 바이트 재전송과 새 HTTP 업무 재시도를 구분했다.

**성립하는 답의 예:** 데이터 없는 세 메시지의 핵심 값은 다음과 같다.

| 방향 | 플래그 | SEQ | ACK | 메시지 처리 뒤 상태 |
|---|---|---|---|---|
| 클라이언트 → 서버 | SYN | 1,000 | 아직 유효한 확인 없음 | 클라이언트 SYN-SENT, 서버 SYN-RECEIVED |
| 서버 → 클라이언트 | SYN+ACK | 7,000 | 1,001 | 클라이언트 ESTABLISHED, 서버 SYN-RECEIVED |
| 클라이언트 → 서버 | ACK | 1,001 | 7,001 | 양쪽 ESTABLISHED |

SYN은 한 칸을 쓰지만 순수 ACK는 쓰지 않아 첫 클라이언트 데이터는 1,001부터다. `ORD`는 1,001~1,003, `ER42`는 1,004~1,007이다. 뒤만 먼저 받으면 서버의 누적 ACK는 1,001이고, 앞이 복구돼 연속 수신하면 1,008이다. 다음 표는 앱이 읽기 전의 수신 상태와 읽을 수 있는 범위를 구분한다.

| 시점 | 수신 측 보관 상태 | 앱이 순서대로 읽을 수 있는 범위 | 누적 ACK |
|---|---|---|---|
| 뒤 조각만 도착 | 1,004~1,007 보관, 앞부분 대기 | 이 데이터의 앞부분부터는 아직 읽을 수 없음 | 1,001 |
| 앞 조각 복구 | 1,001~1,007이 연속으로 완성 | ORDER42의 바이트, 읽기 호출 횟수는 미정 | 1,008 |

세 번째 ACK가 유실되고 아직 후속 데이터가 없으면 클라이언트는 ESTABLISHED여도 서버는 SYN-RECEIVED로 대기할 수 있다. 뒤의 재전송·후속 ACK로 상태가 바뀌는 것과 구분한다. 앱이 다시 만든 HTTP 주문은 새로운 바이트여서 TCP가 원래 주문의 업무 중복으로 제거하지 않는다.

**오개념 교정:** “순수 ACK를 보냈으니 다음 데이터 번호도 하나 증가한다” → 순수 ACK는 순서 공간을 소비하지 않는다. 데이터 바이트 수와 SYN 등의 제어 정보를 기준으로 번호를 계산한다.
📍 되짚기: [04장 §4. 왜 연결 시작에 세 번의 교환이 필요할까](../../docs/04-tcp-and-tls.md#4-왜-연결-시작에-세-번의-교환이-필요할까).

**후속 복습의 기준:**
- [ ] 첫 데이터가 201부터이고 2바이트 수신 뒤 ACK=203이라고 계산했다.
- [ ] 5바이트 복구 뒤 ACK=208이라고 계산했다.
- [ ] TCP가 앱의 쓰기·읽기 호출 경계를 보존하지 않음을 설명했다.

SYN이 번호 한 칸을 사용하므로 첫 데이터는 201부터다. 201~202의 2바이트를 연속 수신하면 ACK=203이고, 203~207의 5바이트까지 복구되면 ACK=208이다. TCP는 순서 있는 바이트 흐름을 제공하므로 앱의 두 번 쓰기가 상대의 두 번 읽기와 일치할 필요는 없다.

### 3-3

**확인할 능력:** 동시 변경과 복구·결과 인지를 분리해 재현한다.

- [ ] 조정 없는 순서에서 각 요청의 기억·DB 재고·주문 수를 분리했다.
- [ ] 조건부 UPDATE 경쟁에서 대기·조건 재평가·변경 행 수와 주문 추가를 연결했다.
- [ ] A 커밋과 롤백 두 경우의 B 처리를 비교했다.
- [ ] WAL·커밋 기록·데이터 페이지·앱의 응답 인지를 별도로 기록했다.
- [ ] 주어진 장치 보존 가정 안에서 미확정 결과와 복구되는 확정 변경을 구분했다.

**성립하는 답의 예:** 조정 없는 순서에서 로컬 기억과 DB를 나누면 다음과 같다. ‘없음’은 아직 그 값을 읽지 않았다는 뜻이다.

| 단계 | A의 기억 | B의 기억 | DB 재고 | 주문 수 |
|---|---|---|---|---|
| 시작 | 없음 | 없음 | 1 | 0 |
| A 읽기 | 1 | 없음 | 1 | 0 |
| B 읽기 | 1 | 1 | 1 | 0 |
| A가 하나 빼서 쓰기 | 0 | 1 | 0 | 0 |
| B도 자기 기억에서 하나 빼서 쓰기 | 0 | 0 | 0 | 0 |
| A 주문 추가 | 0 | 0 | 0 | 1 |
| B 주문 추가 | 0 | 0 | 0 | 2 |

A가 DB에 0을 써도 B의 기억은 자동으로 바뀌지 않는다. 따라서 최종 재고만 검사하면 두 주문을 허용한 오류가 가려진다.

조건부 UPDATE를 주문 추가와 묶으면, A가 같은 행을 갱신하는 동안 B의 갱신은 기다릴 수 있다. A의 종료 결과에 따라 다음처럼 나뉜다.

| A의 결과 | B가 확인할 행과 UPDATE 결과 | B의 주문 처리 | 둘의 최종 확정 결과 |
|---|---|---|---|
| 주문을 추가하고 커밋 | 재고 0에 조건 재평가, 변경 행 수 0 | 주문을 추가하지 않음 | 재고 0, A 주문 하나 |
| 재고 변경도 롤백 | 재고 1에서 변경 가능, 변경 행 수 1 | 주문 추가와 함께 커밋 | 재고 0, B 주문 하나 |

이는 설명한 PostgreSQL Read Committed의 경쟁 사례다. B가 받은 변경 행 수를 무시하고 주문을 추가하면 이 결과를 유지하지 못한다. 다음은 동기 영속 기록과 장치 보존을 가정한 장애 복구 결과다.

| 장애 시점 | 재시작 뒤 확정 결과 | 앱이 아는 결과 |
|---|---|---|
| ① 미확정 변경, 유효한 커밋 기록 없음 | 해당 트랜잭션의 변경은 확정 결과로 보이지 않음 | 성공을 확정할 근거 없음 |
| ② WAL·커밋은 영속, 데이터 페이지 일부 미반영 | WAL을 이용해 확정 변경을 복구 | 응답이 없으므로 커밋 여부를 별도로 확인해야 함 |
| ③ 같은 영속 기록 뒤 응답 수신 | 확정 변경을 유지·필요 시 복구 | 커밋 성공을 전달받음 |

②와 ③의 DB 결과는 같을 수 있어도 앱의 지식은 다르다. 데이터 페이지를 모두 쓰지 않았다는 이유로 미확정으로 판단하거나, 응답 유실을 롤백으로 판단하면 안 된다. 이 표는 문제의 영속 기록·장치 보존 가정을 사용한다.

**오개념 교정:** “데이터 페이지가 덜 써졌거나 앱이 응답을 못 받으면 롤백이다” → 영속 WAL과 유효한 커밋 기록이 있으면 확정 변경을 복구할 수 있다. 앱이 결과를 아는지는 응답 수신의 별도 문제다.
📍 되짚기: [09장 §6. 메모리에서 바꾼 여러 페이지를 어떻게 장애 뒤에도 남길까](../../docs/09-transactions-and-recovery.md#6-메모리에서-바꾼-여러-페이지를-어떻게-장애-뒤에도-남길까).

**후속 복습의 기준:**
- [ ] 복구 가능 시점과 사고 사이 10분이 RPO 목표 5분보다 큼을 설명했다.
- [ ] 중단 후 25분이 RTO 목표 30분 안임을 계산했다.
- [ ] 로컬 WAL도 사라진 장애는 이전 복구 예의 보존 가정 밖이라고 설명했다.

최신 복구 가능 시점과 사고 사이 간격은 10분으로 RPO 목표 5분을 넘는다. 중단부터 복구까지 25분이므로 제시한 RTO 30분은 충족한다. 로컬 WAL 자체가 사라졌으므로 그것을 이용한 복구를 보장할 수 없다. 다른 곳의 백업·변경 기록으로 정한 범위까지 복구해야 한다.

복습 위치: [09장 §9](../../docs/09-transactions-and-recovery.md#9-복제와-백업은-어떤-실패를-복구할까).

### 3-4

**확인할 능력:** 배포·종료·데이터 전환의 진행 조건을 설계한다.

- [ ] 각 앱의 버전·초기화·준비 상태와 새 요청 허용을 분리했다.
- [ ] A의 새 유입 중단 후 기존 주문 마무리를 따로 유지했다.
- [ ] 12초 남은 요청과 종료 제한의 관계·추가 확인할 값을 명시했다.
- [ ] 옛 독자·작성자와 백필·검증·읽기 전환, 구체적 롤백 대상을 연결했다.
- [ ] 사용자 성공·지연으로 다음 교체를 진행·중단할 근거를 적었다.

**성립하는 답의 예:** 이 설계에서 새 v2는 먼저 옛 열 `full_name`을 읽고 두 열에 함께 쓰는 **호환 버전**으로 만든다. 새 열을 읽는 전환은 이후 v3에서 한다. 한 번의 교체로 모든 구조를 제거하려 하지 않는 선택이다. 아래는 실제 배포 관측이 아닌 문제 조건으로 만든 전환 예다.

| 단계 | 실행·진행 중 작업 | 새 요청 후보 | 데이터의 읽기·쓰기와 진행 조건 |
|---|---|---|---|
| 확장 | A·B는 v1 유지 | A, B | `display_name` 추가, v1은 옛 열만 사용 |
| C 시작 | v2 C는 초기화 중 | A, B | C를 아직 후보로 넣지 않음 |
| C 준비 | C의 설정·수신·준비 응답 확인 | A, B, C | v1과 v2 모두 옛 열을 읽음, v2는 두 열에 함께 씀 |
| A 배정 중단 | A의 기존 주문은 12초 남아 처리 중 | B, C | A의 주문·응답을 보존, 종료 제한 확인 전 즉시 강제 종료하지 않음 |
| A 마무리 | 주문·응답 완료 확인 후 A 정리·종료 | B, C | 남은 처리와 정리를 끝낼 실제 시간 확보 |
| 옛 작성자 교체 | D도 v2로 시작·준비한 뒤 B를 같은 방식으로 드레이닝·종료 | C, D | v1 웹 앱뿐 아니라 옛 열만 쓰는 배치·관리 도구도 남지 않았는지 확인 |
| 백필 | C·D v2가 계속 요청 처리 | C, D | 현재 행의 옛 값을 원자적으로 새 열에 채움, 누락·불일치 검증 |
| 읽기 전환 | v3를 일부씩 배포 | 준비된 v2·v3 | v3는 새 열을 읽되 두 열에 함께 씀, 롤백 대상은 v2 |
| 축소 | 롤백 기간 종료 뒤 새 열만 읽고 쓰는 정리 버전으로 모두 전환 | 준비된 새 버전 | 옛 열 독자·작성자가 없다는 근거 뒤 옛 열 제거 |

A의 종료 시간은 마지막 새 요청 수락과 드레이닝의 시작 시점을 함께 확인해 계산한다. 남은 12초와 연결·자원 정리에 필요한 시간을 강제 종료 한도가 허용해야 한다. 제품의 기본값은 문제에 없으므로 실제 제한·전파 지연·최장 작업 시간을 확인할 값으로 남긴다. 부족하면 배포를 멈추고 제한이나 작업 재처리 계약을 조정한다.

C가 준비되지 않거나 기존 주문이 진행 중이면 해당 종료 단계로 넘어가지 않는다. 버전별 요청 성공·지연을 관찰하고, 재고·주문 불일치 같은 업무 오류가 생기면 추가 교체를 멈춘다. 오류율·P99를 비교할 기간과 허용 범위는 문제에 주어지지 않았으므로 배포 전에 정할 값으로 적는다. DB를 공유하는 v2·v3의 읽기·쓰기 호환을 유지한 구간에서 v2로 트래픽을 되돌릴 수 있다. 최초 v1은 새 열을 유지하지 않아 같은 롤백 대상으로 취급하지 않는다.

다른 설계도 필요한 준비 용량·진행 중 작업·데이터 호환성과 진행·중단 근거를 만족하면 인정한다. 특정 제품의 기본값이나 모범 표의 버전 이름과 일치할 필요는 없다.

**오개념 교정:** “이전 이미지만 남아 있으면 언제든 안전하게 되돌릴 수 있다” → 옛 앱이 현재 데이터 구조와 값에서 읽고 쓸 수 있어야 한다. 이미지 보관과 데이터 호환성을 함께 확인해야 한다.
