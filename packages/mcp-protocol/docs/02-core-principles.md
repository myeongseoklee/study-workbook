# 핵심 원리 — MCP는 무엇을 왜 그렇게 풀었나

## 학습 목표

MCP의 구조적 결정(호스트-클라이언트-서버 분리, 1:1 연결, 무상태, 프리미티브 3+1종)이 각각 어떤 문제를 풀기 위한 것인지 설명할 수 있고, 새 기능 제안이 이 원칙들과 충돌하는지 판별할 수 있다.

## 선수 지식

- [01-prerequisites.md](01-prerequisites.md)의 JSON-RPC, LLM 도구 호출

## 원리 1: 통합 폭발 문제 — M×N을 M+N으로

### 왜 이게 중요한가

MCP가 없으면 AI 앱 M개 × 외부 시스템 N개 = M×N개의 커스텀 통합이 필요하다. 각 앱이 GitHub 연동, Slack 연동, DB 연동을 따로 만든다. MCP는 그 사이에 공용 프로토콜을 끼워 **M+N**으로 줄인다: 앱은 MCP 클라이언트 한 번, 시스템은 MCP 서버 한 번만 구현하면 서로 조합된다. 공식 문서의 비유는 "AI 애플리케이션의 USB-C 포트"다.

### 메커니즘

이 발상의 직계 조상은 **LSP(Language Server Protocol)**다. 에디터 M개 × 언어 N개 문제를 언어 서버라는 표준 인터페이스로 풀었듯, MCP는 AI 앱 × 컨텍스트 소스 문제를 푼다. 공식 명세가 LSP에서 영감을 받았다고 명시한다.

### 트레이드오프

| 얻는 것 | 포기하는 것 |
|---|---|
| 한 번 만들면 모든 클라이언트에서 동작 | 특정 앱에 최적화된 커스텀 통합보다 표현력 제약 |
| 생태계 재사용 (서버 레지스트리, Inspector 등 공용 도구) | 프로토콜 버전 관리라는 새 부담 |

## 원리 2: 호스트–클라이언트–서버, 그리고 1:1 연결

### 왜 이게 중요한가

용어를 섞어 쓰면 보안 논의가 무너진다. **호스트(host)**는 사용자가 마주하는 AI 앱(Claude Desktop, VS Code), **클라이언트(client)**는 호스트가 서버 하나당 하나씩 만드는 프로토콜 커넥터, **서버(server)**는 컨텍스트·기능을 제공하는 프로그램이다. 클라이언트와 서버는 **항상 1:1**이다. 호스트가 서버 3개에 붙으면 클라이언트도 3개다.

### 메커니즘 — 누가 무엇을 책임지나

- **호스트**: 클라이언트 생성·수명 관리, 보안 정책과 동의(consent) 집행, 사용자 인가 결정, LLM 통합·샘플링 조율, 여러 클라이언트에 걸친 컨텍스트 합성
- **클라이언트**: 자기 서버와의 메시지 왕복, 모든 요청에 프로토콜 버전·능력 첨부, 구독·알림 관리, 서버 간 보안 경계 유지
- **서버**: 프리미티브(tools/resources/prompts) 노출, 좁고 집중된 책임, 로컬 프로세스일 수도 원격 서비스일 수도 있음

"서버"는 실행 위치가 아니라 역할이다. 같은 머신에서 stdio로 뜨면 "로컬 서버", 인터넷 너머 Streamable HTTP면 "원격 서버"라 부르지만 프로토콜 의미는 같다.

### 왜 1:1인가

경계를 자르기 위해서다. 클라이언트 하나가 서버 여럿과 얘기하면 서버 A의 응답이 서버 B로 새는 경로가 생긴다. 1:1이면 "이 연결에서 오간 것"이 곧 "이 서버가 아는 것"이고, 호스트만이 여러 서버의 정보를 합칠 수 있는 유일한 지점이 된다.

## 원리 3: 네 가지 설계 원칙

명세가 명시한 원칙들이다. 각각이 구체적 프로토콜 결정으로 이어진다.

1. **서버는 극도로 만들기 쉬워야 한다** — 복잡한 조율(대화 관리, LLM 호출, 동의 UI)은 전부 호스트 몫. 서버는 좁은 기능에 집중. → 그래서 최소 서버는 "요청 받으면 응답"만 하면 된다.
2. **서버는 고도로 조합 가능해야 한다** — 각 서버가 고립된 기능 단위. 공유 프로토콜이 상호운용을 보장. → 그래서 파일 서버 + DB 서버 + Slack 서버를 한 호스트에 꽂아 함께 쓴다.
3. **서버는 전체 대화를 읽을 수 없고, 다른 서버 속을 볼 수 없어야 한다** — 서버는 필요한 컨텍스트만 받는다. 전체 대화 이력은 호스트에 남는다. 서버 간 상호작용은 호스트가 통제한다. → 이것이 아래 원리 4(서버는 요청을 시작할 수 없다)의 뿌리다.
4. **기능은 점진적으로 추가한다** — 코어는 최소한, 나머지는 능력(capability) 협상으로. 서버와 클라이언트가 독립적으로 진화하고 하위 호환을 유지한다. → 그래서 모든 기능이 capability 선언 뒤에 있고, 확장(extensions)은 opt-in 협상이다.

### 원리 3의 프로토콜적 귀결: 모든 상호작용은 클라이언트가 시작한다

`2026-07-28` 리비전에서 **서버는 JSON-RPC 요청을 보낼 수 없다** (클라이언트는 JSON-RPC 응답을 보내지 않는다). 서버가 사용자 입력이나 LLM 완성이 필요하면, 자기 응답 안에 "이런 입력이 필요하다"(`InputRequiredResult`)를 담아 돌려주고 클라이언트가 입력을 모아 **원래 요청을 재시도**한다. 이것이 MRTR 패턴이다([08-mrtr-client-features.md](08-mrtr-client-features.md)). 메시지 방향이 한쪽으로 고정되면 전송 구현(특히 확장성 있는 HTTP 서버)이 단순해지고, 서버가 임의 시점에 클라이언트를 찔러볼 수 있는 통로가 사라진다.

## 원리 4: 무상태(stateless) 프로토콜

### 왜 이게 중요한가

`2026-07-28`의 최대 변화다. **요청 하나를 처리하는 데 필요한 모든 정보가 그 요청 안에 있다.** 서버는 이전 요청에서 아무것도 추론하면 안 된다 — 같은 연결 위의 요청이라도.

이유는 배포 현실이다. 원격 MCP 서버는 로드밸런서 뒤에 여러 인스턴스로 뜬다. 세션이 있으면 sticky routing이나 공유 저장소가 필요하다. 무상태면 어떤 인스턴스가 받아도 처리할 수 있고, 서버 재시작·프로세스 교체에도 클라이언트는 그냥 재시도하면 된다.

### 메커니즘

- 모든 요청의 `_meta`에 프로토콜 버전과 클라이언트 능력이 실린다 (핸드셰이크로 "합의된 상태"를 만들지 않는다) — [03-messages-meta.md](03-messages-meta.md)
- 열린 연결(stdio 프로세스 포함)은 **세션이 아니다**. 클라이언트는 무관한 요청들을 한 전송 위에 섞어 보낼 수 있고, 서버는 연결 정체성을 대화 연속성의 근거로 삼으면 안 된다
- 여러 요청에 걸쳐야 하는 상태(장바구니, 트랜잭션)는 **명시적 식별자(핸들)**로 — 서버가 핸들을 발급하고 클라이언트(모델)가 다음 호출의 인자로 되돌려준다 ([06-tools.md](06-tools.md) § 상태가 필요한 도구)
- 장수 요청(`subscriptions/listen`)도 요청/응답이다 — 응답이 열린 알림 스트림일 뿐, 상태는 그 요청에 스코프된다

### 트레이드오프

| 얻는 것 | 포기하는 것 / 대가 |
|---|---|
| 수평 확장, 스티키 라우팅 불필요 | 요청마다 `_meta` 반복 전송 (약간의 오버헤드) |
| 재시작·재연결이 "재시도"로 단순화 | 크로스 요청 상태는 애플리케이션이 핸들로 직접 설계 |
| 리스트 응답이 연결마다 달라질 수 없음 → 캐시 가능 | 핸들 탈취라는 새 공격면 ([11-security.md](11-security.md)) |

## 원리 5: 프리미티브와 제어 주체

서버가 노출하는 것 3종 + 클라이언트가 제공하는 것. **"누가 사용 시점을 결정하는가"**로 나뉜다는 게 핵심이다.

| 프리미티브 | 제어 주체 | 무엇 | 예 |
|---|---|---|---|
| **Tools** | **모델** | 모델이 호출을 결정하는 실행 함수 | 항공권 검색, 파일 쓰기, API POST |
| **Resources** | **애플리케이션** | 앱이 붙일지 결정하는 읽기용 컨텍스트 데이터 | 파일 내용, DB 스키마, git 이력 |
| **Prompts** | **사용자** | 사용자가 명시적으로 고르는 템플릿 | 슬래시 커맨드, "휴가 계획" 템플릿 |
| **Elicitation** (클라이언트 기능) | 서버가 요청, 사용자가 응답 | 처리 중 부족한 정보를 사용자에게 묻기 | 예약 확정 전 좌석 선호 확인 |

이 구분이 UI 설계까지 결정한다: Tools는 모델이 자동 발견·호출하되 사람이 승인(human-in-the-loop)하고, Resources는 앱이 트리뷰·검색·자동 첨부로 노출하고, Prompts는 슬래시 커맨드·메뉴로 노출한다. Prompts의 "사용자 제어"는 **사용 시점**을 사용자가 정한다는 뜻이지 내용을 사용자가 쓴다는 뜻이 아니다 — 내용은 서버가 정의한다.

클라이언트 기능 중 Sampling(서버가 클라이언트의 LLM에 완성 요청)과 Roots(파일시스템 경계 안내)는 `2026-07-28`에서 deprecated다 — [08-mrtr-client-features.md](08-mrtr-client-features.md)에서 이유와 마이그레이션을 다룬다.

## 원리 6: 신뢰와 안전 — 프로토콜이 강제할 수 없는 것

명세의 보안 원칙: **사용자 동의와 통제**(모든 데이터 접근·작업에 명시적 동의), **데이터 프라이버시**(호스트는 동의 없이 리소스 데이터를 다른 곳에 전송 금지), **도구 안전**(도구 = 임의 코드 실행 경로. 신뢰할 수 없는 서버의 도구 설명·어노테이션은 **untrusted**로 취급, 호출 전 명시적 동의).

중요한 자기 인식이 명세에 있다: "MCP 자체는 이 원칙들을 프로토콜 수준에서 강제할 수 없다." 동의 UI, 접근 통제는 구현자(특히 호스트)의 책임이다. 프로토콜은 경계를 그어줄 뿐이다.

### ⚠️ 암기 필수

- [ ] **참여자 구조**: 호스트(AI 앱, 보안·동의·조율) → 클라이언트(커넥터) —1:1— 서버(기능 제공). 클라이언트:서버 = 항상 1:1
  - 이유: 모든 보안 논의("누가 무엇을 볼 수 있나")의 좌표계
- [ ] **프리미티브 제어 주체**: Tools=모델, Resources=애플리케이션, Prompts=사용자 (+ Elicitation은 클라이언트가 서버에 제공하는 기능)
  - 이유: 새 기능을 어느 프리미티브로 만들지 판단하는 기준이자 UI 설계의 근거
- [ ] **무상태 3원칙**: 요청은 자기완결(버전·능력 携帯) / 연결≠세션 / 크로스 요청 상태는 명시적 핸들
  - 이유: `2026-07-28` 설계 전체를 관통하는 판단 기준 — "이 정보를 어디에 두지?"의 답

## 자가 진단

<details>
<summary>Q1: "서버는 전체 대화를 읽을 수 없다"는 원칙이 MRTR 패턴과 어떻게 연결되는가?</summary>

**즉답 예시**: 서버가 임의 시점에 클라이언트로 요청을 보낼 수 있으면 대화 밖 정보를 능동적으로 캐낼 통로가 된다. 2026-07-28은 서버발 JSON-RPC 요청 자체를 없애고, 서버의 정보 요구를 "처리 중인 클라이언트 요청에 대한 응답(InputRequiredResult)" 안으로 한정했다. 서버는 자기가 받은 요청의 문맥 안에서만, 클라이언트가 재시도라는 형태로 동의해야만 추가 정보를 얻는다.

</details>

<details>
<summary>Q2: 호스트가 서버 4개에 연결된 상태에서, 서버 A의 도구 결과를 서버 B에 넘겨야 하는 워크플로우가 있다. 프로토콜상 누가 그 전달을 수행하는가, 왜?</summary>

**즉답 예시**: 호스트다. 클라이언트는 자기 서버와만 1:1로 통신하고 서버끼리는 서로를 볼 수 없다. 여러 서버에 걸친 컨텍스트 합성과 서버 간 상호작용 통제는 설계 원칙상 호스트의 책임이다. (그리고 서버 A의 출력은 서버 B 입장에서 untrusted 입력이므로, 호스트가 이 경계에서 검토 정책을 적용해야 한다.)

</details>

<details>
<summary>Q3: 무상태 프로토콜인데 쇼핑카트 같은 상태가 필요하면 어떻게 하는가? 그 방식의 새 위험은?</summary>

**즉답 예시**: 서버가 생성 도구에서 명시적 핸들(예: `basket_id`)을 발급하고, 이후 호출마다 그 핸들을 평범한 도구 인자로 받아 상태를 조회한다. 위험은 핸들 탈취/추측 — 그래서 핸들을 인증으로 취급하지 말고(소유≠권한), 충분한 엔트로피로 생성하고, 서버 측에서 인증된 주체에 바인딩해 다른 주체의 핸들 제시를 거부해야 한다.

</details>

<details>
<summary>Q4: "서버는 만들기 쉬워야 한다"는 원칙이 실제 프로토콜 규칙 어디에 반영돼 있는지 두 가지만?</summary>

**즉답 예시**: (1) 복잡한 것은 전부 호스트로 — 동의 UI, LLM 조율, 컨텍스트 합성이 서버 책임 밖이다. (2) 기능이 전부 선택적 capability라서 최소 서버는 `server/discover`와 자기가 선언한 프리미티브 몇 개만 구현하면 된다. (덧붙이면, MRTR 덕에 서버는 클라이언트로 요청을 보내는 채널 관리조차 필요 없다.)

</details>
