# 워크북 — MCP 프로토콜 정복 (문제)

## 사용법

`docs/`를 다 읽은 뒤, **자료를 덮고** 푼다. 정답과 해설은 전부 [93-solutions.md](93-solutions.md)에 있다 — 문항 번호가 그대로 대응한다. 막히면 정답을 열기 전에 각 문항이 가리키는 학습 파일로 먼저 돌아가라. 파트 3의 코딩 과제 풀이는 별도 브랜치에서 한다(레포 `README.md` § 규약 4 — `sol/mcp-protocol/{과제번호}`).

모든 문항의 기준은 프로토콜 리비전 **2026-07-28**이다.

## 파트 1. 회수 연습 (자료를 덮고)

> 정답: [93-solutions.md](93-solutions.md) 파트 1. 문항은 `docs/90-must-memorize.md`의 카드 1~18과 1:1 대응한다.

**1-1.** MCP의 세 참여자(호스트/클라이언트/서버)의 책임을 각각 한 줄로 쓰고, 클라이언트와 서버의 연결 관계(수 관계)를 말하라.

**1-2.** 서버의 세 프리미티브 각각의 **제어 주체**를 쓰고, 클라이언트가 서버에 제공하는 기능 중 deprecated되지 않은 것 하나를 대라.

**1-3.** 무상태 원칙 3가지를 쓰라. 그중 "요청은 자기완결"을 실현하는 `_meta`의 필수 필드 2개와 권장 필드 1개의 정확한 키 이름(프리픽스 포함)은? 필수 필드가 빠지면 어떤 에러가 오는가?

**1-4.** 다음 에러 코드의 이름/의미와, HTTP 전송에서의 상태 코드를 쓰라: `-32602`, `-32601`, `-32020`, `-32021`, `-32022`. 그리고 레거시 코드 `-32002`는 어떻게 취급해야 하는가?

**1-5.** JSON-RPC 구현 정의 대역(-32000~-32099)을 MCP가 어떻게 쪼갰는지 쓰고, 애플리케이션 자체 에러 코드는 어디에 할당해야 하는지 답하라.

**1-6.** `resultType`의 (a) 코어 허용 값 2개, (b) 필드가 아예 없을 때의 처리, (c) 모르는 값일 때의 처리를 쓰라. (b)와 (c)가 다른 이유는?

**1-7.** initialize 핸드셰이크 없이 버전 합의가 이루어지는 흐름을 3단계로 쓰라. `server/discover`는 서버와 클라이언트 각각에게 의무인가 선택인가?

**1-8.** stdio에서 dual-era 클라이언트가 `server/discover` 프로브를 보냈을 때 가능한 세 가지 결과와 각각의 판정·행동을 쓰라. HTTP에서는 무엇을 보고 판정하는가?

**1-9.** 2026-07-28에서 deprecated된 4가지 기능과 각각의 마이그레이션 경로를 쓰라.

**1-10.** stdio 전송에서 (a) stdout과 stderr의 용도 구분, (b) 메시지 프레이밍 규칙, (c) 클라이언트 주도 종료 절차 3단계를 쓰라.

**1-11.** Streamable HTTP에서 (a) JSON-RPC 요청 POST에 대한 두 가지 응답 형태, (b) 알림 POST에 대한 응답, (c) 필수 헤더 3종과 본문 불일치 시의 응답을 쓰라. SSE 스트림이 끊긴 미완 요청은 어떻게 복구하는가?

**1-12.** 전송별 취소 방법(HTTP / stdio)을 쓰고, **서버가** `notifications/cancelled`를 보낼 수 있는 유일한 경우를 대라.

**1-13.** HTTP 서버의 Origin 검증은 어떤 공격을 막는가? 검증 실패 시 응답과, 로컬 실행 시 바인딩 권장 사항은?

**1-14.** 도구의 두 오류 계층 각각의 (a) 와이어 형태, (b) 대표 사례 2개씩, (c) 계층을 가르는 판단 기준 한 문장을 쓰라.

**1-15.** MRTR에 대해: (a) `input_required`를 돌려줄 수 있는 메서드 3개, (b) `inputRequests` 값으로 허용되는 요청 3종, (c) InputRequiredResult의 최소 구성 규칙, (d) 재시도의 id 규칙, (e) requestState가 인가·로직에 영향을 줄 때의 보호 요구를 쓰라.

**1-16.** elicitation의 form 모드로 요청이 **금지**된 정보 유형과 그 대안, 그리고 URL 모드에서 서버가 반드시 수행해야 하는 사용자 검증(피싱 방어)을 쓰라. `action: "accept"`는 URL 모드에서 무엇을 의미하고 무엇을 의미하지 않는가?

**1-17.** (a) `subscriptions/listen` 필터 4종, (b) 스트림의 첫 메시지와 그 의미, (c) 알림-구독 상관 키, (d) 재연결 시 클라이언트의 의무, (e) 캐시 힌트(`ttlMs`+`cacheScope`)가 의무인 6개 오퍼레이션, (f) `cacheScope: "private"`의 의미를 쓰라.

**1-18.** MCP 인가 체인을 401부터 토큰 사용까지 순서대로 쓰라(각 단계의 RFC 번호 포함). 그리고 토큰 취급 3금칙을 대라.

## 파트 2. 판단 문제 (시나리오)

> 해설: [93-solutions.md](93-solutions.md) 파트 2. 각 문항에 **선택과 근거**를 모두 적어라.

**2-1.** 두 서버를 만들려 한다. (A) 팀원 20명이 쓰는 사내 이슈 트래커 연동 서버(사내 IdP 있음), (B) 개발자 각자의 로컬 git 저장소를 읽는 서버. 각각에 전송과 자격증명 방식을 고르고 근거를 쓰라. 그리고 (B)를 HTTP로 만드는 것이 오히려 나은 조건을 하나 대라.

**2-2.** 날씨 도구 서버에서 다음 세 실패가 발생한다: ① 클라이언트가 `get_wether`(오타)를 호출, ② `date: "어제"`처럼 파싱 불가능한 값, ③ 날씨 API 업스트림이 500 반환. 각각을 프로토콜 오류/실행 오류 중 어디로 보낼지 정하고 근거를 쓰라. 하나라도 반대로 설계하면 어떤 증상이 나타나는가?

**2-3.** dual-era HTTP 클라이언트를 만든다. modern 요청에 `400 Bad Request`가 왔을 때의 분기 로직을 설계하라. "400이면 무조건 initialize 폴백"으로 구현하면 어떤 서버에서 어떤 문제가 생기는가?

**2-4.** 쇼핑카트 MCP 서버를 설계한다. "연결이 유지되는 동안 카트를 서버 메모리에 들고 있으면 되지 않느냐"는 동료 제안을 평가하고, 규격에 맞는 설계와 그때 지켜야 할 핸들 원칙 4가지를 쓰라. 카트 조회가 실패했을 때(만료된 핸들) 어떤 형태로 응답해야 모델이 회복할 수 있는가?

**2-5.** 서버가 사용자의 서드파티(GitHub) 액세스 토큰이 필요하다. "form elicitation으로 토큰을 입력받아 저장하자"는 제안의 문제를 지적하고, 규격이 의도한 설계를 흐름으로 쓰라. 이때 MCP 클라이언트가 준 우리 서버용 토큰을 GitHub에 그대로 쓰면 안 되는 이유도 포함하라.

**2-6.** 호스트 앱에서 `tools/list` 캐시를 설계한다. 서버는 `ttlMs: 300000`, `cacheScope: "public"`, `listChanged: true`를 준다. (a) 캐시 유효 판정 로직, (b) list_changed 수신 시 처리, (c) TTL을 폴링 주기로 쓰면 안 되는 이유, (d) 이 응답이 인증된 엔드포인트에서 왔다면 public 캐시를 다른 사용자 요청에 재사용해도 되는지를 쓰라.

**2-7.** 서드파티 API로 위임하는 MCP 프록시 서버의 보안 리뷰를 맡았다. confused deputy 관점에서 최소한 확인해야 할 항목 3가지와, 각각이 뚫렸을 때의 공격 시나리오를 한 줄씩 쓰라.

**2-8.** 호스트가 서버 30개, 도구 400개에 연결된다. (a) 모든 도구 정의를 컨텍스트에 싣는 방식의 세 가지 비용, (b) progressive discovery의 3층 구조, (c) 전환 시점 판단 기준, (d) 이 패턴이 프롬프트 캐시와 충돌하는 지점과 완화책, (e) 반대로 "전부 로드"가 나은 조건을 쓰라.

## 파트 3. 재현 과제 (직접 만들기)

> 해설: [93-solutions.md](93-solutions.md) 파트 3. 코딩 과제의 **명세는 `tests/`에 있다** — 문제와 함께 주어지는 실행 가능한 정의다. 풀이 순서: 브랜치 생성 → `tests/`를 읽는다 → `src/`의 🎯 TODO를 채운다 → `pnpm test {과제번호}` → 통과 후에만 `solutions/`와 비교.

**3-1.** 메시지 분류기와 에러 대역. (과제 `03-01`)
- 명세: `tests/03-01-message-rules/index.test.ts` · 스켈레톤: `src/03-01-message-rules/index.ts`
- 핵심 함정: null id의 처리, 부재 vs 미지의 resultType, 음수 대역의 부등호 방향
- 소요 예상: 25~40분 · 막히면: `docs/03-messages-meta.md`

**3-2.** 버전·능력 게이트와 세대(era) 판정. (과제 `04-01`)
- 명세: `tests/04-01-version-gate/index.test.ts` · 스켈레톤: `src/04-01-version-gate/index.ts`
- 핵심 함정: 세 거부(-32602/-32022/-32021)의 검사 순서, 빈 능력 선언 `{}` vs 부재, 폴백을 특정 코드에 걸기
- 소요 예상: 30~45분 · 막히면: `docs/04-lifecycle-versioning.md`

**3-3.** 최소 도구 서버 코어 (tools/list + tools/call). (과제 `06-01`)
- 명세: `tests/06-01-tool-server/index.test.ts` · 스켈레톤: `src/06-01-tool-server/index.ts`
- 핵심 함정: 네 가지 실패의 목적지(−32602 / isError / −32603 / −32601)가 전부 다르다, 결정적 정렬, handler 유출
- 소요 예상: 40~60분 · 막히면: `docs/06-tools.md` § 오류의 2계층

**3-4.** MRTR requestState의 봉인과 검증. (과제 `08-01`)
- 명세: `tests/08-01-mrtr-state/index.test.ts` · 스켈레톤: `src/08-01-mrtr-state/index.ts`
- 핵심 함정: 검증 순서(무결성이 내용 검사보다 먼저), 만료 경계(now === expiresAt), 불투명성
- 소요 예상: 30~45분 · 막히면: `docs/08-mrtr-client-features.md` § requestState 보안
