# 00. 개요 — 멀티 에이전트 시스템, 무지의 무지에서 시작하기

## 이 워크북은 무엇인가

사내에서 멀티 에이전트 시스템을 구축하려는 **3년차 백엔드 개발자**를 위한 실습형 학습 자료다. "무엇을 모르는지조차 모르는" 상태에서 출발해, 직접 코드를 짜면서 판단 기준을 세우는 것을 목표로 한다.

각 챕터는 다음 구조를 따른다: **핵심 원리(WHY)** → **필수 지식(HOW)** → **🛠 직접 해볼 것**(실습) → **⚠️ 암기 필수** → **자가진단**.

## 먼저: 에이전트는 마법이 아니다 — "프롬프트 + 도구"다

거창해 보이는 "에이전트"의 실체는 단순하다:

```
광고 전문가 에이전트 = LLM + "너는 광고 도메인 전문가야"(프롬프트) + [도구 몇 개]
```

**에이전트 = (역할을 적은 프롬프트) + (할 수 있는 일 몇 개).** 그리고 **"여러 에이전트가 협업한다" = 그 (프롬프트+도구) 조합들을 순서대로 부르고 결과를 넘기는 코드**다. 이 그림만 잡으면 이후 나오는 오케스트레이터·플랫폼·프로토콜이 전부 이 위에 얹히는 층으로 보인다.

## 두 번째: "멀티 에이전트"는 사실 두 가지다

이 단어는 서로 다른 두 개를 가리킨다. 시작 전에 구분해야 헷갈리지 않는다.

| 축 A — 오케스트레이터-워커 | 축 B — 전문가 협업 / 플랫폼 |
|---|---|
| 리드 하나가 임무를 소유, 서브에이전트는 **일회성 일꾼** | 각 에이전트가 **1급 시민**(분석가·광고 전문가·개발자), 지속되는 역할·도구 |
| 위계적 (함수가 헬퍼를 부름) | 동료 협업 (전문가 팀이 회의로 문제 해결) |

*"이번주 광고 어떻게 세팅?"* 에 분석·광고·개발 에이전트가 각자 관점을 대고 종합하는 것 — 이게 축 B다. 이 워크북은 **개별 에이전트 제작(축 A·B 공통 토대)부터 시작해, 축 B의 협업과 그걸 서비스 인프라로 짓는 법까지** 다룬다.

## 세 번째: 앱 레이어 vs 인프라 레이어

같은 전문가 3개를 어디에 두느냐로 두 방식이 갈린다:

- **앱 레이어** — 3개가 한 프로그램 안의 **함수**. 오케스트레이터가 순서대로 호출. 쉽고, 대부분의 시작점.
- **인프라 레이어** — 3개가 각각 **독립 서비스**(Agent Card·레지스트리·A2A). 마이크로서비스처럼. 여러 팀이 나눠 만들거나 독립 배포가 필요할 때.

> **핵심 판단:** 모놀리스로 충분한데 마이크로서비스부터 짓지 않듯, **앱 레이어로 충분한데 플랫폼부터 짓지 마라.** 승격 조건은 [08장](08-agent-platform-infra.md)에 게이트로 정리돼 있다.

## 네 번째: 멀티 에이전트를 의심하라

에이전트를 여러 개로 쪼개면 **비용·지연시간·실패 지점이 전부 곱셈으로 늘어난다.** 툴 10개 붙인 단일 에이전트로 될 일을 5개로 쪼개 디버깅 지옥에 빠지는 경우가 많다. **정당화 조건(미리보기):** 서브태스크가 ① 병렬화 가능 ② 독립 컨텍스트 필요 ③ 명확한 병합 규칙 — 이 셋이 안 맞으면 단일 에이전트가 거의 항상 낫다([07장](07-should-you-build-multi-agent.md)).

## 이 워크북 사용법

1. **순서대로 읽되, 실습을 건너뛰지 마라.** 0주차 `while` 루프를 직접 안 짜면 이후 프레임워크가 뭘 감추는지 영영 모른다.
2. **각 챕터의 🛠 과제를 실제로 실행하라.** 읽기만 하면 "안다는 착각"만 남는다.
3. **암기 카드는 챕터를 다 소화한 뒤에 본다.** 처음부터 외우려 하지 마라.

주당 5~6시간 기준. 시간이 부족하면 0주차·5~6주차(평가/관측성)를 절대 건너뛰지 마라 — 대부분의 사내 프로젝트가 거기서 무너진다. 08장은 "여러 사람이 에이전트를 나눠 맡는" 상황이면 일찍 봐도 좋다.
