# 04. 멀티 에이전트 협업 — 전문가들을 어떻게 나누고 합치나 (3~4주차)

## 학습 목표

이 챕터를 다 읽고 실습하면, **두 종류의 "멀티 에이전트"를 구분**하고, 여러 전문가 에이전트가 협업하는 흐름을 코드로 짤 수 있으며, 조정(오케스트레이션)을 중앙에 둘지 분산할지 판단하고, "쓰기는 단일 스레드로" 원칙이 왜 생사를 가르는지 설명할 수 있다.

## 선수 지식

[02장](02-what-is-an-agent.md)의 에이전트 루프(에이전트 = 프롬프트 + 도구 + LLM 루프), [03장](03-langgraph-basics.md)의 State/Reducer/조건부 엣지.

## 핵심 원리 (WHY) — "멀티 에이전트"는 사실 두 가지다

이 단어는 두 개의 아주 다른 것을 가리킨다. 먼저 이걸 구분해야 이후가 안 헷갈린다.

| | 축 A — 오케스트레이터-워커 | 축 B — 전문가 협업 |
|---|---|---|
| 서브에이전트의 지위 | 리드가 부리는 **일회성 일꾼**. 정체성·지속성 없음 | 각자 **1급 시민** — 지속되는 역할(분석가/광고 전문가/개발자), 자기 페르소나·도구 |
| 관계 | 위계적. 리드가 소환→회수→폐기 | **동료(peer)**. 대등하게 의견 내고 핸드오프 |
| 비유 | 함수가 헬퍼 함수를 부름 | 전문가 팀이 회의로 문제를 푼다 |
| 대표 사례 | Anthropic 리서치 시스템(리드+서브) | 도메인 전문가 크루, 에이전트 플랫폼 |

두 축은 배타적이지 않다 — 협업하는 전문가 에이전트(축 B) 하나가 내부적으로 오케스트레이터-워커(축 A)로 구현될 수도 있다. 하지만 **설계 관점이 다르다.** 이 챕터는 주로 축 B(전문가 협업)를 다루고, 그걸 "서비스 인프라"로 짓는 방법은 [08장](08-agent-platform-infra.md)으로 넘긴다.

## 필수 지식 (HOW) — 마법이 아니라 "프롬프트 + 도구를 순서대로 부르는 코드"

멀티 에이전트가 거창해 보이지만, 실체는 단순하다. 먼저 개별 에이전트부터:

```
광고 전문가 에이전트 = LLM
                     + 시스템 프롬프트: "너는 광고 도메인 전문가야"
                     + 도구: [벤치마크 조회, 캠페인 세팅 API]
```

**에이전트 = (역할을 적은 프롬프트) + (할 수 있는 일 몇 개).** "분석 에이전트"는 프롬프트가 "너는 데이터 분석가"이고 도구가 "성과 DB 조회"인 것뿐이다.

그러면 **"여러 에이전트가 협업한다" = 서로 다른 (프롬프트+도구) 조합을 순서대로/조건부로 부르고 결과를 넘기는 코드**다. *"이번주 광고 어떻게 세팅?"* 을 예로 들면:

```
사용자: "이번주 광고 어떻게 세팅하지?"
   │
   ├─→ ① 분석 에이전트   ("지난주 성과 뽑아줘")
   │      → "CTR 2.1%, 전환 320건, A타겟이 최고"
   │
   ├─→ ② 광고 전문가     (①의 결과를 넘기며 "이 데이터면 전략은?")
   │      → "A타겟에 예산 60%, 크리에이티브 B 확대"
   │
   ├─→ ③ 개발 에이전트   (②의 전략을 넘기며 "이 세팅을 API로 구현")
   │      → 실제 세팅 or 세팅 스크립트
   │
   └─→ 종합해서 사용자에게 답변
```

**이 화살표 흐름을 짜는 코드가 "협업"의 전부다.** 앞 에이전트의 답을 뒤 에이전트에게 넘기고, 마지막에 합친다.

### 전문가 역할 부여 — 협업의 본질

축 B의 핵심은 각 에이전트에 **뚜렷한 전문가 역할**을 주는 것이다. 프레임워크(예: CrewAI)는 이걸 **역할(role)·목표(goal)·배경(backstory)** 세 항목으로 정형화한다:

- **role**: "시니어 광고 전략가"
- **goal**: "주어진 성과 데이터로 이번주 캠페인 전략을 세운다"
- **backstory**: "10년간 퍼포먼스 마케팅을 해온 전문가로, ROAS 최적화에 강하다"

이 세 줄이 그 에이전트의 시스템 프롬프트가 되고, 여기에 도구를 붙이면 전문가 에이전트가 된다. **다중 관점(분석/전략/구현)의 종합**이라는 협업의 가치가 여기서 나온다.

### 협업 토폴로지 3가지

전문가들을 어떻게 잇느냐:

1. **슈퍼바이저(Supervisor)** — 중앙 조정자가 "다음은 누구 차례"를 결정. 통제·디버깅 쉬움. 실무 기본값.
2. **네트워크(Network)** — 조정자 없이 에이전트들이 직접 핸드오프. 유연하지만 무한 루프·책임 소재 불명 위험.
3. **그룹챗(Group Chat)** — 여러 에이전트가 공유 대화 스레드에서 발언하고, 매니저가 발언 순서를 라우팅(AutoGen식). 복잡한 작업을 동적으로 쪼갤 때.

```
   supervisor              network                 group chat
       S
   ┌───┼───┐               A ─────── B             A   B   C
   A   B   C               │         │             └───┼───┘
                           └─── C ───┘              thread ←── manager
```

세 토폴로지가 갈리는 것은 결국 엣지다 — 슈퍼바이저는 모든 엣지가 `S`를 지나고, 네트워크는 `S`가 사라진 자리에 에이전트 사이의 직선이 생기고, 그룹챗은 개별 엣지 대신 공유 스레드 하나가 그 자리를 대신한다.

### ⭐ 조정(오케스트레이션)은 사라지지 않는다 — 위치만 바뀐다

멀티 에이전트를 아무리 나눠도 누군가는 이 5가지를 **반드시** 해야 한다: ① 요청 접수 → ② 누가 할지 결정 → ③ 컨텍스트 전달 → ④ 언제 끝났는지 판단 → ⑤ 최종 종합. 이걸 하는 게 오케스트레이터다.

**진짜 선택지는 "오케스트레이터 있냐 없냐"가 아니라 "조정 로직을 어디에 두냐"다:**

```
중앙집중 (지휘자)  ←──────────────────→  분산 (동료)
오케스트레이터 하나가        각 에이전트가 스스로
순서를 정하고 종합           "이건 네 담당" 하며 넘김

통제·디버깅 쉬움            유연·확장 쉬움
한눈에 흐름 보임            (에이전트 추가해도 중앙 안 건드림)
god object 위험             흐름 흩어져 디버깅 어려움, 루프 위험
```

완전 분산조차 보통 **얇은 진입점 + 공유 상태(블랙보드)**가 암묵적 조정자 역할을 한다. "조정자가 아예 없는" 설계는 실무에 거의 없다. 그리고 오케스트레이터 자신의 똑똑함도 스펙트럼이다: **하드코딩 라우팅 → LLM 라우터 → 계획 에이전트(스스로 계획) → 완전 분산**. 왼쪽일수록 통제가 쉽고, 오른쪽일수록 유연하다.

## 실제 사례 — Anthropic의 리서치 시스템

Anthropic이 공개한 멀티 에이전트 리서치 시스템은 **중앙집중(슈퍼바이저) + 병렬화의 실전**이다:

- 리드 에이전트가 질문을 보고 계획한 뒤 **3~5개 서브에이전트를 동시 생성**해 병렬 검색. 복잡한 질의에서 리서치 시간 **최대 90% 단축**.
- **툴 설계가 성패를 가른다:** 잘못된 툴을 일부러 써보는 "툴 테스트 에이전트"로 툴 설명을 고쳐, 이후 작업 완료 시간 **40% 감소**.

교훈: 멀티 에이전트의 이득은 **병렬화 가능한 작업**에서 나온다. 순차 의존이 강하면 나눠도 이득이 없다.

## 반드시 알아야 할 원칙 — 단일 작성자(Single-Writer)

Cognition이 실전에서 뽑아낸, 멀티 에이전트를 "그나마 작동하게" 만드는 원칙:

> **여러 에이전트가 지능(읽기·판단)을 보태되, 쓰기(최종 상태 확정)는 단일 스레드로 유지하라.**

여러 전문가가 정보를 읽고 제안할 수는 있지만, **최종 답을 확정하는 쓰기는 한 곳에서만** 일어나게 한다. 이렇게 하면 **컨텍스트 파편화**(에이전트들이 서로 다른 정보를 봐 모순된 결정을 내리는 것)를 억제한다. 병렬로 모으되(read fan-out), 결정은 한 지점으로(single write). [03장](03-langgraph-basics.md)의 append 리듀서가 "여러 읽기 결과를 안전하게 한 곳에 모으는" 그 도구다. 축 B에서도 **최종 종합/쓰기를 누가 소유하는가**는 오케스트레이터가 맡는 게 보통이다.

## 🛠 직접 해볼 것 — 광고 세팅 3전문가 협업

- [ ] 전문가 3개를 각각 **역할 프롬프트 + 가짜 도구(스텁)**로 정의: `분석가`(성과 DB 조회 스텁), `광고 전략가`(벤치마크 스텁), `개발자`(캠페인 API 스텁)
- [ ] **중앙 오케스트레이터**를 짜서 위 화살표 흐름(①→②→③→종합)대로 순서 호출, 앞 결과를 뒤로 전달
- [ ] LangGraph로 다시 구현: supervisor 노드 + 전문가 노드 3개 + 조건부 엣지. 전문가 결과를 **append 리듀서**로 공유 상태에 모으기 (덮어쓰기로 바꿔 결과가 사라지는 것 관찰)
- [ ] **핸드오프 실습**: ②가 ①의 컨텍스트를 (a) 넘기는 버전과 (b) 안 넘기는 버전을 비교 — 출력 품질 차이로 컨텍스트 전달의 중요성 체감
- [ ] **오케스트레이터 형태 바꿔보기**: 하드코딩 순서 → LLM이 "다음 누구?"를 정하는 라우터로 승격 → 통제/유연성 트레이드오프 관찰
- [ ] **단일 작성자 실습**: 최종 답 확정 노드를 딱 하나만 두기 → 여러 노드가 동시에 최종 상태를 쓰게 바꿔 모순이 생기는 것 관찰

**자가진단:**
1. 축 A(오케스트레이터-워커)와 축 B(전문가 협업)의 차이를 한 문장으로?
2. "에이전트가 협업한다"를 코드 수준에서 풀어 설명하면?
3. 조정(오케스트레이션)을 완전히 없앨 수 있는가? (답: 없다 — 위치만 바뀐다)
4. 중앙집중 vs 분산 조정의 트레이드오프는?
5. 단일 작성자 원칙은 무엇을 병렬로, 무엇을 단일로 두는가?

## ⚠️ 암기 필수

- [ ] **멀티 에이전트는 두 종류: 축 A(오케스트레이터-워커, 일회성 워커) vs 축 B(전문가 협업, 1급 시민 동료).** 설계 전에 어느 쪽인지 정하라.
- [ ] **에이전트 = 프롬프트 + 도구. 협업 = 그걸 순서대로 부르고 결과를 넘기는 코드.** 마법이 아니다.
- [ ] **조정(오케스트레이션)은 없앨 수 없다 — 위치(중앙집중 vs 분산)만 바뀐다.** 실무 기본값은 중앙집중.
- [ ] **단일 작성자 원칙: 읽기·판단은 병렬, 쓰기(최종 확정)는 단일 스레드.** 어기면 컨텍스트 파편화로 깨진다.
- [ ] **멀티 에이전트의 이득은 병렬화 가능한 작업에서만.** 순차 의존 작업은 나눠도 이득 없음.
