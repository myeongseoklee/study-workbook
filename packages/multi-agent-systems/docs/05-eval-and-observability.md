# 05. 평가와 관측성 — 진짜 승부처 (5~6주차)

## 학습 목표

이 챕터를 다 읽고 실습하면, 손으로 만든 평가셋으로 에이전트 품질을 측정하고, 트레이싱으로 실패 지점을 찾고, 실패를 유형별로 분류해 대응할 수 있다.

## 선수 지식

[02~04장](02-what-is-an-agent.md)에서 만든 에이전트/멀티 에이전트. 돌아가는 무언가가 있어야 평가할 대상이 생긴다.

## 핵심 원리 (WHY) — 대부분의 프로젝트가 여기서 죽는다

> **PoC는 되는데 운영이 안 되는 이유의 99%가 이 챕터에 있다.**

에이전트는 **비결정적**이다. 같은 입력에 다른 출력이 나온다. 그래서 "한 번 돌려보니 되네"는 아무것도 증명하지 못한다. 데모에서 잘 되던 게 실사용자 앞에서 무너지는 이유는, **측정 없이 감으로 만들었기 때문**이다.

전통적 소프트웨어는 "통과/실패"가 이진적이라 유닛 테스트로 잡힌다. 에이전트는 "80%는 맞고 20%는 미묘하게 틀림" 같은 확률적 품질이라, **평가셋(eval set)으로 분포를 봐야** 한다. 이게 이 챕터가 로드맵의 진짜 승부처인 이유다.

## 필수 지식 (HOW)

### 1. 평가셋(Eval Set) — 손으로 30~50개

가장 흔한 실수는 평가를 자동 생성으로 때우려는 것이다. **처음엔 손으로 만들어라.**

- **30~50개짜리 입력-기대결과 쌍을 직접 작성한다.** 실제 사용자가 던질 법한 질문, 특히 **까다로운 엣지 케이스**를 포함.
- 손으로 만들어야 하는 이유: 만드는 과정에서 **당신이 문제를 이해하게 된다.** 자동 생성은 "그럴듯하지만 실제로 안 중요한" 케이스를 양산한다.
- 에이전트를 고칠 때마다 평가셋 전체를 돌려 **회귀(regression)를 잡는다.** "A를 고쳤더니 B가 깨졌다"를 자동으로 발견.

### 2. 트레이싱(Tracing) — 어디서 깨졌나

에이전트는 여러 LLM 호출·툴 호출의 연쇄라, "왜 틀렸나"를 로그만으로 못 찾는다. **트레이싱**은 한 요청이 어느 노드·어느 툴을 거쳤고 각 단계에서 무슨 입출력이 오갔는지 전 과정을 기록한다.

- **LangSmith** — LangChain/LangGraph 생태계의 트레이싱·평가 도구.
- **OpenTelemetry(OTel)** — 벤더 중립 표준. 이미 백엔드에서 OTel을 쓴다면 에이전트 트레이스도 같은 파이프라인으로 보낼 수 있다.
- 백엔드 감각: 이건 **분산 추적(distributed tracing)**과 같은 문제다. 마이크로서비스에서 요청이 어느 서비스에서 느려졌나 찾던 그 기술을, LLM 호출 체인에 적용하는 것.

### 3. 실패 모드 분류(Failure Mode Taxonomy)

"틀렸다"를 뭉뚱그리면 못 고친다. 에이전트 실패는 대개 다음 유형으로 나뉘고, **유형마다 처방이 다르다**:

| 실패 유형 | 증상 | 처방 방향 |
|---|---|---|
| **툴 호출 실패** | 툴을 잘못된 인자로 부르거나, 있어야 할 툴을 안 부름 | 툴 설명·스키마 개선 ([04장](04-multi-agent-patterns.md)의 Anthropic 40% 사례) |
| **잘못된 라우팅** | 슈퍼바이저가 엉뚱한 서브에이전트에게 위임 | 라우팅 프롬프트·조건부 엣지 로직 수정 |
| **무한 루프** | 같은 행동을 반복하며 종료 못 함 | 반복 상한·종료 조건 점검 ([02장](02-what-is-an-agent.md)) |
| **컨텍스트 오염** | 이전 단계의 잘못된 정보가 뒤 단계를 오염 | 핸드오프 시 넘기는 컨텍스트 정제, 단일 작성자 원칙 |

트레이싱으로 실패를 **어느 유형인지 먼저 분류**하고, 그 유형에 맞는 곳만 고친다. 유형을 안 나누면 아무 데나 프롬프트를 만지며 시간을 태운다.

## 🛠 직접 해볼 것 — 평가 루프 만들기

- [ ] **평가셋 30개 손으로 작성**: 당신 에이전트가 풀 문제의 입력-기대결과 쌍. 최소 1/3은 엣지 케이스로.
- [ ] 평가셋을 자동으로 돌려 통과율을 출력하는 스크립트 작성 (정확 일치가 어려우면 "핵심 조건 충족" 같은 완화된 판정 기준 설계)
- [ ] 에이전트 프롬프트를 한 군데 바꾼 뒤 평가셋 재실행 → **회귀가 잡히는지** 확인
- [ ] **트레이싱 붙이기**: LangSmith 또는 OTel로 한 요청의 전체 경로를 기록하고, 각 단계 입출력을 눈으로 확인
- [ ] **실패 하나를 유형 분류**: 일부러 실패하는 케이스를 만들고, 트레이스를 보며 4가지 유형 중 무엇인지 판정 → 그 유형에 맞는 곳만 수정
- [ ] "LLM을 심판으로 쓰기(LLM-as-judge)"를 실험: 기대결과와 실제결과를 다른 LLM에게 채점시키기 — 편하지만 심판도 비결정적임을 관찰

**자가진단:**
1. 평가셋을 자동 생성 대신 손으로 만들라는 이유는?
2. 에이전트가 "가끔 틀린다"를 유닛 테스트로 못 잡는 이유는? (답: 비결정적·확률적 품질)
3. 트레이싱 없이 멀티 에이전트를 디버깅하기 어려운 이유는?
4. "무한 루프"와 "컨텍스트 오염"은 처방이 왜 다른가?

## ⚠️ 암기 필수

- [ ] **평가셋은 30~50개를 손으로 만든다.** 자동 생성으로 시작하지 마라 — 만드는 과정이 문제 이해다.
- [ ] **에이전트는 비결정적이라 "한 번 돌려보니 됨"은 증명이 아니다.** 분포를 평가셋으로 봐야 한다.
- [ ] **실패는 유형(툴 호출/라우팅/무한 루프/컨텍스트 오염)을 먼저 분류하고 유형별로 고친다.** 뭉뚱그리면 못 고친다.
- [ ] **트레이싱 = LLM 호출 체인의 분산 추적.** 어느 단계에서 깨졌나 없이는 디버깅 불가.
