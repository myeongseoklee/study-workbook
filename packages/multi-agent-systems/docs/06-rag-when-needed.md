# 06. 필요해지면 RAG — 검색이 실제로 필요할 때 (7주차+)

## 학습 목표

이 챕터를 다 읽으면, RAG가 무엇을 해결하는지, 언제 필요하고 언제 과잉인지 판단할 수 있고, 청킹·임베딩·검색·리랭킹의 역할을 구분할 수 있다.

## 선수 지식

[02~05장](02-what-is-an-agent.md)까지의 에이전트 기본기. RAG는 에이전트에 "검색 능력"을 붙이는 것이라, 에이전트 없이 RAG만 배우면 반쪽이다.

## 핵심 원리 (WHY) — RAG는 부분집합이지 핵심이 아니다

> **RAG를 7주차에 두는 이유:** RAG(Retrieval-Augmented Generation)는 멀티 에이전트의 **한 부품**일 뿐, 오케스트레이션의 핵심이 아니다. RAG부터 배우면 "검색 잘하는 법"만 익히고 정작 에이전트를 못 만든다.

RAG가 푸는 문제는 하나다: **LLM은 자기가 학습한 것만 안다.** 회사 내부 문서, 최신 데이터, 특정 도메인 지식은 모델 안에 없다. 그래서:

1. 질문이 들어오면 → 관련 문서를 **검색(retrieval)**해서
2. 그 문서를 프롬프트에 **끼워넣고(augment)** →
3. LLM이 그걸 근거로 **답을 생성(generation)**한다.

즉 "LLM에게 오픈북 시험을 보게 하는 것"이다. 검색 단계가 좋은 문서를 찾아주면 답이 좋아지고, 못 찾아주면 LLM이 헛소리(hallucination)를 한다. 그래서 RAG의 품질은 **검색의 품질**이 좌우한다.

**언제 RAG가 필요한가:** 에이전트가 참조해야 할 지식이 (a) 모델 학습 데이터에 없고, (b) 프롬프트에 통째로 넣기엔 너무 크고, (c) 자주 바뀌는 경우. 이 셋이 아니면 RAG는 과잉이다 — 지식이 작으면 그냥 프롬프트에 넣는 게 낫다.

## 필수 지식 (HOW) — RAG 파이프라인의 4단계

### 1. 청킹(Chunking) — 문서를 조각으로

긴 문서를 통째로 검색·삽입할 수 없으니 **의미 단위로 자른다.** 너무 크게 자르면 관련 없는 내용이 섞여 검색 정확도가 떨어지고, 너무 잘게 자르면 맥락이 끊긴다. 청크 크기·겹침(overlap)이 검색 품질의 첫 변수다.

**왜 크기가 그렇게 중요한가.** 임베딩은 청크 하나를 **벡터 하나로** 압축한다 — 즉 그 청크의 평균적 의미다. 그래서 한 청크에 여러 주제가 들어 있으면 벡터가 주제들의 **중간 어딘가**를 가리키게 되고, 어느 질문에도 어중간하게 가깝고 어느 질문에도 확실히 가깝지 않다. 이것이 **희석(dilution)**이다.

같은 문서를 네 방식으로 잘라 *"환불 언제까지 돼?"* 와의 유사도를 실제로 재면 이렇게 나온다.

| 청크 | 유사도 |
|---|---|
| 환불·배송·멤버십·고객센터를 한 덩어리로 (157자) | 0.73 |
| 환불 항목만 (41자) | **0.79** |
| 환불 항목에서 "환불 정책:" 제목만 잘림 (34자) | 0.79 |
| `"미개봉 상태에서만 가능하다"` 만 (15자) | 0.64 |

읽어낼 것이 둘이다. **위에서 아래로 갈수록 좋아지지 않는다** — 가장 잘게 자른 것이 가장 나쁘다. 그리고 제목이 잘린 셋째는 둘째와 거의 같다. `"환불"`이라는 낱말이 본문에 남아 있기 때문이다.

그러니 치명적인 것은 청크가 **조금** 어긋나는 게 아니라, 넷째처럼 **의미를 지탱하는 낱말이 잘려 나가는 것**이다. `"미개봉 상태에서만 가능하다"`에는 무엇이 가능한지가 없다 — 사람이 읽어도 모르는 문장이니 임베딩도 모른다. **겹침(overlap)이 존재하는 이유**가 이것이다. 문장이 경계에 걸쳐 반쪽 나는 사태를 앞뒤를 조금 겹쳐 담아 막는다.

### 2. 임베딩(Embedding)과 벡터DB — 의미로 검색

각 청크를 **임베딩 모델**로 벡터(숫자 배열)로 바꾼다. 의미가 비슷한 텍스트는 벡터 공간에서 가깝다. 질문도 같은 방식으로 벡터화한 뒤, **벡터DB**에서 가까운 청크를 찾는다 — 이게 "의미 기반 검색(semantic search)"이다. 키워드가 안 겹쳐도 의미가 통하면 찾아낸다.

- **벡터DB**는 이 "가까운 벡터 찾기"를 대규모로 빠르게 해주는 저장소다. 지금 단계에선 **원리만 알면 되고, 직접 운영·튜닝하게 될 때 레퍼런스를 펴라.**

#### 벡터 하나는 무엇에 대응하나 — 청크 하나다

헷갈리기 쉬운 지점부터 정리한다. **차원(축)은 "성격을 재는 기준"이고, 벡터 하나는 그 기준들에 매겨진 점수판 전체다.**

기준이 둘뿐인 모델을 상상하면 이렇다.

```
   축1 = IT 기기다운가 ,  축2 = 먹는 것다운가

   "아이폰"  → (0.9, 0.2)     ┐ 두 벡터가 거의 같은 방향
   "갤럭시"  → (0.9, 0.0)     ┘
   "사과"    → (0.1, 0.9)       혼자 다른 쪽을 가리킨다
```

실제 모델은 축이 수백~수천 개다(OpenAI `text-embedding-3-small`은 1536, 앞서 실측한 Gemini 임베딩은 3072). 그래도 구조는 같다 — **텍스트 하나가 그만큼 긴 숫자 배열 하나**가 된다.

그러면 청크 안의 토큰이 여러 개일 때는? 모델 안에서는 토큰마다 벡터가 만들어지지만, **최종 출력은 청크 전체를 대표하는 벡터 하나**다. 토큰 벡터들을 그냥 평균 내는 것이 아니라, **어텐션**으로 어느 토큰이 어느 토큰과 얽혀 있는지 문맥을 반영한 뒤 하나로 모은다. *"사과를 한 입 베어 물었다"*에서 `"사과"`가 `"베어 물었다"`와 강하게 얽히므로 먹는 것 쪽으로 기우는 식이다.

**그래서 청크를 5개로 쪼개면 저장되는 벡터도 5개다** — 토큰 수와 무관하다. 그리고 이것이 앞 절 희석의 정체다. 한 청크에 주제가 여럿이면 그 모두를 **하나의 벡터에** 담아야 하니, 결과는 어느 쪽도 아닌 중간이 된다.

#### Node에서 연습하는 두 경로

이 장의 선택 과제는 같은 하이브리드 검색을 두 방식으로 제공한다. **둘 중 하나만 골라도 된다.**

| 경로 | 무엇을 직접 하나 | 무엇을 배우나 |
|---|---|---|
| 스토어 없이 | 코사인 유사도와 top-k까지 직접 계산 | 벡터 검색 내부의 수학과 경계 조건 |
| `MemoryVectorStore` 사용 | 벡터 저장과 유사도 검색은 라이브러리에 위임 | Node에서 벡터 스토어를 조립하고 키워드 검색과 결합하는 법 |

문서가 몇 개뿐이면 전수 비교도 충분하다. 문서 수가 커져 검색 비용이 문제가 될 때 `hnswlib-node` 같은 근사 최근접 이웃 인덱스나 외부 벡터DB로 옮긴다. `MemoryVectorStore`는 프로세스가 끝나면 데이터도 사라지므로 학습·프로토타입용이다.

#### "가깝다"를 무엇으로 재나 — 코사인 유사도

임베딩이 만든 벡터는 **화살표**라고 생각하면 된다. 원점에서 어느 방향으로 얼마나 뻗어 있는지가 전부다. 그리고 의미가 비슷한 텍스트는 **비슷한 방향**을 가리킨다.

여기서 중요한 건 **방향이지 길이가 아니다.** 같은 주제를 짧게 쓴 글과 길게 쓴 글은 같은 쪽을 가리키되 길이만 다르다 — 관련도를 재려면 길이를 지우고 각도만 봐야 한다.

필요한 재료가 둘이다.

**① 내적(dot product)** — 성분끼리 곱해서 더한다.

```
   a = [3, 4],  b = [6, 8]
   a · b = 3×6 + 4×8 = 18 + 32 = 50
```

기하적으로는 "두 화살표가 얼마나 같은 쪽을 보는가"에 각자의 길이를 곱한 값이다. 방향이 같을수록 커지고, 직각이면 0이 되고, 반대면 음수다. 문제는 **길이가 섞여 있다**는 것 — 그래서 이것만으로는 관련도를 못 잰다.

**② 크기(norm)** — 화살표의 길이. 피타고라스 정리 그대로다.

```
   ‖a‖ = √(3² + 4²) = √25 = 5        (직각삼각형 3-4-5)
   ‖b‖ = √(6² + 8²) = √100 = 10
```

이제 내적을 두 길이로 나누면 길이 성분이 상쇄되고 **각도만 남는다.** 이것이 코사인 유사도다.

```
                  a · b              Σ aᵢbᵢ
   cos(a, b) = ───────────  =  ──────────────────────
                ‖a‖ · ‖b‖       √(Σ aᵢ²) · √(Σ bᵢ²)

   a · b = Σ aᵢbᵢ      내적 — 성분끼리 곱해 더한다
   ‖a‖   = √(Σ aᵢ²)    크기 — 원점에서의 거리
```

위 예를 넣어 보면 `50 / (5 × 10) = 1`이다. `b`는 `a`의 정확히 2배 길이인데 결과가 1 — **길이가 달라도 방향이 같으면 1**이라는 것이 눈으로 확인된다.

| cos 값 | 두 벡터의 관계 | 사잇각 |
|---|---|---|
| 1 | 같은 방향 | 0° |
| 0.71 | 꽤 비슷함 | 45° |
| 0 | 직각 — 서로 무관 | 90° |
| -1 | 정반대 | 180° |

**왜 "코사인"이라는 이름인가.** 두 벡터의 길이를 각각 1로 줄이고(단위 원 위의 점으로 만들고), 한쪽 화살표 끝에서 다른 화살표에 수직으로 빛을 비춰 생기는 **그림자의 길이**가 바로 이 값이다. 직각삼각형에서 `밑변 ÷ 빗변`이 코사인이고, 빗변을 1로 맞췄으니 밑변(그림자) 자체가 코사인 값이 된다. 방향이 나란하면 그림자가 길고, 수직이면 점으로 사라져 0, 반대편으로 지면 음수다.

값이 각도이므로 **역코사인으로 되돌릴 수 있다** — 유사도가 "얼마나 가까운지" 감이 안 잡힐 때 각도로 보면 낫다.

```ts
const 각도 = Math.acos(0.7071) * 180 / Math.PI;   // 45
```

> 앞서 청킹 실측에서 최고가 0.79였는데, 각도로는 약 38°다. **내용이 맞는 청크도 40° 가까이 벌어져 있다** — 질문과 문서는 애초에 모양이 다르기 때문이고, 그래서 다음 절이 필요하다.

**길이로 나누는 것이 핵심이다.** 나누지 않으면(=내적만 쓰면) 성분이 큰 벡터가 무조건 이긴다 — 임베딩의 크기는 대체로 텍스트 길이를 따라가므로, 그건 관련도가 아니라 **길이를 재는 것**이 된다. 방향만 보려고 크기를 지우는 것이 "정규화"다.

경계 하나: 어느 한쪽이 **영벡터**면 분모가 0이라 `NaN`이 나온다. `NaN`은 어떤 비교에서도 거짓이라 정렬이 조용히 뒤틀리므로, 0으로 떨어뜨려 막는다.

두 벡터의 **차원 수가 다르면 계산하지 않는다.** 같은 인덱스에서 비교하는 문서와 질문은 같은 임베딩 모델이 만든 같은 차원이어야 한다. 차원이 다르다는 것은 모델 교체 중 벡터를 섞었거나 색인이 깨졌다는 신호다. 짧은 쪽에 맞춰 조용히 자르면 장애를 숨기므로 오류로 드러내야 한다.

> 실무에선 직접 구현할 일이 드물다(벡터DB·라이브러리가 한다). 다만 **왜 정규화가 필요한지**를 모르면 "긴 문서만 검색되는" 증상 앞에서 원인을 못 찾는다.

#### 벡터 공간은 학습 데이터가 정한다

같은 낱말이라도 **모델이 무엇을 읽고 자랐느냐에 따라 다른 방향을 가리킨다.** 일반 문서로 학습한 모델은 `"사과"`를 먹는 것 쪽에 놓지만, IT 커뮤니티 글만 읽은 모델은 기업 쪽에 놓는다. 좌표계 자체가 코퍼스의 산물이다.

여기서 두 가지가 따라온다.

**① 모델을 바꾸면 벡터를 전부 다시 만들어야 한다.** 좌표계가 다르므로 옛 벡터와 새 벡터는 거리를 비교하는 것 자체가 무의미하다. 섞이면 에러가 아니라 "이상하게 관련 없는 게 나온다"로 나타나 원인 찾기가 어렵다. 그래서 임베딩 모델 교체는 코드 배포가 아니라 **데이터 마이그레이션**으로 다뤄야 한다.

**② 사내 용어는 범용 모델이 모른다.** `"오퍼월"`, `"ADV-2026-X9"`, 사내 프로젝트명 같은 것은 학습 데이터에 없었으니 엉뚱한 좌표를 받는다. 그럼 사내 데이터로 파인튜닝해야 하나 — 원리적으로는 맞지만 비용·시간이 크고 **문서가 바뀔 때마다 다시 학습해야** 해서 실무에서는 잘 택하지 않는다. 대신 이렇게 우회한다.

| 우회 | 방식 |
|---|---|
| **하이브리드 검색** | 의미는 벡터가, 사내 고유명사는 키워드가 잡게 한다 (§ 4) |
| 용어 사전 매핑 | 색인·질의 앞단에서 약어를 풀어 준다 (`알파` → `신재생 배터리 사업`) |
| 도메인 특화 모델 | 금융·의료처럼 **용어 지식이 관건인** 분야엔 특화 모델이 나와 있다 |

마지막 항목은 분야를 가린다. 텍스트의 뜻이 중요한 도메인에는 특화 모델이 의미가 있지만, 광고·리워드처럼 **핵심 데이터가 텍스트가 아니라 사용자 행동 로그**인 영역은 사정이 다르다 — 그쪽은 범용 임베딩에 하이브리드를 얹는 편이 실용적이고, 행동 예측은 임베딩 검색이 아니라 별도 모델의 일이다.

#### 질문과 문서는 모양이 다르다 — 비대칭 문제

질문과 청크를 같은 모델로 벡터화해 비교하지만, 둘은 애초에 생김새가 다르다. 질문은 짧고 구어체(*"환불 언제까지 돼?"*)이고 문서는 길고 문어체(*"구매 후 7일 이내, 미개봉 상태에서만 전액 환불이 가능하다"*)다. **내용이 정확히 대응해도 유사도가 1에 한참 못 미치는 이유**가 이것이다 — 실측하면 0.8 근처에서 천장을 친다.

이 간극을 줄이는 두 기법이 있다. 발상은 같다 — **비교하는 두 쪽의 모양을 맞춘다.**

| 기법 | 무엇을 바꾸나 | 비교 형태 |
|---|---|---|
| **질문 생성 색인** | 색인 쪽 — 청크마다 "이 청크가 답할 수 있는 질문"을 LLM으로 만들어 **그 질문을** 임베딩해 저장 | 질문 ↔ 질문 |
| **HyDE** (Hypothetical Document Embeddings) | 질의 쪽 — 질문으로 **가상의 답변**을 LLM에게 먼저 쓰게 하고, 그 답변을 임베딩해 검색 | 답변 ↔ 답변 |

둘 다 대가가 있다. 질문 생성 색인은 **색인 시점에** LLM 호출이 청크 수만큼 들고, 문서가 바뀌면 그 질문도 다시 만들어야 한다(§ 위의 재색인 비용에 얹힌다). HyDE는 **질의 시점마다** LLM 호출이 하나 더 붙어 지연이 늘고, 가상 답변이 틀리면 틀린 방향으로 검색한다.

> 순서는 다른 단계와 같다 — **검색이 실제로 병목일 때** 꺼낸다. 청크 크기를 고치는 것이 먼저고, 이 기법들은 그것으로 안 될 때다.

### 3. 리랭킹(Reranking) — 다시 정렬

벡터 검색이 뽑은 상위 후보들을, 더 정교한 모델로 **질문과의 관련도 순으로 다시 매긴다.** 벡터 검색은 빠르지만 거칠고, 리랭커는 느리지만 정확하다. "빠른 검색으로 후보를 넓게 뽑고, 리랭커로 좁게 정렬"하는 2단계가 실무 정석이다.

#### 왜 벡터 검색은 거칠고 리랭커는 정확한가

차이는 성능 튜닝이 아니라 **구조**다. 두 방식이 질문과 문서를 만나게 하는 시점이 다르다.

```
   벡터 검색 (bi-encoder)          리랭커 (cross-encoder)

   질문  → [모델] → 벡터           질문 ┐
                      ↘                  ├→ [모델] → 관련도 점수
   문서  → [모델] → 벡터  → 각도    문서 ┘
   (색인 때 미리 계산)              (질문이 와야 계산 시작)
```

**벡터 검색은 질문과 문서를 따로 벡터로 만들어 각도만 비교한다.** 문서 벡터는 질문이 무엇일지 모르는 색인 시점에 이미 만들어져 있다 — 그래서 미리 계산해 재사용할 수 있고, 백만 건이어도 빠르다. 대신 *"이 질문에 이 문서가 답이 되는가"*를 직접 따진 적이 없다. 각자 요약된 벡터 둘의 방향만 본 것이다.

**리랭커는 질문과 문서를 한 덩어리로 모델에 넣는다.** 어텐션이 질문의 낱말과 문서의 낱말을 직접 교차 참조하므로 *"질문의 '언제까지'가 문서의 '7일 이내'에 대응한다"* 같은 판단이 가능하다. 대신 **미리 계산해둘 수 없다** — 질문이 와야 시작하고, 후보 하나마다 모델을 한 번씩 돌려야 한다.

#### 그래서 2단계인 것이다

산수를 해 보면 왜 나눠야 하는지 바로 보인다.

| | 문서 100만 건에 직접 | 2단계로 |
|---|---|---|
| 벡터 검색 | — | 100만 건 → 후보 100개 (미리 계산된 벡터끼리, 빠름) |
| 리랭커 | **100만 번 호출** — 불가능 | **100번 호출** — 감당 가능 |

리랭커를 전체에 돌릴 수 없으니, 싸고 거친 방법으로 후보를 좁히고 비싼 방법을 거기에만 쓴다. **1단계는 빠뜨리지 않는 것(recall)이 목표고, 2단계는 정확히 줄 세우는 것(precision)이 목표다.**

여기서 후보 수가 손잡이가 된다.

- **너무 적게 뽑으면**(예: 5개) 정답이 애초에 후보에 없어 리랭커가 구제할 방법이 없다. 리랭커는 없는 것을 만들어내지 못한다.
- **너무 많이 뽑으면**(예: 500개) 리랭킹 호출이 그만큼 늘어 지연·비용이 커진다.
- 관례적으로 **1단계에서 50~100개**를 뽑고, 리랭킹 후 **상위 3~5개**만 프롬프트에 넣는다.

#### 이 장의 서술 순서와 실행 순서는 다르다

주의할 점이 하나 있다. 이 장은 청킹 → 임베딩 → 리랭킹 → 하이브리드 순으로 설명하지만, **실제 파이프라인에서 리랭킹은 하이브리드 다음**이다.

```
   키워드 검색 ┐
               ├→ RRF 융합 → 후보 100개 → 리랭커 → 상위 3~5개 → 프롬프트
   벡터 검색   ┘
   └──── 후보를 모으는 단계 ────┘   └── 줄 세우는 단계 ──┘
```

§4의 하이브리드는 **후보를 모으는** 방법이고, 리랭킹은 **모인 후보를 정렬하는** 방법이다. 둘은 경쟁하는 선택지가 아니라 파이프라인의 다른 자리다.

#### 언제 넣나 — 증상으로 가른다

리랭킹은 지연과 비용을 늘리므로 아무 때나 넣지 않는다. 판단은 [05장](05-eval-and-observability.md)의 방식과 같다 — **증상을 먼저 분류한다.**

| 증상 | 처방 |
|---|---|
| 정답 문서가 후보에는 **들어오는데** 상위 3개 안에 못 든다 | **리랭킹이 듣는다** — 정렬 문제다 |
| 정답 문서가 후보에 **아예 없다** | 리랭킹은 무용. 청킹 크기나 하이브리드(§4)를 봐야 한다 |
| 후보도 정렬도 맞는데 답이 틀리다 | 검색 문제가 아니다. 프롬프트나 생성 쪽을 본다 |

두 번째를 첫 번째로 착각하고 리랭커를 붙이면, 비용만 늘고 아무것도 나아지지 않는다. **없는 문서를 위로 올릴 수는 없다.**

무엇으로 리랭킹하나 — 전용 리랭커 모델(Cohere Rerank, BGE-reranker 등)을 쓰거나, LLM에게 *"이 문서가 이 질문에 답하는가"*를 점수로 내게 할 수도 있다. 후자는 별도 인프라가 필요 없지만 느리고 비싸며, 심판이 비결정적이라는 [05장](05-eval-and-observability.md)의 문제를 그대로 물려받는다.

### 4. 하이브리드 검색(Hybrid Search) — 의미 + 키워드

의미 검색(벡터)은 "비슷한 뜻"에 강하지만 **정확한 고유명사·코드·ID**엔 약하다. 그래서 키워드 검색(BM25 등)과 **결합(hybrid)**한다. 제품 코드나 에러 코드처럼 정확히 일치해야 하는 것은 키워드가, 개념적 질문은 벡터가 잡는다.

`"ERR_2041"`이 왜 벡터에 약한지 보면 이해가 빠르다 — 그건 **의미가 아니라 글자**다. 임베딩은 비슷한 뜻을 가깝게 놓지, 비슷한 문자열을 가깝게 놓지 않는다. 반대로 *"환불하고 싶은데요"* 같은 질의는 문서에 그 단어가 하나도 없어도 벡터가 잡아낸다. **두 검색은 서로의 사각을 메운다 — 그래서 교체가 아니라 결합이다.**

#### 어떻게 굴러가나 — 두 엔진을 따로 돌린다

흔한 오해가 하나 있다. **키워드로 문서를 찾아 그걸 질의에 붙여 임베딩에 다시 던지는 것이 아니다.** 그러면 질의마다 임베딩을 새로 계산해야 해서 느리다.

두 검색은 **각자 독립적으로 돌고, 결과 목록만 합친다.**

```
                 ┌─→ 키워드 엔진(BM25)  ─→  A(1위) B(2위) C(3위)
   사용자 질의 ──┤
                 └─→ 벡터 엔진(코사인)   ─→  C(1위) A(2위) D(3위)
                                                   │
                                          순위 융합 (RRF)
                                                   │
                                            최종: A, C, …
```

색인 시점에 각 청크를 **양쪽에 미리 등록**해 둔다 — 키워드 인덱스에 원문을, 벡터DB에 임베딩을. 질의 시점에는 둘을 병렬로 조회하고 순위만 섞는다.

#### 어떻게 합치나 — 순위로 합친다 (RRF)

문제가 하나 있다. 키워드 점수(BM25)와 벡터 유사도는 **단위도 분포도 다르다.** 그대로 더할 수 없고, 정규화해서 더하려 해도 코퍼스가 바뀔 때마다 스케일이 흔들린다.

그래서 점수를 버리고 **순위만 쓴다.** 각 검색 결과에서 문서의 기여도를 순위의 역수로 매기고 합산하는 방식이 **RRF(Reciprocal Rank Fusion)**다.

```
                       1
   RRF(d) =   Σ    ─────────────
            랭킹 r  k + rank_r(d)

   rank_r(d) : 랭킹 r 에서 문서 d 의 순위 (1부터 센다)
   k         : 상위 편중을 얼마나 완화할지 정하는 상수 (관례값 60)
   d 가 어느 랭킹에 없으면 그 랭킹은 합에 기여하지 않는다
```

**왜 하필 역수인가.** 순위를 그냥 뒤집어 점수로 쓰면(1위=10점, 2위=9점…) 문서 수에 따라 점수 범위가 달라지고, 1위와 2위의 차이가 9위와 10위의 차이와 같아진다. 역수는 그렇지 않다.

```
   순위 :   1      2      3      4      5   …
   1/순위:  1.00   0.50   0.33   0.25   0.20
   차이 :     0.50   0.17   0.08   0.05
```

**앞쪽 차이는 크고 뒤로 갈수록 작아진다.** 검색 결과에서 1위와 2위의 격차가 9위와 10위의 격차보다 의미 있다는 직관과 맞는다. 여기에 `k`를 더해(`1/(k+순위)`) 그 편중을 조절한다 — `k`가 작을수록 1위의 몫이 커지고, 클수록 순위 간 격차가 평평해져 뒤 문서가 따라잡을 여지가 생긴다.

이 모양이 만드는 성질이 중요하다 — 1등과 2등의 차이는 크고 뒤로 갈수록 차이가 줄어든다. 결과적으로 **한 검색에서만 1위인 문서보다, 두 검색 모두에서 상위인 문서가 이긴다.** 하이브리드가 노리는 바가 정확히 그것이다.

위 그림의 결과를 `k=60`으로 실제로 계산해 보면 그것이 확인된다.

```
   문서 A : 키워드 1위, 벡터 2위  →  1/61 + 1/62  =  0.03252   ← 최종 1위
   문서 C : 키워드 3위, 벡터 1위  →  1/63 + 1/61  =  0.03227
```

C는 벡터 검색 **1위**인데도 A에 밀린다. A가 양쪽에서 고르게 상위였기 때문이다. 차이는 근소하지만 방향은 분명하다.

RRF를 쓰는 실무적 이유가 둘 더 있다.

- **가중치를 안 정해도 된다.** "키워드 70% + 벡터 30%" 같은 값을 손으로 맞추려 하면 질의 유형마다 최적값이 달라 끝이 없다. RRF는 그 손잡이가 `k` 하나뿐이고 관례값으로도 충분히 쓸 만하다.
- **순위권 밖은 자동으로 걸러진다.** 한쪽에서 500위인 문서는 기여가 `1/560`로 0에 가까워 노이즈가 되지 않는다.

대부분의 벡터DB와 검색엔진(Elasticsearch, Pinecone, Milvus, Weaviate 등)이 이 융합을 옵션으로 제공한다 — 직접 구현하는 것은 원리를 알기 위한 것이고, 실서비스에서는 켜서 쓰면 된다.

> **트레이드오프:** RAG의 각 단계는 정확도↔지연시간↔비용의 교환이다. 리랭킹을 넣으면 정확도는 오르지만 지연·비용이 는다. 하이브리드는 커버리지가 오르지만 파이프라인이 복잡해진다. **"검색이 실제로 병목일 때"만 이 복잡도를 추가하라.**

| `extra-2-memory-vector-store.ts` | § 2 · § 4 | `MemoryVectorStore`에 벡터를 넣고 키워드 랭킹과 결합 |
| `extra-4-rerank.ts` | § 3 리랭킹 | 싼 점수로 좁히고 정밀 점수로 다시 세우는 2단계 |

`extra-1`과 `extra-2`는 **같은 하이브리드 검색을 두 방식으로** 만든다(위 「Node에서 연습하는 두 경로」) — 둘 중 하나만 골라도 된다. `extra-3`·`extra-4`는 각자 다른 단계라 겹치지 않는다.

파이프라인 순서로 읽으면 이렇게 이어진다.

```
   extra-3          extra-1 / extra-2              extra-4
   청킹      →   키워드+벡터 검색 → RRF 융합   →   리랭킹   →  프롬프트
```

**자가진단:**
1. RAG가 해결하는 근본 문제 한 문장은? (답: LLM은 학습한 것만 안다)
2. RAG의 품질을 좌우하는 단계는? (답: 검색)
3. 벡터 검색이 약한 질문 유형은? (답: 정확한 고유명사·코드·ID)
4. 리랭킹을 언제 넣어야 하나? (답: 검색이 실제 병목이고 정확도가 부족할 때)
5. 코사인 유사도에서 길이로 나누지 않으면 무엇을 재게 되나?
6. 두 검색 결과를 합칠 때 점수 대신 순위를 쓰는 이유는?
7. 청크를 크게 잡으면 왜 유사도가 떨어지나? 반대로 너무 잘게 잡으면?
8. 청크에 토큰이 100개면 저장되는 벡터는 몇 개인가?
9. 임베딩 모델을 교체하면 왜 기존 벡터를 못 쓰나?
10. 하이브리드 검색에서 두 엔진은 순차로 도나, 따로 도나?
11. 리랭커는 왜 전체 문서에 바로 쓸 수 없나?
12. 정답 문서가 후보에 아예 없을 때 리랭킹을 붙이면 어떻게 되나?

## ⚠️ 암기 필수

- [ ] **RAG = LLM에게 오픈북 시험. 검색이 좋은 문서를 찾아주면 답이 좋고, 못 찾으면 헛소리(hallucination).**
- [ ] **RAG 품질은 검색 품질이 좌우한다.** 생성 모델을 바꾸기 전에 검색부터 의심하라.
- [ ] **벡터 검색은 의미에 강하고 정확한 코드/ID에 약하다 → 하이브리드(벡터+키워드)로 보완.**
- [ ] **RAG가 필요한 조건: 지식이 (a) 모델에 없고 (b) 프롬프트에 다 넣기엔 크고 (c) 자주 바뀜.** 아니면 과잉.
- [ ] **코사인 유사도는 방향만 본다 — 길이로 나누지 않으면 관련도가 아니라 길이를 재게 된다.**
- [ ] **서로 다른 검색을 합칠 땐 점수가 아니라 순위로(RRF). 점수는 단위가 달라 더할 수 없다.**
- [ ] **청크 하나 = 벡터 하나.** 토큰별 벡터를 어텐션으로 문맥까지 반영해 하나로 압축한 결과다.
- [ ] **벡터 공간은 학습 데이터가 정한다 → 모델 교체는 전면 재색인이고, 사내 용어는 범용 모델이 모른다.**
- [ ] **하이브리드는 두 엔진을 병렬로 돌리고 순위만 합친다.** 키워드 결과를 임베딩에 다시 던지는 게 아니다.
- [ ] **벡터 검색은 질문·문서를 따로 임베딩(미리 계산 가능), 리랭커는 함께 넣어 판단(미리 계산 불가).** 그래서 1단계는 recall, 2단계는 precision.
- [ ] **리랭킹은 후보에 있는 것만 올릴 수 있다.** 정답이 후보에 없으면 청킹·하이브리드를 봐야 한다.

## 심화 도서 (필요해질 때)

이 챕터는 원리만 다룬다. 실제로 RAG 파이프라인을 튜닝하게 되면 다음을 펴라(모두 실재 확인됨):

- **테디노트의 랭체인을 활용한 RAG 비법노트(기본 & 심화)** — 한국어 RAG 실습서로 밀도가 좋다. 청킹·리랭킹·하이브리드를 실제로 만질 때.
- **RAG 마스터: 랭체인으로 완성하는 LLM 서비스** — 위와 내용이 상당히 겹치니 **둘 중 하나만**.
- **벡터 데이터베이스 설계와 구축(Vector DB에서 RAG, Graph DB까지)** — 벡터DB를 직접 운영·튜닝하게 될 때 펴는 레퍼런스. 지금은 보류.
