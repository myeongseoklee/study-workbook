# 08. 에이전트 플랫폼 인프라 — 에이전트를 서비스로 짓기

## 학습 목표

이 챕터를 다 읽으면, "에이전트를 앱 레이어로 짓는 것"과 "인프라 레이어(플랫폼)로 짓는 것"의 차이를 코드/아키텍처 수준에서 설명하고, Agent Card·레지스트리·A2A·MCP가 각각 무슨 역할인지 구분하며, **언제 플랫폼으로 승격해야 하는지** 판단할 수 있다.

## 선수 지식

[04장](04-multi-agent-patterns.md)의 전문가 협업과 오케스트레이션. 이 챕터는 "여러 전문가 에이전트를 협업시킨다"를 **어떻게 배포·연결하느냐**로 한 단계 내려간다.

## 핵심 원리 (WHY) — 에이전트를 인프라로 짓는다 = 마이크로서비스로 짓는다

> **한 문장:** 에이전트를 인프라 레이어로 구축한다는 건, 모놀리스 → 마이크로서비스 전환을 함수 대신 에이전트에 적용하는 것이다.

3년차 백엔드면 이미 아는 그림이다. 같은 3개 전문가 에이전트가 **어디에 사느냐**만 달라진다.

### 앱 레이어 — 한 프로그램 안의 함수 3개

```typescript
async function analystAgent(q: string)  { /* LLM + "너는 분석가" + DB조회 도구 */ }
async function adExpertAgent(q: string)  { /* LLM + "너는 광고 전문가" + 벤치마크 도구 */ }
async function devAgent(q: string)       { /* LLM + "너는 개발자" + 캠페인 API 도구 */ }

// 오케스트레이터 = 그냥 내 코드 (함수를 순서대로 호출)
const data     = await analystAgent("지난주 성과");
const strategy = await adExpertAgent(`이 데이터로 전략: ${data}`);
const result   = await devAgent(`이 전략 구현: ${strategy}`);
```

전부 한 프로세스. 호출 = **함수 호출**. 컨텍스트 전달 = **변수 넘기기**.

### 인프라 레이어 — 각 에이전트가 독립 서비스

```
[분석 에이전트]   독립 서버 :8001   POST /invoke, /.well-known/agent.json
[광고 전문가]     독립 서버 :8002   POST /invoke, /.well-known/agent.json   ← 각자 컨테이너 배포,
[개발 에이전트]   독립 서버 :8003   POST /invoke, /.well-known/agent.json     각자 스케일/버전/재배포

[레지스트리]              ← 위 3개의 Agent Card 목록 ("누가 뭘 할 수 있나")
[오케스트레이터/게이트웨이] ← 요청 접수 → 레지스트리 조회 → 각 서버에 네트워크 호출
[세션 스토어(Redis/DB)]   ← 에이전트들이 공유하는 중간 결과·컨텍스트
[관측성/인증/비용]        ← 분산 추적, 서비스 간 인증, 에이전트별 요금
```

호출 = **네트워크 호출**. 컨텍스트 전달 = **공유 세션 스토어 or 페이로드**. 딱 마이크로서비스다.

## 필수 지식 (HOW)

### 1. 매핑 — 당신이 이미 아는 것 → 에이전트 인프라

| 백엔드에서 아는 것 | 에이전트 인프라에서 | 새것? |
|---|---|---|
| 함수 → HTTP 서비스 | 에이전트 = `/invoke` 엔드포인트 (안엔 우리가 아는 LLM 루프) | 아니오 |
| 서비스 디스커버리 / API 게이트웨이 | 레지스트리 + 오케스트레이터 | 아니오 |
| OpenAPI 명세 | **Agent Card**(능력 명세) | **예** |
| 서비스 간 REST/gRPC | **A2A**(에이전트↔에이전트), **MCP**(에이전트↔도구) | **예** |
| 로컬 변수로 상태 전달 | 공유 세션 스토어 | 아니오 |
| 동기 호출 | 오래 걸리니 비동기: 요청→작업ID→폴링/웹훅 | 아니오 |
| 분산 추적·인증·레이트리밋 | 그대로 | 아니오 |

**진짜 새로 배우는 건 두 가지뿐이다: Agent Card와 A2A/MCP.** 나머지는 하던 백엔드 그대로다.

### 2. Agent Card — 유일하게 새로운 아티팩트

각 에이전트 서비스가 "나는 누구고 뭘 할 수 있다"를 **기계가 읽는 JSON**으로 노출한다. A2A 표준에선 보통 `/.well-known/agent.json` 같은 well-known URI에 둔다. 대략 이런 모양:

```json
{
  "name": "ad-domain-expert",
  "description": "광고 전략 수립 전문가",
  "url": "https://agents.internal/ad-expert",
  "capabilities": ["캠페인 예산 배분", "타겟 추천", "크리에이티브 전략"],
  "input_schema": { "query": "string", "context": "object" },
  "auth": { "schemes": ["bearer"] }
}
```

오케스트레이터는 "광고 관련 요청이네" → 레지스트리에서 이 카드를 찾아 → `url`로 호출. **OpenAPI로 서비스를 찾던 것과 똑같고, 명세 포맷만 Agent Card로 바뀐 것이다.** 카드가 곧 에이전트 사이의 **계약(contract)**이다.

### 3. A2A vs MCP — 두 프로토콜의 역할 구분

이 둘을 헷갈리면 안 된다. **방향이 다르다.**

- **MCP (Model Context Protocol)** — Anthropic, 2024-11. **에이전트 ↔ 도구/데이터**를 표준화. "AI의 USB-C 포트". 한 에이전트가 외부 도구(파일·DB·API)를 붙일 때의 규격.
- **A2A (Agent2Agent)** — Google, 2025-04. **에이전트 ↔ 에이전트**를 표준화. 서로 다른 팀·벤더가 만든 에이전트가 상대를 발견(Agent Card)하고 작업을 위임·협업할 때의 규격.

한 문장 기억법: **MCP는 에이전트에게 "손발(도구)"을 달아주고, A2A는 에이전트끼리 "대화(협업)"하게 한다.** 둘은 경쟁이 아니라 층이 다르다 — 실제로 CrewAI 같은 프레임워크는 둘 다 지원한다.

### 4. 오케스트레이터는 인프라로 가도 사라지지 않는다

[04장](04-multi-agent-patterns.md)에서 봤듯 조정은 없앨 수 없다. 인프라 레이어에서 달라지는 건 딱 둘:

- 에이전트를 **함수 호출 → 네트워크 호출**로 부른다
- 에이전트 목록을 **하드코딩 → 레지스트리에서 동적 발견**한다

즉 오케스트레이터는 그대로 있고, **자기도 하나의 서비스(라우팅 게이트웨이)가 될 뿐**이다. 마이크로서비스에서 API 게이트웨이/BFF가 안 사라지는 것과 같다.

### 5. 팀 구조 매핑 — "한 명이 하나씩"의 함의

에이전트를 여러 개발자가 **하나씩 나눠 맡는다면**, 이건 인프라 레이어를 정당화하는 진짜 이유 중 하나다 (Conway의 법칙 — 조직 구조가 곧 시스템 경계):

```
개발자 A → 오케스트레이터 / 플랫폼 코어
개발자 B → 분석 에이전트
개발자 C → 광고 전문가 에이전트
개발자 D → 개발 에이전트
```

여러 사람이 각자 에이전트를 독립 개발하면, 서로 안 부딪히고 병렬로 일하려면 **에이전트 사이의 명확한 계약(= Agent Card, 입출력 스키마)**이 실제 값어치를 갖는다. 계약만 합의하면 각자 자기 에이전트를 자유롭게 구현·배포할 수 있다.

## 언제 플랫폼으로 승격하나 — 과잉 방지 게이트

**핵심: 계약은 인프라식으로 명확하게, 조정은 중앙 오케스트레이터로 단순하게.** 이게 대부분의 사내 팀에 맞는 스윗스팟이다. 아래 압력이 **실제로** 나타나기 전엔 풀 플랫폼(동적 레지스트리·A2A·자율 협상)을 짓지 마라:

| 승격 트리거 | 그러면 필요한 것 |
|---|---|
| 여러 팀/사람이 에이전트를 **독립 개발**해 연동 | 명확한 계약(Agent Card), 독립 배포 |
| 한 에이전트만 자주 바뀌어 **따로 배포·스케일** 필요 | 에이전트 = 서비스 |
| **외부/타 조직** 에이전트와 협업 | A2A 같은 상호운용 프로토콜 |
| 소집할 전문가가 **런타임에 열려 있음**(계속 늘어남) | 동적 발견(레지스트리) |

**아무 트리거도 안 걸리면 → 앱 레이어(함수 + 중앙 오케스트레이터)가 정답.** 모놀리스로 충분한데 마이크로서비스부터 짓지 않는 것과 같은 판단이다. 단, "여러 사람이 하나씩 맡는다"는 첫 트리거에 걸리므로, **계약(Agent Card 수준의 인터페이스 합의)은 일찍 도입**하는 게 이득이다.

## 프레임워크 지형

축 B(전문가 협업)와 플랫폼을 다룰 때 주력 도구들:

- **CrewAI** — 역할(role/goal/backstory) 기반 크루. 도메인 전문가 팀 멘탈모델에 가장 직관적. MCP/A2A 지원.
- **AutoGen** (Microsoft) — 대화형 그룹챗. 에이전트들이 공유 스레드에서 토론, 매니저가 발언 라우팅.
- **LangGraph** — 명시적 그래프/스웜. 협업 흐름을 세밀하게 통제([03장](03-langgraph-basics.md)).
- **A2A 프로토콜** (Google) — 특정 프레임워크가 아니라 에이전트 상호운용 표준. 이기종·멀티팀·외부 연동용.

**선택 기준:** 개념 잡기·소규모 크루 → CrewAI. 흐름 통제·프로덕션 → LangGraph. 토론형 협업 → AutoGen. 이기종/외부 연동 → A2A. 하나로 시작해 필요할 때 조합한다.

## 🛠 직접 해볼 것 — 인프라 레이어 최소 뼈대

- [ ] [04장](04-multi-agent-patterns.md)에서 함수로 짠 3전문가를, **에이전트 2개를 각각 작은 HTTP 서버**로 분리 (Fastify로 `/invoke` 엔드포인트, 내부는 그 LLM 루프)
- [ ] 각 서버에 **Agent Card**(`/.well-known/agent.json`)를 노출: name·description·capabilities·input_schema
- [ ] **오케스트레이터**를 짜서 Agent Card를 읽고 → 요청에 맞는 서버를 골라 → 네트워크로 호출 → 종합
- [ ] 컨텍스트 전달을 (a) 페이로드로 넘기기 vs (b) 공유 세션 스토어(간단히 dict/Redis)로 두 방식 비교
- [ ] **비동기 체감**: 한 에이전트에 sleep을 넣어 오래 걸리게 만들고, 동기 호출로 막히는 것 → 작업ID+폴링으로 바꿔보기
- [ ] **승격 게이트 판정**: 지금 만드는 프로젝트가 위 4가지 트리거 중 실제로 걸리는 게 있는지 표로 체크 → 앱 레이어면 앱 레이어로 남기는 결정을 내려보기

## 🛠 직접 해볼 것 — LLM Provider 추상화 (멀티 LLM)

플랫폼은 특정 LLM 벤더에 묶이면 안 된다. 하나의 인터페이스 뒤에 여러 벤더를 어댑터로 두고, 설정으로 갈아끼운다 — 이게 폴리글랏 원칙의 "LLM 판(版)"이다. (실습 파일: `src/08-01-llm-provider/index.ts`)

- [ ] `LLMProvider` 인터페이스를 정한다: `{ name, model, ask(system, user): Promise<string> }`
- [ ] **Gemini 어댑터**(OpenAI 호환)는 주어져 있다 — 읽고 구조를 파악
- [ ] **Claude(cc) 어댑터를 직접 구현**: 같은 인터페이스를 Anthropic SDK로. system은 top-level 파라미터, 응답은 content 블록 배열 — 벤더마다 형식이 다르다는 걸 손으로 체감
- [ ] `getProvider()`가 env(`LLM_PROVIDER`)로 어댑터를 고르게 하고, `LLM_PROVIDER=gemini` / `=anthropic` 로 바꿔 **호출부 코드는 그대로인데 벤더만 갈리는 것** 확인
- [ ] (심화) 인터페이스에 tool 호출 지원을 추가하고, OpenAI function ↔ Anthropic tool_use 형식을 어댑터에서 정규화

> **핵심:** 어댑터 패턴 = "계약(인터페이스)은 하나, 구현(벤더)은 여럿". Agent Card가 에이전트 사이의 계약이듯, `LLMProvider`는 플랫폼과 LLM 벤더 사이의 계약이다. 벤더 교체가 호출부에 새어나가지 않게 하는 것이 플랫폼의 일이다.

**자가진단:**
1. "에이전트를 인프라로 짓는다"를 한 문장으로? (답: 마이크로서비스로 짓는다)
2. Agent Card는 백엔드의 무엇에 대응하나? (답: OpenAPI 명세 = 서비스 계약)
3. MCP와 A2A의 방향 차이는? (답: MCP=에이전트↔도구, A2A=에이전트↔에이전트)
4. 인프라 레이어로 가면 오케스트레이터는 사라지나? (답: 아니, 서비스가 될 뿐)
5. 당신 프로젝트는 승격 트리거 중 무엇이 걸리는가?

## ⚠️ 암기 필수

- [ ] **에이전트를 인프라로 짓기 = 마이크로서비스로 짓기.** 함수→서비스, 서비스디스커버리→레지스트리, OpenAPI→Agent Card. 새것은 Agent Card와 A2A/MCP 둘뿐.
- [ ] **Agent Card = 에이전트 사이의 계약(능력 명세 JSON).** 팀이 병렬 개발하려면 이 계약을 일찍 합의하라.
- [ ] **MCP는 에이전트↔도구, A2A는 에이전트↔에이전트.** 방향이 다르다. 경쟁 아님, 층이 다름.
- [ ] **오케스트레이터는 인프라로 가도 안 사라진다 — 서비스가 될 뿐.** 조정은 위치만 바뀐다.
- [ ] **승격 게이트: ① 다팀 독립개발 ② 독립 배포/스케일 ③ 외부 연동 ④ 런타임 개방. 아무것도 안 걸리면 앱 레이어가 정답.**
