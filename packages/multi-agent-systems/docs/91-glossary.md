# 91. 용어 해설집 — 레이어별로 묶어 읽기

단순 사전이 아니라, **용어를 5개 레이어로 묶고 개념 간 인과 관계와 함께** 정리한다. 본문에서 처음 만난 용어를 여기서 다시 확인하되, "이 용어가 어느 층의 문제인지"를 함께 잡아라.

---

## 레이어 1 — LLM 기본기 (모든 것의 바닥)

**LLM (Large Language Model)**
토큰 배열을 받아 토큰 배열을 반환하는 모델. API 호출은 본질적으로 텍스트 요청/응답이다. 특별한 점은 응답이 **비결정적**이고 요금이 **토큰 단위**라는 것뿐. → 이 성질이 [05장 평가/관측성](05-eval-and-observability.md)의 존재 이유다.

**토큰(Token)**
LLM이 텍스트를 자르는 단위. 대략 영어 1토큰 ≈ 4글자, 한글은 더 잘게 쪼개진다. 입력·출력 토큰에 각각 요금. → 비용 계산과 컨텍스트 윈도우의 단위.

**컨텍스트 윈도우(Context Window)**
한 번의 호출에 넣을 수 있는 최대 토큰 수. 넘으면 오래된 내용을 잘라야 한다. → 멀티 에이전트를 나누는 동기 중 하나("각 에이전트에게 필요한 컨텍스트만").

**비결정성(Non-determinism)**
같은 입력에 다른 출력이 나오는 성질. 전통적 소프트웨어의 이진적 통과/실패와 달리 "확률적 품질"을 만든다. → "한 번 됐다"가 증명이 안 되는 이유, 평가셋이 필요한 이유.

**할루시네이션(Hallucination)**
LLM이 근거 없이 그럴듯한 거짓을 생성하는 현상. 검색이 좋은 근거를 못 대주면 심해진다. → [06장 RAG](06-rag-when-needed.md)가 완화하려는 대상.

## 레이어 2 — 에이전트의 심장 (단일 에이전트)

**tool_use / Function Calling (툴 호출 / 함수 호출)**
LLM이 직접 코드를 못 실행하므로, "이 함수를 이 인자로 불러줘"라는 **구조화된 JSON 요청**을 반환하는 메커니즘. **실행은 개발자 코드가** 한다. → 에이전트 루프의 핵심 부품. [01장](01-prerequisites.md), [02장](02-what-is-an-agent.md).

**에이전트 루프(Agent Loop)**
LLM 호출 → tool_use 파싱 → 함수 실행 → 결과 주입 → 반복. 이 `while` 루프가 에이전트의 정의. → [02장](02-what-is-an-agent.md)에서 손으로 짠다.

**워크플로 vs 에이전트**
통제권의 위치로 나뉜다. **워크플로**는 개발자가 흐름을 코드로 고정, **에이전트**는 LLM이 흐름을 동적으로 결정. 흐름이 뻔하면 워크플로. → [02장](02-what-is-an-agent.md).

**시스템 프롬프트(System Prompt)**
에이전트의 정체성·규칙을 정의하는 메시지. user/assistant 메시지와 함께 대화를 구성. → 프롬프트 설계는 "컨텍스트 엔지니어링"으로 다시 등장.

**5가지 워크플로 패턴**
프롬프트 체이닝 / 라우팅 / 병렬화 / 오케스트레이터-워커 / 평가자-최적화. 완전한 에이전트로 가기 전 대부분의 문제를 푸는 통제된 흐름들. → [02장](02-what-is-an-agent.md).

## 레이어 3 — LangGraph (워크플로 엔진)

**StateGraph**
노드들이 공유 상태를 읽고 쓰며 통신하는 그래프. 노드 시그니처는 `State -> Partial<State>`. **`.compile()` 해야 실행 가능.** → [03장](03-langgraph-basics.md).

**노드/엣지/조건부 엣지(Node/Edge/Conditional Edge)**
노드=작업 단위, 엣지=전이, 조건부 엣지=상태에 따른 분기. 에이전트 루프의 `if (toolUse) { ... } else break`가 조건부 엣지다.

**리듀서(Reducer)**
상태 병합 규칙. `(기존값, 새값) -> 합쳐진값`. 기본은 덮어쓰기, `append` 리듀서가 **병렬을 안전하게** 만든다. → 멀티 에이전트에서 서브에이전트 결과를 모으는 도구([04장](04-multi-agent-patterns.md)).

**체크포인터(Checkpointer)**
매 노드 실행 후 상태를 직렬화 저장 → 일시정지/재개, 크래시 복구. MemorySaver(개발)/SqliteSaver(단일 서버)/PostgresSaver(멀티 인스턴스). → 인터럽트의 전제 조건.

**인터럽트(Interrupt) / Human-in-the-loop**
실행 중 멈춰 사람 승인을 기다리는 원시 기능. **체크포인터 필수.** `interruptBefore`(액션 전 승인) vs `interruptAfter`(실행 후 검토). 재개는 `new Command({ resume })`. 프리빌트 `createAgent` 에는 `interruptBefore` 옵션이 없고 `humanInTheLoopMiddleware` 로 **툴 단위**로 건다. → [03장](03-langgraph-basics.md).

**프리빌트 에이전트(`createAgent`) / 미들웨어**
그래프를 직접 조립하지 않고 얻는 ReAct 루프. **`langchain` 패키지**에 있다(구 `@langchain/langgraph/prebuilt` 의 `createReactAgent`, deprecated — 옵션도 `llm` → `model`). 확장은 모델·툴 호출을 감싸는 미들웨어로 한다(HITL·요약·툴 에러·호출 상한). `langchain` 은 `@langchain/core`·`@langchain/langgraph` **위에 얹히는** 상위 패키지이며 둘을 대체하지 않는다. → [03장](03-langgraph-basics.md).

**스레드(Thread)**
체크포인터가 상태를 묶는 단위(대화 세션 식별자). 같은 thread로 재실행하면 죽은 지점부터 재개된다.

## 레이어 4 — 멀티 에이전트 (분산 시스템)

**두 축 — 축 A(오케스트레이터-워커) vs 축 B(전문가 협업)**
"멀티 에이전트"가 가리키는 두 가지. **축 A**: 리드가 일회성 워커를 부림(위계적). **축 B**: 각 에이전트가 지속되는 역할을 가진 1급 시민으로 동료처럼 협업. 설계 전에 어느 쪽인지 정한다. → [04장](04-multi-agent-patterns.md).

**슈퍼바이저(Supervisor)**
중앙 에이전트가 어느 서브에이전트에게 작업을 줄지 결정. 통제·디버깅이 상대적으로 쉬움. → [04장](04-multi-agent-patterns.md).

**그룹챗(Group Chat)**
여러 에이전트가 공유 대화 스레드에서 발언하고 매니저가 발언 순서를 라우팅(AutoGen식). 복잡한 작업을 동적으로 쪼갤 때.

**중앙집중 vs 분산 오케스트레이션**
조정 로직을 한 오케스트레이터에 모으나(중앙집중: 통제 쉬움, god object 위험) vs 각 에이전트에 흩뿌리나(분산: 유연·확장 쉬움, 디버깅 어려움). 조정 자체는 없앨 수 없고 **위치만 바뀐다**. 오케스트레이터 똑똑함도 스펙트럼: 하드코딩 라우팅→LLM 라우터→계획 에이전트→완전 분산. → [04장](04-multi-agent-patterns.md).

**블랙보드(Blackboard)**
에이전트들이 함께 읽고 쓰는 공유 작업공간. 완전 분산 협업에서도 이 공유 상태가 암묵적 조정자 역할을 한다.

**네트워크(Network)**
슈퍼바이저 없이 에이전트들이 직접 핸드오프. 유연하지만 통제 어려움·무한 루프 위험.

**핸드오프(Handoff)**
한 에이전트가 제어권과 컨텍스트를 다른 에이전트에게 넘기는 행위. **넘기는 컨텍스트의 품질이 결과 품질을 좌우.**

**오케스트레이터-워커(Orchestrator–Worker)**
리드가 작업을 쪼개 워커들에게 위임하고 종합. 하위 작업 수를 미리 모를 때. Anthropic 리서치 시스템(리드+3~5 서브에이전트, 90% 단축)의 구조.

**컨텍스트 파편화(Context Fragmentation)**
에이전트를 나눌 때 각자 다른 정보를 봐서 모순된 결정을 내리는 현상. 멀티 에이전트의 고질병. → 단일 작성자 원칙으로 억제.

**단일 작성자 원칙(Single-Writer Principle)**
여러 에이전트가 읽기·판단은 병렬로 하되, **쓰기(최종 상태 확정)는 단일 스레드로** 유지. Cognition이 실전에서 뽑아낸, 멀티 에이전트를 작동하게 만드는 핵심 원칙. → [04장](04-multi-agent-patterns.md).

**컨텍스트 엔지니어링(Context Engineering)**
프롬프트 엔지니어링의 다음 단계 — 동적 시스템에서 에이전트에게 줄 컨텍스트를 자동으로 잘 구성하는 것. Cognition이 "에이전트 엔지니어의 1순위 과제"라 부른 것. → [07장](07-should-you-build-multi-agent.md).

## 레이어 4.5 — 에이전트 플랫폼 / 인프라

**앱 레이어 vs 인프라 레이어**
같은 전문가 에이전트들을 **한 프로그램 안 함수**로 두나(앱 레이어: 함수 호출, 변수로 컨텍스트 전달) vs **각각 독립 서비스**로 두나(인프라 레이어: 네트워크 호출, 공유 세션 스토어). 인프라 레이어 = 에이전트를 마이크로서비스로 짓기. → [08장](08-agent-platform-infra.md).

**에이전트 = 서비스(Agent-as-a-Service)**
에이전트를 독립 배포·버전·스케일되는 서비스(`/invoke` 엔드포인트)로 만드는 것. 안에는 우리가 아는 그 LLM 루프. 함수가 HTTP 서비스로 승격한 것.

**Agent Card**
에이전트가 "나는 누구고 뭘 할 수 있다"를 노출하는 **기계가 읽는 JSON 명세**(A2A 표준은 보통 `/.well-known/agent.json`). name·description·capabilities·input_schema·auth 포함. 백엔드의 **OpenAPI 명세**에 대응 = 에이전트 사이의 **계약**. 팀이 병렬 개발하려면 일찍 합의할 것.

**레지스트리(Registry)**
Agent Card들의 목록. 오케스트레이터가 "이 요청엔 어떤 에이전트가 있나"를 조회하는 곳. 서비스 디스커버리에 대응.

**A2A (Agent2Agent)**
Google(2025-04)의 **에이전트↔에이전트** 상호운용 표준. 서로 다른 팀·벤더 에이전트가 Agent Card로 상대를 발견하고 작업을 위임·협업. → [08장](08-agent-platform-infra.md).

**MCP (Model Context Protocol)**
Anthropic(2024-11)의 **에이전트↔도구/데이터** 표준. "AI의 USB-C 포트". 한 에이전트가 외부 도구를 붙이는 규격. A2A와 방향이 다르다(경쟁 아님, 층이 다름).

**CrewAI / AutoGen**
축 B 프레임워크. **CrewAI**: 역할(role/goal/backstory) 기반 크루, 도메인 전문가 팀 멘탈모델에 직관적. **AutoGen**(Microsoft): 대화형 그룹챗, 에이전트들이 공유 스레드에서 토론. 둘 다 축 B 협업을 정형화한다.

## 레이어 5 — 운영과 검색 (평가·RAG)

**평가셋(Eval Set)**
입력-기대결과 쌍 30~50개. **손으로** 만든다(만드는 과정이 문제 이해). 변경할 때마다 돌려 회귀를 잡음. → [05장](05-eval-and-observability.md).

**트레이싱(Tracing)**
한 요청이 어느 노드·툴을 거쳤고 무슨 입출력이 오갔는지 전 과정 기록. LangSmith / OpenTelemetry. LLM 호출 체인의 분산 추적. → [05장](05-eval-and-observability.md).

**LLM-as-judge**
기대결과와 실제결과를 다른 LLM에게 채점시키는 평가 방식. 편하지만 심판도 비결정적임을 유의.

**RAG (Retrieval-Augmented Generation)**
질문에 관련된 문서를 **검색**해 프롬프트에 **끼워넣고** 답을 **생성**. "LLM에게 오픈북 시험". 품질은 검색이 좌우. → [06장](06-rag-when-needed.md).

**청킹(Chunking)**
긴 문서를 의미 단위 조각으로 자름. 청크 크기·겹침이 검색 품질의 첫 변수.

**임베딩(Embedding) / 벡터DB**
텍스트를 의미를 담은 벡터로 변환 → 벡터DB에서 가까운 청크를 찾는 "의미 기반 검색". 정확한 코드/ID엔 약함.

**리랭킹(Reranking)**
벡터 검색이 뽑은 후보를 더 정교한 모델로 관련도 순 재정렬. "빠른 검색으로 넓게, 리랭커로 좁게".

**하이브리드 검색(Hybrid Search)**
의미 검색(벡터) + 키워드 검색(BM25 등) 결합. 개념 질문은 벡터가, 정확한 고유명사/코드는 키워드가 잡음.

## 레이어 관통 — 백엔드에서 이미 아는 것

**상태 관리 / 재시도 / 타임아웃 / 멱등성 / 관측성** — 전부 백엔드의 분산 시스템 개념 그대로다. 에이전트에서 새로 배우는 것은 오직 **비결정적 컴포넌트(LLM)를 통제하는 법**뿐. → [01장](01-prerequisites.md).
