# Redis Pub/Sub 실시간 알림 학습 개요

## 왜 이 주제를 학습하는가

여러 대로 늘어난 백엔드 서버가 같은 사실을 동시에 알아야 하는 상황은 흔합니다. 관리자가 공지를 하나 올렸을 때 어느 서버에 붙어 있는 사용자든 같은 순간에 그 공지를 보아야 하고, 어느 서버가 사용자 정보를 고쳤을 때 나머지 서버가 들고 있던 로컬 캐시는 즉시 무효가 되어야 합니다. 서버끼리 서로를 직접 호출하도록 만들면 서버가 늘어날 때마다 호출하는 쪽을 고쳐야 하므로, 중간에 메시지 중개자를 두는 편이 낫습니다.

Redis Pub/Sub은 그 중개자 가운데 가장 값싸고 가장 빠른 선택지입니다. 동시에 **가장 쉽게 잘못 쓰이는** 선택지이기도 합니다. 메시지를 저장하지 않으므로 발행 순간에 구독하고 있지 않았던 구독자는 그 메시지를 영영 받지 못하고, 구독을 시작한 커넥션은 그 순간부터 성격이 달라지기 때문입니다.

이 자료는 세 가지 판단에 무게를 둡니다.

| 판단 | 이 자료가 답하는 질문 |
|---|---|
| **실시간 알림 기능의 설계와 구현** | 구독 커넥션을 어디에 두고 누가 관리하는가. 클라이언트마다 구독하면 무엇이 무너지는가 |
| **Pub/Sub의 한계와 대안 판정** | 이 업무에 Pub/Sub을 써도 되는가. 안 된다면 Redis Streams와 Kafka 중 무엇인가 |
| **운영과 장애 대응** | 메시지가 사라졌다는 신고를 받았을 때 무엇을 먼저 보는가 |

곁들여 다루는 Server-Sent Events(SSE)는 브라우저까지 메시지를 내려보내는 통로일 뿐이고 Pub/Sub과는 무관한 기술입니다. 그래서 이 자료에서도 보조 위치인 [09-sse-aside.md](09-sse-aside.md)에 따로 두었습니다.

## 강의가 주장한 것과 이 자료가 보강한 것

강의는 실습 중심이라 구현 절차를 자세히 보여주는 대신 운영과 대안 판정을 짧게 지나갑니다. 두 영역이 정확히 이 자료의 관점 가운데 둘이므로, 그 부분은 Redis 공식 문서로 따로 확인해 채웠습니다. 어느 것이 강의의 주장이고 어느 것이 보강인지는 각 문서 본문에서 구분해 밝힙니다.

| 본문의 주장 | 원본 좌표 | 보강 여부 |
|---|---|---|
| Pub/Sub은 1대 N 브로드캐스트이고 발행자와 구독자가 느슨하게 결합된다 | `[02:00]`, `[18:30]` | 강의의 주장 |
| 구독한 커넥션은 메시지 수신 전용이 되어 일반 명령을 받지 못한다 | `[03:00]`, `[17:30]`, `[28:00]` | 강의의 주장. **허용 명령의 정확한 목록과 RESP3에서의 변화는 보강** |
| `get_message`에 타임아웃을 주는 까닭은 루프에서 다른 상태를 점검할 틈을 만들기 위해서다 | `[11:30]`~`[14:00]` | 강의의 주장 |
| `asyncio.sleep(0.01)`은 이벤트 루프 독점과 CPU 과사용을 막는다 | `[14:30]` | 강의의 주장 |
| 클라이언트마다 구독 객체를 만드는 구조는 안티패턴이고, 정석은 앱 시작 시 한 번 구독한 뒤 내부에서 팬아웃하는 것이다 | `[15:30]`~`[17:30]`, `[26:00]` | 강의의 주장 |
| Pub/Sub의 메시지는 휘발성이라 발행 시점에 구독하지 않았으면 영영 받지 못한다 | `[21:00]`, `[28:00]` | 강의의 주장 |
| 느린 구독자가 출력 버퍼 한계를 넘으면 Redis가 그 클라이언트를 끊는다 | 없음 | **보강** |
| 일반 Pub/Sub은 클러스터의 모든 노드로 전파되고, Sharded Pub/Sub이 그것을 좁힌다 | `[25:30]`의 "서버가 몇백 대가 되어도 된다"는 발언에 대응 | **보강** |
| `PUBLISH`의 반환값이 정확히 무엇을 세는가 | `[09:30]`에서 값을 응답에 담기만 함 | **보강** |
| Redis Streams가 소비자 그룹·확인 응답·재처리로 Pub/Sub과 갈라진다 | `[28:30]`에서 이름만 언급 | **보강** |
| SSE의 동시 연결 수 제약 | 없음 | **보강** |

## 이 학습 후 할 수 있는 것

- [ ] 구독 전용 커넥션을 분리해야 하는 까닭을 프로토콜 수준에서 설명할 수 있습니다.
- [ ] 클라이언트 접속마다 구독하는 구조가 왜 무너지는지 설명하고, 팬아웃 레지스트리로 고쳐 쓸 수 있습니다.
- [ ] 메시지가 사라졌다는 신고를 받았을 때 휘발성 때문인지 느린 구독자 강제 종료 때문인지 갈라 볼 수 있습니다.
- [ ] 주어진 업무 요건에서 Pub/Sub과 Redis Streams 중 어느 것을 써야 하는지 근거를 들어 판정할 수 있습니다.
- [ ] Redis Cluster에서 채널 수가 늘어날 때 무엇이 비싸지는지 알고 Sharded Pub/Sub을 언제 쓸지 판단할 수 있습니다.
