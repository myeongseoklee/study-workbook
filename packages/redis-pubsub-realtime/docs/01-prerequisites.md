# 선수 지식

## 이 파일을 건너뛰어도 되는 경우

- Redis 명령이 요청 하나에 응답 하나로 끝나는 구조라는 것을 이미 알고 있습니다.
- `SUBSCRIBE`와 `PUBLISH`를 Redis CLI에서 한 번이라도 직접 써 본 적이 있습니다.
- 비동기 제너레이터가 값을 하나씩 내어놓으면서 함수의 실행을 중단했다가 재개한다는 것을 알고 있습니다.

세 가지가 모두 해당하면 [02-core-principles.md](02-core-principles.md)로 넘어가십시오.

## 필수 개념 1: Redis 명령의 요청·응답 모형

Redis 클라이언트는 서버와 TCP 커넥션을 하나 열고, 그 위로 명령을 문자열로 보낸 뒤 응답을 받습니다. `SET key value`를 보내면 `OK`가 돌아오고, `GET key`를 보내면 값이 돌아옵니다. **명령을 보낸 쪽이 응답을 받으면 그 커넥션은 곧바로 다음 명령을 받을 수 있는 상태로 돌아옵니다.**

이 왕복이 짧기 때문에 애플리케이션은 보통 커넥션을 여러 개 만들어 풀(pool)에 담아 두고, 요청을 처리할 때마다 하나를 빌렸다가 되돌려 줍니다. 커넥션 하나를 여러 요청이 돌려 쓰는 것이 전제이고, 그 전제가 성립하려면 **어떤 요청도 커넥션을 오래 붙잡고 있지 않아야** 합니다.

이 자료의 절반은 이 전제가 깨지는 자리에 관한 이야기입니다. 구독은 응답을 받고 끝나는 명령이 아니라 **응답을 계속 기다리는 상태**로 들어가는 명령이기 때문입니다.

## 필수 개념 2: 채널과 발행·구독

Redis Pub/Sub에는 저장되는 것이 없습니다. 키도 값도 만들지 않고, **채널**이라는 이름표만 씁니다.

| 명령 | 하는 일 |
|---|---|
| `SUBSCRIBE ch` | 이 커넥션을 `ch` 채널의 구독자로 등록합니다 |
| `PSUBSCRIBE ch.*` | 글로브(glob) 패턴에 들어맞는 모든 채널을 구독합니다 |
| `PUBLISH ch msg` | `ch` 채널에 `msg`를 발행합니다 |
| `UNSUBSCRIBE ch` | 구독을 해제합니다 |

`PUBLISH`가 하는 일은 "지금 이 채널을 구독하고 있는 커넥션들에게 이 문자열을 밀어 넣는 것"이 전부입니다. 구독자가 하나도 없으면 그 메시지는 아무 데도 가지 않고 사라지며, Redis는 그 사실을 어디에도 남기지 않습니다.

채널 이름에 콜론을 넣어 계층을 흉내 내는 관행이 널리 쓰입니다. 이 자료의 실습 코드도 `system:notices`라는 이름을 씁니다. 다만 **콜론은 Redis에게 아무 의미도 없는 평범한 글자**입니다. 계층처럼 보이는 것은 사람이 읽기 편하도록 만든 약속일 뿐이고, 그 계층을 실제로 이용하려면 `PSUBSCRIBE system:*`처럼 패턴 구독을 따로 걸어야 합니다.

**더 알아보기**: [Redis Pub/Sub 공식 문서](https://redis.io/docs/latest/develop/pubsub/)

## 필수 개념 3: 비동기 제너레이터와 스트리밍 응답

이 자료의 실습 코드는 Python과 FastAPI로 되어 있고, 그 안에서 비동기 제너레이터를 씁니다. 코드를 읽는 데 필요한 만큼만 정리합니다.

보통의 함수는 값을 한 번 반환하고 끝납니다. 제너레이터는 `yield`로 값을 하나 내어놓고 **그 자리에서 멈춘 채로** 호출한 쪽에 제어를 넘겼다가, 다음 값을 요구받으면 멈췄던 자리에서 이어서 실행합니다. 비동기 제너레이터는 여기에 `await`가 더해진 것이라, 값을 내어놓기 전에 다른 작업을 기다릴 수 있습니다.

HTTP 응답을 한꺼번에 만들어 보내는 대신 조금씩 흘려보내려면 이런 함수가 필요합니다. 응답 본문의 길이를 미리 알 수 없고, 언제 다음 조각이 생길지도 모르기 때문입니다. FastAPI에서는 이 제너레이터를 `StreamingResponse`에 넘기면 됩니다.

TypeScript로 옮기면 대응 관계는 다음과 같습니다.

| Python | TypeScript |
|---|---|
| `async def gen(): yield x` | `async function* gen() { yield x }` |
| `async with obj as o:` | `await using o = obj` 또는 `try` / `finally`로 정리 |
| `await asyncio.sleep(0.01)` | `await new Promise((r) => setTimeout(r, 10))` |

이 레포의 코딩 과제는 TypeScript로 되어 있고 Redis 서버를 띄우지 않습니다. 강의의 Python 코드를 그대로 옮기는 대신, 그 코드가 담고 있는 판단을 순수 함수로 떼어내 판정합니다.

## 필수 개념 4: 이벤트 루프를 독점한다는 말의 뜻

비동기 런타임은 한 스레드 위에서 여러 작업을 번갈아 실행합니다. 작업이 `await`를 만나면 제어를 런타임에 돌려주고, 런타임은 그 틈에 다른 작업을 실행합니다. **그러므로 `await`를 만나지 않고 계속 도는 반복문은 다른 모든 작업을 멈춰 세웁니다.**

```python
while True:
    check_something()   # await가 없다
```

이 반복문은 CPU를 한 코어만큼 계속 쓰면서, 같은 프로세스에서 처리되어야 할 다른 HTTP 요청까지 굶깁니다. 실습 코드가 반복문 끝에 아주 짧은 `asyncio.sleep`을 넣는 것은 이 상황을 막기 위해서입니다. 자세한 것은 [04-realtime-notification.md](04-realtime-notification.md)에서 다시 다룹니다.

## 자가 진단

다음 질문에 답할 수 있으면 다음 파일로 넘어가십시오. 먼저 스스로 답해 본 뒤 토글을 열어 비교하십시오.

<details>
<summary>Q1: Redis 클라이언트가 커넥션을 풀에 담아 돌려 쓰는 것이 가능한 까닭은 무엇인가?</summary>

명령 하나가 요청과 응답 한 쌍으로 끝나고, 응답을 받은 커넥션은 곧바로 다음 명령을 받을 수 있는 상태로 돌아오기 때문입니다. 어떤 명령도 커넥션을 오래 붙잡지 않는다는 것이 풀의 전제입니다. 이 전제가 깨지는 명령이 있다면 그 명령을 실행한 커넥션은 풀에 돌려주면 안 됩니다.

</details>

<details>
<summary>Q2: 채널 이름 `system:notices`의 콜론은 Redis에서 어떤 의미를 갖는가?</summary>

아무 의미도 갖지 않습니다. Redis에게는 이름의 일부인 평범한 글자일 뿐입니다. 사람이 읽을 때 계층으로 보이도록 만든 관행이고, 그 계층을 실제로 이용하려면 `PSUBSCRIBE system:*` 같은 패턴 구독을 따로 걸어야 합니다.

</details>

<details>
<summary>Q3: 구독자가 하나도 없는 채널에 `PUBLISH`하면 그 메시지는 어떻게 되는가?</summary>

아무 데도 가지 않고 사라집니다. Redis는 발행된 메시지를 어디에도 저장하지 않으므로 나중에 구독을 시작한 클라이언트가 그 메시지를 받을 방법이 없습니다. 이것이 [02-core-principles.md](02-core-principles.md)에서 다룰 휘발성입니다.

</details>

<details>
<summary>Q4: `await` 없이 도는 무한 반복문이 비동기 서버에서 문제가 되는 까닭은 무엇인가?</summary>

비동기 런타임이 한 스레드 위에서 작업을 번갈아 실행하는데, 제어를 돌려주는 지점이 `await`이기 때문입니다. `await`가 없으면 런타임은 그 반복문에서 벗어날 기회를 얻지 못하므로 같은 프로세스의 다른 요청이 전부 멈춥니다. CPU를 한 코어만큼 계속 쓰는 것은 그다음 문제입니다.

</details>
