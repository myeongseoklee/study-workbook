# 암기 카드

> 반복 복습용입니다. 모든 항목은 설계 판단이나 장애 진단에 곧바로 쓰입니다.
>
> 이 파일의 카드 **18장은 본문의 `⚠️ 암기 필수` 마커 18개와 1:1로 대응**합니다. 묶거나 나눈 것이 없으므로 어느 카드든 본문의 한 자리로 곧장 돌아갈 수 있습니다. [92-workbook.md](../workbook/92-workbook.md)의 파트 1도 이 순서 그대로 18문항입니다.

## 수치와 기본값

| 번호 | 항목 | 값 | 되짚기 |
|---|---|---|---|
| **M1** | `client-output-buffer-limit pubsub`의 hard limit | **32MB** | [06](06-operations-and-failure.md) |
| | 같은 지시자의 soft limit | **8MB** | |
| | 같은 지시자의 soft seconds | **60초** | |
| **M2** | Sharded Pub/Sub이 도입된 Redis 판본 | **7.0** | [07](07-cluster-and-sharded-pubsub.md) |
| **M3** | Redis 접속이 시작하는 프로토콜 | **RESP2**. RESP3는 `HELLO 3`으로 협상하며, 실제 사용 버전은 클라이언트 라이브러리가 정합니다 | [03](03-connection-isolation.md) |

`normal` 클래스의 기본값이 `0 0 0`으로 사실상 무제한인 것과 대조해서 기억하십시오. 구독자와 복제본만 한계를 갖는 까닭은 이들이 데이터를 밀어 넣는 방식으로 받기 때문입니다.

## 불변 트레이드오프와 경계

| 번호 | 기억할 것 | 되짚기 |
|---|---|---|
| **M4** | **Pub/Sub의 전달 보장은 at-most-once다.** 서버가 보낸 뒤에는 다시 보낼 기회가 없다 | [02](02-core-principles.md) |
| **M5** | **RESP2 구독 상태에서 허용되는 명령은 구독 관리와 연결 관리뿐이고 데이터 명령은 하나도 없다** | [02](02-core-principles.md) |
| **M6** | **그 제약은 RESP3에서 사라진다. 그래도 커넥션은 분리해야 한다** — 구독 커넥션은 구독 수명 내내 묶여 있어 풀에 돌려줄 수 없기 때문이다 | [03](03-connection-isolation.md) |
| **M7** | **정석은 프로세스마다 구독 하나이고, 클라이언트 팬아웃은 프로세스 메모리 안에서 한다** — Redis 쪽 비용을 사용자 수가 아니라 서버 대수에 묶는 것이 목적이다 | [05](05-fanout-registry.md) |
| **M8** | **채널 구독 해제는 그 채널을 듣는 마지막 클라이언트가 떠날 때만 한다** — 먼저 해제하면 남은 클라이언트가 조용히 알림을 잃는다 | [05](05-fanout-registry.md) |
| **M9** | **일반 Pub/Sub은 클러스터의 모든 노드로 전파되므로 노드를 늘릴수록 메시지 하나의 전파량이 늘어난다** | [07](07-cluster-and-sharded-pubsub.md) |
| **M10** | **Sharded Pub/Sub의 샤드 채널은 키와 같은 알고리즘으로 슬롯에 배정되고, 패턴 구독을 쓸 수 없다** | [07](07-cluster-and-sharded-pubsub.md) |
| **M11** | **판정 순서: 놓쳐도 되면 Pub/Sub이고, 그렇지 않으면 긴 보존이나 되감기가 필요한 경우에만 Redis 밖의 메시지 큐이며, 나머지가 Streams다.** 재처리 요구는 첫 질문의 답을 뒤집을 뿐이고 수단을 확정하지는 않는다 | [08](08-pubsub-or-streams.md) |
| **M12** | **소비자 그룹은 적어도 한 번을 다루는 장치이고 정확히 한 번을 보장하지 않는다** | [08](08-pubsub-or-streams.md) |
| **M13** | **"Streams는 저장한다"는 복제가 비동기이고 AOF 정책에 달려 있다.** 지속성이 중요하면 강한 fsync 정책이 필요하다 | [08](08-pubsub-or-streams.md) |

## 명령과 반환값

| 번호 | 기억할 것 | 되짚기 |
|---|---|---|
| **M14** | **`PUBLISH`의 반환값은 밀어 넣은 클라이언트 수다.** 패턴 구독자를 포함하고, 클러스터에서는 발행한 노드에 붙은 클라이언트만 센다. 처리 완료를 뜻하지 않는다 | [06](06-operations-and-failure.md) |
| **M15** | **채널 구독과 들어맞는 패턴 구독을 함께 걸면 같은 메시지를 두 번 받는다.** 중복 제거는 애플리케이션의 책임이다 | [02](02-core-principles.md) |
| **M16** | **Pub/Sub은 데이터베이스 번호를 넘나든다.** 10번에서 발행한 것을 1번의 구독자가 듣는다. 격리하려면 채널 이름에 환경을 붙인다 | [02](02-core-principles.md) |

`PUBLISH`의 반환값과 대조되는 명령이 `PUBSUB NUMSUB`입니다. 이쪽은 패턴 구독자를 **제외**합니다. 두 값이 다르다고 해서 어느 한쪽이 틀린 것이 아니라 세는 대상이 처음부터 다릅니다.

## 진단 신호

| 번호 | 증상 | 가장 가능성 높은 원인 | 되짚기 |
|---|---|---|---|
| **M17** | 로그에 `overcoming of output buffer limits`가 보인다 | **느린 구독자의 강제 종료**입니다. 그 문구가 없는데 메시지가 비었다면 원인은 휘발성입니다 | [06](06-operations-and-failure.md) |
| **M18** | 떠난 클라이언트의 구독 커넥션이 쌓인다 | **`get_message`에 타임아웃이 없습니다.** 타임아웃이 만드는 것은 속도가 아니라 반복문에서 다른 상태를 점검할 틈입니다 | [04](04-realtime-notification.md) |

`client-output-buffer-limit`의 판정 규칙을 함께 기억하십시오. **hard는 도달 즉시 끊고, soft는 그 상태가 지정 초 동안 연속으로 유지되어야 끊습니다.** 중간에 한계 아래로 내려가면 경과 시간이 초기화되므로, 누적으로 오해하면 정상 클라이언트를 끊는 판정을 만들게 됩니다.

| 확인하고 싶은 것 | 명령 |
|---|---|
