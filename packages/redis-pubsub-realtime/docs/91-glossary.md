# 용어 해설집 — 다섯 개 레이어로 구조화

학습 자료 [01](01-prerequisites.md)부터 [09](09-sse-aside.md)까지 등장한 용어를, 단편적 사전이 아니라 **개념의 인과 구조**로 정리합니다.

## 전체 지도

이 자료가 다루는 영역은 다섯 개 레이어가 쌓인 그림입니다.

```
┌──────────────────────────────────────┐
│ L5  Browser transport                │  SSE / polling / WebSocket
├──────────────────────────────────────┤
│ L4  Guarantees you buy               │  Streams / consumer group / XACK
├──────────────────────────────────────┤
│ L3  Flow control and diagnosis       │  output buffer / hard-soft limit
├──────────────────────────────────────┤
│ L2  Messaging vocabulary             │  channel / pattern / fan-out
├──────────────────────────────────────┤
│ L1  Protocol and connection          │  RESP2-RESP3 / subscribed state
└──────────────────────────────────────┘
```

아래로 갈수록 **바이트가 오가는 방식에 가깝고**, 위로 갈수록 **업무가 요구하는 보장에 가깝습니다.** 위 레이어는 아래 레이어가 주지 못하는 것을 보완하면서 쌓입니다. L1이 구독 커넥션의 성격을 정하고, L2가 그 위에서 메시징의 어휘를 세우고, L3이 그 어휘로는 표현되지 않는 흐름 제어를 다루고, L4가 L2의 휘발성을 돈 주고 메우고, L5가 그것을 브라우저까지 내려보냅니다.

**용어를 외우는 것이 아니라 이 인과의 흐름을 잡는 것이 핵심입니다.**

# L1. 프로토콜과 커넥션 — 구독한 커넥션은 왜 특별한가

## 핵심 인과 흐름

```
TCP 커넥션 하나
   ↓ (SUBSCRIBE를 보낸다)
구독 상태로 들어간다
   ↓ (서버가 밀어 보내는 메시지를 계속 읽는 통로가 된다)
푸시 프로토콜로 의미론이 바뀐다  ← RESP2에서만
   ↓ (응답과 푸시를 구별할 방법이 없다)
데이터 명령이 금지된다  ← RESP2에서만
   ↓ (그리고 프로토콜과 무관하게)
구독 수명 내내 묶여 있어 풀에 돌려줄 수 없다
   ↓
구독 전용 커넥션을 따로 둔다
```

## 용어

### **RESP2 · RESP3**
- **정의**: Redis 클라이언트와 서버가 주고받는 데이터의 직렬화 규약이고, 숫자는 그 판본입니다.
- **메커니즘**: 접속은 기본적으로 RESP2로 시작하고, `HELLO 3`으로 협상해야 RESP3가 됩니다. RESP3는 서버가 밀어 보내는 메시지에 별도의 형식을 부여해 응답과 구별할 수 있게 합니다.
- **인접**: → 구독 상태, 푸시 메시지
- **본문 위치**: [03-connection-isolation.md](03-connection-isolation.md)

### **구독 상태 (subscribed state)** ⭐
- **정의**: `SUBSCRIBE` 계열 명령을 실행한 커넥션이 들어가는 상태입니다.
- **메커니즘**: RESP2에서는 이 상태의 클라이언트가 아홉 개 명령만 실행할 수 있고 데이터 명령은 하나도 포함되지 않습니다. RESP3에서는 이 제약이 없습니다.
- **인접**: → RESP2, 커넥션 풀, 구독 전용 커넥션
- **본문 위치**: [02-core-principles.md](02-core-principles.md) 원리 2

### **커넥션 풀**
- **정의**: 미리 열어 둔 커넥션을 요청마다 빌려 주고 돌려받는 구조입니다.
- **메커니즘**: "빌린 것을 곧 돌려준다"를 전제로 삼습니다. 구독은 그 전제를 깨는 유일한 사용 방식이므로 풀에서 꺼낸 커넥션으로 구독하면 안 됩니다.
- **인접**: → 구독 전용 커넥션
- **본문 위치**: [01-prerequisites.md](01-prerequisites.md) 필수 개념 1

### **구독 전용 커넥션**
- **정의**: 오직 구독만을 위해 따로 잡아 두고 풀에 돌려주지 않는 커넥션입니다.
- **메커니즘**: 강의의 코드에서는 `.pubsub()`이 만드는 객체가 이것을 잡습니다. RESP3로 올려도 이 분리는 유지해야 하는데, 이유가 프로토콜 금지에서 풀 점유로 바뀔 뿐이기 때문입니다.
- **인접**: → 커넥션 풀, 팬아웃 레지스트리
- **본문 위치**: [03-connection-isolation.md](03-connection-isolation.md)

# L2. 메시징 어휘 — 무엇을 얻고 무엇을 내주는가

## 핵심 인과 흐름

```
채널이라는 이름표 하나
   ↓ (발행자와 구독자가 그 이름만 안다)
서로의 존재를 모른 채 통신한다 = 느슨한 결합
   ↓ (구독자를 늘려도 발행자가 그대로다)
1대 N 브로드캐스트
   ↓ (저장하지 않으므로 발행이 싸다)
at-most-once  ← 그 값싸기의 대가
```

## 용어

### **채널**
- **정의**: 발행과 구독이 만나는 이름표입니다. 키 공간과 무관하며 저장되는 것이 없습니다.
- **메커니즘**: 데이터베이스 번호를 넘나들므로 10번에서 발행한 것을 1번의 구독자가 듣습니다. 격리가 필요하면 이름 앞에 환경을 붙입니다. 이름 안의 콜론은 사람이 보기 위한 관행일 뿐 Redis에게는 평범한 글자입니다.
- **인접**: → 패턴 구독, 샤드 채널
- **본문 위치**: [02-core-principles.md](02-core-principles.md) 필수 지식 2

### **패턴 구독 (`PSUBSCRIBE`)**
- **정의**: 글로브 형식 패턴으로 들어맞는 모든 채널을 한꺼번에 구독하는 방식입니다.
- **메커니즘**: 전달되는 메시지의 종류가 `message`가 아니라 `pmessage`이고, 원소가 하나 더 붙어 어느 패턴 때문에 받았는지를 알려 줍니다. 채널과 패턴을 함께 걸면 같은 메시지를 두 번 받습니다.
- **인접**: → 채널, 샤드 채널(패턴을 쓸 수 없음)
- **본문 위치**: [02-core-principles.md](02-core-principles.md) 필수 지식 1

### **at-most-once** ⭐
- **정의**: 메시지가 전달된다면 한 번 전달되고, 전달되지 않을 수도 있다는 보장입니다.
- **메커니즘**: 서버가 보낸 뒤에는 다시 보낼 기회가 없습니다. 구독자가 오류를 만났거나 연결이 끊겨 처리하지 못했으면 그 메시지는 영구히 사라집니다.
- **인접**: → at-least-once(L4), 휘발성
- **본문 위치**: [02-core-principles.md](02-core-principles.md) 원리 3

### **느슨한 결합**
- **정의**: 발행자와 구독자가 서로의 존재를 모르는 채로 통신하는 상태입니다.
- **메커니즘**: 중간에 채널만 있으므로 구독자를 늘려도 발행자의 코드가 바뀌지 않습니다. 대가는 발행자가 누가 받았는지 알 수 없다는 것입니다.
- **인접**: → 채널, `PUBLISH` 반환값
- **본문 위치**: [02-core-principles.md](02-core-principles.md) 원리 1

### **팬아웃 (fan-out)**
- **정의**: 받은 메시지 하나를 여러 수신자에게 나누어 주는 동작입니다.
- **메커니즘**: Redis가 발행 시점에 하는 것도 팬아웃이고, 정석 구조에서 서버 프로세스가 자기에게 붙은 클라이언트들에게 하는 것도 팬아웃입니다. 후자를 프로세스 안으로 들여오는 것이 비용을 사용자 수에서 서버 대수로 옮기는 방법입니다.
- **인접**: → 팬아웃 레지스트리, 참조 계수
- **본문 위치**: [05-fanout-registry.md](05-fanout-registry.md)

### **팬아웃 레지스트리**
- **정의**: 채널마다 어떤 클라이언트가 듣고 있는지를 담아 두고, 메시지가 오면 나누어 주는 서버 안의 자료 구조입니다.
- **메커니즘**: 등록과 해제, 팬아웃, 이탈 정리, 참조 계수에 따른 구독 해제를 책임집니다. 해제는 여러 번 불려도 같은 결과여야 합니다.
- **인접**: → 참조 계수
- **본문 위치**: [05-fanout-registry.md](05-fanout-registry.md)

### **참조 계수 (reference counting)**
- **정의**: 한 채널을 듣고 있는 클라이언트의 수를 세는 것입니다.
- **메커니즘**: 그 수가 0이 되는 순간에만 Redis 쪽 구독을 해제합니다. 먼저 해제하면 남은 클라이언트가 알림을 잃는데 오류가 아무 데도 나타나지 않아 조용히 틀립니다.
- **인접**: → 팬아웃 레지스트리
- **본문 위치**: [05-fanout-registry.md](05-fanout-registry.md)

### **샤드 채널 (Sharded Pub/Sub)**
- **정의**: Redis 7.0부터 쓸 수 있는, 슬롯에 배정되는 채널입니다.
- **메커니즘**: 키를 슬롯에 배정할 때와 같은 알고리즘으로 채널 이름을 해시합니다. 전파가 그 샤드 안으로 제한되므로 클러스터 버스 트래픽이 줄고 샤드를 더해 확장할 수 있습니다. 패턴 구독은 쓸 수 없습니다.
- **인접**: → 채널, 패턴 구독, 클러스터 버스
- **본문 위치**: [07-cluster-and-sharded-pubsub.md](07-cluster-and-sharded-pubsub.md)

### **클러스터 버스**
- **정의**: 클러스터의 노드들이 서로 통신하는 내부 경로입니다.
- **메커니즘**: 일반 Pub/Sub의 메시지가 이 경로로 다른 모든 노드에 전파됩니다. 구독자가 있는지 보지 않고 보내므로 노드가 늘수록 전파량도 늘어납니다.
- **인접**: → 샤드 채널
- **본문 위치**: [07-cluster-and-sharded-pubsub.md](07-cluster-and-sharded-pubsub.md)

# L3. 흐름 제어와 진단 — 밀어 넣는 쪽과 받는 쪽의 속도가 어긋날 때

## 핵심 인과 흐름

```
Redis가 구독자에게 밀어 넣는다 (푸시 방식)
   ↓ (구독자가 읽어 가는 속도가 더 느리다)
서버 쪽 출력 버퍼에 쌓인다
   ↓ (무한정 자랄 수 없다)
hard / soft 한계에 걸린다
   ↓
Redis가 그 클라이언트의 연결을 닫는다
   ↓ (구독을 잃는다)
그 뒤에 발행된 메시지를 못 받는다 = 두 번째 유실 경로
```

## 용어

### **클라이언트 출력 버퍼** ⭐
- **정의**: 서버가 클라이언트에게 보내려고 준비해 둔, 아직 읽히지 않은 데이터가 머무는 공간입니다.
- **메커니즘**: 구독자와 복제본은 데이터를 밀어 넣는 방식으로 받으므로 이 버퍼가 쌓이기 쉽고, 그래서 이 둘만 기본 한계를 갖습니다. `normal` 클래스는 기본값이 전부 0이라 사실상 무제한입니다.
- **인접**: → hard limit, soft limit, `omem`
- **본문 위치**: [06-operations-and-failure.md](06-operations-and-failure.md)

### **hard limit · soft limit · soft seconds**
- **정의**: `client-output-buffer-limit`이 받는 세 값입니다. `pubsub` 클래스의 기본값은 32MB, 8MB, 60초입니다.
- **메커니즘**: hard limit에 도달하면 즉시 끊습니다. soft limit은 그 상태가 지정된 초 동안 **연속으로** 유지되어야 끊습니다. 중간에 아래로 내려가면 경과 시간이 초기화됩니다. 값을 0으로 두면 그 한계가 해제됩니다.
- **인접**: → 클라이언트 출력 버퍼
- **본문 위치**: [06-operations-and-failure.md](06-operations-and-failure.md)

### **`omem` · `obl` · `oll`**
- **정의**: `CLIENT LIST`가 보여 주는 출력 관련 필드입니다.
- **메커니즘**: `omem`이 출력 버퍼가 쓰는 메모리, `obl`이 출력 버퍼의 길이, `oll`이 출력 목록의 길이입니다. 버퍼가 가득 차면 응답이 목록에 줄을 섭니다. `CLIENT LIST TYPE PUBSUB`으로 구독 클라이언트만 골라 볼 수 있습니다.
- **인접**: → 클라이언트 출력 버퍼
- **본문 위치**: [06-operations-and-failure.md](06-operations-and-failure.md)

# L4. 보장을 사는 수단 — 휘발성을 무엇으로 메우는가

## 핵심 인과 흐름

```
메시지를 지우지 않고 쌓아 둔다
   ↓ (남아 있으니 다시 읽을 수 있다)
소비자가 마지막으로 읽은 식별자를 기억한다
   ↓ (다시 읽을 수 있으니 확인 응답이 성립한다)
확인되지 않은 것이 대기 목록에 남는다
   ↓ (소비자가 죽으면 그것을 다른 소비자가 가져간다)
at-least-once
   ↓ (정확히 한 번은 여전히 얻을 수 없다)
처리하는 쪽을 멱등하게 만든다
```

## 용어

### **Redis Streams** ⭐
- **정의**: 메시지를 무기한 덧붙여 보관하는 자료 구조입니다.
- **메커니즘**: 명시적으로 지우라고 하지 않는 한 계속 쌓이고, 각 소비자가 마지막으로 받은 식별자를 기억해 자기 관점의 새 메시지를 판별합니다. 이것이 Pub/Sub과 갈리는 근본 지점입니다.
- **인접**: → 소비자 그룹, at-most-once(L2)
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

### **소비자 그룹 (consumer group)**
- **정의**: 스트림에서 데이터를 받아 여러 소비자에게 나누어 주는 가상의 소비자입니다.
- **메커니즘**: 같은 스트림에 그룹을 여럿 둘 수 있고, 처리 완료를 명시적으로 확인받으며, 미처리 항목을 조회하고 소유권을 옮길 수 있습니다. `XGROUP`으로 만들고 `XREADGROUP`으로 읽습니다.
- **인접**: → 대기 항목 목록, `XACK`
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

### **대기 항목 목록 (Pending Entries List, PEL)**
- **정의**: 소비자에게 전달은 되었으나 아직 확인 응답을 받지 못한 메시지들의 목록입니다.
- **메커니즘**: 이 목록이 비어 있지 않다는 사실 자체가 "누군가 받아 갔는데 끝냈다는 말이 없다"는 신호입니다. `XPENDING`으로 들여다봅니다.
- **인접**: → `XACK`, `XAUTOCLAIM`
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

### **`XACK`**
- **정의**: 소비자가 메시지 처리를 마쳤음을 알리는 명령입니다.
- **메커니즘**: 그 메시지를 대기 항목 목록에서 지웁니다. 이미 확인된 것은 성공 수에 세지 않습니다.
- **인접**: → 대기 항목 목록
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

### **`XAUTOCLAIM`과 최소 유휴 시간**
- **정의**: 오래 대기 상태였던 메시지의 소유권을 다른 소비자에게 넘기는 명령입니다. Redis 6.2.0부터 쓸 수 있습니다.
- **메커니즘**: 지정한 최소 유휴 시간을 넘긴 것만 가져가고, 가져가는 순간 그 메시지의 유휴 시간이 초기화됩니다. 그래서 같은 순간에 여러 소비자가 같은 것을 가져가지 못합니다. 그래도 정확히 한 번의 처리는 일반적으로 얻을 수 없습니다.
- **인접**: → 대기 항목 목록, 멱등성
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

### **`MAXLEN` · `MINID`**
- **정의**: 스트림의 길이를 제한하는 두 전략입니다.
- **메커니즘**: `MAXLEN`은 길이가 임계값을 넘는 동안 가장 오래된 것부터 버리고, `MINID`는 임계값보다 작은 식별자를 전부 버립니다. 임계값 앞의 `~`는 최소한 그만큼은 되도록 자르되 조금 더 많아도 좋다는 뜻이며 훨씬 쌉니다.
- **인접**: → Redis Streams
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

### **at-least-once와 멱등성**
- **정의**: 적어도 한 번은 전달된다는 보장과, 같은 처리를 여러 번 해도 결과가 같다는 성질입니다.
- **메커니즘**: 소비자 그룹은 앞쪽을 제공하지만 정확히 한 번을 보장하지 않습니다. 소비자가 처리를 마치고 확인을 보내기 직전에 죽으면 그 메시지가 다시 전달되기 때문입니다. 그러므로 뒤쪽은 애플리케이션이 스스로 만들어야 합니다.
- **인접**: → at-most-once(L2), 소비자 그룹
- **본문 위치**: [08-pubsub-or-streams.md](08-pubsub-or-streams.md)

# L5. 브라우저 전달 — 서버에서 화면까지

## 핵심 인과 흐름

```
서버가 HTTP 연결을 유지한 채 밀어 준다 (SSE)
   ↓ (연결 하나를 오래 붙잡는다)
브라우저의 동시 연결 수 한계에 걸린다  ← HTTP/1.1일 때
   ↓ (HTTP/2로 옮기면)
연결 하나 위에서 스트림이 다중화된다
   ↓
한계가 서버가 광고하는 동시 스트림 수로 바뀐다
```

## 용어

### **Server-Sent Events (SSE)**
- **정의**: 서버가 HTTP 연결을 유지한 채 브라우저로 데이터를 밀어 주는 단방향 스트리밍입니다.
- **메커니즘**: 콘텐츠 유형이 `text/event-stream`이고, `data: `로 시작하는 줄 뒤에 빈 줄을 넣으면 이벤트 하나가 됩니다. 브라우저에서 서버로 가는 통로는 없으므로 보낼 것이 있으면 평범한 요청을 따로 해야 합니다.
- **인접**: → 폴링, 웹소켓
- **본문 위치**: [09-sse-aside.md](09-sse-aside.md)

### **동시 연결 수 한계**
- **정의**: 브라우저가 한 출처에 대해 동시에 유지하는 HTTP/1.1 연결 수의 상한입니다.
- **메커니즘**: 널리 알려진 값은 브라우저와 출처의 조합마다 6이지만, **이것은 규격의 규정이 아니라 브라우저 구현이 채택한 관행입니다.** HTTP/1.1의 현행 규격은 특정 최댓값을 정하지 않고 보수적일 것을 권할 뿐입니다.
- **인접**: → `SETTINGS_MAX_CONCURRENT_STREAMS`
- **본문 위치**: [09-sse-aside.md](09-sse-aside.md)

### **`SETTINGS_MAX_CONCURRENT_STREAMS`**
- **정의**: HTTP/2에서 보내는 쪽이 받는 쪽에게 허용할 최대 동시 스트림 수를 알리는 설정입니다.
- **메커니즘**: 처음에는 한계가 없고, 병렬성을 불필요하게 제한하지 않도록 100보다 작지 않게 두기를 규격이 권합니다. HTTP/2에서는 이 값이 SSE 연결 수의 실질적인 상한이 됩니다.
- **인접**: → 동시 연결 수 한계
- **본문 위치**: [09-sse-aside.md](09-sse-aside.md)
