# 축적된 상태 설계 — 쌓고, 접고, 버리는 세 지층

## 왜 이 주제를 학습하는가

KV 캐시, 슬라이딩 윈도우, 이벤트 소싱은 보통 따로 배웁니다. GPU 최적화 이야기, 어텐션 변종 이야기, 백엔드 아키텍처 패턴 이야기로요. 그렇게 배우면 세 개의 지식이 생깁니다.

그런데 세 개는 **같은 하나의 문제**를 풀고 있습니다.

> 시간이 지나면서 계속 쌓이는 사건들이 있다. 현재 상태는 그 사건들을 접어서 얻는다. 사건은 무한히 쌓이지만 메모리는 유한하다. **무엇을 쌓고, 어떻게 접고, 무엇을 버릴 것인가?**

이 질문이 세 지층에서 각각 다른 이름으로 반복됩니다.

| 지층 | 무엇을 쌓나 | 어떻게 접나 | 무엇을 버리나 |
|---|---|---|---|
| **GPU 메모리** (KV 캐시) | 토큰별 Key/Value 벡터 | 어텐션 가중합 | 슬라이딩 윈도우 축출 |
| **데이터베이스** (이벤트 소싱) | 도메인 이벤트 | 리플레이(fold) | 스냅샷 + 보존 정책 |
| **에이전트 컨텍스트** | 대화·도구 결과 | 요약·압축 | 컨텍스트 축출 |

세 번째 줄이 이 학습의 도착지입니다. 당신이 하네스를 만들 때 내리는 결정 — 시스템 프롬프트를 앞에 고정할지, 대화를 언제 요약할지, 캐시를 언제 무효화할지 — 는 앞의 두 지층에서 이미 풀린 문제입니다. **원리를 한 번 배우면 세 곳에 쓸 수 있습니다.**

## 이 자료가 답하는 질문

**공통 원리**
- 왜 상태를 덮어쓰는 대신 사건을 쌓는 것이 이득인가?
- 재생 비용을 줄이는 방법은 무엇이고, 그것이 왜 "최적화일 뿐"인가?
- 버릴 때 절대 버려서는 안 되는 것을 어떻게 식별하는가?

**KV 캐시 (03~06)**
- 어텐션이 정확히 무엇이고, K/V는 왜 재사용 가능한가?
- 캐시가 있고 없음에 따라 시간복잡도가 왜 그렇게 계산되는가?
- 캐시 크기 공식은 왜 그런 항들의 곱인가?
- 절감 기법(MQA/GQA/MLA/양자화/PagedAttention)은 각각 무엇을 포기하는가?
- 캐시는 물리적으로 어디에 저장되는가?
- prefill과 decode는 왜 성격이 정반대인가?
- 프롬프트 캐싱의 실무적 함의는 무엇인가?

**슬라이딩 윈도우 (07)**
- 구현은 정확히 어떻게 하는가 (마스크·rolling buffer)?
- 좁은 창으로 멀리 보는 원리는 무엇이고, 그 한계는 무엇인가?
- 순수 SWA / full attention / 하이브리드는 어떻게 고르는가?

**이벤트 소싱과 에이전트 (08~09)**
- 이벤트 소싱은 위 4원리의 어떤 구현인가?
- 그 원리가 에이전트 하네스 설계에 어떻게 적용되는가?

## 이 학습 후 할 수 있는 것

- [ ] 특정 모델의 KV 캐시 크기를 구성값(레이어·KV헤드·head_dim)만 보고 직접 계산할 수 있다
- [ ] "이 워크로드가 왜 느린가"를 compute-bound / memory-bound로 나눠 진단할 수 있다
- [ ] 프롬프트 캐시 적중률이 0인 코드를 보고 무엇이 프리픽스를 깨뜨리는지 찾아낼 수 있다
- [ ] 하이브리드 어텐션 모델을 RAG·에이전트 워크로드에 쓸 때의 위험을 판단할 수 있다
- [ ] 어떤 바운디드 컨텍스트에 이벤트 소싱을 적용할지, 어디에 CRUD를 남길지 결정할 수 있다
- [ ] 에이전트 하네스의 컨텍스트·캐시·메모리 설계를 4원리로 검토할 수 있다

## 이 자료가 다루지 않는 것

- 어텐션의 수학적 도출(스케일링 인자 √d의 유도, 위치 인코딩의 종류별 비교) → 원논문
- 특정 추론 서버의 설정 옵션 전체 목록 → vLLM/TGI 공식 문서
- 이벤트 소싱의 프레임워크별 구현(Axon, EventStoreDB API 등) → 각 제품 문서
- 프롬프트 캐싱의 언어별 SDK 문법 → Claude API 공식 문서 (본문은 개념과 규격만)

원리를 이해하면 위 항목들은 30초 안에 찾을 수 있습니다. 그 판단 기준을 만드는 것이 이 자료의 목적입니다.
