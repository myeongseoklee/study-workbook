# 01. 선수 지식 — 어텐션, 접기(fold), append-only 로그

## 학습 목표

이 파일을 다 읽으면 (1) 어텐션이 무엇을 계산하는지와 K·V가 왜 불변인지 설명할 수 있고, (2) "상태는 로그를 접은 결과"라는 문장의 의미를 이해하고, (3) 이 자료 전반에서 같은 단어가 서로 다른 뜻으로 쓰이는 지점을 구분할 수 있습니다.

## 이 파일을 건너뛰어도 되는 경우

- 어텐션의 Q/K/V 구조와 causal mask를 이미 알고 있다 → "핵심 원리 2"부터
- `reduce`/`fold`와 append-only 로그 개념도 익숙하다 → "용어 지뢰밭"만 읽으세요 (이 절은 건너뛰지 마세요 — 뒤 파일에서 같은 단어가 세 가지 뜻으로 나옵니다)

## 핵심 원리 1: 어텐션(Attention)이란 무엇인가

### 해결하는 문제

문장에서 어떤 단어의 의미는 **다른 단어들과의 관계**로 결정됩니다.

> "그 은행에 갔다" vs "강 은행에 앉았다"

"은행"의 의미는 그 단어 자체가 아니라 주변 단어("갔다" / "강", "앉았다")를 봐야 정해집니다. 그러니 각 단어의 표현(벡터)을 만들 때, **다른 단어들의 정보를 섞어 넣어야** 합니다.

문제는 "어떤 단어를 얼마나 섞을지"입니다. 모든 단어를 균등하게 섞으면 정보가 뭉개지고, 고정된 규칙(예: 직전 3개만)으로 섞으면 문장마다 달라지는 관계를 잡지 못합니다.

**어텐션의 답: 섞는 비율을 데이터가 결정하게 한다.**

### 메커니즘 — 도서관 비유

각 토큰(단어)은 세 가지 벡터로 변환됩니다. 세 개 모두 같은 입력 벡터에 서로 다른 가중치 행렬을 곱해서 만듭니다.

| 이름 | 역할 | 비유 |
|---|---|---|
| **Query (Q)** | "나는 무엇을 찾고 있는가" | 검색어 |
| **Key (K)** | "나는 무엇에 대한 정보인가" | 책의 색인 표제어 |
| **Value (V)** | "내가 실제로 담고 있는 내용" | 책의 본문 |

계산은 세 단계입니다.

```
1단계 — 매칭 점수:   score(i, j) = Qᵢ · Kⱼ / √d
   토큰 i의 검색어와 토큰 j의 색인이 얼마나 맞는가. (내적 = 두 벡터의 방향 유사도)
   √d로 나누는 이유: 차원이 크면 내적 값이 커져 softmax가 극단으로 쏠리는 것을 완화.

2단계 — 비율로 변환:  α(i, j) = softmax_j( score(i, j) )
   점수들을 "합이 1인 비율"로 바꿈. 0.7 / 0.2 / 0.1 처럼.

3단계 — 가중합:      outputᵢ = Σⱼ α(i, j) · Vⱼ
   그 비율대로 각 토큰의 내용을 섞음.
```

`softmax`는 "실수 여러 개를 받아, 큰 값에 더 큰 비중을 주면서 전체 합이 1이 되도록 만드는 함수"입니다. 합이 1이라는 성질이 뒤에서 매우 중요해집니다(→ 07의 attention sink).

### Causal mask — 미래는 볼 수 없다

문장을 생성하는 모델(decoder)은 **자기보다 뒤에 오는 토큰을 볼 수 없습니다.** 아직 생성되지 않았으니까요. 그래서 1단계 점수 계산에서 `j > i`인 항을 `-∞`로 만듭니다. softmax를 통과하면 그 비율은 0이 됩니다.

```
          t1   t2   t3   t4
   t1 →   ■    ·    ·    ·      ■ = 볼 수 있음
   t2 →   ■    ■    ·    ·      · = 마스크됨 (미래)
   t3 →   ■    ■    ■    ·
   t4 →   ■    ■    ■    ■
```

이 삼각형 모양이 뒤에서 슬라이딩 윈도우와 비교될 기준 그림입니다.

### ⭐ 이 자료에서 가장 중요한 관찰: K와 V는 불변이다

토큰 3번의 K와 V는 **토큰 3번의 입력 벡터에만** 의존합니다. 나중에 토큰 4, 5, 6이 생겨도 토큰 3의 K·V는 바뀌지 않습니다.

- **Q는 매번 새로 필요합니다** — 새로 생성하는 토큰이 "무엇을 찾는지"는 그 토큰의 것이니까
- **K·V는 한 번 계산하면 영원히 같습니다** — 과거 토큰이 "무엇에 대한 정보이고 무슨 내용인지"는 변하지 않으니까

여기서 곧바로 따라옵니다: **K·V를 저장해두면 재계산이 필요 없다.** 그게 KV 캐시입니다(→ 03).

### 멀티헤드(Multi-Head)

위 계산을 한 벌만 하지 않고 여러 벌(head) 병렬로 합니다. 각 head가 서로 다른 종류의 관계를 잡도록 학습됩니다(어떤 head는 문법적 의존, 어떤 head는 지시 관계 등). head 수를 `n_heads`, 각 head의 벡터 차원을 `head_dim`이라 부릅니다.

```
전체 차원(hidden) = n_heads × head_dim
예) Llama 3.1 70B: 8192 = 64 × 128
```

`n_heads`와 `head_dim`은 KV 캐시 크기 공식에 직접 등장하므로 기억해두세요.

## 핵심 원리 2: 접기(fold) — 상태는 사건들의 함수다

### 무엇인가

프로그래밍에서 `fold`(또는 `reduce`)는 **목록을 하나의 값으로 접는 연산**입니다.

```javascript
// 목록 → 하나의 값
[1, 2, 3, 4].reduce((acc, x) => acc + x, 0)   // → 10
//            ↑ 접는 함수              ↑ 초기값
```

이 자료 전체를 관통하는 문장은 이것입니다.

> **상태 = fold(초기값, 사건들의 순서열)**

세 지층에서 각각 이렇게 나타납니다.

| 지층 | 사건들 | 접는 함수 | 결과 상태 |
|---|---|---|---|
| KV 캐시 | 토큰별 (K, V) | 어텐션 가중합 | 다음 토큰의 표현 |
| 이벤트 소싱 | 도메인 이벤트 | `apply(state, event)` | 애그리게이트 현재 상태 |
| 에이전트 | 메시지·도구 결과 | 모델의 forward pass | 다음 응답 |

### 왜 이게 중요한가

`fold`로 표현되는 상태는 **재계산 가능**합니다. 사건 목록만 남아 있으면 상태는 언제든 다시 만들 수 있습니다. 이 성질이 다음을 모두 가능하게 합니다.

- 특정 시점의 상태 복원 (사건을 그 지점까지만 접기)
- 새로운 관점의 상태 파생 (다른 접는 함수를 적용)
- 디버깅 (같은 사건열을 다시 접어 재현)
- **캐싱** (중간까지 접은 결과를 저장해두고 이어서 접기)

마지막 항목이 KV 캐시와 프롬프트 캐싱의 정체입니다.

## 핵심 원리 3: Append-only 로그

### 무엇인가

**끝에만 추가하고, 이미 쓴 것은 수정·삭제하지 않는** 저장 방식입니다.

```
[CRUD 방식]                  [Append-only 방식]
balance = 8000               1. 계좌개설
  ↑ UPDATE로 덮어씀           2. 입금 10000
  ↑ 이전 값은 사라짐          3. 결제 3000
                             4. 환불 1000
                             → balance는 위 4건을 접어서 도출 (8000)
```

### 왜 이득인가

세 가지가 동시에 따라옵니다.

1. **불변 = 캐시 가능.** 바뀌지 않는 데이터는 안심하고 저장·재사용할 수 있습니다. 무효화를 걱정할 필요가 없습니다.
2. **순서 = 재현 가능.** 같은 순서로 다시 접으면 같은 결과가 나옵니다.
3. **접두사 공유 가능.** 두 로그가 앞부분이 같다면, 그 앞부분의 접은 결과를 공유할 수 있습니다.

3번이 프롬프트 캐싱의 원리입니다(→ 06).

### 대가

**무한히 커집니다.** 그래서 스냅샷(재생 비용 절감)과 축출(용량 절감)이 필요해집니다. 이것이 02의 원리 3·4입니다.

## ⚠️ 용어 지뢰밭 — 같은 단어, 다른 뜻

이 자료는 세 개의 분야를 오갑니다. 같은 단어가 분야마다 다른 뜻으로 쓰이는 지점을 미리 못박아 둡니다. **여기서 헷갈리면 뒤 파일이 전부 흐려집니다.**

| 단어 | 뜻 A | 뜻 B | 구분 방법 |
|---|---|---|---|
| **프로젝션 (projection)** | 신경망의 선형 변환 — 입력 벡터에 행렬을 곱해 Q/K/V를 만드는 것 | 이벤트 소싱의 **읽기 모델** — 이벤트 스트림에서 파생시킨 조회용 뷰 | 03~07에서는 A, 08~09에서는 B |
| **캐시 (cache)** | KV 캐시 — 모델 내부의 계산 재사용 구조. **없으면 결과가 같고 느릴 뿐** | 애플리케이션 캐시 — 데이터 사본 | 03~06은 전자. "진실 원천인가?"로 구분 — KV 캐시는 파생물 |
| **컨텍스트 (context)** | 컨텍스트 윈도우 — 모델이 한 번에 볼 수 있는 토큰 수 (하드 제약) | 바운디드 컨텍스트 — DDD의 도메인 경계 | 08에만 후자가 등장 |
| **스냅샷 (snapshot)** | 이벤트 소싱 — N건마다 저장하는 상태 사본 (최적화) | 컨테이너/VM 이미지 | 이 자료는 전자만 |
| **상태 (state)** | 파생된 현재 값 (fold의 결과) | 진실 원천 | **이 자료에서 "상태"는 항상 파생물**입니다. 진실 원천은 로그 |
| **축출 (eviction)** | 캐시에서 항목을 내보내 메모리를 회수 | 데이터 삭제 | 축출은 진실 원천을 지우지 않음. 삭제는 지움 |

특히 마지막 두 줄이 핵심 인지 전환입니다. 평소 사고("상태가 진짜, 로그는 부산물")를 뒤집어야 이 자료가 읽힙니다.

## 자가 진단

각 질문을 먼저 스스로 답한 뒤 토글을 열어 비교하세요.

<details>
<summary>Q1: 왜 Q는 매번 새로 계산해야 하는데 K·V는 재사용할 수 있는가?</summary>

**즉답 예시**: Q는 "지금 생성하려는 토큰이 무엇을 찾는가"를 나타내므로 그 토큰의 것이고, 새 토큰마다 새로 필요합니다. K·V는 "각 과거 토큰이 무엇에 대한 정보이고 무슨 내용인가"를 나타내며, 각 토큰의 입력 벡터에만 의존합니다. 뒤에 새 토큰이 붙어도 과거 토큰의 입력은 변하지 않으므로 K·V도 변하지 않습니다. 따라서 저장해두고 재사용할 수 있습니다.

</details>

<details>
<summary>Q2: softmax의 "합이 1" 성질이 왜 중요한가? (뒤 파일에서 어떻게 쓰이는가)</summary>

**즉답 예시**: 어텐션 비율의 합이 1로 고정되어 있으므로, 모델은 "볼 만한 것이 없을 때도 어딘가에 비중을 줘야" 합니다. 이 제약 때문에 모델은 의미와 무관하게 특정 토큰(주로 맨 앞)에 점수를 몰아주는 배출구를 학습합니다 — attention sink. 그 토큰을 캐시에서 버리면 남은 토큰에 비율이 강제 재분배되면서 분포가 깨집니다(→ 07).

</details>

<details>
<summary>Q3: "상태 = fold(초기값, 사건열)"로 표현하면 무엇이 가능해지는가? 네 가지를 들라.</summary>

**즉답 예시**: (1) 특정 시점 상태 복원 — 사건을 그 지점까지만 접으면 됩니다. (2) 새 관점의 파생 — 다른 접는 함수를 적용해 새 뷰를 만들 수 있습니다. (3) 재현·디버깅 — 같은 사건열을 다시 접으면 같은 결과가 나옵니다. (4) 캐싱 — 중간까지 접은 결과를 저장해두고 이어서 접을 수 있습니다. KV 캐시와 프롬프트 캐싱이 (4)의 사례입니다.

</details>

<details>
<summary>Q4: 이 자료에서 "프로젝션"과 "캐시"는 각각 두 가지 뜻으로 쓰인다. 어떻게 구분하는가?</summary>

**즉답 예시**: 프로젝션 — 03~07(KV 캐시·SWA 파트)에서는 신경망의 선형 변환(입력에 행렬을 곱해 Q/K/V 생성), 08~09(이벤트 소싱·에이전트 파트)에서는 이벤트 스트림에서 파생시킨 조회용 읽기 모델입니다. 캐시 — "진실 원천인가?"로 구분합니다. KV 캐시는 파생물(없어도 결과가 같고 느릴 뿐)이고, 애플리케이션 캐시는 원본 데이터의 사본입니다.

</details>

<details>
<summary>Q5: append-only 로그가 주는 이득 세 가지와, 그 대가로 생기는 문제는 무엇인가?</summary>

**즉답 예시**: 이득 — (1) 불변이므로 안심하고 캐시할 수 있다(무효화 걱정 없음), (2) 순서가 보존되므로 재현 가능하다, (3) 앞부분이 같은 두 로그는 접두사의 접은 결과를 공유할 수 있다. 대가 — 무한히 커진다. 그래서 스냅샷(재생 비용 절감)과 축출(용량 절감)이 필요해진다.

</details>
