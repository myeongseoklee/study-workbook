# 02. 관통 4원리 — 축적 · 접기 · 스냅샷 · 축출

## 학습 목표

이 파일을 다 읽으면 KV 캐시·이벤트 소싱·에이전트 컨텍스트를 **네 개의 같은 원리의 세 구현**으로 볼 수 있습니다. 이후 파일들은 이 네 원리에 살을 붙이는 작업입니다.

## 선수 지식

- [01-prerequisites.md](01-prerequisites.md) 전체 — 특히 fold와 append-only 로그, 그리고 용어 지뢰밭

---

## 네 원리가 왜 네 개인가

원리들은 독립적이지 않습니다. **앞의 원리가 뒤의 원리를 필연적으로 요구합니다.**

```
① 축적 (append-only로 쌓는다)
      │  쌓기만 하면 상태를 어떻게 얻는가?
      ▼
② 접기 (fold로 상태를 도출한다)
      │  로그가 길어지면 접는 비용이 선형으로 커진다
      ▼
③ 스냅샷 (중간 결과를 저장해 재생을 건너뛴다)
      │  스냅샷을 떠도 로그 자체는 계속 커진다
      ▼
④ 축출 (오래된 것을 버린다)
      │  그런데 아무거나 버리면 망가진다 → 앵커를 남긴다
      ▼
     (다시 ①로: 남은 로그에 계속 쌓는다)
```

이 순환을 기억하면 어느 지층에서든 "지금 어느 원리를 다루고 있는가"를 알 수 있습니다.

---

## 원리 ①: 축적 — 덮어쓰지 않고 추가한다

### 왜 이게 중요한가

**덮어쓰기는 정보를 파괴합니다.** `UPDATE balance = 8000`은 "왜 8000이 되었는가"를 지웁니다. 그리고 정보가 파괴되면 되돌릴 수 없습니다.

반면 추가만 하면 세 가지 성질이 공짜로 따라옵니다.

| 성질 | 왜 따라오는가 | 실무 효과 |
|---|---|---|
| **불변성** | 이미 쓴 것을 안 바꾸므로 | 무효화 걱정 없이 캐시 가능 |
| **순서** | 추가 순서가 곧 시간 순서 | 재현·재생 가능 |
| **접두사 공유** | 두 로그의 앞부분이 같다면 같은 바이트 | 앞부분의 계산 결과를 공유 가능 |

### 메커니즘

```
KV 캐시:      토큰 생성 → (K, V) 계산 → 캐시 배열 끝에 append
이벤트 소싱:   커맨드 검증 → 이벤트 생성 → events 테이블에 INSERT (UPDATE 없음)
에이전트:      턴 종료 → 메시지 배열 끝에 append (과거 메시지 수정 안 함)
```

### 트레이드오프

| 얻는 것 | 포기하는 것 |
|---|---|
| 불변·재현·접두사 공유 | 저장 공간이 단조 증가 |
| 완전한 이력 | 잘못 쓴 것을 지울 수 없음 (보정 항목을 새로 추가해야 함) |
| 동시성 제어가 단순 (append 지점만 경합) | 조회 성능이 나쁨 (매번 접어야 함 → 원리 ②③이 필요) |

### ⚠️ 축적 원리의 규율: 앞부분을 건드리지 마라

세 지층 모두에서 **앞부분 수정은 최악의 연산**입니다.

- KV 캐시 / 프롬프트 캐싱: 프리픽스 한 바이트만 바뀌면 그 뒤 전체가 무효 (→ 06)
- 이벤트 소싱: 과거 이벤트 수정은 그것을 접어 만든 모든 프로젝션을 오염
- 에이전트: 시스템 프롬프트 편집은 대화 전체의 캐시를 파괴

**설계 원칙**: 안정적인 것을 앞에, 변동하는 것을 뒤에 둡니다. 이 한 문장이 실무에서 가장 자주 쓰입니다.

## 원리 ②: 접기 — 상태는 진실 원천이 아니라 파생물이다

### 왜 이게 중요한가

이것은 **인지 전환**입니다. 평소 우리는 "상태가 진짜고 로그는 부산물(감사 로그)"이라고 생각합니다. 네 원리는 그 반대를 요구합니다.

> 로그가 진실 원천이고, 상태는 로그를 접은 결과다.

이 전환이 되면 이후 모든 것이 자연스러워집니다. 캐시를 지워도 되는 이유(다시 접으면 됨), 스냅샷이 최적화일 뿐인 이유(진실 원천이 아님), 새 뷰를 나중에 만들 수 있는 이유(다르게 접으면 됨)가 모두 여기서 나옵니다.

### 메커니즘

```
state = initial
for event in log:
    state = apply(state, event)
```

지층별 `apply`가 무엇인지:

| 지층 | `apply(state, event)` |
|---|---|
| KV 캐시 | 어텐션: 새 Q와 캐시된 모든 K로 점수 → softmax → V 가중합 |
| 이벤트 소싱 | 도메인 로직: `AccountOpened` → 계좌 생성, `Deposited` → 잔액 증가 |
| 에이전트 | 모델의 forward pass: 전체 메시지 배열 → 다음 응답 |

### 트레이드오프

| 얻는 것 | 포기하는 것 |
|---|---|
| 시점 복원, 사후 파생, 재현 | 조회할 때마다 접어야 함 → O(로그 길이) |
| 상태를 안심하고 버릴 수 있음 | 접는 함수가 바뀌면 과거 결과와 달라질 수 있음 |

두 번째 항목이 실무 함정입니다. 이벤트 소싱에서 `apply` 로직을 바꾸면 과거 이벤트를 재생한 결과가 예전과 달라집니다. 그래서 재생 결정론성(deterministic replay)이 규율로 요구됩니다(→ 08).

## 원리 ③: 스냅샷 — 재생 비용을 자른다, 진실 원천은 건드리지 않는다

### 왜 이게 중요한가

원리 ②를 그대로 쓰면 로그가 10만 건일 때 매번 10만 번 접어야 합니다. 비현실적입니다.

**스냅샷은 "여기까지 접은 결과"를 저장해둔 것입니다.** 이후에는 `스냅샷 + 그 뒤 이벤트`만 접으면 됩니다.

```
[스냅샷 없음]  ev1 ev2 ev3 ... ev99998 ev99999 ev100000   → 10만 번 접기
[스냅샷 있음]  [snapshot@99900] + ev99901...ev100000       → 100번 접기
```

### ⭐ 스냅샷의 철칙: 최적화일 뿐, 진실 원천이 아니다

스냅샷을 전부 지워도 시스템은 **느려질 뿐 틀리지 않습니다.** 로그로부터 다시 만들 수 있으니까요.

이 성질을 잃으면 안 됩니다. 스냅샷을 진실 원천으로 취급하기 시작하면(예: 스냅샷만 남기고 로그를 지우면) 원리 ②가 무너지고, 시점 복원·사후 파생·재현이 모두 사라집니다.

### 세 지층의 스냅샷

| 지층 | 스냅샷의 형태 | 진실 원천은 여전히 |
|---|---|---|
| KV 캐시 | **KV 캐시 자체가 스냅샷** — "여기까지의 K·V" | 토큰 시퀀스 (다시 prefill하면 재생성됨) |
| 프롬프트 캐싱 | 접두사 구간의 KV | 요청 본문의 프롬프트 텍스트 |
| 이벤트 소싱 | N건마다 저장한 애그리게이트 상태 | events 테이블 |
| 에이전트 | 대화 압축(compaction) 결과 요약 | 원본 대화 이력 (보관했다면) |

에이전트 줄에 단서가 붙은 것에 주의하세요. **압축 후 원본을 버리면 그것은 스냅샷이 아니라 축출입니다** — 되돌릴 수 없습니다. 이 구분이 09의 핵심 판단 중 하나입니다.

### 트레이드오프

| 얻는 것 | 포기하는 것 |
|---|---|
| 재생 비용 감소 | 저장 공간 추가 |
| 시작 지연 감소 | 스냅샷 스키마가 `apply` 로직에 결합됨 — 로직 변경 시 스냅샷 무효화 필요 |

## 원리 ④: 축출 — 무엇을 버리고, 무엇은 절대 남기는가

### 왜 이게 중요한가

스냅샷은 **재생 비용**을 줄이지만 **로그 자체의 크기**는 줄이지 않습니다. 무한 스트림(끝없는 대화, 끝없는 생성)에서는 결국 버려야 합니다.

여기서 두 가지 질문이 갈립니다.

1. **얼마나 남기나** — 창 크기(W), 컨텍스트 예산
2. **무엇을 절대 버리면 안 되나** — 앵커(anchor)

### ⭐ 2번이 이 자료에서 가장 반직관적인 지점입니다

"오래된 것부터 버린다"는 당연해 보이지만, 세 지층 모두에서 **순진하게 앞에서부터 버리면 시스템이 급격히 망가집니다.**

| 지층 | 순진하게 앞부터 버리면 | 원인 | 처방 |
|---|---|---|---|
| KV 캐시 | perplexity가 급등 (10~100배 관측) | 맨 앞 토큰이 attention sink — softmax의 비중 배출구 역할 | 앞 4개 토큰의 KV를 영구 고정 (→ 07) |
| 에이전트 컨텍스트 | 지시 위반, 도구 오사용, 페르소나 붕괴 | 시스템 프롬프트·도구 정의가 행동의 앵커 | 앞부분 고정, 뒤에서만 축출 |
| 이벤트 소싱 | 상태 재구성 불가 | 이벤트는 상태의 유일한 근거 | 축출 대신 스냅샷 + 아카이브. **삭제는 최후수단** |

세 줄이 같은 구조를 말합니다. **앞부분에는 "적은 양이지만 없으면 전체가 망가지는 것"이 있습니다.** 그것을 식별하고 고정하는 것이 축출 설계의 절반입니다.

### 축출의 세 가지 형태

| 형태 | 방식 | 되돌릴 수 있나 |
|---|---|---|
| **슬라이딩 윈도우** | 최근 W개만 유지, 오래된 것 덮어쓰기 | ❌ |
| **선택적 축출** | 중요도 점수로 선별해 버리기 | ❌ |
| **오프로드** | 느린 저장장치로 옮기기 (버리지 않음) | ✅ |

오프로드는 엄밀히 축출이 아니라 **계층화**입니다. 지연을 대가로 정보를 보존합니다(→ 03의 저장 위치, 09의 외부 메모리).

### 트레이드오프

| 얻는 것 | 포기하는 것 |
|---|---|
| 고정된 메모리 상한 | 창 밖 정보의 정확한 회수 능력 |
| 무한 스트림 처리 가능 | 되돌릴 수 없음 (오프로드 제외) |

## 세 지층 종합 매핑

| | ① 축적 | ② 접기 | ③ 스냅샷 | ④ 축출 |
|---|---|---|---|---|
| **KV 캐시** | 토큰별 (K,V) append | 어텐션 가중합 | 캐시 자체 / 프롬프트 캐싱 | 슬라이딩 윈도우 + sink 고정 |
| **이벤트 소싱** | events 테이블 INSERT | `apply(state, ev)` 리플레이 | N건마다 상태 저장 | 아카이브·보존 정책 (삭제 지양) |
| **에이전트 컨텍스트** | 메시지 배열 append | 모델 forward pass | compaction 요약 | 컨텍스트 편집 + 프롬프트 고정 |

## ⚠️ 암기 필수

- [ ] **네 원리의 순환**: 축적 → 접기 → 스냅샷 → 축출 → (축적). 앞이 뒤를 필연적으로 요구한다
  - 이유: 어떤 시스템의 상태 설계를 검토할 때 빠진 원리를 찾는 체크리스트가 된다
- [ ] **상태는 파생물, 로그가 진실 원천** — 이 전환이 안 되면 나머지가 안 읽힌다
  - 이유: 캐시를 지워도 되는 이유, 스냅샷이 최적화일 뿐인 이유가 모두 여기서 나온다
- [ ] **스냅샷을 전부 지워도 시스템은 느려질 뿐 틀리지 않는다** — 이 성질을 잃으면 스냅샷이 아니다
  - 이유: 압축 후 원본을 버리는 설계가 스냅샷이 아니라 축출이라는 판단의 근거
- [ ] **안정적인 것을 앞에, 변동하는 것을 뒤에** — 세 지층 공통 배치 규율
  - 이유: 프롬프트 캐시 적중, 프로젝션 오염 방지, 컨텍스트 축출 안전성이 모두 이 배치에 달려 있다
- [ ] **앞부분에는 "적지만 없으면 전체가 망가지는 것"이 있다** (attention sink / 시스템 프롬프트 / 초기 이벤트)
  - 이유: 축출 정책을 설계할 때 가장 먼저 확인할 항목. 순진한 FIFO 축출이 시스템을 깨뜨리는 원인

## 자가 진단

<details>
<summary>Q1: 스냅샷과 축출의 결정적 차이는 무엇인가?</summary>

**즉답 예시**: 스냅샷은 **되돌릴 수 있고** 축출은 되돌릴 수 없습니다. 스냅샷은 로그로부터 다시 만들 수 있는 파생물이므로 전부 지워도 시스템은 느려질 뿐 틀리지 않습니다. 축출은 정보를 실제로 버리므로 그 정보에 의존하는 질문에 더 이상 답할 수 없습니다. 그래서 "대화를 요약하고 원본을 버리는" 설계는 스냅샷처럼 보이지만 실제로는 축출입니다.

</details>

<details>
<summary>Q2: 왜 세 지층 모두에서 "앞부분 수정"이 최악의 연산인가?</summary>

**즉답 예시**: 상태가 로그를 앞에서부터 접은 결과이기 때문입니다. 위치 N을 수정하면 N 이후의 모든 접은 결과가 달라지므로, N 이후에 저장해둔 모든 중간 결과(캐시·스냅샷·프로젝션)가 무효가 됩니다. 반면 끝에 추가하는 것은 이전 결과를 전혀 건드리지 않습니다. 그래서 "안정적인 것을 앞에, 변동하는 것을 뒤에" 배치하는 것이 세 지층 공통 규율입니다.

</details>

<details>
<summary>Q3: 오프로드는 왜 엄밀히 축출이 아닌가?</summary>

**즉답 예시**: 축출은 정보를 버리고, 오프로드는 더 느린 저장 계층으로 옮길 뿐 보존합니다. 그래서 오프로드는 되돌릴 수 있습니다(필요할 때 다시 불러오면 됩니다) — 대가는 용량이 아니라 지연입니다. 엄밀히는 축출이 아니라 계층화(tiering)입니다.

</details>

<details>
<summary>Q4: "네 원리의 순환"을 이용해, 이벤트 소싱을 도입했지만 조회가 느린 시스템을 진단해보라.</summary>
