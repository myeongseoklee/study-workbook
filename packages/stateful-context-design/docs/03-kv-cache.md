## 핵심 원리: KV 캐시는 원리 ③(스냅샷)의 GPU 구현이다

토큰 시퀀스가 로그이고, 어텐션이 접는 함수이며, **KV 캐시는 "여기까지 접기 위한 중간 결과"를 저장한 스냅샷**입니다.

원리 ③의 철칙이 그대로 적용됩니다: **KV 캐시를 전부 지워도 결과는 같습니다. 다시 계산하면 되니까요.** 느려질 뿐 틀리지 않습니다. 이 성질이 오프로드·양자화·재계산 같은 기법이 모두 정당한 이유입니다 — 진실 원천을 건드리지 않으니까요.

## 필수 지식 1: 시간복잡도는 왜 그렇게 계산되는가

기호를 먼저 고정합니다.

| 기호 | 의미 |
|---|---|
| `n` | 현재까지의 시퀀스 길이 |
| `N` | 최종 생성 길이 |
| `d` | 모델 차원 (hidden size) |
| `L` | 레이어 수 |

한 레이어에서 일어나는 일은 두 부류입니다.

- **projection** — 각 토큰의 입력 벡터에 행렬을 곱해 Q/K/V를 만드는 것. 토큰 1개당 `O(d²)`
- **attention** — 토큰 쌍 사이 점수를 내고 가중합하는 것. 토큰 쌍 1개당 `O(d)`

### 캐시가 없을 때

n번째 토큰을 생성하려면 **시퀀스 전체를 처음부터 다시 forward** 해야 합니다. 과거 토큰의 K·V가 메모리에 없으니까요.

```
projection:  n개 토큰 × O(d²)                    = O(n·d²)
attention:   토큰 i가 1..i를 봄 → 쌍의 총수 = Σᵢ i ≈ n²/2
             n²/2 쌍 × O(d)                     = O(n²·d)
─────────────────────────────────────────────────────────
한 스텝 비용:                                     O(n²·d + n·d²)
```

여기서 `n`이 커지면 `n²·d` 항이 지배합니다. 그리고 N개 토큰을 전부 생성하려면 이 스텝을 n=1부터 N까지 반복하니:

```
전체 비용 = Σ_{n=1}^{N} O(n²·d) = O(N³·d)
```

**세제곱입니다.** 생성 길이가 2배가 되면 비용은 8배가 됩니다.

### 캐시가 있을 때

과거 토큰의 K·V가 이미 메모리에 있으므로 **새 토큰 하나만** 처리합니다.

```
projection:  새 토큰 1개 × O(d²)                  = O(d²)
attention:   새 Q 1개가 캐시된 n개 K를 봄 → n쌍
             n쌍 × O(d)                          = O(n·d)
─────────────────────────────────────────────────────────
한 스텝 비용:                                      O(n·d + d²)
```

N개 전부 생성하면:

```
전체 비용 = Σ_{n=1}^{N} O(n·d) = O(N²·d)
```

### 정리 — 두 가지 층위를 구분하라

여기서 혼동이 자주 발생합니다. **스텝당 복잡도와 전체 복잡도는 다릅니다.**

| | 스텝당 (n번째 토큰) | 전체 (N개 생성) |
|---|---|---|
| 캐시 없음 | `O(n²·d)` | `O(N³·d)` |
| 캐시 있음 | `O(n·d)` | `O(N²·d)` |
| **절감 배수** | **n배** | **N배** |

"KV 캐시가 O(n²)을 O(n)으로 만든다"는 흔한 요약은 **스텝당** 이야기입니다. 전체로 보면 세제곱이 제곱이 됩니다.

**남은 제곱은 없앨 수 없습니다.** n번째 토큰이 앞의 n개를 봐야 한다는 것은 어텐션의 정의이므로, 캐시로 제거되는 것은 *재계산*뿐이고 *필연적 계산*은 남습니다. 이 남은 `O(N²·d)`를 줄이려면 아예 볼 대상을 줄여야 합니다 — 그것이 슬라이딩 윈도우입니다(→ 07).

## 필수 지식 2: 캐시 크기 공식은 왜 그런 항들의 곱인가

공식을 외우지 말고 **한 항씩 쌓아 올리세요.**

```
① 토큰 1개, 레이어 1개, 헤드 1개의 K 벡터        = head_dim 개의 값
② K와 V 둘 다 저장해야 하므로                    × 2
③ KV 헤드가 n_kv개 있으므로                      × n_kv
④ 레이어가 L개 있고 각 레이어가 자기 K·V를 가지므로 × L
⑤ 토큰이 s개 있으므로                            × s
⑥ 요청을 b개 동시 처리하므로                      × b
⑦ 값 하나를 몇 바이트로 저장하는지                × bytes_per_value
```

곱하면:

```
KV 캐시 크기 = 2 × L × n_kv × head_dim × s × b × bytes
               ↑    ↑    ↑        ↑        ↑   ↑    ↑
             K와V 레이어 KV헤드  헤드차원  길이 배치 정밀도
```

각 항이 왜 필요한지가 위 ①~⑦에 다 있습니다. **④를 놓치는 실수가 가장 흔합니다** — 어텐션은 레이어마다 독립적으로 일어나므로 레이어 수만큼 캐시가 곱해집니다.

### 정밀도별 바이트 수

| dtype | bytes | 용도 |
|---|---|---|
| FP32 | 4 | 거의 안 씀 |
| FP16 / BF16 | 2 | **기본값** |
| FP8 | 1 | KV 양자화 (→ 04) |
| INT4 | 0.5 | 공격적 KV 양자화 |

### 실제 계산 — Llama 3.1 70B

공개된 구성값입니다.

| 항목 | 값 |
|---|---|
| 레이어 수 (`L`) | 80 |
| Query 헤드 수 | 64 |
| **KV 헤드 수 (`n_kv`)** | **8** (GQA) |
| head_dim | 128 |
| hidden size | 8192 (= 64 × 128) |

**토큰 1개당 캐시 크기** (fp16, 배치 1):

```
2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes = 320 KB
```

여기서 규모 감각이 나옵니다.

| 시나리오 | 계산 | KV 캐시 |
|---|---|---|
| 8K 컨텍스트, 배치 1 | 320KB × 8,192 | **2.5 GB** |
| 128K 컨텍스트, 배치 1 | 320KB × 131,072 | **40 GB** |
| 8K 컨텍스트, 배치 16 | 2.5GB × 16 | **40 GB** |

마지막 두 줄이 같은 40 GB인 것에 주의하세요. **긴 컨텍스트 1개와 짧은 컨텍스트 16개는 메모리 관점에서 동등합니다.** 이것이 서빙 시 "동시 처리 개수(batch)와 컨텍스트 길이가 같은 예산을 나눠 쓴다"는 의미입니다.

### GQA가 없었다면

같은 모델이 MHA(`n_kv` = Query 헤드 수 = 64)였다면:

```
토큰당: 320 KB × 8 = 2.5 MB
128K 컨텍스트: 2.5MB × 131,072 ≈ 320 GB
```

**H100 80GB 4장을 KV 캐시만으로 채웁니다.** GQA 없이 긴 컨텍스트는 성립하지 않습니다 — 이것이 04의 출발점입니다.

### 핵심 성질: 시퀀스 길이에 **선형**

공식에서 `s`는 1차항입니다. 어텐션 **연산**은 시퀀스에 제곱으로 늘지만 **캐시 메모리**는 선형으로 늡니다. 이 차이가 두 종류의 병목을 만듭니다(→ 05).

## 필수 지식 3: 캐시는 어디에 저장되는가

### 기본 위치: GPU HBM

KV 캐시는 **모델 가중치와 같은 GPU 메모리(HBM, High Bandwidth Memory)** 에 있습니다. 이유는 단순합니다 — 매 토큰마다 캐시 전체를 읽어야 하므로, 연산이 일어나는 곳과 같은 메모리에 있어야 합니다.

HBM 예산은 이렇게 나뉩니다.

```
┌─────────────────────── GPU HBM ───────────────────────┐
│ 모델 가중치        70B × 2 bytes(fp16) = 140 GB       │  ← 고정
│ KV 캐시            위 계산에 따라 가변                 │  ← 요청량에 따라 변동
│ 활성값(activation) 순간적으로 필요한 중간 계산값        │
│ 단편화·예약 여유                                       │
└───────────────────────────────────────────────────────┘
```

70B fp16 가중치만 140 GB이므로 **단일 H100 80GB로는 모델조차 안 들어갑니다.** 여러 GPU에 나눠 올리고(텐서 병렬), 그 나머지 공간을 KV 캐시가 씁니다. 그래서 "동시 처리 가능 요청 수"는 결국 `(HBM 총량 − 가중치 − 활성값) ÷ 요청당 KV 캐시`로 결정됩니다.

### 오프로드 — 왜 쉽지 않은가

CPU DRAM이나 NVMe로 캐시를 내보내면 용량은 늘어납니다. 문제는 대역폭입니다.

| 계층 | 대역폭 자릿수 | 특징 |
|---|---|---|
| GPU HBM | **TB/s** 단위 | 연산과 같은 위치 |
| CPU DRAM (PCIe 경유) | **수십 GB/s** 단위 | HBM 대비 대략 50배 이상 느림 |
| NVMe SSD | **수 GB/s** 단위 | 더 느림 |

정확한 수치는 GPU·플랫폼 세대마다 다르므로 벤더 스펙을 확인해야 하지만, **자릿수 격차 자체가 결론을 정합니다**: decode 단계는 토큰 하나 만들 때마다 캐시 전체를 읽으므로(→ 05), 캐시를 느린 계층에 두면 토큰 생성 속도가 그 계층의 대역폭에 직접 묶입니다.

그래서 오프로드는 이렇게 쓰입니다.

- ✅ **긴 컨텍스트의 앞부분** — 자주 안 쓰는 구간을 내려두고 필요할 때만 올림
- ✅ **prefill 결과의 세션 간 재사용** — 다음 요청까지 어딘가 보관해야 함 (프롬프트 캐싱의 백엔드)
- ❌ **활발히 decode 중인 시퀀스의 캐시** — 매 토큰 왕복이 발생해 실용성 없음

**02의 용어로**: 오프로드는 축출이 아니라 **계층화**입니다. 정보를 버리지 않고 지연을 대가로 보존합니다.

## 우리 프로젝트와의 연결

`cc-system` 하네스에서 이 계산이 직접 쓰이는 지점:

- **서브에이전트 병렬 개수** — 워크플로에서 동시에 띄우는 에이전트 수는 위 "배치 × 컨텍스트" 예산과 같은 구조의 제약을 받습니다. 각 에이전트가 긴 컨텍스트를 들고 있으면 병렬도가 줄고, 짧으면 늘어납니다.
- **긴 캐시 파일을 에이전트 입력으로 넘길 때** — `.cc-system/cache/*.md` 산출물을 그대로 프롬프트에 붙이면 그 길이가 선형으로 메모리·비용에 반영됩니다. 포인터로 위임하는 설계(compose-handover의 "포인터 우선 원칙")는 이 비용을 직접 줄입니다.

## ⚠️ 암기 필수

- [ ] **KV 캐시 크기 = 2 × L × n_kv × head_dim × s × b × bytes** — 7개 항의 의미까지
  - 이유: 모델 구성값만 보고 "이 컨텍스트 길이를 이 GPU에서 감당할 수 있나"를 즉시 판단하는 유일한 도구
- [ ] **캐시 메모리는 시퀀스에 선형, 어텐션 연산은 제곱** — 둘이 다르다
  - 이유: 병목이 메모리인지 연산인지 가르는 근본 원인 (→ 05의 prefill/decode 비대칭)
- [ ] **스텝당 O(n²d)→O(nd), 전체 O(N³d)→O(N²d)** — 층위를 섞지 말 것
  - 이유: "O(n²)를 O(n)으로"라는 요약이 스텝당 이야기임을 알아야 남은 제곱의 정체를 이해할 수 있다
- [ ] **KV 캐시는 GPU HBM에 있고, 모델 가중치와 예산을 나눠 쓴다**
  - 이유: 동시 처리 가능 요청 수 = (HBM − 가중치 − 활성값) ÷ 요청당 캐시. 용량 계획의 기본식

## 자가 진단

<details>
<summary>Q1: KV 캐시 크기 공식에서 "× L (레이어 수)"이 왜 필요한가?</summary>

**즉답 예시**: 어텐션은 레이어마다 독립적으로 일어나고, 각 레이어는 자기만의 K·V projection 가중치를 가집니다. 즉 레이어 1의 K와 레이어 2의 K는 완전히 다른 값이며 둘 다 저장해야 합니다. 그래서 토큰 하나가 차지하는 캐시는 한 레이어 분량의 L배입니다. 이 항을 빼먹으면 80레이어 모델의 캐시를 80배 작게 추정하게 됩니다.

</details>

<details>
<summary>Q2: "8K 컨텍스트 배치 16"과 "128K 컨텍스트 배치 1"의 KV 캐시가 같은 이유는?</summary>

**즉답 예시**: 공식에서 `s`와 `b`가 모두 1차항으로 곱해지므로, 둘의 곱이 같으면 캐시 크기도 같습니다(8192 × 16 = 131,072 × 1). 실무 함의는 "긴 컨텍스트 지원과 높은 동시 처리량은 같은 메모리 예산을 나눠 쓰는 경쟁 관계"라는 것입니다. 컨텍스트 상한을 늘리면 동시 요청 수가 줄어듭니다.

</details>

<details>
<summary>Q3: 캐시가 있어도 여전히 O(N²·d)가 남는 이유는 무엇이고, 그걸 줄이려면 무엇을 해야 하는가?</summary>

**즉답 예시**: n번째 토큰이 앞의 n개 토큰을 모두 봐야 한다는 것은 어텐션의 정의입니다. 캐시가 없애주는 것은 과거 K·V의 *재계산*뿐이고, "새 Q가 n개의 K와 점수를 낸다"는 *필연적 계산*은 남습니다. 이걸 줄이려면 볼 대상 자체를 줄여야 합니다 — 최근 W개만 보게 하는 슬라이딩 윈도우가 그 방법이고, 그러면 스텝당 비용이 `O(W·d)`로 상수화됩니다.

</details>

<details>
<summary>Q4: 활발히 decode 중인 시퀀스의 KV 캐시를 CPU 메모리로 오프로드하면 무슨 일이 생기는가?</summary>

**즉답 예시**: decode는 토큰 하나를 만들 때마다 캐시 전체를 읽으므로, 매 토큰마다 CPU↔GPU 왕복이 발생합니다. PCIe 대역폭은 HBM보다 자릿수로 느리기 때문에 토큰 생성 속도가 PCIe 대역폭에 직접 묶여 실용성이 없어집니다. 오프로드는 자주 접근하지 않는 구간(긴 컨텍스트의 앞부분)이나 세션 간 보관(프롬프트 캐싱 백엔드)에 적합합니다.

</details>
