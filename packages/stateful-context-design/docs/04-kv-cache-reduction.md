# 04. KV 캐시 절감 기법 — 공식의 각 항을 공격하기

## 학습 목표

이 파일을 다 읽으면 절감 기법들을 "공식의 어느 항을 줄이는가"로 분류할 수 있고, 각 기법이 **무엇을 대가로 지불하는지** 말할 수 있습니다. 새 기법을 만나도 같은 틀로 배치할 수 있게 됩니다.

## 선수 지식

- [03-kv-cache.md](03-kv-cache.md)의 캐시 크기 공식과 7개 항의 의미

---

## 핵심 원리: 기법의 지도는 공식이 그려준다

절감 기법은 종류가 많아 보이지만, **모두 아래 공식의 특정 항을 공격**합니다.

```
KV 캐시 = 2 × L × n_kv × head_dim × s × b × bytes
              ▲    ▲        ▲       ▲   ▲    ▲
              │    │        │       │   │    └── ⑤ 양자화
              │    │        │       │   └─────── ④ 접두사 공유
              │    │        │       └─────────── ③ 슬라이딩 윈도우·축출 (→ 07)
              │    └────────┴─────────────────── ① MQA / GQA / MLA
              └──────────────────────────────── ② 크로스레이어 공유
                                          + ⑥ PagedAttention (항이 아니라 낭비를 줄임)
```

이 지도를 머리에 넣으면 "이 기법이 무엇을 줄이는가"를 항상 즉답할 수 있습니다.

---

## ① `n_kv`를 줄인다 — MQA / GQA / MLA

이 계열이 **가장 큰 효과**를 냅니다. `n_kv`는 8배, 16배 단위로 줄일 수 있는 항이기 때문입니다.

### MHA → MQA → GQA의 스펙트럼

표준 어텐션(MHA)은 Query 헤드마다 자기 K·V 헤드를 가집니다. Query 헤드가 64개면 K·V 헤드도 64개입니다.

```
MHA (n_kv = 64)          MQA (n_kv = 1)           GQA (n_kv = 8)
Q1 Q2 Q3 ... Q64         Q1 Q2 Q3 ... Q64         Q1..Q8  Q9..Q16  ...
│  │  │      │            └──┴──┴──────┘            └──┬──┘  └──┬──┘
K1 K2 K3 ... K64              KV(1개 공유)             KV1      KV2   ...(8개)
= 캐시 100%              = 캐시 1/64                = 캐시 1/8
```

**MQA**(Multi-Query Attention)는 모든 Query 헤드가 **단 하나의** K·V 헤드를 공유합니다. 캐시가 극적으로 줄지만 품질이 떨어집니다 — 서로 다른 관계를 잡던 head들이 같은 색인·내용을 보게 되니까요.

**GQA**(Grouped-Query Attention)는 그 중간입니다. Query 헤드를 G개 그룹으로 나누고, **그룹마다 하나의** K·V 헤드를 공유합니다. `G=1`이면 MQA, `G=헤드수`면 MHA이므로 GQA는 둘을 포함하는 일반형입니다.

GQA 논문의 핵심 기여는 두 가지입니다: 기존 MHA 체크포인트를 **원래 사전학습 연산의 약 5%** 로 uptraining해서 GQA로 전환하는 레시피, 그리고 그 결과가 **MHA에 가까운 품질과 MQA에 가까운 속도**를 동시에 낸다는 것입니다. 처음부터 다시 학습할 필요가 없다는 점이 채택을 결정했습니다 — 그래서 현재 Llama·Mistral 계열의 사실상 표준입니다.

Llama 3.1 70B의 `n_kv=8`이 바로 이것입니다. Query 64개를 8그룹으로 묶어 **캐시를 8분의 1로** 줄였습니다(03의 320KB vs 2.5MB 대비).

### MLA — 다른 방향의 해법

**MLA**(Multi-head Latent Attention, DeepSeek-V2)는 헤드를 공유하는 대신 **K·V를 저차원 잠재 벡터로 압축해서 저장**합니다. 캐시에는 압축된 벡터만 들어가고, 어텐션 계산 시점에 필요한 형태로 복원합니다.

```
[GQA]  헤드 수를 줄여서 저장량 감소       → 표현력을 헤드 공유로 지불
[MLA]  차원을 압축해서 저장량 감소        → 표현력을 저차원 병목으로 지불 + 복원 연산 추가
```

DeepSeek-V2 논문은 DeepSeek 67B 대비 **KV 캐시 93.3% 감소**와 **최대 생성 처리량 5.76배**를 보고합니다. 압축비 자체는 `(128×128)/512 = 32`배(약 96.9% 감소)이지만, 위치 인코딩 처리 등 구현상 필요한 부분 때문에 실측은 93.3%입니다.

### 비교

| 기법 | `n_kv` 효과 | 얻는 것 | 포기하는 것 | 대표 모델 |
|---|---|---|---|---|
| **MHA** | 기준 | 최대 표현력 | 캐시 폭발 | 초기 GPT 계열 |
| **MQA** | 1/64 수준 | 최대 절감 | 품질 저하 명확 | (단독 사용 드묾) |
| **GQA** | 1/8 수준 | 품질≈MHA, 속도≈MQA, uptraining 가능 | 중간 절감 | Llama 3.x, Mistral |
| **MLA** | 실측 93.3% 감소 | 최대 절감 + 품질 유지 | 구현 복잡도, 복원 연산 | DeepSeek-V2/V3 |

## ② `L`을 줄인다 — 크로스레이어 공유

여러 레이어가 **하나의 K·V를 공유**하게 만드는 접근입니다. 공식의 `L`이 실효적으로 줄어듭니다.

효과는 크지만 대가도 큽니다 — 레이어마다 다른 추상 수준의 관계를 잡던 것이 뭉개집니다. 그래서 보통 **전 레이어가 아니라 일부 구간에만** 적용하거나, 하이브리드 어텐션의 global 레이어 쪽에만 적용합니다(→ 07).

이 축은 아직 GQA만큼 표준화되지 않았으므로, 실무에서는 "선택 가능한 옵션이 있다" 정도로 알아두면 충분합니다.

## ④ `b`의 중복을 없앤다 — 접두사 공유 (Prefix Sharing)

배치 안의 여러 요청이 **같은 앞부분**을 가지는 경우가 매우 흔합니다.

```
요청 A: [긴 시스템 프롬프트 3000토큰] + "파리 날씨 알려줘"
요청 B: [긴 시스템 프롬프트 3000토큰] + "런던 인구 알려줘"
        └──────── 완전히 동일 ────────┘
```

순진하게 처리하면 3000토큰의 KV를 두 번 저장하고 두 번 계산합니다. **접두사 공유**는 이 구간의 KV를 하나만 두고 여러 요청이 참조하게 만듭니다.

이것이 **02 원리 ①의 "접두사 공유" 성질이 그대로 실현된 것**입니다 — append-only이므로 앞부분이 같으면 계산 결과도 같다는 보장이 있어서 가능합니다.

두 층위에서 나타납니다.

| 층위 | 무엇을 공유하나 | 이 자료에서 |
|---|---|---|
| **요청 간 (동시)** | 배치 내 여러 요청의 공통 프리픽스 | 이 절 |
| **요청 간 (시간차)** | 이전 요청이 만든 프리픽스 KV를 나중 요청이 재사용 | → [06-prompt-caching.md](06-prompt-caching.md) |

두 번째가 프롬프트 캐싱입니다. 원리는 동일하고 유효 기간(TTL)과 과금이 붙습니다.

**규율은 하나뿐입니다: 프리픽스가 바이트 단위로 같아야 합니다.** 06에서 이 규율이 실무에서 어떻게 깨지는지 자세히 다룹니다.

## ⑤ `bytes`를 줄인다 — KV 양자화

캐시에 저장하는 값의 정밀도를 낮춥니다. FP16(2바이트) → FP8(1바이트) → INT4(0.5바이트).

```
FP16 → FP8:  캐시 50% 감소
FP16 → INT4: 캐시 75% 감소
```

### 왜 KV 캐시가 양자화하기 좋은 대상인가

**모델 가중치 양자화보다 안전한 편입니다.** 가중치는 모든 토큰의 계산에 반복 사용되므로 오차가 누적되지만, KV는 어텐션 가중합에 한 번씩 들어가고 softmax가 값의 절대 크기보다 상대 비율에 반응하기 때문입니다.

다만 **무조건 안전하지는 않습니다.** 특히 K는 점수 계산에 직접 들어가 softmax를 통과하므로, V보다 양자화 오차에 민감한 경향이 보고됩니다. 그래서 실무 구현은 K와 V에 다른 정밀도를 쓰거나, 채널별 스케일을 따로 두는 방식을 씁니다.

**판단 기준**: 긴 컨텍스트에서 정확한 사실 회수가 중요한 워크로드(RAG, 인용)라면 보수적으로, 대화 지속성이 주된 워크로드라면 공격적으로 갈 수 있습니다. 반드시 자신의 평가셋으로 확인해야 하는 항목입니다.

## ⑥ 낭비를 없앤다 — PagedAttention

이건 공식의 항을 줄이는 게 아니라 **공식과 실제 사용량의 격차**를 줄입니다.

### 해결하는 문제: 단편화와 과잉 예약

순진한 구현은 각 요청마다 **최대 길이만큼 연속된 메모리를 미리 예약**합니다. 실제 생성 길이는 모르니까요.

```
[순진한 방식] 요청마다 최대 2048토큰 분량 예약
요청 A: [■■■■□□□□□□□□□□□□]  실제 4토큰 사용, 2044 낭비
요청 B: [■■■■■■■■□□□□□□□□]  실제 8토큰 사용, 2040 낭비
```

vLLM 논문은 기존 시스템이 이런 단편화와 과잉 예약으로 **메모리의 60~80%를 낭비**한다고 보고합니다.

### 메커니즘: OS의 가상 메모리를 빌려온다

**KV 캐시를 고정 크기 블록(page)으로 쪼개고, 블록 단위로 필요할 때 할당합니다.** 논리적으로 연속된 시퀀스가 물리적으로는 흩어져 있어도 되며, 블록 테이블이 매핑을 관리합니다.

```
[PagedAttention] 블록 단위 할당
요청 A 논리: [t1 t2 t3 t4]
요청 A 물리: 블록7 → 블록2      ← 흩어져 있어도 됨
```

효과는 두 가지입니다.

1. **낭비가 마지막 블록에만 발생** → 논문 보고 기준 낭비 4% 미만
2. **블록 공유가 자연스러워짐** → 접두사 공유(④)가 "같은 블록을 참조 카운트로 공유"하는 것으로 구현됨

vLLM은 같은 지연 수준에서 **처리량 2~4배 향상**을 보고합니다. 절감 기법이 아닌 **메모리 관리 기법**이라는 점에서 성격이 다르지만, 실효 용량을 늘린다는 점에서 실무 효과는 가장 큽니다.

## 종합 비교

| 기법 | 공격 항 | 대표 절감폭 | 무엇을 지불하는가 | 되돌릴 수 있나 |
|---|---|---|---|---|
| GQA | `n_kv` | 1/8 수준 | 헤드 표현력 (경미) | ❌ 학습 시점 결정 |
| MQA | `n_kv` | 1/64 수준 | 헤드 표현력 (명확) | ❌ 학습 시점 결정 |
| MLA | `n_kv`·차원 | 93.3% (보고) | 구현 복잡도, 복원 연산 | ❌ 학습 시점 결정 |
| 크로스레이어 공유 | `L` | 구성에 따라 | 레이어별 추상 수준 | ❌ 학습 시점 결정 |
| 슬라이딩 윈도우 | `s` | `O(s)`→`O(W)` | 창 밖 정보의 정확한 회수 | ❌ 주로 학습 시점 |
| 접두사 공유 | `b` 중복 | 공통 구간만큼 | 없음 (프리픽스 규율만) | ✅ 런타임 |
| KV 양자화 | `bytes` | 50~75% | 수치 정밀도 | ✅ 런타임 |
| PagedAttention | 낭비 | 낭비 60~80%→4% 미만 | 구현 복잡도 | ✅ 런타임 |

### ⭐ 이 표에서 읽어야 할 것: 마지막 열

**되돌릴 수 있는 기법과 없는 기법이 갈립니다.**

- **학습 시점 결정** (GQA/MQA/MLA/크로스레이어/SWA) — 모델을 고르는 순간 이미 정해집니다. 추론 단계에서 바꿀 수 없습니다. **모델 선택의 판단 기준**이 됩니다.
- **런타임 결정** (접두사 공유·양자화·PagedAttention) — 서빙 설정으로 켜고 끕니다. **운영의 조정 손잡이**입니다.

앱을 만드는 입장에서는 전자를 "모델 스펙"으로 읽고, 후자를 "튜닝 대상"으로 다루면 됩니다.

## ⚠️ 암기 필수

- [ ] **GQA는 `n_kv`를 줄여 캐시를 그 비율만큼 줄인다. Llama 3.1 70B는 64/8 = 8배 절감**
  - 이유: 모델 카드에서 `num_key_value_heads`를 보면 캐시 규모를 즉시 환산할 수 있다
- [ ] **절감 기법은 "학습 시점 결정"과 "런타임 결정"으로 갈린다**
  - 이유: 전자는 모델 선택의 기준, 후자는 운영 튜닝 대상. 잘못 분류하면 없는 손잡이를 찾게 된다
- [ ] **접두사 공유의 유일한 요구사항은 프리픽스의 바이트 동일성**
  - 이유: 프롬프트 캐시 미적중 디버깅의 출발점이 항상 이것

<details>
<summary>Q2: PagedAttention은 왜 "절감 기법"이 아니라 "메모리 관리 기법"인가?</summary>

**즉답 예시**: 캐시 크기 공식의 어떤 항도 줄이지 않습니다. 같은 시퀀스에 필요한 K·V의 양은 그대로입니다. 대신 순진한 구현이 단편화와 과잉 예약으로 버리던 공간(논문 기준 60~80%)을 회수해서 **실효 용량**을 늘립니다. 부수 효과로 블록 공유가 자연스러워져 접두사 공유의 구현 기반이 됩니다.

</details>

<details>
<summary>Q3: KV 양자화가 가중치 양자화보다 상대적으로 안전한 이유와, 그래도 조심해야 하는 지점은?</summary>

**즉답 예시**: 가중치는 모든 토큰의 계산에 반복 사용되어 오차가 누적되지만, KV는 어텐션 가중합에 한 번씩 들어가고 softmax가 절대 크기보다 상대 비율에 반응하므로 상대적으로 관대합니다. 다만 K는 점수 계산에 직접 들어가 softmax를 통과하므로 V보다 오차에 민감한 경향이 있어, 실무 구현은 K/V에 다른 정밀도나 채널별 스케일을 씁니다. 긴 컨텍스트에서 정확한 사실 회수가 중요한 워크로드에서는 반드시 자체 평가셋으로 확인해야 합니다.

</details>

**즉답 예시**: 시도할 수 있는 것(런타임) — KV 양자화 켜기(FP8), PagedAttention 기반 서버로 전환, 접두사 공유 활성화, 컨텍스트 상한이나 동시 요청 수 조정, 자주 안 쓰는 구간 오프로드. 시도할 수 없는 것(학습 시점 결정) — GQA/MQA/MLA로 바꾸기, 크로스레이어 공유 도입, 슬라이딩 윈도우 추가. 후자가 필요하면 **다른 모델로 교체**하는 것이 유일한 방법입니다.
