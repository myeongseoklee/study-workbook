# 05. prefill과 decode — 한 요청 안의 두 가지 다른 작업

## 학습 목표

이 파일을 다 읽으면 (1) 추론이 왜 성격이 정반대인 두 단계로 나뉘는지, (2) 왜 입력 토큰이 출력 토큰보다 싼지, (3) 성능 문제를 만났을 때 어느 단계의 문제인지 지표로 판별하는 방법을 설명할 수 있습니다.

## 핵심 원리: 스냅샷을 "만드는 일"과 "쓰는 일"은 다른 작업이다

02의 언어로 두 단계를 정의하면 이렇습니다.

| 단계 | 02 원리로 말하면 | 하는 일 |
|---|---|---|
| **prefill** | 스냅샷을 **만든다** | 프롬프트 전체를 한 번에 처리해 KV 캐시를 채움 |
| **decode** | 스냅샷을 **쓰면서 이어 쌓는다** | 토큰 1개 생성 → K·V를 캐시에 append → 반복 |

이 둘은 같은 모델, 같은 가중치를 쓰지만 **하드웨어 관점에서 완전히 다른 작업**입니다. 그 차이가 지연·비용·용량 계획 전부를 지배합니다.

```
사용자 프롬프트 3000토큰 → 응답 500토큰 생성

[prefill]  3000토큰을 한 번에 forward → KV 캐시 3000개 분량 생성
           └─ 사용자 체감: "첫 글자가 나오기까지의 대기"
[decode]   토큰 1개 → append → 토큰 1개 → append → ... (500회)
           └─ 사용자 체감: "글자가 흘러나오는 속도"
```

## 필수 지식 1: 왜 성격이 정반대인가 — 연산 강도

핵심 개념은 **연산 강도(arithmetic intensity)** 입니다.

> 연산 강도 = 수행하는 연산량 ÷ 메모리에서 읽어야 하는 데이터량

GPU는 연산 능력이 메모리 대역폭보다 훨씬 빠르게 발전해 왔습니다. 그래서 **연산 강도가 낮은 작업은 GPU 연산기가 놀면서 메모리를 기다립니다.**

### prefill: 연산 강도가 높다

프롬프트 3000토큰을 **동시에** 처리합니다. 가중치 행렬 하나를 읽어서 3000개 토큰에 모두 적용합니다.

```
가중치 W를 1번 읽고 → 3000개 토큰의 벡터에 곱함
= 행렬 × 행렬 (GEMM)
→ 읽은 데이터당 연산량이 많음 → 연산 강도 높음 → compute-bound
```

**연산기가 바쁩니다.** GPU를 제대로 활용하는 상태입니다.

### decode: 연산 강도가 낮다

토큰 **1개**를 처리합니다. 그런데 그 1개를 위해 읽어야 하는 것은 다음과 같습니다.

```
매 토큰마다 HBM에서 읽어야 하는 것:
  ① 모델 가중치 전체        (70B fp16 = 140 GB)
  ② 그 시퀀스의 KV 캐시 전체 (03 계산: 8K 컨텍스트면 2.5 GB)

그 데이터로 하는 연산:
  토큰 1개분 = 행렬 × 벡터 (GEMV)
→ 읽은 데이터당 연산량이 극히 적음 → 연산 강도 낮음 → memory-bound
```

**연산기가 놉니다.** 토큰 생성 속도는 사실상 `HBM 대역폭 ÷ (가중치 + KV 캐시 크기)` 로 결정됩니다.

### ⭐ 여기서 나오는 결론

> **긴 컨텍스트 추론의 병목은 연산이 아니라 메모리 대역폭이다.**

03에서 본 "캐시 메모리는 시퀀스에 선형"이 여기서 지연으로 변환됩니다. 컨텍스트가 2배 길어지면 매 토큰 읽어야 할 KV가 2배가 되고, 토큰 생성이 그만큼 느려집니다. 04의 절감 기법들이 **메모리 절약 기법이 동시에 속도 향상 기법인 이유**가 정확히 이것입니다.

## 필수 지식 2: 배칭이 왜 decode에서 특히 중요한가

decode가 memory-bound라는 사실에서 매우 실용적인 결론이 따라옵니다.

```
[배치 1]  가중치 140GB 읽기 → 토큰 1개 생성
[배치 32] 가중치 140GB 읽기 → 토큰 32개 생성    ← 같은 읽기로 32배 산출!
```

**가중치는 모든 요청이 공유하므로, 한 번 읽어서 여러 시퀀스에 동시 적용할 수 있습니다.** 놀고 있던 연산기를 채우는 셈입니다. 그래서 서빙 시스템은 배치를 최대한 키우려 합니다.

### 하지만 KV 캐시는 공유되지 않는다

```
가중치:    모든 요청 공유          → 배칭으로 읽기 비용 분산 ✅
KV 캐시:   요청마다 완전히 별개    → 배칭해도 읽는 양이 비례 증가 ❌
```

이것이 **배칭의 수익 한계**입니다. 배치를 키우면 가중치 읽기는 분산되지만 KV 캐시 읽기는 그대로 늘어납니다. 그리고 03에서 봤듯 배치를 키우면 KV 캐시 메모리도 선형으로 늘어 결국 HBM이 먼저 터집니다.

**연결**: 이 두 제약이 "긴 컨텍스트 지원 vs 높은 동시 처리량"이라는 트레이드오프의 물리적 정체입니다. 04의 캐시 절감 기법은 이 트레이드오프를 완화하는 도구입니다 — KV가 작아지면 같은 HBM으로 더 큰 배치를 돌릴 수 있고, 배치가 커지면 처리량이 오릅니다.

## 필수 지식 3: 가격 구조의 정체

두 단계의 비대칭이 API 가격에 직접 반영됩니다.

| | 처리 방식 | 병목 | 상대 비용 |
|---|---|---|---|
| 입력 토큰 (prefill) | 병렬 일괄 | 연산 | **싸다** |
| 출력 토큰 (decode) | 순차 1개씩 | 메모리 대역폭 | **비싸다** |

Claude API 기준 실제 배수를 보면 (2026-06-24 캐시 기준):

| 모델 | 입력 $/1M | 출력 $/1M | 배수 |
|---|---|---|---|
| Claude Opus 5 | $5.00 | $25.00 | 5배 |
| Claude Sonnet 5 | $3.00 | $15.00 | 5배 |
| Claude Haiku 4.5 | $1.00 | $5.00 | 5배 |

**출력이 입력의 5배**라는 것이 위 물리적 비대칭의 가격 표현입니다.

### 실무 함의: 최적화 우선순위가 정해진다

같은 100토큰을 아끼는 두 방법의 가치가 다릅니다.

- 프롬프트에서 100토큰 줄이기 → 입력 단가
- 응답에서 100토큰 줄이기 → **출력 단가 (5배 가치)**

그래서 "간결하게 답하라"는 지시가 프롬프트를 100토큰 늘리더라도, 응답을 200토큰 줄이면 **순이익**입니다. 에이전트 워크로드에서 특히 큽니다 — 도구 호출 루프의 매 턴이 출력을 생성하기 때문입니다.

## 필수 지식 4: 진단 신호 — 어느 단계의 문제인가

성능 지표는 두 단계에 1:1 대응합니다. **지표를 보면 어디를 손대야 할지 즉시 알 수 있습니다.**

| 지표 | 정식 이름 | 지배하는 단계 | 나쁠 때의 의미 |
|---|---|---|---|
| **TTFT** | Time To First Token | prefill | 프롬프트가 길다 / 큐 대기 / 캐시 미적중 |
| **TPOT** (또는 ITL) | Time Per Output Token / Inter-Token Latency | decode | KV 캐시가 크다 / 배치 경합 / 대역폭 포화 |
| **처리량** | throughput (tok/s 총합) | 주로 decode | 배치가 작다 / HBM 여유가 없다 |

### 처방이 갈린다

| 증상 | 진단 | 처방 |
|---|---|---|
| TTFT가 길다, TPOT는 정상 | prefill 문제 | 프롬프트 캐싱(→ 06), 프롬프트 단축, chunked prefill |
| TTFT는 정상, TPOT가 길다 | decode 문제 | KV 양자화, 컨텍스트 단축, 배치 조정 |
| 둘 다 나쁘고 부하가 높다 | 용량 문제 | HBM 증설, 배치 정책 조정, 모델 교체 |
| TTFT가 요청마다 튄다 | 큐 대기 또는 캐시 적중 편차 | 캐시 적중률 확인(→ 06), 부하 분산 |

**첫 줄이 가장 중요합니다.** 프롬프트 캐싱은 **prefill을 건너뛰는 기법**이므로 TTFT만 개선합니다. TPOT가 문제인데 프롬프트 캐싱을 붙이면 아무 효과가 없습니다.

### chunked prefill — 두 단계의 간섭 문제

한 GPU가 여러 요청을 처리할 때, 긴 prefill이 들어오면 진행 중인 decode들이 멈춥니다(prefill이 연산기를 독점하므로). 사용자 체감으로는 "잘 흘러나오던 응답이 갑자기 멈칫"합니다.

**chunked prefill**은 긴 prefill을 조각으로 쪼개서 decode 사이사이에 끼워 넣습니다. TTFT는 약간 나빠지지만 TPOT의 튐(jitter)이 줄어듭니다. 인터랙티브 서비스에서 자주 쓰는 트레이드오프입니다.

## 우리 프로젝트와의 연결

- **긴 캐시 파일을 에이전트에 넘길 때** — `.cc-system/cache/*.md`를 통째로 붙이면 그 비용은 prefill(입력 단가)이고, 프롬프트 캐싱으로 상당 부분 회수 가능합니다. 반면 에이전트가 장문 산출물을 쓰는 비용은 decode(출력 단가, 5배)이고 **회수 수단이 없습니다.**
- **그래서 `compose-handover`의 분량 캡이 비용 장치이기도 합니다** — 합성층이 캐시를 다시 풀어쓰면 그것은 전부 출력 토큰입니다. 포인터로 위임하면 출력이 줄어듭니다.
- **서브에이전트 효과(effort) 설정** — 낮은 effort는 생성 토큰을 줄이므로 decode 비용에 직접 작용합니다. 조사관 에이전트를 sonnet으로 내린 결정과 같은 축의 최적화입니다.

## ⚠️ 암기 필수

- [ ] **prefill = compute-bound(병렬 일괄), decode = memory-bound(순차 1개씩)**
  - 이유: 성능 문제의 절반이 이 구분만으로 진단된다
- [ ] **decode에서 매 토큰마다 읽는 것 = 모델 가중치 전체 + 해당 시퀀스 KV 캐시 전체**
  - 이유: 컨텍스트가 길어지면 왜 토큰 생성이 느려지는지의 유일한 설명
- [ ] **가중치는 배칭으로 분산되지만 KV 캐시는 안 된다**
  - 이유: 배칭 수익의 한계이자 "긴 컨텍스트 vs 동시 처리량" 트레이드오프의 물리적 정체
- [ ] **출력 토큰은 입력의 약 5배 단가** (Claude 전 모델 공통 비율)
  - 이유: 프롬프트를 늘려서 응답을 줄이는 것이 순이익인 판단 근거
- [ ] **TTFT는 prefill 지표, TPOT는 decode 지표. 프롬프트 캐싱은 TTFT만 개선한다**
  - 이유: 잘못된 처방(TPOT 문제에 캐싱 적용)을 막는 결정적 구분

## 자가 진단

<details>
<summary>Q1: 왜 decode 단계에서 GPU 연산기가 "놀고" 있는가?</summary>

**즉답 예시**: 토큰 1개를 만들기 위해 모델 가중치 전체(70B fp16이면 140GB)와 그 시퀀스의 KV 캐시 전체를 HBM에서 읽어야 하는데, 그 데이터로 하는 연산은 토큰 1개분(행렬×벡터)뿐입니다. 연산 강도(연산량÷메모리 읽기량)가 극히 낮아서 연산기가 메모리를 기다립니다. 그래서 토큰 생성 속도가 사실상 HBM 대역폭에 묶입니다.

</details>

<details>
<summary>Q2: 배치를 키우면 처리량이 오르지만 무한히 오르지 않는다. 두 가지 이유를 들라.</summary>

**즉답 예시**: (1) KV 캐시는 요청마다 별개이므로 배칭으로 읽기 비용이 분산되지 않습니다 — 가중치만 공유됩니다. 배치가 커지면 읽어야 할 KV 총량이 비례해서 늘어납니다. (2) KV 캐시 메모리도 배치에 선형으로 늘어나므로 HBM이 먼저 고갈됩니다(03의 공식에서 `b`가 1차항). 결국 `(HBM − 가중치 − 활성값) ÷ 요청당 KV`가 배치 상한이 됩니다.

</details>

<details>
<summary>Q3: 어떤 서비스의 TPOT가 나빠서 프롬프트 캐싱을 도입했다. 결과는?</summary>

**즉답 예시**: 아무 효과가 없습니다. 프롬프트 캐싱은 prefill을 건너뛰는 기법이므로 TTFT(첫 토큰까지의 시간)만 개선합니다. TPOT는 decode 단계 지표이고, decode는 캐시된 KV를 **읽어야** 하는 작업이므로 캐싱으로 사라지지 않습니다 — 오히려 프리픽스가 길면 읽을 KV가 많아 TPOT에는 불리합니다. TPOT 문제의 처방은 KV 양자화, 컨텍스트 단축, 배치 조정입니다.

</details>

<details>
<summary>Q4: "간결하게 답하라"는 지시로 프롬프트가 150토큰 늘고 응답이 400토큰 줄었다. 이득인가?</summary>

**즉답 예시**: 이득입니다. 출력 단가가 입력의 약 5배이므로, 입력 150토큰 증가의 비용은 출력 30토큰과 같습니다. 출력 400토큰 절감은 그보다 훨씬 큽니다. 게다가 프롬프트의 고정 부분은 프롬프트 캐싱으로 추가 할인이 가능하지만(→ 06) 출력에는 그런 수단이 없습니다. 에이전트의 도구 호출 루프처럼 턴이 반복되는 워크로드에서 이 격차는 턴 수만큼 곱해집니다.

</details>
