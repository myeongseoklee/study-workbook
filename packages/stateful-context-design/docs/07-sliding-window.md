## 핵심 원리: `O(s)`를 `O(W)` 상수로 바꾸는 유일한 방법

03의 공식에서 시퀀스 항 `s`는 1차항이었습니다. 캐시가 컨텍스트 길이에 선형으로 커진다는 뜻입니다.

슬라이딩 윈도우는 **각 토큰이 최근 W개만 보게** 제한합니다. 그러면 W개보다 오래된 K·V는 아무도 참조하지 않으므로 버릴 수 있습니다.

```
공식의 s가 min(s, W)로 대체됨 → s > W 이후로는 상수
```

100만 토큰을 흘려보내도 캐시는 W개 분량으로 고정됩니다. **무한 스트림 처리가 원리적으로 가능해지는 유일한 방법**입니다.

대가는 명확합니다: 창 밖의 정보를 **직접** 볼 수 없습니다. "직접"이 왜 중요한 단어인지는 두 번째 절에서 다룹니다.

## 필수 지식 1: 구현 — 마스크와 rolling buffer

두 부분으로 나뉩니다. **마스크**는 "무엇을 볼 수 있는가"(학습·추론 공통 정의), **버퍼**는 "메모리를 어떻게 쓰는가"(추론 최적화)입니다.

### ① 어텐션 마스크

causal mask에 조건을 하나 더 붙입니다.

```
[Full causal]         볼 수 있음 ⟺  j ≤ i
[Sliding window]      볼 수 있음 ⟺  i − W < j ≤ i
```

W=4일 때 그림으로:

```
      t1  t2  t3  t4  t5  t6  t7
t7 →   ·   ·   ·   ■   ■   ■   ■     ■ = 볼 수 있음
t6 →   ·   ·   ■   ■   ■   ■         · = 마스크
t5 →   ·   ■   ■   ■   ■
t4 →   ■   ■   ■   ■
t3 →   ■   ■   ■
t2 →   ■   ■
t1 →   ■
```

01의 삼각형이 **띠(band)** 로 바뀐 것입니다. 각 행의 ■ 개수가 최대 W개로 고정되므로 어텐션 연산량도 토큰당 `O(W·d)` 상수가 됩니다.

### ② Rolling buffer cache — 원형 버퍼

마스크만으로는 메모리가 줄지 않습니다. 실제 절감은 **크기 W의 고정 배열을 원형으로 재사용**해서 얻습니다.

```
W = 4, 토큰 0~7을 처리
position:   0  1  2  3  4  5  6  7
buffer idx: 0  1  2  3  0  1  2  3     ← position % W
                        ↑  ↑  ↑  ↑
                     토큰 0~3의 자리를 덮어씀

버퍼 상태 (토큰 7까지 처리 후):
  idx 0: 토큰 4의 K/V
  idx 1: 토큰 5의 K/V
  idx 2: 토큰 6의 K/V
  idx 3: 토큰 7의 K/V
```

**구현 시 반드시 처리해야 하는 세 가지:**

**(a) 논리 위치와 버퍼 인덱스의 분리.** 버퍼 인덱스는 `position % W`이지만, 위치 인코딩(RoPE 등)은 **논리 위치**를 씁니다. 버퍼 인덱스를 위치로 잘못 쓰면 토큰 4와 토큰 0이 같은 위치로 취급되어 모델이 완전히 망가집니다. 둘을 별도로 관리해야 합니다.

**(b) 순서 복원(unrotate).** 어텐션 계산 시 버퍼는 물리적으로 회전된 상태(`[t4, t5, t6, t7]`이 인덱스 `0,1,2,3`에 있지만, 다음 스텝엔 `[t8, t5, t6, t7]`이 됨)입니다. 시간 순서가 중요한 연산에서는 논리 순서로 재정렬해야 합니다.

**(c) prefill에서의 청킹.** 프롬프트가 W보다 길면 한 번에 처리할 수 없습니다(버퍼가 W개뿐). W 단위 청크로 나눠 순차 처리하며, 각 청크는 이전 청크가 남긴 버퍼 상태를 봅니다.

Mistral 7B는 이 rolling buffer로 32k 시퀀스에서 **캐시 메모리를 8배** 줄였다고 보고합니다(품질 저하 없이). 또 마스크의 띠 구조를 FlashAttention·xFormers에 반영해 16K 시퀀스 W=4096에서 **속도 2배**를 얻었습니다.

### ③ 순진하게 자르면 안 되는 이유 → attention sink

여기서 구현의 세 번째 요소가 필수로 들어옵니다. 다음 절이 그것입니다.

## 필수 지식 2: 좁은 창으로 멀리 보는 원리 — 그리고 그 한계

### 레이어 누적 (receptive field)

핵심은 **레이어가 쌓이면 유효 시야가 곱해진다**는 것입니다. CNN의 receptive field와 정확히 같은 원리입니다.

```
레이어 1: 토큰 t7의 표현은 [t4..t7]의 정보를 담음        (직접 시야 W=4)
레이어 2: 토큰 t7은 [t4..t7]의 "레이어1 표현"을 봄
          그런데 t4의 레이어1 표현은 이미 [t1..t4]를 담고 있음
          → t7은 간접적으로 [t1..t7]의 정보에 접근      (유효 시야 8)
레이어 3: → 유효 시야 12
...
레이어 L: → 유효 시야 ≈ W × L
```

Mistral 7B의 실제 수치:

```
W = 4096, 32 레이어 → 이론적 attention span ≈ 4096 × 32 = 131,072 ≈ 131K 토큰
```

창이 4096인데 32k 컨텍스트를 처리하는 것이 이 원리 덕분입니다.

### ⚠️ "이론적"이라는 단어가 핵심입니다

간접 전파는 **손실이 있습니다.** 이유를 두 가지로 나눠 보면:

**(a) 정보가 압축을 거칩니다.** t4의 레이어1 표현은 `[t1..t4]` 네 토큰을 하나의 벡터로 접은 것입니다. 그 벡터에서 t1의 구체적 내용을 다시 분리해낼 수 없습니다. 레이어를 거칠수록 이 압축이 누적됩니다.

**(b) 지목(addressing)이 불가능합니다.** full attention에서 t7은 t1의 K와 **직접** 점수를 매겨 "바로 저것"이라고 지목할 수 있습니다. SWA에서 t7은 t1을 지목할 수 없고, t4를 통해 흘러온 흐릿한 정보만 받습니다.

이 차이가 실무 결과로 나타나는 지점:

| 작업 | 간접 전파로 충분한가 |
|---|---|
| 대화 지속성 ("아까 말한 톤 유지") | ✅ 대체로 충분 — 확산된 정보로 족함 |
| 요약 (전체 흐름 파악) | ✅ 대체로 충분 |
| 문서 중간의 특정 문장 정확 인용 | ❌ **취약** — 지목이 필요 |
| needle-in-haystack (긴 문서에서 한 사실 찾기) | ❌ **취약** — 정확히 이 능력을 측정하는 벤치마크 |
| 100개 항목 중 3번째 항목의 값 | ❌ 취약 |

**판단 규칙**: "회수(retrieval)"가 필요하면 SWA 비중이 큰 모델을 조심하고, "지속(continuity)"이면 괜찮습니다.

### Attention sink — 순진하게 자르면 왜 망가지는가

여기가 이 자료에서 **가장 반직관적인 부분**입니다.

단순히 오래된 KV를 버리면 성능이 급격히 붕괴합니다. StreamingLLM 논문은 초기 토큰이 축출될 때 **perplexity가 10~100배 급등**하는 것을 관측했습니다.

**원인은 의미가 아니라 softmax의 제약입니다.**

01에서 본 대로 softmax는 비율의 합을 1로 맞춥니다. 그래서 모델은 "지금 볼 만한 것이 딱히 없을 때도 어딘가에 비중을 줘야" 합니다. 모델은 학습 과정에서 그 배출구를 만들어냅니다 — **의미와 무관하게 맨 앞 토큰(주로 첫 토큰)에 점수를 몰아주는** 습관입니다. 이것을 **attention sink**라 부릅니다.

```
어텐션 분포 (전형적 관측 — 막대 길이는 예시)
  sink   t1     ████████████████    의미와 무관하게 매우 높음
  recent t_n-2  ███
  recent t_n-1  ██
  recent t_n    █
  middle ...    ·                   그 사이 대부분의 토큰 — 거의 0
```

싱크를 버리면 그 비중이 **남은 토큰들에 강제로 재분배**됩니다. 의미 없이 배출되던 점수가 갑자기 의미 있는 토큰들에 얹히면서 분포 전체가 왜곡됩니다.

**처방: 앞 몇 개 토큰을 영구 고정합니다.**

```
StreamingLLM 방식:  [싱크 4개 영구 고정] + [최근 W개 슬라이딩]
                     t1 t2 t3 t4          ... t_{n-W} ... t_n
                     ↑ 절대 버리지 않음        ↑ 원형 버퍼로 순환
```

앞 4개만 남기면 무한 스트리밍에서도 안정적으로 동작합니다. 논문은 Llama-2·MPT·Falcon·Pythia 계열에서 이 방식으로 **최대 400만 토큰**까지 안정적 언어 모델링을 보고합니다.

**02의 원리 ④로 돌아가면**: "앞부분에는 적지만 없으면 전체가 망가지는 것이 있다"의 가장 순수한 사례입니다. 4개 토큰 — 전체의 0.0001% — 가 400만 토큰의 안정성을 지탱합니다.

## 필수 지식 3: 순수 SWA / full attention / 하이브리드

### 세 가지 비교

| | 순수 SWA | Full attention | 하이브리드 |
|---|---|---|---|
| **캐시 크기** | `O(W)` 상수 | `O(s)` 선형 | global 레이어만 `O(s)` |
| **어텐션 연산** | 토큰당 `O(W·d)` | 토큰당 `O(s·d)` | 혼합 |
| **장거리 지목** | ❌ 간접만 | ✅ 완전 | ✅ global 레이어가 담당 |
| **무한 스트림** | ✅ | ❌ | ❌ (global이 선형) |
| **대표 모델** | Mistral 7B (초기) | 초기 GPT 계열 | Gemma 2 / Gemma 3 |
| **현재 위치** | 특수 목적 | 짧은 컨텍스트 | **주류** |

### 왜 하이브리드가 주류가 되었나

순수 SWA는 장거리 회수가 약하고, 순수 full attention은 메모리를 먹습니다. **레이어별로 섞으면 둘의 약점을 서로 메웁니다** — 소수의 global 레이어가 장거리 정확도를 담당하고, 다수의 local 레이어가 캐시 비용을 낮춥니다.

| 모델 | local : global | local 창 | global 범위 |
|---|---|---|---|
| **Gemma 2** | 1 : 1 (교대) | 4,096 | 8,192 |
| **Gemma 3** | **5 : 1** | **1,024** | 컨텍스트 전체 |

Gemma 3의 변화 방향을 읽으세요. **local 비중을 늘리고(1:1→5:1) 창을 좁혔습니다(4096→1024).** 캐시를 더 공격적으로 줄인 것입니다.

Gemma 3 기술 보고서가 제시하는 효과:

```
32K 토큰 기준 KV 캐시 메모리 오버헤드
  global-only 방식:  60%
  Gemma 3 하이브리드: 15% 미만
```

그리고 ablation 결과, 이 변경이 **모델 품질에는 미미한 영향**만 준다고 보고합니다. "큰 메모리·연산 절감을 작은 품질 손실로 산다"는 것이 하이브리드가 채택된 근거입니다.

### 선택 기준

| 상황 | 선택 |
|---|---|
| 끝없는 스트림 처리 (실시간 로그, 무한 대화) | 순수 SWA + attention sink |
| 컨텍스트가 짧고(≤8K) 최대 정확도 필요 | Full attention |
| **긴 컨텍스트 + 회수 정확도 둘 다** | **하이브리드** (사실상 기본 선택) |

이 결정은 대부분 **모델을 고르는 것**입니다 — 04에서 본 대로 학습 시점 결정이므로 추론 단계에서 바꿀 수 없습니다.

## 필수 지식 4: 실무적 함의

### ① 학습 시 W와 추론 시 W를 다르게 쓰면 위험하다

모델은 특정 W로 학습되었고, 위치 인코딩 분포도 그 W에 맞춰져 있습니다. 추론에서 W를 임의로 늘리면 학습 시 보지 못한 상대 거리가 등장해 품질이 떨어질 수 있습니다.

**규칙: 설정값을 바꿀 수 있다는 것이 바꿔도 된다는 뜻은 아닙니다.** 반드시 자체 평가셋으로 확인하세요.

### ② RAG·인용 워크로드에서 특히 조심

가장 실무적인 함정입니다.

```
[취약] "이 100페이지 계약서에서 해지 조항의 정확한 문구를 인용해줘"
       → 정확한 지목이 필요. SWA 비중이 큰 모델에서 문구가 흐려질 수 있음
[안전] "이 계약서의 전반적 위험을 요약해줘"
       → 확산된 정보로 충분
```

RAG 시스템을 만들 때 모델의 어텐션 구조를 확인해야 합니다. **needle-in-haystack 스코어가 이 능력의 대리 지표**입니다.

### ③ 프롬프트 캐싱과의 상성

06에서 본 접두사 재사용은 "저장된 KV를 로드"하는 것입니다. 그런데 SWA local 레이어에서는 **창 밖으로 밀려난 KV가 애초에 존재하지 않습니다.**

```
하이브리드 모델에서 긴 프리픽스를 재사용할 때
  global 레이어: 프리픽스 전체의 KV가 남아 있음 → 재사용 가능
  local 레이어:  창 W 분량만 존재 → 재사용 대상이 적음
```

**함의**: 하이브리드 모델에서 캐싱의 이득은 global 레이어 비중에 좌우됩니다. Gemma 3처럼 5:1이면 global이 1/6뿐이므로, 같은 프리픽스 길이에서 캐싱으로 절약되는 절대량이 1:1 모델보다 작습니다. (제공자별 구현 세부는 다를 수 있으므로, 실측 `cache_read_input_tokens`로 확인하는 것이 정답입니다.)

### ④ 컨텍스트 상한과 실효 정확도는 다르다

"1M 컨텍스트 지원"은 **투입 가능한 토큰 수**이고, 그 전 구간에서 정확한 회수가 되는지는 별개입니다. SWA 비중이 큰 모델은 상한과 실효 정확도의 격차가 더 큽니다.

**판단 도구**: 컨텍스트 길이 스펙이 아니라 자신의 워크로드에 가까운 벤치마크(회수형이면 needle-in-haystack, 요약형이면 요약 품질)를 봅니다.

### ⑤ 에이전트 워크로드에서의 양면성

09에서 자세히 다루지만 미리 짚으면:

- ✅ **긴 대화 지속** — SWA가 잘 견디는 영역
- ❌ **"20턴 전에 도구가 반환한 정확한 값 재사용"** — 취약. 그래서 에이전트는 SWA에 의존하지 않고 **외부 메모리**(파일, 노트)에 명시적으로 기록합니다

- [ ] **SWA 유효 시야 ≈ W × L (레이어 누적). Mistral 7B는 4096 × 32 ≈ 131K**
  - 이유: 좁은 창 모델이 왜 긴 컨텍스트를 처리하는지의 유일한 설명
- [ ] **간접 전파는 손실이 있다 — 압축 누적 + 지목 불가.** 지속은 견디고 회수는 취약
  - 이유: RAG·인용 워크로드에서 모델을 고르는 결정 기준
- [ ] **순진하게 앞부터 버리면 perplexity가 10~100배 급등. 원인은 attention sink**
  - 이유: 축출 구현의 필수 요건. 앞 4개 토큰 고정이 표준 처방
- [ ] **attention sink의 원인은 의미가 아니라 softmax의 "합이 1" 제약**
  - 이유: 왜 의미 없는 토큰을 남겨야 하는지 이해하지 못하면 "최적화"라며 제거하게 된다
- [ ] **하이브리드가 주류. Gemma 2는 1:1(local 4096), Gemma 3는 5:1(local 1024)**
  - 이유: 방향(local 비중↑, 창↓)이 업계 추세를 보여주고, 모델 스펙 읽기의 기준이 된다
- [ ] **32K 기준 KV 오버헤드: global-only 60% → Gemma 3 하이브리드 15% 미만**
  - 이유: 하이브리드 채택의 정량 근거

## 자가 진단

<details>
<summary>Q1: rolling buffer를 구현할 때 버퍼 인덱스를 위치 인코딩에 그대로 쓰면 무슨 일이 생기는가?</summary>

**즉답 예시**: 모델이 완전히 망가집니다. 버퍼 인덱스는 `position % W`이므로 토큰 0과 토큰 W가 같은 인덱스를 가집니다. 그 인덱스를 위치로 쓰면 두 토큰이 같은 위치로 취급되어 상대 거리 계산이 뒤엉킵니다. 논리 위치(단조 증가)와 버퍼 인덱스(순환)를 **반드시 분리해서** 관리해야 하며, RoPE 같은 위치 인코딩은 논리 위치를 씁니다.

</details>

<details>
<summary>Q2: W=1024인 모델이 "10만 토큰 컨텍스트"를 처리한다고 한다. 모순인가?</summary>

**즉답 예시**: 모순이 아닙니다. 레이어 누적 덕분입니다 — 레이어 1의 토큰이 최근 1024개를 보고, 레이어 2는 "이미 1024개를 요약한 표현들"을 다시 1024개 봅니다. L레이어면 유효 시야가 약 `W × L`까지 확장됩니다. 단 이것은 **간접** 전파이므로, 10만 토큰 중 특정 문장을 정확히 지목해 인용하는 능력은 full attention보다 확실히 약합니다. "처리한다"와 "정확히 회수한다"를 구분해야 합니다.

</details>

<details>
<summary>Q3: attention sink 토큰은 의미가 없다. 그럼 왜 버리면 안 되는가?</summary>

**즉답 예시**: softmax는 비율의 합을 1로 맞추므로, 모델은 볼 만한 것이 없을 때도 어딘가에 비중을 배출해야 합니다. 학습 과정에서 모델은 맨 앞 토큰을 그 배출구로 삼는 습관을 만듭니다. 싱크를 버리면 배출되던 비중이 남은 토큰들에 강제 재분배되면서 어텐션 분포 전체가 왜곡되고, perplexity가 10~100배 급등합니다. **의미가 없다는 것과 구조적으로 필요하다는 것은 다릅니다.**

</details>

<details>
<summary>Q4: RAG 시스템에 Gemma 3(5:1 하이브리드, local 1024)를 쓸 때 어떤 위험을 점검해야 하는가?</summary>

**즉답 예시**: local 레이어가 6개 중 5개이므로 장거리 지목은 소수의 global 레이어가 담당합니다. 검색된 긴 문서에서 특정 문장을 정확히 인용해야 하는 작업(회수형)은 이 구조에서 상대적으로 취약할 수 있습니다. 점검 방법은 컨텍스트 길이 스펙이 아니라 **자신의 데이터로 needle-in-haystack 유형 평가**를 돌리는 것입니다. 요약·전반적 판단이 주 업무라면 하이브리드의 메모리 이득을 그대로 취하면 됩니다.

</details>

<details>
<summary>Q5: 하이브리드 모델에서 프롬프트 캐싱의 이득이 왜 모델 구조에 좌우되는가?</summary>

**즉답 예시**: 캐싱은 저장된 KV를 재사용하는 것인데, local 레이어에서는 창 밖으로 밀려난 KV가 애초에 존재하지 않습니다. 따라서 긴 프리픽스에서 재사용 가능한 양은 global 레이어 비중에 비례합니다. Gemma 3처럼 5:1이면 global이 1/6이므로 같은 프리픽스 길이에서 절약되는 절대량이 1:1 모델보다 작습니다. 제공자별 구현 세부는 다를 수 있으므로 실측 `cache_read_input_tokens`로 확인하는 것이 정답입니다.

</details>
