# 08. 이벤트 소싱 — 같은 네 원리의 데이터베이스 구현

## 학습 목표

이 파일을 다 읽으면 이벤트 소싱을 02의 네 원리로 재구성할 수 있고, 어떤 바운디드 컨텍스트에 적용할지 판단할 수 있으며, **재생(replay)의 부작용 문제**를 설명할 수 있습니다. 마지막 항목이 09의 핵심 재료입니다.

## 핵심 원리: 네 원리를 그대로 DB에 옮긴 것

| 02 원리 | 이벤트 소싱에서 |
|---|---|
| ① 축적 | 도메인 이벤트를 `events` 테이블에 INSERT만 함 (UPDATE 없음) |
| ② 접기 | `apply(state, event)`를 순서대로 적용해 애그리게이트 상태 도출 |
| ③ 스냅샷 | N건마다 상태 사본 저장 / 조회용 프로젝션 |
| ④ 축출 | 아카이브·보존 정책 (삭제는 최후수단) |

**핵심 역전**: 현재 상태를 저장하는 대신, 상태를 만든 사건들을 저장합니다.

```
[CRUD]  accounts 테이블
        accountSN=1, balance=8000      ← UPDATE가 역사를 지웠다

[Event Sourcing]  events 테이블 (append-only)
        1  AccountOpened      { accountSN: 1 }
        2  Deposited          { amount: 10000 }
        3  TicketPurchased    { amount: 3000, ticketId: "T-1" }
        4  RefundIssued       { amount: 1000, reason: "발급 실패" }
        → balance = 8000 은 위 4건을 접어서 도출한 결과
```

은행 통장이나 회계 원장과 같은 사고방식입니다 — 잔액을 고쳐 쓰지 않고 거래를 한 줄씩 append합니다.

## 필수 지식 1: 왜 하는가

| 얻는 것 | 왜 그런가 |
|---|---|
| **완전한 감사 로그** | 원리 ①의 부산물. 별도 로그 테이블이 불필요 |
| **시간 여행** | 원리 ②의 부산물. 이벤트를 그 지점까지만 접으면 임의 시점 상태 복원 |
| **사후 질문 대응** | 당시엔 안 물었던 질문에 나중에 답할 수 있음 — 새 프로젝션을 만들어 과거부터 재생 |
| **디버깅** | 프로덕션 버그를 해당 스트림 재생으로 재현 |
| **도메인 표현력** | `UPDATE status='cancelled'` 대신 `OrderCancelledByUser` vs `OrderExpiredBySystem` |

마지막 항목이 특히 중요합니다. **CRUD에서는 "왜 바뀌었는지"가 구조적으로 소실됩니다.** 이벤트 소싱은 그 의도를 타입으로 강제합니다.

## 필수 지식 2: 구성 요소

### Append-only 이벤트 스토어

이벤트는 불변입니다. 수정도 삭제도 없습니다. 잘못 기록했으면 **보정 이벤트(compensating event)** 를 새로 append합니다 — 회계에서 오기를 지우지 않고 역분개하는 것과 같습니다.

### 애그리게이트와 리플레이

```
load(id) → 이벤트 스트림 읽기 → fold → 현재 상태
              ↓
        커맨드 검증 (불변식 체크)
              ↓
        새 이벤트 append
```

### 스냅샷

원리 ③입니다. 이벤트가 10만 건이면 매번 전부 재생하는 것은 비현실적이므로, N건마다 상태를 저장하고 "스냅샷 + 이후 이벤트"만 재생합니다.

**철칙 재확인**: 스냅샷을 전부 지워도 시스템은 느려질 뿐 틀리지 않습니다. 이벤트가 진실 원천입니다.

### 프로젝션 (읽기 모델)

`SELECT * FROM events WHERE ...`로 목록 조회를 하는 것은 불가능합니다. 그래서 이벤트를 구독해 **조회 전용 뷰**를 갱신합니다.

```
커맨드 → 애그리게이트 → 이벤트 스토어 → (구독) → 프로젝션 A (유저별 잔액)
                                            → 프로젝션 B (일별 정산)
                                            → 프로젝션 C (검색 인덱스)
```

여기서 자연스럽게 **CQRS**(쓰기 모델 ≠ 읽기 모델)로 이어집니다. 프로젝션은 "조회 패턴에 맞춰 미리 접어둔 결과"이므로 **원리 ③의 변형**입니다.

### 낙관적 동시성 제어

`(streamId, version)` 유니크 제약으로 처리합니다. 두 요청이 동시에 version 5를 쓰려 하면 하나가 실패하고 재시도합니다. **append 지점 하나에만 경합이 생긴다**는 것이 원리 ①의 이점입니다.

## 필수 지식 3: ⭐ 재생의 부작용 문제 — 09으로 이어지는 핵심

이것이 이벤트 소싱에서 가장 미묘하고, **에이전트 설계에 직접 옮겨지는** 문제입니다.

Fowler가 명시적으로 경고하는 지점입니다: 이벤트를 재생할 때 **그 이벤트가 외부 시스템에 메시지를 보내는 것이었다면 문제가 생깁니다.** 외부 시스템은 "실제 처리"와 "재생"을 구별할 수 없기 때문입니다.

```
이벤트: PaymentRequested { amount: 10000 }
  실제 처리 시: PG사에 결제 요청 전송 ✅
  재생 시:      PG사에 결제 요청 재전송 ❌ ← 중복 결제!
```

### 해법: 게이트웨이로 감싼다

외부 시스템 호출을 전용 게이트웨이로 감싸고, **게이트웨이가 "지금 실제 처리인가 재생인가"를 판단**해 외부 호출을 허용/차단합니다.

여기서 Fowler의 설계 원칙이 나옵니다:

> **도메인 로직은 실행 컨텍스트(실제인지 재생인지)를 알아서는 안 된다.**

도메인 로직에 `if (isReplay) { skip }`이 들어가기 시작하면 두 경로가 갈라지고 재생 결정론성이 무너집니다. 컨텍스트 판단은 게이트웨이가 투명하게 처리해야 합니다.

### 그래서 나오는 규율: 재생 결정론성

**같은 이벤트열을 재생하면 항상 같은 상태가 나와야 합니다.** 이를 깨뜨리는 것들:

| 깨뜨리는 것 | 왜 | 처방 |
|---|---|---|
| `now()`, `random()` | 재생 시 다른 값 | 이벤트에 값을 **기록**해두고 재생 시 그것을 읽음 |
| 외부 API 조회 | 응답이 변함 | 조회 결과를 이벤트에 기록 |
| `apply` 로직 변경 | 같은 이벤트가 다른 상태를 만듦 | 버전 관리 또는 업캐스터 |

**규칙: 재생에 필요한 모든 것을 이벤트 안에 넣습니다.** 이벤트는 "무엇을 하라"가 아니라 "무엇이 일어났고 그때 값이 무엇이었는가"입니다.

## 필수 지식 4: 실제로 아픈 지점들

### 스키마 진화가 영구 부채가 된다

2년 전 이벤트도 오늘 코드로 읽혀야 합니다. 필드 추가는 괜찮지만 의미 변경은 어렵습니다.

대응은 **업캐스터**(구버전 이벤트를 읽을 때 신버전으로 변환) 또는 버전드 이벤트 타입(`OrderPlacedV2`) — 어느 쪽이든 코드에 영구히 남습니다.

### 최종 일관성이 UX로 새어 나온다

쓰기 직후 프로젝션이 아직 안 갱신됐으면 목록에 안 보입니다. "저장했는데 왜 안 보여요?" 문제.

대응: 동기 프로젝션(일부만), 클라이언트 낙관적 업데이트, read-your-writes 토큰.

### 삭제가 원리적으로 불가능하다

GDPR "잊혀질 권리"와 append-only는 정면 충돌합니다. 실무 해법은 **crypto-shredding** — 개인정보를 유저별 키로 암호화해 저장하고, 삭제 요청 시 키를 폐기합니다. 이벤트는 남지만 복호화 불가.

### 이벤트 입도를 되돌리기 어렵다

테이블 스키마는 마이그레이션하면 되지만, 이미 쌓인 이벤트의 입도가 잘못됐다면 — 너무 잘게 쪼갰거나, CRUD를 그대로 옮겨 `UserUpdated { ...전체필드 }` 같은 걸 만들었다면 — 사실상 재설계입니다.

**진단 신호**: 이벤트 이름이 `XxxUpdated`, `XxxChanged`뿐이면 CRUD를 이벤트로 위장한 것입니다. 의도가 담긴 이름(`AddressCorrected`, `SubscriptionUpgraded`)이 나오지 않는다면 도메인 분석이 덜 된 것입니다.

## 필수 지식 5: 언제 쓰고 언제 피하나

### 적합

- 도메인 자체가 이미 원장·거래 개념인 곳 — 결제, 정산, 포인트/티켓, 재고, 예약
- 감사 요구가 규제 수준인 곳 — 금융, 의료
- "어떻게 이 상태에 도달했는가"가 비즈니스 질문인 곳
- 하나의 쓰기가 여러 이질적 읽기 모델을 먹여야 하는 곳

### 부적합

- 단순 CRUD 마스터 데이터 — 설정, 코드 테이블, 관리자 화면
- 상태 이력에 아무도 관심 없는 도메인
- 팀에 경험이 없고 일정이 촉박한 경우 — 학습 곡선이 실재하고 잘못 시작하면 되돌리기 비쌈

### ⭐ 핵심 판단: 전 시스템이 아니라 바운디드 컨텍스트 단위로 고른다

정산·포인트 컨텍스트는 이벤트 소싱, 유저 프로필·설정은 평범한 CRUD — **이 혼합이 정상이고 오히려 권장됩니다.** "전부 이벤트 소싱"은 거의 항상 잘못된 결정입니다.

## 흔한 오해 정리

| 오해 | 실제 |
|---|---|
| 이벤트 소싱 = CQRS | 별개 패턴. 다만 이벤트 소싱은 조회 문제 때문에 CQRS를 거의 강제함 |
| 이벤트 소싱 = Kafka | Kafka는 메시지 로그(보존 기간·파티션 단위). 이벤트 스토어는 스트림별 무기한 보존 + 버전 기반 동시성 제어가 필요. **Postgres 테이블 하나로 시작하는 게 보통 더 낫습니다** |
| 이벤트 = 통합 메시지 | 도메인 이벤트(내부, 세밀)와 통합 이벤트(외부 공개, 안정적 계약)는 분리. 내부 이벤트를 외부에 그대로 노출하면 스키마 진화가 막힘 |
| 로그 남기는 거랑 같음 | 로그는 부산물이라 버려도 되지만, 이벤트는 삭제하면 상태가 소실됨 |

## 우리 프로젝트와의 연결

`cc-system`에 이미 이 패턴이 들어 있습니다.

- **`daily-report`의 월별 JSON 누적 DB** — 계획·진행상황·backlog·특이사항을 덮어쓰지 않고 날짜별로 누적합니다. 주간보고는 그것을 **접어서** 만드는 프로젝션에 해당합니다.
- **`CLAUDE.md`의 변경 이력 표** — 날짜·변경 내용·대상·사유를 append합니다. 현재 하네스 상태는 그 이력을 접은 결과이고, "왜 이렇게 됐는가"에 답할 수 있는 이유가 이 append-only 규율입니다.
- **`.cc-system/cache/` 매니페스트** — 산출물별 `path_scope`·`git_commit`·타임스탬프를 기록해 stale 판정에 씁니다. 이는 스냅샷 + 무효화 메타데이터 구조입니다.

## ⚠️ 암기 필수

- [ ] **재생 시 외부 시스템 호출은 재실행되어 부작용을 낸다. 게이트웨이로 감싸고, 도메인 로직은 실행 컨텍스트를 몰라야 한다**
  - 이유: 이벤트 소싱 도입 시 가장 흔한 프로덕션 사고이자, 09의 에이전트 재생 문제와 같은 구조
- [ ] **재생 결정론성: `now()`/`random()`/외부 조회 결과를 이벤트에 기록해둔다**
  - 이유: 이 규율이 깨지면 시간 여행·디버깅·프로젝션 재구축이 전부 신뢰할 수 없게 된다
- [ ] **바운디드 컨텍스트 단위로 선택. 혼합이 정상**
  - 이유: "전부 이벤트 소싱"은 거의 항상 잘못된 결정
- [ ] **진단 신호: 이벤트 이름이 `XxxUpdated`뿐 = CRUD를 이벤트로 위장한 것**
  - 이유: 입도 설계 실패는 되돌리기 비싸므로 초기에 잡아야 한다

## 자가 진단

<details>
<summary>Q1: 이벤트 소싱을 도입했는데 재생할 때마다 이메일이 다시 발송된다. 원인과 처방은?</summary>

**즉답 예시**: 도메인 로직이 이벤트를 적용하면서 직접 외부 시스템(메일 서버)을 호출하고 있습니다. 외부 시스템은 실제 처리와 재생을 구별할 수 없으므로 재생 시에도 발송됩니다. 처방은 외부 호출을 게이트웨이로 감싸고, 게이트웨이가 실행 컨텍스트(실제/재생)를 판단해 차단하는 것입니다. **도메인 로직 안에 `if (isReplay)`를 넣지 않는 것이 중요합니다** — 두 경로가 갈라지면 재생 결정론성이 무너집니다.

</details>

<details>
<summary>Q2: 어떤 이벤트의 `apply` 로직에 `if (now() > deadline)` 판단이 들어 있다. 무엇이 문제인가?</summary>

**즉답 예시**: 재생 결정론성이 깨집니다. 같은 이벤트열을 나중에 재생하면 `now()`가 다르므로 다른 상태가 나옵니다. 시간 여행·디버깅·프로젝션 재구축이 모두 신뢰할 수 없게 됩니다. 처방: 판단에 쓰인 시각을 **이벤트를 기록할 때 이벤트 안에 저장**하고, `apply`는 그 값을 읽습니다. 규칙은 "재생에 필요한 모든 것을 이벤트 안에 넣는다"입니다.

</details>

<details>
<summary>Q3: 프로젝션이 왜 원리 ③(스냅샷)의 변형인가?</summary>

**즉답 예시**: 프로젝션은 특정 조회 패턴에 맞춰 이벤트를 미리 접어둔 결과입니다. 스냅샷이 "애그리게이트 상태를 미리 접어둔 것"이라면, 프로젝션은 "조회용 뷰를 미리 접어둔 것"입니다. 두 가지 성질을 공유합니다 — 진실 원천이 아니라 파생물이고(전부 지우고 이벤트에서 재구축 가능), 재생 비용을 줄이는 최적화입니다.

</details>

<details>
<summary>Q4: 팀이 "우리 시스템 전체를 이벤트 소싱으로 바꾸자"고 한다. 어떻게 답하겠는가?</summary>

**즉답 예시**: 바운디드 컨텍스트 단위로 골라야 한다고 답합니다. 이벤트 소싱은 도메인이 이미 원장·거래 개념이거나 "어떻게 이 상태가 됐는가"가 비즈니스 질문인 곳에서 값을 냅니다. 설정·코드 테이블·관리자 화면 같은 단순 마스터 데이터에 적용하면 스키마 진화 부채, 최종 일관성 UX 문제, 삭제 불가 문제만 얻습니다. 정산·포인트는 이벤트 소싱, 유저 프로필은 CRUD — 이 혼합이 정상입니다.

</details>
