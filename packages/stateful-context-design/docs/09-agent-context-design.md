## 핵심 원리: 에이전트 대화는 append-only 이벤트 로그다

LLM API는 **stateless**입니다. 매 턴 전체 이력을 다시 보냅니다. 그 이력이 무엇인지 정확히 보면:

```
messages = [
  { role: "user",      content: "..." },              ← 이벤트 1
  { role: "assistant", content: [tool_use ...] },     ← 이벤트 2
  { role: "user",      content: [tool_result ...] },  ← 이벤트 3
  { role: "assistant", content: "..." },              ← 이벤트 4
  ...
]
```

**끝에만 추가하고 과거를 수정하지 않는 순서열** — 정확히 append-only 로그입니다. 그리고 다음 응답은 이 로그를 모델이 접은 결과입니다.

이 관점이 잡히면 에이전트 설계 결정 대부분이 이미 풀린 문제로 보입니다.

| 02 원리 | 에이전트에서 | 이 파일의 절 |
|---|---|---|
| ① 축적 | 메시지 배열 append, 과거 수정 금지 | 1 |
| ② 접기 | 모델 forward pass | 1 |
| ③ 스냅샷 | compaction, 외부 메모리, 파생 뷰 | 2 |
| ④ 축출 | 컨텍스트 편집, 앵커 고정 | 3 |
| (ES 고유) | 재생 부작용, 보정 이벤트, 결정론성 | 4 |

## 1. 원리 ①②의 적용 — 로그 규율

### 과거 턴을 수정하지 마라 — 두 가지 이유

에이전트 하네스에서 "이전 메시지를 고쳐서 다시 보내는" 유혹이 자주 생깁니다. 지시를 강화하거나, 실패한 도구 호출을 지우거나, 오래된 정보를 갱신하려고요.

**두 가지가 동시에 깨집니다.**

| 깨지는 것 | 왜 |
|---|---|
| **프롬프트 캐시** | 06 — 위치 N 수정은 N 이후 전체를 무효화. 긴 대화에서 비용이 폭발 |
| **재현성** | 08 — 같은 로그를 재생해도 다른 결과가 나옴. 디버깅·트레이스가 신뢰할 수 없게 됨 |

### 안정 → 변동 배치가 곧 캐시 전략

06의 배치 규율을 하네스 관점으로 번역하면:

```
[위치 0]  도구 정의          ← 절대 요청마다 바꾸지 말 것 (전체 캐시 무효)
[다음]    시스템 프롬프트     ← 세션 내 고정
[다음]    스킬/가이드 본문    ← 안정
[다음]    프로젝트 컨텍스트   ← 세션 단위
[뒤]      대화 이력          ← append만
[맨 뒤]   현재 턴 입력       ← 변동
```

**흔한 실수 두 가지:**

- **유저·모드별로 도구 목록을 구성** → 도구는 위치 0이므로 캐시 공유가 전면 차단됩니다. 도구 집합은 고정하고 시스템 프롬프트나 지시로 사용 여부를 조절하세요.
- **시스템 프롬프트에 현재 시각·세션 ID 보간** → 매 요청 프리픽스가 달라집니다. 뒤쪽으로 옮기세요.

### 세션 중간 지시는 append로

모드 전환이나 갱신된 컨텍스트를 주입해야 할 때, 최상위 `system`을 편집하면 전체 캐시가 날아갑니다. 대신 `messages[]`에 `{"role": "system", ...}` 메시지를 **append**합니다 (Claude Opus 5/4.8/Fable 5/Mythos 5, 베타 헤더 불필요).

이것이 원리 ①의 순수한 적용입니다 — **수정하지 말고 추가하라.** 부수 효과로 사용자 입력에 위조될 수 없는 운영자 채널이 됩니다.

## 2. 원리 ③의 적용 — 스냅샷과 파생 뷰

### Compaction은 스냅샷인가 축출인가

컨텍스트가 한계에 가까워지면 이력을 요약해 새 컨텍스트를 시작합니다. 이것이 스냅샷인지 축출인지는 **한 가지로 갈립니다.**

| 원본 처리 | 정체 | 되돌릴 수 있나 |
|---|---|---|
| 원본 이력을 어딘가에 보관 | **스냅샷** (원리 ③) | ✅ |
| 원본을 버림 | **축출** (원리 ④) | ❌ |

02의 철칙 — "스냅샷을 전부 지워도 느려질 뿐 틀리지 않는다" — 을 만족하는지 확인하면 됩니다. 요약만 남기고 원본을 버렸다면 그 성질을 잃었으므로 축출입니다.

**설계 함의**: 되돌릴 수 없는 결정을 자동으로 내리지 않게 하세요. 요약을 만들면서 원본을 파일이나 로그로 남겨두면, 요약이 중요한 정보를 빠뜨렸을 때 복구할 길이 있습니다.

### 요약의 오차는 누적된다

**스냅샷에서 스냅샷을 만들면 오차가 곱해집니다.**

```
원본 → 요약1 → (요약1에서) 요약2 → 요약3 → ...
              ↑ 원본의 손실이 이미 포함된 것을 다시 요약
```

이벤트 소싱에서는 스냅샷을 항상 **이벤트 로그에서** 만들지, 이전 스냅샷에서 만들지 않습니다. 에이전트에서도 같은 규율이 필요합니다 — 가능하면 **원본 이력에서** 요약을 만들고, 요약의 요약을 반복하지 않습니다.

반복이 불가피하면 **연쇄 횟수를 세고 상한을 두세요.** `cc-system`의 캐시 매니페스트가 이미 이 장치를 갖고 있습니다: update 연쇄 카운터가 3 이상이면 자동으로 rebuild(전체 재생성)를 추천합니다. 이것이 정확히 "스냅샷 연쇄의 drift를 로그에서 재구축으로 끊는" 처방입니다.

### 외부 메모리 = 프로젝션

08의 프로젝션(읽기 모델)이 에이전트에서는 이렇게 나타납니다.

| 에이전트의 파생 뷰 | 대응하는 프로젝션 |
|---|---|
| 작업 노트 / TODO 파일 | 진행 상태 뷰 |
| 결정 기록 (`.md` 파일) | 의사결정 이력 뷰 |
| 벡터 인덱스 | 검색 인덱스 프로젝션 |
| `.cc-system/cache/*.md` | 분석 산출물 뷰 |

**성질도 같습니다**: 파생물이므로 지워도 재생성 가능하고, 조회 패턴에 맞춰 미리 접어둔 것이며, 최종 일관성을 가집니다(로그가 갱신되고 뷰가 아직 반영 안 된 순간이 존재).

### Just-in-time 참조 — 포인터를 저장하고 필요할 때 가져오기

파생 뷰를 컨텍스트에 **전부 미리 넣는 대신**, 가벼운 식별자(파일 경로, 쿼리)만 두고 필요할 때 읽어오는 방식이 권장됩니다. Anthropic의 컨텍스트 엔지니어링 지침이 명시하는 원칙이기도 합니다: **목표 결과를 낼 확률을 최대화하는 최소한의 고신호 토큰 집합을 찾는 것.**

`cc-system`의 `compose-handover`가 이미 이 원칙을 코드화하고 있습니다 — 캐시 내용을 합성 문서에 다시 풀어쓰지 않고 **의미적 포인터로 위임**합니다. 05의 관점을 더하면 이유가 하나 더 생깁니다: 풀어쓴 내용은 전부 **출력 토큰**(입력의 약 5배 단가)이고, 포인터는 짧은 출력입니다.

## 3. 원리 ④의 적용 — 축출과 앵커

### 무엇을 절대 버리면 안 되는가

07의 attention sink에서 배운 것을 그대로 옮깁니다: **앞부분에는 적지만 없으면 전체가 망가지는 것이 있습니다.**

에이전트 컨텍스트의 앵커:

| 앵커 | 버리면 |
|---|---|
| 시스템 프롬프트 / 행동 규약 | 페르소나 붕괴, 지시 위반 |
| 도구 정의 | 도구 오사용, 존재하지 않는 도구 호출 |
| 원래 과업 목표 | 목표 표류(drift) — 다른 일을 하기 시작 |
| 확정된 제약·결정 | 이미 배제한 방향을 다시 시도 |

**처방은 SWA와 동일합니다: 앞부분을 고정하고 중간에서 축출합니다.**

```
[고정: 시스템 프롬프트 + 도구 정의 + 과업 목표]  ← 절대 축출 안 함 (= sink)
[축출 대상: 오래된 도구 결과, 중간 탐색 과정]     ← 여기서 버림
[고정: 최근 N턴]                                ← 슬라이딩 윈도우
```

이 구조가 06의 캐시 배치와 **정확히 일치**하는 것에 주목하세요. 안정적인 것을 앞에 두면 캐시 적중과 축출 안전성이 동시에 만족됩니다. **두 요구가 같은 방향을 가리킵니다.**

### 무엇을 먼저 버리는가

| 우선 축출 (신호 대비 부피가 큼) | 늦게 축출 |
|---|---|
| 성공한 도구 호출의 **원시 출력** (긴 파일 내용, 검색 결과 전문) | 실패한 도구 호출의 에러 (→ 4절 참고) |
| 중간 탐색 과정 (읽었지만 관련 없던 파일) | 결정과 그 근거 |
| 이미 요약으로 대체된 구간 | 사용자의 명시적 지시 |

원시 출력은 대체로 **결론만 남기면 되는** 것들입니다. Claude API의 컨텍스트 편집이 `clear_tool_uses`를 첫 전략으로 제공하는 이유입니다.

### 오프로드가 축출보다 낫다

03에서 본 구분을 상기하세요 — 오프로드는 버리지 않고 옮깁니다. 에이전트에서는 이것이 매우 저렴합니다.

```
[축출]    긴 도구 출력을 컨텍스트에서 제거          → 정보 소실
[오프로드] 파일에 쓰고 컨텍스트에는 경로만 남김      → 필요하면 다시 읽음
```

**규칙: 버리기 전에 쓸 수 있는지 확인하세요.** 파일 시스템이 있는 에이전트에게 순수 축출은 거의 항상 차선입니다.

## 4. 이벤트 소싱 고유 규율의 적용

여기가 08에서 예고한 부분입니다. 네 개의 규율이 하네스 결정에 직접 대응합니다.

### ① 재생 부작용 — 가장 중요한 대응

08의 문제를 다시 보세요.

> 이벤트를 재생할 때 외부 시스템에 메시지를 보내는 것이었다면, 외부 시스템은 실제 처리와 재생을 구별할 수 없다.

에이전트에서 **완전히 같은 문제**가 발생합니다.

```
로그: assistant → tool_use: send_email(...)
      user      → tool_result: "발송 완료"

이 로그를 재생(resume, 재시도, 트레이스 재현)하면?
  → 캐시된 결과를 쓰면: 안전 ✅
  → 도구를 재실행하면:  중복 발송 ❌
```

**처방도 같습니다: 게이트웨이로 감싸고, 실행 컨텍스트를 판단합니다.**

`cc-system`의 Workflow `resumeFromRunId`가 정확히 이 구조입니다 — 변경되지 않은 `agent()` 호출의 프리픽스는 **캐시된 결과를 즉시 반환**하고, 첫 변경 지점 이후만 실제로 실행합니다. 도구를 다시 돌리지 않으므로 재생이 안전합니다.

**설계 규칙 세 가지:**

| 도구의 성격 | 재생 시 |
|---|---|
| 읽기 전용 (파일 읽기, 검색) | 재실행 안전 — 다만 결과가 변했을 수 있음 |
| 멱등한 쓰기 (같은 요청 반복 = 1회 효과) | 재실행 안전 |
| **비멱등 쓰기** (메일 발송, 결제, PR 생성) | **반드시 캐시된 결과 사용** |

비멱등 도구에는 **멱등 키**를 설계에 넣으세요 — 도구 입력에 요청 ID를 포함시켜 외부 시스템이 중복을 거를 수 있게 하면, 재생 안전성이 하네스가 아니라 프로토콜 수준에서 보장됩니다.

### ② 재생 결정론성

08의 규율: `now()`, `random()`, 외부 조회 결과를 **로그에 기록**해두고 재생 시 그것을 읽습니다.

`cc-system`의 Workflow 스크립트가 이 규율을 **문법 수준에서 강제**합니다: `Date.now()`, `Math.random()`, 인자 없는 `new Date()`가 모두 throw합니다. 이유가 명시돼 있습니다 — "그것들은 resume을 깨뜨린다". 타임스탬프가 필요하면 `args`로 주입하거나 워크플로가 끝난 뒤 찍습니다.

이것을 일반 규칙으로 쓰면:

> 에이전트 실행 중 비결정적 값이 필요하면, **로그에 남는 형태로 주입**하라. 실행 중에 생성하지 말라.

### ③ 보정 이벤트 — 실패를 지우지 말고 추가하라

08에서 본 대로 잘못된 것을 지우는 대신 보정 항목을 append합니다. 에이전트에서:

```
❌ 실패한 도구 호출을 로그에서 삭제하고 재시도
   → 캐시 무효화 + 모델이 실패를 모르므로 같은 실패를 반복

✅ 에러 결과를 그대로 append (is_error: true)
   → 모델이 실패를 보고 다른 접근을 택함
```

**병렬 도구 호출에서 특히 중요합니다.** 여러 도구를 동시에 호출했을 때, 실패한 것을 빼고 성공한 것만 결과로 돌려주면 안 됩니다 — 모든 `tool_use` 블록에 대응하는 `tool_result`가 있어야 하고, 실패는 `is_error: true`로 표시해 돌려줍니다.

이것이 축출 우선순위 표에서 "실패한 도구 호출의 에러"가 늦게 축출되는 항목인 이유입니다 — 그 정보가 다음 시도의 방향을 정합니다.

### ④ 스키마 진화 — 도구 정의 변경

08의 문제: 2년 전 이벤트도 오늘 코드로 읽혀야 합니다.

에이전트에서: **이력에 남은 `tool_use` 블록은 그 시점의 도구 스키마를 참조합니다.** 도구 정의를 바꾸면 과거 이력의 호출이 현재 스키마와 맞지 않게 됩니다.

- 필드 추가는 대체로 안전
- 필드 의미 변경·삭제는 과거 이력 해석을 깨뜨림
- 도구 이름 변경은 최악 (과거 호출이 존재하지 않는 도구를 참조)

**게다가 도구 정의 변경은 전체 캐시를 무효화합니다**(06). 두 이유가 겹치므로 도구 스키마는 **보수적으로 진화**시켜야 합니다.

## ⚠️ 암기 필수

- [ ] **에이전트 대화 = append-only 이벤트 로그. 과거 수정은 캐시와 재현성을 동시에 깨뜨린다**
  - 이유: 하네스 설계 결정의 절반이 이 한 문장에서 따라온다
- [ ] **요약 후 원본을 버리면 스냅샷이 아니라 축출이다** (되돌릴 수 없음)
  - 이유: 자동 compaction이 회복 불가한 결정을 내리는지 판단하는 기준
- [ ] **앵커 = 시스템 프롬프트 + 도구 정의 + 과업 목표 + 확정 제약. 축출 대상에서 제외**
  - 이유: attention sink와 같은 구조. 앞에서부터 자르는 순진한 축출이 에이전트를 망가뜨리는 원인
- [ ] **비멱등 도구는 재생 시 캐시된 결과를 쓴다. 멱등 키를 프로토콜에 넣는다**
  - 이유: resume·재시도가 중복 발송·중복 결제를 내는 사고를 막는 유일한 방법
- [ ] **실행 중 비결정적 값(`now()`, `random()`)을 생성하지 말고 주입한다**
  - 이유: 결정론적 재생이 깨지면 resume·트레이스 재현·디버깅이 전부 신뢰할 수 없게 된다
- [ ] **버리기 전에 파일로 쓸 수 있는지 확인한다 (오프로드 > 축출)**
  - 이유: 파일 시스템이 있는 에이전트에게 순수 축출은 거의 항상 차선

## 자가 진단

<details>
<summary>Q1: 에이전트가 컨텍스트 한계에 도달했다. 대화를 요약하고 원본을 지웠다. 02의 원리로 이것을 무엇이라 부르는가?</summary>

**즉답 예시**: 축출입니다(원리 ④), 스냅샷이 아닙니다. 스냅샷의 정의적 성질은 "전부 지워도 로그에서 다시 만들 수 있다"인데, 원본을 버렸으므로 그 성질을 잃었습니다. 되돌릴 수 없는 결정이 자동으로 내려진 것이고, 요약이 중요한 정보를 빠뜨렸다면 복구할 길이 없습니다. 원본을 파일이나 로그로 남겨두면 스냅샷이 되고, 요약 품질 문제를 사후에 고칠 수 있습니다.

</details>

<details>
<summary>Q2: 에이전트가 이메일을 보낸 뒤 실행이 중단됐다. 재시도(resume)할 때 무엇을 확인해야 하는가?</summary>

**즉답 예시**: `send_email` 같은 **비멱등 도구가 재실행되지 않는지** 확인해야 합니다. 로그에 `tool_use: send_email`이 남아 있고 그 결과도 남아 있다면, 재생 시 캐시된 결과를 반환해야 합니다 — 도구를 다시 호출하면 중복 발송입니다. 08의 게이트웨이 패턴과 같은 구조이며, `cc-system`의 Workflow `resumeFromRunId`가 변경되지 않은 호출의 캐시된 결과를 반환하는 방식으로 이를 구현합니다. 근본 해법은 도구 입력에 멱등 키를 넣어 외부 시스템이 중복을 거르게 하는 것입니다.

</details>

<details>
<summary>Q3: 도구 호출이 실패했다. 로그에서 그 호출을 지우고 다시 시도하는 것이 왜 나쁜가? 두 가지 이유를 들라.</summary>

**즉답 예시**: (1) 캐시 — 로그 중간을 수정하면 그 위치 이후 전체 프리픽스가 무효화되어 긴 대화에서 비용이 폭발합니다(06). (2) 학습 신호 — 모델이 실패를 보지 못하므로 같은 실패를 반복할 가능성이 큽니다. 올바른 처방은 에러 결과를 `is_error: true`로 그대로 append하는 것이며, 이는 이벤트 소싱의 보정 이벤트와 같은 규율입니다(지우지 말고 추가하라). 병렬 도구 호출에서는 특히 중요합니다 — 모든 `tool_use`에 대응하는 `tool_result`가 있어야 합니다.

</details>

<details>
<summary>Q4: 하네스가 컨텍스트를 절약하려고 "앞부분 30%를 잘라내는" 정책을 넣었다. 어떤 증상이 예상되는가?</summary>

**즉답 예시**: 앵커가 잘려나가므로 (a) 시스템 프롬프트 상실 → 페르소나 붕괴·지시 위반, (b) 도구 정의 상실 → 존재하지 않는 도구 호출이나 오사용, (c) 원래 과업 목표 상실 → 목표 표류(다른 일을 시작), (d) 확정된 제약 상실 → 이미 배제한 방향을 재시도. 07의 attention sink와 같은 구조입니다 — 앞부분에는 양이 적지만 없으면 전체가 망가지는 것이 있습니다. 처방은 앞부분을 고정하고 **중간의 원시 도구 출력**에서 축출하는 것입니다.

</details>

<details>
<summary>Q5: 요약을 반복하면 정보가 drift한다. 이벤트 소싱은 이 문제를 어떻게 피하고, 에이전트에서는 무엇을 해야 하는가?</summary>

**즉답 예시**: 이벤트 소싱은 스냅샷을 항상 **이벤트 로그에서** 만들고, 이전 스냅샷에서 만들지 않습니다. 그래서 오차가 누적되지 않습니다. 에이전트에서도 가능하면 원본 이력에서 요약을 만들어야 하고, 요약의 요약을 반복하지 않아야 합니다. 반복이 불가피하면 연쇄 횟수를 세고 상한을 둡니다 — `cc-system`의 캐시 매니페스트가 update 연쇄 카운터 3 이상에서 rebuild(로그에서 전체 재생성)를 추천하는 것이 이 장치입니다.

</details>

<details>
<summary>Q6: "긴 도구 출력을 컨텍스트에서 제거"와 "파일에 쓰고 경로만 남김" 중 왜 후자가 원칙적으로 우월한가?</summary>

**즉답 예시**: 전자는 축출(정보 소실, 되돌릴 수 없음)이고 후자는 오프로드(정보 보존, 되돌릴 수 있음)입니다. 03에서 본 대로 오프로드는 엄밀히 축출이 아니라 계층화이며, 용량 대신 지연을 지불합니다. 에이전트는 파일 시스템에 접근할 수 있으므로 그 지연이 매우 저렴합니다(도구 호출 1회). 따라서 "버리기 전에 쓸 수 있는지 확인하라"가 규칙이 됩니다. 부수 이점으로, 파일에 남긴 내용은 다음 세션에서도 참조 가능한 파생 뷰(프로젝션)가 됩니다.

</details>
