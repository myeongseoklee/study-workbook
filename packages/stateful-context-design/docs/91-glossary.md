# 91. 용어 해설집 — 5개 레이어로 구조화

학습 자료 [01]~[09]에 등장한 용어를, **단편적 사전이 아니라 개념의 인과 구조**로 정리합니다. 가나다순 정렬은 검색용이지 학습용이 아니므로, 같은 레이어 안에서는 **인과 순서**로 배치했습니다.

## 전체 지도

이 자료가 다루는 영역은 5개 레이어가 쌓인 그림입니다.

```
┌──────┐
│ L5   │  시스템 상태 패턴 (가장 위) — append-only 로그, fold, 이벤트 소싱,
│      │  프로젝션, 스냅샷, 멱등성, 재생 결정론성
├──────┤
│ L4   │  요청 간 상태 — 프롬프트 캐싱, 프리픽스, TTL, 무효화 계층,
│      │  컨텍스트 윈도우, compaction, 컨텍스트 편집
├──────┤
│ L3   │  절감과 축출 — MQA/GQA/MLA, 양자화, PagedAttention,
│      │  SWA, rolling buffer, attention sink
├──────┤
│ L2   │  캐시와 메모리 — KV 캐시, HBM, 연산 강도,
│      │  prefill/decode, TTFT/TPOT
├──────┤
│ L1   │  어텐션 기계 (가장 아래) — Q/K/V, softmax, causal mask,
│      │  멀티헤드, head_dim
└──────┘
```

아래로 갈수록 **물리·수학에 가깝고**, 위로 갈수록 **설계 판단에 가깝습니다.** 위 레이어는 아래 레이어의 한계를 보완하면서 쌓입니다 — L1의 재계산 낭비를 L2가 캐시로 메우고, L2의 메모리 폭발을 L3가 줄이고, L3의 요청 내 소멸을 L4가 연장하고, L4의 개별 최적화를 L5가 일반 패턴으로 묶습니다.

**용어를 외울 게 아니라 이 인과의 흐름을 잡는 게 핵심입니다.**

# L1. 어텐션 기계 — "토큰의 의미는 어떻게 다른 토큰과 섞이는가"

## 핵심 인과 흐름

```
토큰의 의미는 주변 관계로 결정된다
   ↓ (섞는 비율을 데이터가 정하게 하자)
Q·K로 점수를 내고 softmax로 비율화, V를 가중합
   ↓ (합이 1이어야 한다는 제약이 생긴다)
비중을 배출할 곳이 필요해진다 → L3의 attention sink로 이어짐
   ↓ (K·V는 각 토큰의 입력에만 의존한다)
K·V는 불변 → 재사용 가능 → L2의 KV 캐시로 이어짐
```

## 용어

### **어텐션 (Attention)** ⭐
- **정의**: 각 토큰의 표현을 만들 때, 다른 토큰들의 정보를 **데이터가 정한 비율로** 섞는 연산.
- **메커니즘**: `score = Q·K/√d` → `softmax` → `V 가중합`. 3단계.
- **인접**: → Query/Key/Value, softmax, causal mask
- **본문 위치**: [01-prerequisites.md](01-prerequisites.md#핵심-원리-1-어텐션attention이란-무엇인가)

### **Query / Key / Value (Q/K/V)** ⭐
- **정의**: 각 토큰을 세 가지 역할의 벡터로 변환한 것. 같은 입력에 서로 다른 가중치 행렬을 곱해 만듭니다.
- **메커니즘 (도서관 비유)**: Q = 검색어("나는 무엇을 찾는가"), K = 색인 표제어("나는 무엇에 대한 정보인가"), V = 본문("내가 담은 내용").
- **왜 중요**: **K·V는 그 토큰의 입력에만 의존하므로 불변**입니다. 이 성질 하나가 KV 캐시 전체의 근거입니다.
- **인접**: → KV 캐시, projection(선형변환)

### **softmax**
- **정의**: 실수 여러 개를 받아 큰 값에 더 큰 비중을 주면서 **전체 합이 1이 되도록** 만드는 함수.
- **왜 중요**: "합이 1"이라는 제약이 attention sink의 근본 원인입니다 — 볼 게 없어도 어딘가에 비중을 줘야 합니다.
- **인접**: → attention sink

### **causal mask**
- **정의**: 각 토큰이 **자기보다 뒤에 오는 토큰을 볼 수 없게** 점수를 `-∞`로 만드는 마스크.
- **메커니즘**: `j > i`인 항을 차단 → 삼각형 모양. 슬라이딩 윈도우는 여기에 조건을 하나 더 붙여 **띠(band)** 로 만듭니다.
- **인접**: → 슬라이딩 윈도우

### **멀티헤드 (Multi-Head)**
- **정의**: 어텐션 계산을 여러 벌(head) 병렬로 수행하는 것. 각 head가 다른 종류의 관계를 학습합니다.
- **관계식**: `hidden = n_heads × head_dim` (Llama 3.1 70B: 8192 = 64 × 128)
- **인접**: → head_dim, MQA/GQA

### **head_dim**
- **정의**: 한 head가 다루는 벡터 차원. KV 캐시 크기 공식에 직접 등장합니다.
- **인접**: → KV 캐시 크기 공식

### **projection (선형 변환)** ⚠️
- **정의**: 입력 벡터에 가중치 행렬을 곱해 Q/K/V를 만드는 연산. 토큰당 `O(d²)`.
- **⚠️ 주의**: L5의 "프로젝션(읽기 모델)"과 **완전히 다른 뜻**입니다. [01]~[07]에서는 이 뜻, [08]~[09]에서는 L5의 뜻.

# L2. 캐시와 메모리 — "왜 다시 계산하지 않고, 왜 그래도 느린가"

## 핵심 인과 흐름

```
K·V가 불변이다 (L1)
   ↓
저장해두고 재사용 = KV 캐시 → 스텝당 O(n²d)를 O(nd)로
   ↓ (그런데 저장할 곳이 필요하다)
GPU HBM에 모델 가중치와 예산을 나눠 쓴다
   ↓ (매 토큰마다 캐시 전체를 읽어야 한다)
연산 강도가 낮아진다 → decode는 memory-bound
   ↓
긴 컨텍스트의 병목은 연산이 아니라 대역폭 → L3의 절감 기법이 필요해짐
```

## 용어

### **KV 캐시 (KV cache)** ⭐
- **정의**: 각 레이어·각 토큰의 K·V 벡터를 저장해 재계산을 없애는 구조. **원리 ③(스냅샷)의 GPU 구현.**
- **크기 공식**: `2 × L × n_kv × head_dim × s × b × bytes`
- **핵심 성질**: 파생물입니다 — 전부 지워도 결과는 같고 느려질 뿐입니다.
- **본문 위치**: [03-kv-cache.md](03-kv-cache.md)

### **HBM (High Bandwidth Memory)**
- **정의**: GPU에 붙은 고대역폭 메모리. KV 캐시와 모델 가중치가 여기 있습니다.
- **예산 구조**: `HBM = 가중치 + KV 캐시 + 활성값 + 단편화`. 동시 처리 가능 요청 수 = `(HBM − 가중치 − 활성값) ÷ 요청당 캐시`.
- **인접**: → 오프로드, 대역폭 계층

### **연산 강도 (arithmetic intensity)** ⭐
- **정의**: `수행 연산량 ÷ 메모리에서 읽어야 하는 데이터량`.
- **왜 중요**: 이 값이 낮으면 GPU 연산기가 메모리를 기다리며 놉니다. prefill과 decode의 성격 차이를 만드는 단 하나의 개념입니다.
- **인접**: → prefill, decode, compute-bound, memory-bound

### **prefill**
- **정의**: 프롬프트 전체를 한 번에 처리해 KV 캐시를 채우는 단계. **행렬×행렬(GEMM)** → 연산 강도 높음 → **compute-bound**.
- **지표**: TTFT를 결정.

### **decode**
- **정의**: 토큰을 1개씩 생성하며 캐시에 append하는 단계. **행렬×벡터(GEMV)** → 연산 강도 낮음 → **memory-bound**.
- **매 토큰 읽는 것**: 모델 가중치 전체 + 해당 시퀀스 KV 캐시 전체.
- **지표**: TPOT를 결정.

### **TTFT / TPOT (ITL)**
- **정의**: TTFT = Time To First Token(첫 토큰까지). TPOT = Time Per Output Token(토큰당 생성 시간, ITL로도 표기).
- **왜 중요**: **TTFT는 prefill 지표, TPOT는 decode 지표**입니다. 프롬프트 캐싱은 TTFT만 개선합니다.
- **본문 위치**: [05-prefill-and-decode.md](05-prefill-and-decode.md#필수-지식-4-진단-신호--어느-단계의-문제인가)

### **오프로드 (offload)**
- **정의**: KV 캐시를 CPU DRAM이나 NVMe 같은 느린 계층으로 옮기는 것.
- **핵심 구분**: 축출이 아니라 **계층화**입니다 — 정보를 버리지 않고 지연을 지불합니다. 되돌릴 수 있습니다.
- **한계**: 활발히 decode 중인 캐시에는 부적합(매 토큰 왕복). 자주 안 쓰는 구간이나 세션 간 보관에 적합.

### **chunked prefill**
- **정의**: 긴 prefill을 조각으로 쪼개 진행 중인 decode 사이에 끼워 넣는 기법.
- **트레이드오프**: TTFT 약간 악화 ↔ TPOT 튐(jitter) 감소. 인터랙티브 서비스에서 흔한 선택.

# L3. 절감과 축출 — "메모리를 줄이는 대가로 무엇을 내놓는가"

## 핵심 인과 흐름

```
KV 캐시가 s에 선형으로 커진다 (L2)
   ↓ (공식의 각 항을 공격한다)
n_kv → GQA/MQA/MLA  |  bytes → 양자화  |  낭비 → PagedAttention
   ↓ (그래도 s가 남는다)
s를 상수로 만들려면 볼 대상을 잘라야 한다 → 슬라이딩 윈도우
   ↓ (순진하게 앞부터 자르면 망가진다)
softmax의 배출구를 빼앗은 것 = attention sink 손실
   ↓ (앞 몇 개를 고정한다)
그리고 장거리 지목이 약해지므로 → 하이브리드로 절충
```

## 용어

### **MQA / GQA / MLA** ⭐
- **정의**: 공식의 `n_kv`(또는 저장 차원)를 줄이는 계열.
  - **MQA**: 모든 Query 헤드가 K·V 헤드 **1개**를 공유. 최대 절감, 품질 저하 명확.
  - **GQA**: Query 헤드를 그룹으로 묶어 그룹당 K·V 1개. `G=1`이면 MQA, `G=헤드수`면 MHA인 **일반형**. 기존 MHA 체크포인트를 원래 학습 연산의 약 **5%** 로 uptraining 가능 → 사실상 표준.
  - **MLA**: K·V를 저차원 잠재 벡터로 **압축 저장**하고 계산 시 복원. DeepSeek-V2에서 KV 캐시 **93.3% 감소**, 처리량 5.76배.
- **공통 성질**: **학습 시점 결정** — 추론 단계에서 바꿀 수 없습니다.
- **본문 위치**: [04-kv-cache-reduction.md](04-kv-cache-reduction.md)

### **KV 양자화**
- **정의**: 캐시 저장 정밀도를 낮추는 것 (FP16 → FP8 → INT4). 50~75% 절감.
- **왜 상대적으로 안전한가**: KV는 어텐션 가중합에 한 번씩 들어가고 softmax가 절대 크기보다 상대 비율에 반응합니다.
- **주의**: K는 점수 계산에 직접 들어가 V보다 오차에 민감합니다. **런타임 결정**이므로 자체 평가셋으로 확인 가능.

### **PagedAttention**
- **정의**: KV 캐시를 고정 크기 블록으로 쪼개 필요할 때 할당하는 **메모리 관리** 기법(OS 가상 메모리 차용).
- **왜 절감 기법이 아닌가**: 공식의 항을 줄이지 않고 **낭비를 회수**합니다. 기존 시스템의 낭비 60~80% → 4% 미만, 처리량 2~4배.
- **부수 효과**: 블록 공유로 접두사 공유가 자연스럽게 구현됩니다.

### **접두사 공유 (prefix sharing)**
- **정의**: 여러 요청의 동일한 앞부분 KV를 하나만 두고 참조하게 하는 것.
- **근거**: append-only이므로 앞부분이 같으면 계산 결과도 같다는 보장.
- **두 층위**: 동시 요청 간 공유(L3) / 시간차 요청 간 공유 = **프롬프트 캐싱**(L4).

### **슬라이딩 윈도우 어텐션 (SWA)** ⭐
- **정의**: 각 토큰이 최근 **W개**만 보게 제한. 캐시를 `O(s)`에서 `O(W)` **상수**로 만드는 유일한 방법.
- **마스크**: `i − W < j ≤ i` → causal 삼각형이 **띠**로 바뀜.
- **본문 위치**: [07-sliding-window.md](07-sliding-window.md)

### **rolling buffer cache (원형 버퍼)**
- **정의**: 크기 W의 고정 배열을 `position % W`로 순환 재사용하는 구현.
- **구현 필수 3항**: (a) 논리 위치와 버퍼 인덱스 **분리**(위치 인코딩은 논리 위치를 씀), (b) 순서 복원(unrotate), (c) prefill에서 W 단위 청킹.
- **효과**: Mistral 7B에서 32k 시퀀스 캐시 메모리 8배 절감.

### **receptive field (유효 시야)**
- **정의**: 레이어를 쌓으면 간접적으로 도달하는 시야. `≈ W × L`.
- **한계**: 간접 전파는 **손실**이 있습니다 — 압축 누적 + **지목 불가**. 지속은 견디고 회수는 취약.

### **attention sink** ⭐
- **정의**: 모델이 의미와 무관하게 맨 앞 토큰에 어텐션 비중을 몰아주는 현상. softmax의 "합이 1" 제약이 만든 **비중 배출구**.
- **왜 중요**: 버리면 perplexity가 10~100배 급등합니다. **앞 4개 토큰 고정**이 표준 처방이며, 이 방식으로 최대 400만 토큰 안정 동작.
- **일반 원리**: "앞부분에는 적지만 없으면 전체가 망가지는 것이 있다" — L4의 시스템 프롬프트, L5의 초기 이벤트와 같은 구조.

### **하이브리드 어텐션 (local/global 교대)**
- **정의**: 레이어별로 local(SWA)과 global(full)을 섞는 구성.
- **구성값**: Gemma 2 = 1:1 / local 4096. Gemma 3 = **5:1 / local 1024**.
- **효과**: 32K 기준 KV 오버헤드 60% → 15% 미만, 품질 영향 미미(ablation).
- **현재 위치**: **주류.** 긴 컨텍스트와 회수 정확도를 둘 다 원할 때의 기본 선택.

# L4. 요청 간 상태 — "스냅샷의 수명을 요청 경계 밖으로"

## 핵심 인과 흐름

```
KV 캐시는 한 요청 안에서만 산다 (L2)
   ↓ (앞부분이 같으면 계산도 같다는 보장이 있다)
요청이 끝난 뒤에도 보관 = 프롬프트 캐싱
   ↓ (프리픽스 한 바이트가 바뀌면 뒤 전체가 무효)
안정 → 변동 배치 규율이 강제된다
   ↓ (그래도 컨텍스트 윈도우는 유한하다)
compaction(요약)과 컨텍스트 편집(축출)이 필요해진다
   ↓ (요약하면서 원본을 버리면?)
스냅샷이 아니라 축출이 된다 → L5의 판단 기준으로 이어짐
```

## 용어

### **프롬프트 캐싱 (prompt caching)** ⭐
- **정의**: 요청 간에 프리픽스의 KV를 재사용해 prefill을 건너뛰는 기능.
- **개선 대상**: **TTFT만.** decode(TPOT)는 개선되지 않습니다.
- **가격**: 읽기 0.1× / 쓰기 1.25×(5분) 또는 2×(1시간). 손익분기 2회(5분), 3회 이상(1시간).
- **본문 위치**: [06-prompt-caching.md](06-prompt-caching.md)

### **프리픽스 (prefix)** ⭐
- **정의**: 브레이크포인트까지의 프롬프트 바이트 열. 캐시 키가 여기서 유도됩니다.
- **불변식**: **어느 위치의 한 바이트라도 바뀌면 그 뒤 전체가 무효.**
- **렌더 순서**: `tools → system → messages`. tools는 위치 0.

### **브레이크포인트 (cache breakpoint)**
- **정의**: `cache_control`을 붙여 "여기까지 캐시하라"고 표시한 지점. 요청당 **최대 4개**.
- **배치 규칙**: **공유되는 구간의 끝**에 둡니다(전체 프롬프트 끝이 아님).
- **인접**: → 20블록 되돌아보기 창

### **20블록 되돌아보기 창**
- **정의**: 각 브레이크포인트가 기존 캐시를 찾기 위해 뒤로 걸어가는 최대 블록 수.
- **함정**: 한 턴이 20블록을 넘으면(도구 호출 많은 루프) 조용히 미적중. 15블록마다 중간 마커로 대응.

### **TTL (Time To Live)**
- **정의**: 캐시 항목의 유효 기간. `{"type": "ephemeral"}` = 5분, `{"ttl": "1h"}` = 1시간.
- **선택 기준**: 요청 간격이 5분 이내면 5분 TTL, 5분~1시간이면 1시간 TTL, 1시간 초과면 캐싱 이득 없음.

### **무효화 계층 (invalidation hierarchy)**
- **정의**: 캐시가 tools / system / messages 3계층이며, 변경이 자기 계층과 그 아래만 무효화한다는 구조.
- **전면 무효화**: 도구 정의 변경, 모델 교체. **유지**: `tool_choice`, thinking on/off, 메시지 추가.

### **조용한 무효화자 (silent invalidator)**
- **정의**: 에러 없이 캐시를 깨뜨리는 코드 패턴. `datetime.now()`, `uuid4()`, sort 없는 `json.dumps()`, 유저별 도구 목록 등.
- **진단**: 반복 요청에서 `cache_read_input_tokens`가 계속 0.

### **컨텍스트 윈도우 (context window)** ⚠️
- **정의**: 모델이 한 번에 볼 수 있는 최대 토큰 수. **하드 제약**입니다.
- **⚠️ 주의**: L5의 "바운디드 컨텍스트"와 무관한 개념입니다.
- **주의**: 상한과 실효 회수 정확도는 다릅니다 — SWA 비중이 큰 모델에서 격차가 더 큽니다.

### **compaction (압축·요약)**
- **정의**: 컨텍스트가 한계에 가까워지면 이력을 요약해 새 컨텍스트를 시작하는 것.
- **판단 기준**: **원본을 보관하면 스냅샷, 버리면 축출**입니다.
- **주의**: 요약의 요약을 반복하면 오차가 누적됩니다 → 로그에서 만들거나 연쇄 상한을 둡니다.

### **컨텍스트 편집 (context editing)**
- **정의**: 오래된 도구 결과나 thinking 블록을 컨텍스트에서 **제거**하는 것(요약이 아님).
- **전략**: `clear_tool_uses` / `clear_thinking`. 원시 출력이 우선 축출 대상입니다.

# L5. 시스템 상태 패턴 — "네 원리를 어디에 어떻게 적용하는가"

## 핵심 인과 흐름

```
덮어쓰기는 정보를 파괴한다
   ↓
append-only 로그 + fold로 상태 도출 = 이벤트 소싱
   ↓ (로그가 길어지면 접는 비용이 커진다)
스냅샷 / 프로젝션(읽기 모델)
   ↓ (재생할 때 외부 호출이 다시 나간다)
게이트웨이 + 멱등성 + 재생 결정론성이 필요해진다
   ↓ (에이전트 대화도 append-only 로그다)
같은 규율이 하네스 설계로 그대로 옮겨진다
```

## 용어

### **append-only 로그** ⭐
- **정의**: 끝에만 추가하고 이미 쓴 것을 수정·삭제하지 않는 저장 방식.
- **주는 것 3가지**: 불변성(캐시 가능) / 순서(재현 가능) / **접두사 공유**.
- **대가**: 무한히 커집니다 → 스냅샷과 축출이 필요해집니다.

### **fold (접기, reduce)** ⭐
- **정의**: 목록을 하나의 값으로 접는 연산. `상태 = fold(초기값, 사건열)`.
- **왜 중요**: 이 형태로 표현되면 시점 복원·사후 파생·재현·**캐싱**이 모두 가능해집니다.
- **지층별 접는 함수**: 어텐션 가중합 / `apply(state, event)` / 모델 forward pass.

### **이벤트 소싱 (Event Sourcing)** ⭐
- **정의**: 현재 상태 대신 상태를 만든 도메인 이벤트의 순서열을 저장하는 패턴.
- **적용 단위**: **바운디드 컨텍스트별로** 선택합니다. 전 시스템 적용은 거의 항상 잘못된 결정.
- **본문 위치**: [08-event-sourcing.md](08-event-sourcing.md)

### **애그리게이트 (aggregate)**
- **정의**: 불변식을 함께 지켜야 하는 도메인 객체 묶음. 이벤트 스트림 하나의 단위이자 리플레이 대상.
- **동시성 제어**: `(streamId, version)` 유니크 제약으로 낙관적 잠금.

### **프로젝션 / 읽기 모델 (projection / read model)** ⚠️
- **정의**: 이벤트 스트림에서 파생시킨 **조회 전용 뷰**. "조회 패턴에 맞춰 미리 접어둔 결과"이므로 **스냅샷의 변형**입니다.
- **⚠️ 주의**: L1의 "projection(선형 변환)"과 전혀 다른 뜻입니다.
- **에이전트 대응물**: 작업 노트, TODO 파일, 벡터 인덱스, `.cc-system/cache/*.md`.

### **CQRS**
- **정의**: 쓰기 모델과 읽기 모델을 분리하는 패턴.
- **관계**: 이벤트 소싱과 **별개 패턴**이지만, 이벤트 소싱은 조회 문제 때문에 CQRS를 거의 강제합니다.

### **스냅샷 (snapshot)** ⭐
- **정의**: "여기까지 접은 결과"를 저장해 재생 비용을 줄이는 **최적화**.
- **철칙**: 전부 지워도 시스템은 **느려질 뿐 틀리지 않습니다.** 이 성질을 잃으면 스냅샷이 아닙니다.
- **규율**: 항상 **로그에서** 만들고, 이전 스냅샷에서 만들지 않습니다(오차 누적).

### **보정 이벤트 (compensating event)**
- **정의**: 잘못 기록된 것을 지우는 대신 **역효과를 내는 새 이벤트를 추가**하는 것. 회계의 역분개와 같습니다.
- **에이전트 대응물**: 실패한 도구 호출을 삭제하지 않고 에러 결과를 `is_error: true`로 append.

### **재생 (replay) 과 그 부작용** ⭐
- **정의**: 이벤트열을 다시 접어 상태를 재구성하는 것.
- **핵심 함정**: 외부 시스템은 **실제 처리와 재생을 구별할 수 없습니다.** 재생 시 메일이 재발송되고 결제가 중복됩니다.
- **처방**: 외부 호출을 **게이트웨이**로 감싸고 게이트웨이가 실행 컨텍스트를 판단합니다. **도메인 로직은 실제인지 재생인지 몰라야 합니다.**

### **재생 결정론성 (deterministic replay)**
- **정의**: 같은 이벤트열을 재생하면 항상 같은 상태가 나오는 성질.
- **깨뜨리는 것**: `now()`, `random()`, 외부 API 조회, `apply` 로직 변경.
- **규율**: **재생에 필요한 모든 것을 이벤트 안에 기록**합니다. 실행 중 생성하지 말고 주입합니다.

### **멱등성 (idempotency)**
- **정의**: 같은 요청을 여러 번 해도 효과가 1회와 같은 성질.
- **왜 중요**: 재생 안전성을 하네스가 아니라 **프로토콜 수준**에서 보장하는 방법입니다. 도구 입력에 **멱등 키**를 넣습니다.
- **분류**: 읽기 전용(안전) / 멱등한 쓰기(안전) / **비멱등 쓰기(반드시 캐시된 결과 사용)**.

### **바운디드 컨텍스트 (bounded context)** ⚠️
- **정의**: DDD에서 하나의 도메인 모델이 일관되게 통하는 경계.
- **왜 중요**: 이벤트 소싱 적용 여부를 **이 단위로** 결정합니다.
- **⚠️ 주의**: L4의 "컨텍스트 윈도우"와 무관합니다.

### **앵커 (anchor)** ⭐
- **정의**: 양이 적지만 없으면 전체가 망가지는, 축출 금지 대상.
- **세 지층의 앵커**: attention sink 토큰(L3) / 시스템 프롬프트·도구 정의(L4) / 초기 이벤트(L5).
- **에이전트 목록**: 시스템 프롬프트, 도구 정의, 원래 과업 목표, 확정된 제약·결정.
